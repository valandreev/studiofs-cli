# Recover pending regular files without replaying old events

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current. Maintain it under `.agent/PLANS.md`.

## Purpose / Big Picture

After this change, a PostgreSQL-backed mount can recover a locally uploaded but unpublished regular file after redb repair even when its old local event rows are gone. The repair path will restore from a small, inode-scoped recovery record stored in redb and will continue to reject published, deleted, or superseded epochs. This issue does not prune the local event journal; it removes the recovery path's dependency on that history so SFS-735 can define pruning separately.

## Surprises & Discoveries

- Observation: redb repair imports a remote snapshot that replaces the local regular-file overlay before recovery runs. The current recovery function then scans `EVENT_LOG_TABLE` from its first retained sequence to `nextEventSeq` to reconstruct that overlay.
  Evidence: `PgMetaEngine::open_with_options` calls snapshot import before `restore_acknowledged_uploaded_regular_file_overlays_after_redb_repair` in `crates/studiofs-meta/src/pg_engine.rs`.
- Observation: `local_upload_ledger` stores remote fragment proof and replication flags, but no inode, content epoch, chunk, or slice identity. `InodeLifecycleRecord` likewise has no overlay graph.
  Evidence: `crates/studiofs-meta/src/redb_engine/upload_ledger.rs`, `crates/studiofs-meta/src/snapshot_ports.rs`, and `crates/studiofs-meta/src/types.rs`.
- Observation: regular-file commits and upload acknowledgements already update lifecycle state in the same redb transaction; background chunk compaction updates overlay rows separately and must also refresh the recovery copy.
  Evidence: `crates/studiofs-meta/src/redb_engine/inodes.rs` and `crates/studiofs-meta/src/redb_engine/payload_objects.rs`.
- Observation: after the old event rows are removed, repair loses the uploaded file (`size` remains 0 instead of 152); the multi-upload case also loses an earlier uploaded slice (`LocalOnly` instead of `Uploaded`).
  Evidence: focused `cargo test -p studiofs-meta ... -- --nocapture` runs failed those exact assertions with one test executed each.

## Decision Log

- Decision: Store one recovery record per inode in a narrowly scoped local redb table. It contains the pending inode attributes and the current overlay graph only while that epoch has uploaded payloads awaiting publication.
  Rationale: The existing upload ledger and lifecycle record cannot represent the slice graph, and a generic event log would recreate the unbounded history dependency.
  Date/Author: 2026-09-26 / Codex.
- Decision: Keep the table out of snapshot export/import and update or clear it in the same transaction as local overlay, publication, and deletion changes. At repair startup, backfill missing records from the recovered current overlay before remote snapshot import; never read the old event journal to create them.
  Rationale: Snapshot replacement must not erase the recovery source, while existing databases need a one-time repair-time capture of current live state before that replacement.
  Date/Author: 2026-09-26 / Codex.
- Decision: Retain the existing inode-attribute recovery fence and leave local event pruning untouched.
  Rationale: The fence prevents stale epochs from overriding current authority; pruning is explicitly deferred to SFS-735.
  Date/Author: 2026-09-26 / Codex.

## Outcomes & Retrospective

The recovery table is deliberately local-only and outside `RedbSnapshot`, so
remote snapshot replacement preserves it. Existing disks backfill only missing

compaction tests, crate clippy, formatting, and whitespace checks all pass.

## Context and Orientation

`open_meta_engine_with_options` in `crates/studiofs-meta/src/lib.rs` opens redb writable when an unclean close needs repair and sets a recovery counter. `PgMetaEngine::open_with_options` in `crates/studiofs-meta/src/pg_engine.rs` sees that counter, backfills missing uploaded-file recovery rows, imports the remote serving snapshot, rebuilds pending replication state, and then restores matching pending overlays from those rows. The restore helper no longer reads `MetaEvent` rows.

`RedbMetaEngine` stores the live overlay in `regular_file_overlay`; its metadata transaction helpers live in `crates/studiofs-meta/src/redb_engine/inodes.rs` and `payload_objects.rs`. Snapshot import is implemented in `crates/studiofs-meta/src/redb_engine/snapshots.rs` and only replaces explicitly listed tables. A recovery table omitted from `RedbSnapshot` will therefore survive remote snapshot replacement. The local upload ledger in `upload_ledger.rs` tracks uploaded fragment reconciliation, not regular-file overlay identity.

## Plan of Work

Add a redb table keyed by inode and a private serialized row containing the current `InodeAttr` and `RegularFileOverlayState`. Synchronize the row from the same transaction that commits inode lifecycle or uploaded-payload progress. Keep it only for upload-pending state containing an `Uploaded` payload; refresh it after overlay compaction and replace or remove it as the local epoch changes, publishes, or deletes. Add a repair-only backfill that captures missing rows from the recovered current overlay before `pull_snapshot_locked` replaces that overlay. It must not inspect `EVENT_LOG_TABLE` or erase an existing record that may be the only surviving copy.

Replace the event replay loop in `restore_acknowledged_uploaded_regular_file_overlays_after_redb_repair` with a read of these records. Preserve the current identity/committed-size fence, apply the restored attributes and slices through the existing local-only serving-state path, and leave the flushed event cursor unchanged. Extend `replication_backlog` tests to clear the old event rows before restoration and cover durable recovery across redb reopen, with no resurrection after a published, deleted, or superseded transition. Document the resulting invariant in `docs/pg-sync-contract.md`.

## Validation and Acceptance

Acceptance is behavioral: after an uploaded-but-unpublished file is recorded, remove its old `EVENT_LOG_TABLE` rows and replace the serving overlay with a remote projection. Repair must restore the same pending content and uploaded object references from the local recovery row without advancing or reopening the flushed event cursor. Closing and reopening redb must retain the record. Tests must also show that a published, deleted, or superseded state is not restored over a conflicting current attribute. Focused `studiofs-meta` tests, `cargo clippy -p studiofs-meta --all-targets -- -D warnings`, formatting, and `git diff --check` must pass; no full suite is part of acceptance.

## Idempotence and Recovery

The row update is an upsert inside the metadata transaction, so repeating a local sync writes the same record. Repair can be retried after a crash: snapshot import leaves the row intact, restoration is local-only and does not append event-log rows, and the repair counter is cleared only after restoration succeeds. If restoration fails, the counter and record remain for the next open. Event pruning is not performed here.

## Interfaces and Dependencies

Use the existing `redb` transaction APIs and serde/postcard encoding already used by `RedbMetaEngine`. The new recovery row is private to `studiofs-meta`; it does not add a public trait or dependency. Recovery must be exposed to `PgMetaEngine` only through a crate-private `RedbMetaEngine` method returning the persisted attribute/overlay records.
