# Make PostgreSQL worker close bounded and retain unfinished ownership

This living ExecPlan follows `.agent/PLANS.md`. Maintain Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective as implementation proceeds.

## Purpose / Big Picture

Closing a PostgreSQL metadata engine must either join every background worker or report that workers still own resources. A timeout must never detach a redb owner or block indefinitely. After successful close and engine drop, the same redb file must open immediately. Failed startup and early engine destruction must also preserve ownership until each worker exits.

## Surprises & Discoveries

At baseline, `shutdown_complete` meant shutdown started, although unfinished handles had already been removed. Non-checkpoint timeouts detached the handle; checkpoint timeout called an unconditional join. The worker may hold the final engine Arc, so engine destruction can occur on the worker thread itself and must avoid self-join. The existing checkpoint test establishes immediate redb reopen after successful close; its unconditional wait beyond the deadline is replaced by an explicit failure followed by a successful join retry.

Graph generation `2026-09-30T09:40:28Z` reports changed metadata for the inspected paths. Direct source inspection supplies current evidence; runtime.rs also has a known parse gap at lines 290-291.

Both new cancellation regressions failed with an unfinished-checkpoint timeout before adding cancellation and passed afterward. Replacing retained-handle restoration with `drop(handle)` made the retention regression fail at its ownership assertion; the source was restored and the same test passed. A mixed worker panic and checkpoint timeout initially hid unfinished ownership behind the panic error; the new regression failed before separating transient timeout and persistent join errors, then passed.

Postcard 1.1.3 writes individual bytes through `Write::write_all`. Returning `ErrorKind::Interrupted` would cause retries, so checked serialization returns `Error::other` and preserves the original metadata error. Checks are amortized across 64 KiB intervals, including when writes consist of single bytes.

Review caught two scope issues: cancelling every remote operation would also cancel foreground transactions, and the worker-start mutex wait was outside the close deadline. A thread-local scope now enables cancellation only during checkpoint coordination, and start-lock polling shares the close budget. Cleanup-thread spawn failure must also remain nonblocking, so it retains all handles for process lifetime rather than joining inline.

The second review traced checkpoint lease/publication results through `record_remote_operation_result`. Unlike the initial review assessment, remote checkpoint cancellation does reach `PgSyncFailure::from_error`: `Storage` incorrectly records a storage failure and invalidates remote identity/format validation. Both new local-step and remote-result regressions failed with `Storage` instead of `Cancelled` before the fix. A subsequent red assertion showed that ordinary result bookkeeping falsely marked an offline source connected. Worker shutdown now records the cancellation category before reachability/validation bookkeeping, preserving prior observations.

The updated review's byte-boundary finding reproduced three checks for 65,537

Retaining that handle in the existing vacant slot fixed the ownership gap.

## Context and Orientation

In `crates/studiofs-meta/src/pg_engine.rs`, PgBackgroundWorkers holds five optional standard thread JoinHandles. A JoinHandle owns the ability to wait for a thread's termination; dropping it detaches the thread. `pg_engine/lifecycle.rs` registers, signals, and joins those workers. `pg_engine/replication_api.rs` implements the MetaReplication close hook, serialized with lazy worker startup. The VFS caller propagates close errors while completing its local durability barrier. Workers use weak engine references but temporarily upgrade them during work; checkpoint export pins a redb read transaction.

`pg_engine/runtime.rs` submits remote futures to Tokio, the async executor. `pg_engine/checkpoint_coordinator.rs` acquires a process-local single-flight lock, captures a consistent source version/read transaction, claims a fenced remote lease, builds bytes, and publishes them. `redb_engine.rs`, `redb_engine/replication.rs`, and `redb_engine/snapshots.rs` implement table export and projection. Cancellation checks must leave the same byte representation on uninterrupted export.

## Validation and Acceptance

A stalled worker yields a typed timeout within the close budget while its handle remains installed. Releasing it and retrying close joins it and clears the slot. A stalled checkpoint remote future or local lock/export stops on cancellation. An early-drop or partial-startup cleanup owns all registered workers through exit. After success, dropping the engine permits immediate reopen of `meta.redb`. Concurrent close callers respect bounded waits and cannot report completion before ownership is released. Existing checkpoint eligibility/fencing and unchanged export-byte tests continue to pass.

## Idempotence and Recovery

Repeat a failed close to finish joining exited workers. Successful repeated close is a no-op, with terminal join errors preserved. Tests release controlled workers before assertions that could fail, so they cannot leave blocked threads. Cleanup-thread creation failure preserves remaining handles with explicit diagnostics; it must never silently detach a redb owner.
