# Avoid global read-ahead map scans when evicting one inode

This is the living ExecPlan for SFS-656. It follows `.agent/PLANS.md`; keep
`Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` current as the work advances.

## Purpose / Big Picture

StudioFS performs full-inode read-ahead eviction when an inode is deleted or
its stale state is discarded. The current tracker stores every stream and
every in-flight block in two maps keyed by compound keys, so evicting one inode
must visit unrelated entries in both maps. After this change, both kinds of
state are owned by a top-level inode entry. Evicting one inode removes one
entry, while stream-level eviction, sequential detection, and in-flight
deduplication keep their existing behavior.

The change is useful only if it also helps the real contention shape. The
release benchmark in `crates/studiofs-vfs/examples/readahead_eviction.rs`
populates thousands of inodes, runs foreground reads on unrelated inodes, and
measures repeated eviction of one inode. The focused unit tests prove the
multi-stream and cleanup contracts; the benchmark comparison decides whether
the new layout is retained.

## Surprises & Discoveries

- Observation: the original locking claim was too strong. DashMap 6.1
  retains one shard at a time, but `ReadAheadTracker::evict` still traverses
  both globally keyed maps and its cost grows with unrelated tracker state.
  Evidence: the current method at
  `crates/studiofs-vfs/src/readahead.rs:303-307` calls `retain` on `states`
  and `inflight`.
- Observation: normal stream close already uses `evict_stream`; full-inode
  eviction is used by deletion and stale-inode cleanup. The public behavior of
  both paths must remain separate.
  Evidence: graph tracing found `clear_access_tracking_for_stream` for
  `evict_stream`, and deletion cleanup methods for `evict`.
- Observation: the repository has no criterion or divan benchmark dependency.
  Evidence: `crates/studiofs-vfs/Cargo.toml` has no benchmark harness and
  workspace search found no criterion/divan use. A small example binary keeps
  the benchmark release-only, repeatable, and dependency-free.
- Observation: an inode group can temporarily contain only in-flight blocks
  after its last stream is evicted. The group must remain until those blocks
  finish, then be removed if it is still empty; otherwise repeated stream
  close/prefetch activity would retain empty inode groups.
- Observation: a direct nested-DashMap group removed the eviction scan but
  reduced the release foreground signal from 4,009,478 to 1,148,935
  operations; adding an Arc/RwLock lifecycle gate reduced it further to
  943,728. Both were rejected after measurement.
- Observation: a single per-inode mutex with compact vectors restored most of
  the foreground signal while keeping eviction inode-scoped. Three repeated
  runs after warm-up measured 3,201,815, 3,210,967, and 3,498,427 foreground
  operations, with 0.0588-0.0624 microseconds per eviction.

## Decision Log

- Decision: use `DashMap<Ino, InodeReadAheadState>` as the only top-level
  tracker map. Each inode group owns one mutex-protected compact stream list
  and in-flight block list.
  Rationale: `evict(ino)` removes one top-level entry, while a small local
  critical section avoids the extra hash/shard work of nested maps. Unrelated
  inodes still use independent top-level entries, and the release benchmark
  showed a materially better foreground signal than the nested-map variants.
  Date/Author: 2026-08-28 / Codex.
- Decision: hold the top-level entry guard through the group mutex operation,
  and drop it before calling top-level `remove_if`.
  Rationale: the top-level guard prevents the selected group from being
  removed while its local state is updated. Dropping it before `remove_if`
  avoids the documented same-map reference deadlock.
  Date/Author: 2026-08-28 / Codex.
- Decision: remove an empty inode group conditionally after `evict_stream` and
  `finish_prefetch`.
  Rationale: `remove_if` checks the current nested stream/inflight state under
  the selected inode key. A new stream that arrives before the conditional
  removal keeps the group, and an in-flight block keeps the group until its
  completion.
  Date/Author: 2026-08-28 / Codex.
- Decision: use a test-only eviction-pass hook for the red regression and a
  barrier-controlled hook for the stream/group race test.
  Rationale: the performance property is otherwise invisible through the
  public API, and a scheduling sleep cannot prove the cleanup interleaving.
  Both hooks are compiled only for unit tests and are not part of the public
  API or production cost.
  Date/Author: 2026-08-28 / Codex.
- Decision: retain the structural change only if the release benchmark shows
  a useful reduction in per-eviction cost under unrelated foreground reads.
  Rationale: SFS-656 is explicitly medium-priority and benchmark-gated; a
  larger memory footprint or increased read contention would not justify a
  theoretical O(1) eviction alone.
  Date/Author: 2026-08-28 / Codex.

## Context and Orientation

`crates/studiofs-vfs/src/readahead.rs` defines the platform-neutral
`ReadAheadTracker`. `ReadStreamKey` identifies an inode plus a per-handle
stream ID. A `ReadState` stores the last block and the sequential-read window.
`record_read_for_stream` updates that state and filters upcoming blocks against
the in-flight prefetch set. `start_prefetch` and `finish_prefetch` implement
atomic deduplication for worker tasks. `is_prefetch_relevant` checks whether a
queued block is still near any live stream head. `evict_stream` is used when a
single stream closes; `evict` is used when all read-ahead state for one inode is
invalidated.

Before this change, the fields were:

    states: DashMap<ReadStreamKey, ReadState>,
    inflight: DashMap<(Ino, u32), ()>,

Both maps use 256 shards. This is safe but means a full-inode eviction invokes
two whole-map `retain` traversals. The final layout is:

    states: DashMap<Ino, InodeReadAheadState>,

where one `InodeReadAheadState` owns a mutex-protected compact list of
`(stream_id, ReadState)` pairs and a list of in-flight block indices. The
top-level entry is the unit removed by `evict(ino)`.

The only production file expected to change is
`crates/studiofs-vfs/src/readahead.rs`. The benchmark is a new example under
`crates/studiofs-vfs/examples/`; the existing crate manifest needs no explicit
`[[bench]]` section because Cargo automatically builds examples.

## Plan of Work

First add test-only hooks to `ReadAheadTracker` and focused tests in the
existing `tests` module. The eviction-pass hook will be called once for each
global map pass in the old implementation, so the new test expects one
inode-scoped removal and reaches an assertion failure before the production
change. Add a semantic test that eviction clears only the selected inode's
streams and inflight blocks. Add a test that starts with one stream, pauses
after that stream is removed, records a different stream, and then lets the
conditional empty-group cleanup run; the newly recorded stream must survive.
Add a test that leaves an in-flight block behind during stream eviction and
confirms deduplication remains active until `finish_prefetch`.

Next add `crates/studiofs-vfs/examples/readahead_eviction.rs`. Seed 16,384
inodes with four streams each and one in-flight block per inode. Synchronize
four reader threads with a barrier, then evict and recreate inode 1 for a
fixed 250 ms window while those threads issue read-ahead records against
inodes 2 through 16,384. Print the number of evictions, total and per-call
eviction time, and foreground read operations. Run this example in release
mode once before changing the tracker and once after it changes, using the
same command and warm build directory.

Then introduce `InodeReadAheadState` and move all tracker operations to the
inode group. `record_read_with_stamp` obtains the selected inode group and
updates the stream list while holding its mutex; its in-flight filtering reads
the same group's block list. `start_prefetch` creates/selects one group and
atomically checks/inserts the block; `finish_prefetch` removes the block
without creating a missing group, then conditionally removes the group if
both compact collections are empty. Relevance queries inspect only the
selected group's stream list. `evict(ino)` removes the single top-level entry.
`evict_stream` removes one stream, drops the top-level guard, and conditionally
removes the group only if no stream or in-flight block was added concurrently.
Update test-only debug accessors to follow the new nesting.

Finally format and run the crate-scoped checks. Repeat the focused readahead
filter in debug and release profiles, run the concurrent cleanup test several
times without sleeps, and compare the release benchmark output. Do not run a
workspace-wide test suite or native mounted tests.

## Validation and Acceptance

The red test must fail on the old two-map implementation and pass after the
refactor. The focused semantic tests must demonstrate that:

- full eviction removes all streams and in-flight blocks for the selected
  inode but leaves another inode untouched;
- sequential read-ahead behavior still returns the same windows;
- a stream recorded during the cleanup interleaving survives conditional
  empty-group removal; and
- an in-flight block remains deduplicated after its stream is evicted and can
  be scheduled again only after `finish_prefetch`.

The focused readahead command must report a nonzero test count and zero
failures in debug and release profiles. The release benchmark must report
foreground reader operations and a per-eviction measurement for both layouts.
The retained layout must make eviction cost independent of unrelated inode
state without an unacceptable regression in the concurrent foreground-read
signal. `cargo check`, Clippy with warnings denied, formatting, and
`git diff --check` must pass.

Full workspace tests, ignored PostgreSQL tests, and native mounted acceptance
are outside this platform-neutral tracker task and will be explicitly
reported as not run.

## Idempotence and Recovery

The benchmark writes no source artifacts; any generated Cargo output remains
under `target/`. It can be rerun with the same release command after warming
the build. Unit tests use barriers and bounded loops, never fixed scheduling
sleeps. If a barrier test hangs, terminate only that single Cargo process,
preserve the output, and inspect the hook/guard ordering before retrying.

Do not reset, checkout, or discard existing commits or unrelated working-tree
changes. If the benchmark shows no useful release improvement or a material
foreground-read regression, record the result and remove only the proposed
layout/example changes before deciding whether a smaller design is justified.

## Interfaces and Dependencies

Keep the existing public constructors and methods of `ReadAheadTracker`,
`ReadStreamKey`, and `ReadAheadPolicy`. Add only the private group type and
test-only hooks. The intended private shape is:

    struct InodeReadAheadState {
        state: Mutex<InodeReadAheadStateInner>,
    }

    struct InodeReadAheadStateInner {
        streams: Vec<(u64, ReadState)>,
        inflight: Vec<u32>,
    }

`ReadAheadTracker::evict` must remove by inode key. `evict_stream` and
`finish_prefetch` must use a conditional top-level removal equivalent to:

    self.states.remove_if(&ino, |_, inode_state| {
        let state = inode_state.state.lock();
        state.streams.is_empty() && state.inflight.is_empty()
    });

The conditional removal must happen only after any top-level reference guard
used to mutate the group has been dropped. The existing `dashmap = "6"` and
`parking_lot = "0.12"` workspace dependencies are sufficient; do not add a
benchmark framework for this issue.
