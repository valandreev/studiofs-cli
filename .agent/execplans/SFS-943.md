# Return the directory actually removed by rmdir

This living ExecPlan follows `.agent/PLANS.md`.

## Purpose / Big Picture

Concurrent rename must not make rmdir invalidate a surviving directory or report its attributes as those of the removed directory. Metadata must identify the directory removed inside its local transaction, including a dangling directory whose attributes are missing.

## Surprises & Discoveries

The parent Delete session serializes child unlink/rmdir, but ordinary rename calls `rename_atomic` without it. The old comment claiming this gate guarantees the captured identity is false. Metadata also deliberately accepts directory entries with missing inode attributes; the returned identity must remain available in that case.

## Decision Log

- Decision: Preserve the unit-returning metadata rmdir as a default convenience method and require a transaction-backed `rmdir_returning_removed` returning `Option<(Ino, Option<InodeAttr>)>` with an optional expected inode.
  Rationale: Existing callers keep their contract, while VFS obtains both exact removal identity and the last attributes without an unsafe lookup fallback.
  Date/Author: 2026-11-01, Codex.
- Decision: Refresh target lookup each retry and check the expected inode inside the transaction after waiting for its Read barrier, then use the committed transaction result for post-commit work.
  Rationale: The barrier must follow renamed targets; the transaction remains authoritative if rename races the final lookup.
  Date/Author: 2026-11-01, Codex.

## Context and Orientation

`crates/studiofs-vfs/src/vfs/namespace_ops.rs` holds `rmdir_inner`, which waits on a per-inode namespace gate before synchronous local metadata removal. `crates/studiofs-meta/src/redb_engine/fs_ops.rs` resolves and deletes the binding inside a redb write transaction. `MetaFsOps` in `engine.rs`, PostgreSQL's `local_traits.rs`, the read-only engine and VFS `runtime.rs` forward that operation. PostgreSQL only wraps the local mutation; no foreground network operation is added.
