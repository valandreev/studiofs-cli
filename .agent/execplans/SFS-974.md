# Bound standalone janitor concurrency and request rate

This living ExecPlan follows `.agent/PLANS.md`. It records the CLI-only work for SFS-974; the mounted janitor remains independent.

## Purpose / Big Picture

`studiofs janitor <volume>` should keep remote maintenance work from producing an uncontrolled burst against PostgreSQL or an S3-compatible service. Operators will be able to set independent PostgreSQL and S3 in-flight limits and a conservative S3 request rate; small bounded batches and explicit operation timeouts will keep queued work and foreground contention predictable. A loopback provider fixture and slow fake providers will make the limits observable without requiring a production service.

## Surprises & Discoveries

- Observation: Candidate work already arrives in pages of at most 64, but each page is processed sequentially; listing also yields into a single fixed-size eligibility batch.
  Evidence: `pipeline.rs::process_candidate_batch` iterates candidates and awaits `process_orphan` inline.
- Observation: OpenDAL 0.55's `ConcurrentLimitLayer::with_http_concurrent_limit` wraps its shared `HttpClient` fetcher, so it can count actual network requests, including internal list pagination and retry attempts.
  Evidence: The installed OpenDAL 0.55 source in Cargo's registry shows the layer acquires an HTTP semaphore in `ConcurrentLimitHttpFetcher::fetch`.
- Observation: The CLI's PostgreSQL session owns the per-volume advisory lock and performs sync-runtime operations; any parallel claim/finish workers must be joined before releasing that session's lock.
  Evidence: `JanitorMetadataSession::release_global_janitor_lock` closes its PostgreSQL session; the pipeline invokes claims and finishes through that session.
- Observation: The live SFS-973 regression failed at 4 requests/second because the second HEAD waited at least 250 ms while test builds cap HEADs at 200 ms; the timed-out age refresh safely skipped the candidate.
  Evidence: The focused run reported one orphan candidate and one unknown-age skip; direct HEAD returned a timestamp about 600 ms before the test clock. At 32 requests/second, the gate wait is 31.25 ms and the exact RustFS test passes. Production HEAD timeout and default request rate remain 20 seconds and 4 requests/second.

## Decision Log

- Decision: Keep SFS-974 scoped to `crates/studiofs` CLI pipeline and `studiofs-data`'s OpenDAL janitor adapter; do not alter `studiofs-vfs` workers.
  Rationale: The issue explicitly excludes mounted behavior, and the existing provider-neutral pipeline is the CLI's queue/backpressure boundary.
  Date/Author: 2026-11-09 / Codex.
- Decision: Keep PG claims/finishes serial in this change and expose `--pg-concurrency` as an upper bound, defaulting to one.
  Rationale: The held per-volume lock and current metadata adapter share one synchronous PostgreSQL session; the issue explicitly asks to start with serial behavior as the reference and measure before adding concurrent claim workers.
  Date/Author: 2026-11-09 / Codex.
- Decision: Use OpenDAL's operation limiter at the existing candidate-page bound (65 operations) and the configured `s3-concurrency` only at its actual HTTP limiter.
  Rationale: OpenDAL holds an operation permit for the lifetime of a streaming lister. Tying that permit to the S3 wire limit can deadlock when the open listing coexists with stat/delete work; the HTTP limiter counts every actual request and retains its permit until the response body is dropped.
  Date/Author: 2026-11-09 / Codex.
- Decision: Run the SFS-973 resumable-listing fixture at 32 requests/second without changing the production timeout or default rate.
  Rationale: That live test deliberately resumes one-entry pages, so age refresh can issue multiple HEADs; its `cfg(test)` per-HEAD timeout is 200 ms, shorter than the 250 ms pacing at 4 requests/second. The dedicated transport test independently checks a 2 requests/second rate.
  Date/Author: 2026-11-09 / Codex.

## Context and Orientation

`crates/studiofs/src/cli/janitor.rs` parses and validates command options, opens the read-only metadata session, and owns the per-volume lock across each cycle. Its `pipeline` module streams S3 entries, drains the durable PostgreSQL candidate queue, confirms eligibility, claims each object, deletes canonical keys, finishes fenced claims, and persists checkpoints. `crates/studiofs-data/src/janitor.rs` wraps OpenDAL's S3 operator for list/stat/delete. The database claim is an authorization fence; the S3 key list only discovers candidates. The admitted-work queue must remain bounded and checkpoint writes must remain after all admitted tasks finish.

## Plan of Work

Add positive bounded CLI arguments for independent PG and S3 in-flight work and the S3 request rate, using defaults small enough for foreground-friendly maintenance. Thread them through `JanitorOptions`, the cycle context, and the startup banner. In `studiofs-data::janitor`, layer OpenDAL's underlying HTTP client with a shared per-request concurrency gate and a one-second token schedule; this boundary must cover LIST pages, HEAD/stat and each DELETE request, including provider retries. Do not rely only on object-level task limits.

Keep candidate processing serial in this rollout and retain the existing maximum batch of 64 candidates. Claims and finishes stay on the lock-owning metadata session and therefore peak at one PG command, within the configurable PG upper bound. The S3 request budget is enforced inside OpenDAL's shared HTTP client, not at the object-task boundary; this covers provider pagination and retries that pipeline counters cannot observe. A loopback S3 fixture concurrently exercises LIST, HEAD, and DELETE and a second check measures request arrival spacing. The test also protects the distinction between OpenDAL's operation limiter and its HTTP limiter: the streaming lister can remain open while other operations start.

## Validation and Acceptance

The serial configuration `--s3-concurrency 1 --pg-concurrency 1` must parse, and the existing CLI candidate processor must remain serial. A transport-level fixture must verify that S3 listing, stat/HEAD, and DELETE requests share the configured in-flight budget and that request starts obey the rate limit. The existing page size bounds buffered candidates at 64. Existing claim fencing, durable retry/ack semantics, scan caps and checkpoints must still pass focused janitor tests. No claim is made that a larger PG value creates parallel workers or that per-process budgets coordinate a cluster.

On an isolated RustFS fixture, the live resumable-listing test must finish both one-entry `start_after` and prefix-trie scans and claim every expected orphan. It uses 32 requests/second so the request gate stays below the test-only 200 ms HEAD timeout; the loopback transport test separately verifies 2 requests/second.

## Idempotence and Recovery

No new durable work state is introduced. A candidate is checkpointed only after its admitted work has drained. Timed-out operations remain conservative: unknown S3 outcomes are retried through the existing idempotent canonical DELETE and fenced claim protocol; workers must be joined before the lock holder closes. Repeated runs can re-process candidates safely under the existing claim and acknowledgement rules.

## Interfaces and Dependencies

Use existing OpenDAL 0.55 HTTP/concurrency layers and Tokio synchronization primitives. Avoid new dependencies unless the current crate APIs cannot express the required request-level rate. Keep PostgreSQL safety checks and mutation authority in `studiofs-meta`; do not bypass the held volume lock or weaken the existing per-object fencing contract.
