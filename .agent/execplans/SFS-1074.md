# Compile scratch classification rules without filesystem access

This living ExecPlan follows `.agent/PLANS.md`.

## Purpose / Big Picture

SFS-1074 supplies the rule engine for ADR 0014. It accepts the bytes of a
`.studiofsignore` file and classifies a volume-relative path as tracked or
scratch. A background loader can report a rejected update and continue using
the previously compiled rules. The engine is exercised directly through Rust
tests and a disposable Git repository used as a reference.

## Surprises & Discoveries

Git matches byte-oriented paths. Glob syntax alone does not encode Git's
directory-relative precedence, excluded-parent rule, or the StudioFS case
policy. The metadata index folds ASCII names and uses lossy UTF-8 Unicode
lowercase for other names.

Git treats a single CR immediately before a line ending as part of that
ending. A second CR is part of the pattern. Its case-sensitive matcher also
accepts non-UTF-8 rule bytes.

The initial matcher ran one compiled regex per rule. A debug-build probe
using 4,000 distinct literal rules recorded about 1.63 seconds for 1,000
unmatched four-component lookups. The ticket requires simultaneous matching
within a compiled set, so the review fix groups patterns without changing
the order in which their results take precedence.

The same debug probe on the grouped matcher recorded about 7.2 milliseconds
for the 1,000 literal-rule misses. A 4,000-rule extension wildcard file took
about 19 milliseconds for the same lookup sample. These figures are
observations from macOS and are not test thresholds.

## Decision Log

On 2026-11-20, the implementation was scoped to a pure public module in
`studiofs-vfs`, where the cache and loader planned in SFS-1075 can consume it.
The engine receives slash-separated volume path bytes, with an empty path
representing the root, and owns the last successful compiled file for each
directory. This keeps compilation and error recovery separate from lookup and
leaves filesystem access to the caller.

Use `globset` for ordinary glob-to-byte-regex translation. This lets the
engine match canonical volume bytes on every platform, including Windows,
and represent Git-specific recursive stars and bracket syntax in the same
matching layer. The higher-level `ignore` API uses host paths and its own
case policy. StudioFS supplies the directory scopes, ordering, and metadata
name folding explicitly.

Compile the expressions into `regex-automata` groups by scope of the
pattern and whether the target must be a directory. Reverse source order
within a group so a single anchored search yields the last rule that matches
in that group. Compare the resulting line numbers across groups.

Treat malformed syntax as a failed file update so the previous compiled
rules remain active. Git treats malformed lines as nonmatches. The Linear
issue makes atomic retention a StudioFS requirement. It also explicitly
protects paths named `.studiofsignore`, including when an ancestor rule
excludes the directory. This classifier only returns the rule result. The
follow-up runtime work owns namespace and publication decisions.

## Outcomes & Retrospective

The library compiles each directory's rules before replacing its prior set.
It performs byte-based classification with Git precedence and uses metadata
folding on case-insensitive volumes. The final implementation passed eight
focused tests, including both Git comparisons, and the existing metadata
folding equality test. The locked crate check, Clippy, formatting, and diff
checks passed on macOS. Native Windows and mounted runtime behavior were
outside this validation.

## Context and Orientation

`docs/adr/0014-local-only-scratch-layer.md` defines the classification contract.
`crates/studiofs-meta/src/redb_engine/layout.rs` contains the folding used for
the case-insensitive dentry index. A dentry is a directory entry mapping a name
to an inode. `crates/studiofs-vfs/src/lib.rs` exposes the rule engine and the
focused tests live under `crates/studiofs-vfs/tests/`.

## Plan of Work

Compile each directory's rules only when its rule file changes. Publish the
new compiled set after the full file passes validation and preserve the prior
set on failure. Look up ancestor rules with borrowing and compiled matchers.
Respect Git's relative scopes, ordered negation, and excluded directories.
Apply the StudioFS default for AppleDouble names at lowest priority and
protect the rule filename while reporting the offending source lines.

Create a disposable Git worktree with matching rule files and compare
classification for representative paths using `git check-ignore`. Cover
StudioFS-specific extensions and invalid updates via direct assertions.

## Validation and Acceptance

The focused target must report nonzero passing tests, including the Git
comparison in an environment with Git. The compiler, Clippy, formatting, and
diff checks must succeed. Verify that rules are compiled on update and no
per-ancestor heap allocation is required during path lookup.

## Idempotence and Recovery

Repeating a valid update replaces the same directory's compiled set. Repeating
an invalid update leaves that directory's prior rules active. The Git oracle
uses a temporary directory and leaves the project's Git configuration intact.
