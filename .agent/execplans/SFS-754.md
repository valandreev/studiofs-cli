Reuse the existing payload recovery intent files so lightweight startup can remove leftovers without scanning unrelated payloads or pretending deleted payloads remain indexed.

## Surprises & Discoveries


Existing SFS-753 intents already recover an unindexed final payload and preserve indexed payloads. Their parser accepts final paths without a temp path. Runtime mutation gates serialize conflicting puts, deletes, upload transitions and pinning. File-first deletion would leave stale index rows after an index commit failure; lightweight reconciliation prunes only dirty/uploading missing payloads.

The broader runtime gate passed 117/118 tests; `low_space_retry_has_bounded_progress_driven_waits` relied on fixed upload sleeps and expected capacity rejection. New deletion barriers let upload completions coalesce, making that rejection timing-dependent. Replace the fixture's sleeps with a bounded channel notification on each actual wait and exactly the allowed number of upload completions; enough dirty bytes must remain to preserve the rejection assertion.

PR 735 eviction review: the 128-object limit bounds one deletion batch, not a complete pressure pass or the wall-clock duration of a put. The store already coalesces barriers by the full two-byte shard key within each batch. Multiple batches can sync a shard again, because each batch retires its own recovery intent only after its deletions have been persisted.

## Decision Log


Decision (2026-10-01): persist an existing-format intent before dropping index ownership, then delete the payload using the existing rollback path. This keeps index-first ordering while preserving recovery ownership on unlink failure. No new index state, persistence format, dependency or full startup scan is needed. Index commit failure retains the intent without deleting any payload; recovery uses actual index ownership.

Decision (2026-10-01): consolidate runtime single/batch/eviction deletion into a shared gated helper. Keep mutation gates through intent creation, index mutation and file cleanup; clear pins/access bookkeeping only after index removal succeeds.

Decision (2026-10-01): repair the exposed low-space test's coordination, keeping its CapacityExhausted and retry-limit assertions. Only test instrumentation changes; production retry policy remains unchanged.

Decision (2026-10-01): retain removal markers on every index error. The installed redb 4.3.0 WriteTransaction::commit contract says non-poisoned commit errors may arrive after atomic changes became durable. A regression now requires the marker on injected index failure and proves replay preserves rows that remain. Preserve existing staged-temp cleanup even when shared intent serialization fails before persistence.

Decision (2026-10-01): address PR 735's eviction-latency suggestion by documenting and testing the existing shard coalescing and 128-object batch bound. Keep Durable barriers before intent retirement. Do not add a smaller arbitrary batch limit, shard-aware eviction reordering, or asynchronous cleanup without measurements: a smaller batch may increase intent overhead, reordering changes oldest-first selection, and deferred cleanup cannot pretend physically occupied cache space was freed. This change claims operation counts only, with no wall-clock or mounted-throughput improvement.

Decision (2026-10-02): assert literal fixture shard cardinalities instead of deriving barrier expectations from the current distribution. This keeps both intended collision/distinct-shard cases explicit and separates fixture drift from a barrier regression. Production sharding, eviction and durability are unchanged.

## PR 735 Eviction Barrier Follow-up (2026-10-01)


The sole unresolved inline thread, `discussion_r4160250742` at `runtime.rs:664`, correctly identifies an added Durable cost on `put` admission. The current checkout and PR head both started at `e600c7f1` on `feature/sfs-754-report-payload-file-removal-failures-before-dropping-index`, with a clean working tree. Trace the actual path: `put` calls `enforce_budget_before_put`, which runs `evict_to_target_bytes`; each `evict_batch_internal` rechecks eligibility under mutation gates and uses `remove_payloads_locked`. That helper persists a removal intent, drops index ownership and calls `rollback_batch` before returning.

An eviction batch of at most `EVICTION_DELETE_BATCH_SIZE = 128` objects already coalesces deletions in the same full two-byte shard. In Durable mode each batch adds one intent-file sync and one intent-directory barrier, plus S payload-directory barriers for S distinct attempted shards, where S is at most 128. Missing directories produce no successful barrier; a real barrier failure retains the recovery intent and propagates. Those counts exclude redb transaction durability. Fast adds no payload-store sync barriers; Windows directory-barrier calls are intentionally no-ops.

A complete pressure pass may require multiple batches. Its counts add across batches, including repeated shards across different intents, so neither total barriers nor elapsed put time are capped at 128. A successful Durable put after eviction adds its existing two file syncs and three directory barriers. Retain this bounded-batch synchronous tradeoff: each intent can be retired only after its own payload deletions are persisted. Cross-batch coalescing would require retaining all affected batch intents until the shared barriers succeed. A live or asynchronous cleanup worker would also need physical-space accounting and concurrency-safe ownership checks; changing oldest-first selection or adding such a worker is outside this review repair. Consider further optimization only if a measured foreground latency problem warrants it.

## Context and Orientation

Repository root: `/Volumes/Storage/dev/studiofs`. `crates/studiofs-cache/src/payload_store.rs` owns payload files and intent persistence. An intent is a small version-1 text file under `tmp/batch-intents`, naming final payload paths until ownership is settled. `runtime.rs` pairs the store with the redb cache index, which tracks visibility, upload state and byte counters. `startup_recovery.rs` replays intents before reads: final files are removed only when the corresponding index row is absent. `docs/cache.md` describes this local recovery boundary.
