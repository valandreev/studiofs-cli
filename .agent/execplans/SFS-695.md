# Define the PostgreSQL Sync Contracts and Invariants

This is a living ExecPlan for SFS-695. It follows `.agent/PLANS.md`; keep

`Outcomes & Retrospective` current until the issue is handed off.

## Purpose / Big Picture

StudioFS users should be able to distinguish three things that are currently
mixed together: the local metadata view becoming available for mounted reads,
catch-up of remote metadata, and permission to make new shared mutations. A
slow or finite PostgreSQL event history must not turn an otherwise usable local
disk into an unmountable disk, and a new client must not become write-capable
before its initial remote cut is applied.

This change defines that behavior before the follow-up implementation issues
change startup code. The observable result is one canonical PostgreSQL sync
contract, linked from the architecture and operator documentation, plus a
focused repository test that fails if the required vocabulary disappears or
the superseded startup wording returns.

## Surprises & Discoveries

- Observation: `PgMetaEngine::open_with_options` currently performs remote
  checkpoint/catch-up work before returning the engine. Evidence: in
  `crates/studiofs-meta/src/pg_engine.rs`, the startup path calls
  `pull_snapshot_locked(...)` and then `sync_metadata_to_current_head()`.
- Observation: the current catch-up helper repeatedly re-reads the remote
  head, up to 16 rounds, so its target can move while startup is in progress.
  Evidence: `crates/studiofs-meta/src/pg_engine/metadata_sync.rs`,
  `sync_metadata_to_current_head`.
- Observation: the regular event-log query has no page limit. Evidence:
  `query_foreign_event_rows` uses `SELECT_FOREIGN_EVENT_ROWS`, whose SQL orders
  rows after `batch_version > $2` without a `LIMIT`.
- Observation: `docs/metadata.md` already describes local redb as the serving
  source and has checkpoint terminology, but its UUID/offline section still
  says an unavailable remote blocks mount. That wording must be separated into
  identity safety versus sync readiness rather than copied into the new
  contract.
- Observation: the repository already uses
  `crates/studiofs/tests/architecture_vocabulary_test.rs` for documentation
  contracts, so no new test harness or runtime dependency is needed.
- Observation: the first sandboxed Cargo test could not write the existing
  `target/debug/.fingerprint` state and failed with Windows access denied;
  the same focused validation passed when rerun with the approved elevated
  Cargo permission.
- Observation: `restore_pending_batch` merges a failed claimed range with
  newly pending local events, and `flush_pending_claimed_batch` passes the
  resulting full range to `push_projected_event_log_batch_locked`. That
  producer assigns one `batch_version`; `PG_EVENT_INSERT_CHUNK_SIZE` only
  splits SQL parameter arrays inside that transaction and does not bound the
  published batch's replay size.
- Observation: the current `fetch_remote_state` query selects only `vol`,
  `snapshot`, and `format_info`; `create_local_snapshot` then opens a
  `PgMetaEngine`, whose current open path can synchronously chase the moving
  PostgreSQL head. The SFS-695 configuration bullets therefore must be labeled
  as target behavior until SFS-696 through SFS-698 land.
- Observation: `.agent/PLANS.md` requires a narrative `Milestones` section in
  addition to `Progress`; the previous SFS-695 plan had granular progress but
  no milestones.

## Decision Log

- Decision: Make `docs/pg-sync-contract.md` the single canonical PostgreSQL
  sync contract and make `docs/metadata.md` the implementation orientation
  page that links to it.
  Rationale: the mounted-IO document owns data-plane semantics, while the
  PostgreSQL lifecycle needs a focused source of truth that later runtime
  issues can implement without overloading the IO contract.
  Date/Author: 2026-09-11 / Codex.
- Decision: Define local serving readiness, remote catch-up, and write
  authority as separate states/capabilities, not as one generic "mount ready"
  boolean.
  Rationale: a local redb view can serve known state while replay is delayed,
  but a fresh client must remain read-only until its frozen startup target and
  allocator/write-authority checks are complete.
  Date/Author: 2026-09-11 / Codex.
- Decision: A catch-up run captures one remote target version, replays only
  pages in `(cursor, target]`, persists the cursor after each local apply, and
  resumes from that cursor after interruption. New remote events are handled
  by a later sync cycle.
  Rationale: this makes replay bounded and deterministic for one operation and
  prevents a moving remote head from extending mount startup indefinitely.
  Date/Author: 2026-09-11 / Codex.
- Decision: Keep SFS-695 documentation-only with a documentation contract test;
  do not change `PgMetaEngine` behavior before the explicitly related runtime
  issues land.
  Rationale: the issue states that later implementation issues depend on these
  contracts and may temporarily expose intentional test failures. Changing
  runtime startup here would mix the design gate with SFS-698 and SFS-697.
  Date/Author: 2026-09-11 / Codex.
- Decision: Treat `destroy --local` as an independent local lifecycle
  contract. It must not contact PostgreSQL or S3, while full remote destroy and
  identity verification remain separate operations.
  Rationale: local cleanup must remain possible when remote services or finite
  history are unavailable, without weakening the existing active-mount and
  confirmation guards.
  Date/Author: 2026-09-11 / Codex.
- Decision: State checkpoint freshness as an explicit bounded-lag policy rather
  than a periodic best effort, without inventing a numeric default in this
  design issue.
  Rationale: the implementation issue must choose and test the operational
  limit; the contract must already require a measurable maximum lag and a
  degraded/read-only response when that policy cannot be met.
  Date/Author: 2026-09-11 / Codex.
- Decision: Use a producer-side maximum batch envelope rather than exempting
  oversized batches or introducing a composite replay cursor in SFS-695.
  Rationale: the current apply path treats one `batch_version` as an atomic
  replay unit and persists a scalar version cursor. Bounding encoded rows and
  bytes before publication preserves that atomicity and makes replay page and
  operation bounds enforceable; runtime batching belongs to the follow-up
  implementation work.
  Date/Author: 2026-09-11 / Codex.
- Decision: Label the detailed `discover` bullets in `docs/configuration.md`
  as target behavior and document the current transitional behavior beside
  them.
  Rationale: the guide must not promise checkpoint/head capture, background
  replay, or fresh-client read-only authority before SFS-696 through SFS-698
  implement those contracts.
  Date/Author: 2026-09-11 / Codex.
- Decision: Add three narrative milestones covering the canonical contract,
  public documentation alignment, and independent validation/delivery.
  Rationale: `.agent/PLANS.md` requires each milestone to state its scope,
  commands, and independently observable acceptance so a novice can resume the
  work without relying on hidden context.
  Date/Author: 2026-09-11 / Codex.

## Context and Orientation

StudioFS is a Rust 2024 local-first filesystem. `studiofs-meta` owns the local
embedded `redb` metadata view and the PostgreSQL bootstrap/replication path.
`studiofs-vfs` serves foreground filesystem operations from that local view.
The PostgreSQL `metadata_state` row stores a monotonic remote metadata version,
the latest serialized serving checkpoint and its checkpoint version, while
`event_log` stores ordered remote-visible deltas. A serving checkpoint is a
bounded snapshot of the remote-visible namespace, attributes, regular-file
base graph, symlinks, xattrs, and ACL rules.

The current `discover` path in
`crates/studiofs/src/cli/discovery.rs` reads remote volume identity,
`metadata_state.snapshot`, and `metadata_state.format_info`, then writes a new
local metadata root. The current `PgMetaEngine::open_with_options` path in
`crates/studiofs-meta/src/pg_engine.rs` may import a checkpoint and synchronously
try to reach the current PostgreSQL head before returning. These are the
runtime seams that SFS-696 through SFS-698 will change; SFS-695 only fixes the
contract they must implement.

`crates/studiofs/tests/architecture_vocabulary_test.rs` is a portable
documentation contract test. It reads checked-in documents and asserts stable
terms; it does not claim to prove live PostgreSQL or mounted behavior.

## Validation and Acceptance

The canonical document is accepted when it explicitly states all of the
following in operational terms:

- local redb is the foreground serving database and opening it does not require
  remote replay;
- a new client uses the latest published checkpoint before event replay;
- local serving readiness is available independently of remote catch-up;
- catch-up is bounded, paged, ordered, resumable, and persists progress only
  after a local page apply;
- one catch-up operation targets a frozen remote version and does not chase a
  moving head;
- a fresh client may serve the imported local state read-only but cannot gain
  write authority until the startup target is reached and the required
  allocator/authority checks succeed;
- checkpoint lag is bounded by an explicit measurable policy;
- finite or pruned remote history triggers checkpoint rebootstrap or a
  recoverable read-only/degraded state, never a permanently unmountable local
  disk;
- `destroy --local` operates only on local metadata/cache and does not require
  PostgreSQL or S3;
- the on-disk/protocol change is explicitly breaking and migration of existing
  test disks is not required.

The documentation contract test is the local proof that these surfaces and
cross-links remain present. `cargo check -p studiofs`, formatting, and diff
checks provide compile/style evidence for the test change. Live PostgreSQL,
mounted, and future startup behavior are intentionally not claimed by this
issue and remain follow-up validation for SFS-696 through SFS-698. The
local-only destroy boundary is already covered by SFS-721 on `main`.

## Interfaces and Dependencies

The documentation contract names the runtime interfaces that later issues must
preserve:

- local serving view: `redb` overlay over remote-visible base state;
- remote checkpoint: `ServingCheckpoint` at `checkpoint_version`;
- replay cursor: scalar local applied `batch_version`; complete batches are
  page-bounded and `seq_id` is only their ordering tie-breaker;
- startup target: one captured remote `metadata_state.version`;
- lifecycle observations: local-ready, catching-up, target-reached, and
  healthy/degraded health;
- authority observation: read-only versus read/write, independent of local
  serving readiness and catch-up health;
- checkpoint publication: volume-scoped single-flight coordination, with a
  bounded lease or equivalent claim before expensive serialization;
- cleanup boundary: `destroy --local` with no PostgreSQL or S3 dependency.

No new Rust crate, runtime dependency, persisted field, or public API is added
by SFS-695.
