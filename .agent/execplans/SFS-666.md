# Make upload fragment ledger local-first

This ExecPlan is a living document and follows `.agent/PLANS.md`.

## Purpose / Big Picture

Background uploads must return to the pre-snapshot data-plane boundary: local
payload preparation, remote PUT, and local upload completion must not wait for a
PostgreSQL transaction. The upload proof still needs to survive a process crash,
so the upload worker will first commit its fragment ledger entry in the mounted
volume's local redb database. The existing PostgreSQL background runtime will
replay those local entries in batches and retain the current janitor/publication
contract once replication catches up.

The behavior is observable through focused redb reopen tests, replay tests, and
the existing upload lifecycle tests. The performance-sensitive acceptance point
is that `UploadedFragmentLedger::begin_fragment_uploads` and
`confirm_fragment_uploads` perform only local redb work; PostgreSQL calls occur
only from the background replay pass.

## Surprises & Discoveries

- `PgMetaEngine` already owns the local `RedbMetaEngine`; `open_meta_engine_with_options`
  selects it for PostgreSQL-backed volumes. The local ledger can therefore reuse
  the existing metadata file and lifecycle instead of adding a second database
  or a VFS-owned replay thread.
- The existing metadata poll worker already has a wakeup condition variable and
  bounded shutdown handling. Reusing it avoids another thread and makes ledger
  replay follow the existing local-first metadata replication cadence.
- Normal redb metadata writes use relaxed durability. The ledger write must use
  an immediate redb transaction because the upload worker is allowed to proceed
  only after the local recovery record has crossed its durability boundary.

## Decision Log

- Decision: Store one local ledger record per `(volume_id, object_id, fragment_index)`
  with the expected remote proof, a begin-replicated bit, and a confirmed bit.
  Rationale: the record preserves ordering across a crash and permits idempotent
  replay without making PG calls part of the PUT await.
  Date/Author: 2026-08-18 / Codex.
- Decision: Use the existing `PgMetaEngine` background poll for replay rather than
  starting a separate worker.
  Rationale: it already owns the PG connection pool, wakeup, shutdown, and
  local-first replication lifecycle.
  Date/Author: 2026-08-18 / Codex.
- Decision: Keep the current short local batcher at the VFS boundary.
  Rationale: several concurrent objects can share one immediate redb commit;
  removing the batcher would reintroduce one local durability barrier per object.
  Date/Author: 2026-08-18 / Codex.

## Context and Orientation

`crates/studiofs-vfs/src/vfs/upload_lifecycle/worker.rs` builds encrypted
fragments and invokes the `UploadedFragmentLedger` port around each remote PUT.
`crates/studiofs-meta/src/pg_engine.rs` wraps the mounted local
`RedbMetaEngine`; its existing `pg-meta-poll` thread flushes local metadata and
pulls foreign PostgreSQL metadata. `crates/studiofs-meta/src/snapshot_ports.rs`
defines the backend-neutral fragment ledger entry and operations.

The local ledger is not the snapshot read-only artifact state and must not be
exported in `RedbSnapshot`. It is per-client recovery state for uploads that
still need remote ledger replication. Once PostgreSQL confirms the begin and
confirm operations, the local pending row may be removed; repeating an already
successful PG operation remains safe because the PG statements are idempotent.

## Plan of Work

First add a red test in the redb engine tests that records a begin and confirm,
closes the engine, reopens the same database, and expects the pending local
record to remain available until a replay acknowledgement is recorded. Then add
the local table, serialized record, immediate write transaction, bounded scan,
and acknowledgement methods in the redb engine.

The PostgreSQL implementation of `UploadedFragmentLedger` now writes only to
the local redb ledger and wakes the existing poll worker. The replay pass runs
under the existing replication lock:
replicate all pending begins first, mark only matching local records as begun,
then replicate confirmed records and remove only matching locally acknowledged
rows. A failed remote batch must leave the local rows untouched for retry.

The replay pass is called from the existing poll/manual flush paths. The VFS
short batcher remains in place so local redb commits can be shared across
concurrent objects, and trait documentation/tests describe local-first
semantics.

## Validation and Acceptance

The local-ledger reopen test passes and proves that a crash between local
recording and PG replay leaves enough information to retry. The replay failure
test proves that pending rows remain. The replay success test proves begin
precedes confirm and that acknowledgement removes the matching row. The
existing post-PUT visibility VFS test passes, with the VFS upload path no longer
requiring a PG-backed fake to complete a PUT.

`RUSTFLAGS='-D warnings' cargo check --workspace`, formatting, and diff checks
pass. The full `studiofs-meta` unit run has four unrelated failures when run
without PostgreSQL; the three allocator failures report connection refusal and
the runtime checkout test passes when rerun alone. Live PostgreSQL or mounted
throughput validation remains a gap in this environment.

## Idempotence and Recovery

All local ledger updates use upsert/delete-by-identity operations. Reopening the
redb file is safe. Replaying a batch after a crash is safe because begin resets
the remote row to the uploading/pending state and confirm is keyed by the same
fragment identity and expected proof. Local acknowledgement is committed only
after the corresponding PG operation succeeds, so a crash before that commit
causes a harmless retry rather than data loss.

## Outcomes & Retrospective

- Local begin/confirm records use immediate redb commits and survive reopen.
- Replay performs PG begin before PG confirm, acknowledges only matching local
  rows, and leaves rows untouched when PG fails.
- The upload worker still uses its existing local batcher; its PG-backed ledger
  calls now stop at local redb and wake `pg-meta-poll` for asynchronous replay.
- No live PostgreSQL/S3 mount was available for a throughput measurement.
