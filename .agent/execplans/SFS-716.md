# Add a real large-history cold-bootstrap E2E scenario

This is a living ExecPlan for SFS-716 and must be maintained according to `.agent/PLANS.md`. It describes a heavy, opt-in mounted scenario that creates a genuinely large PostgreSQL-visible metadata history, starts a cold client from a checkpoint, interrupts and resumes catch-up, and proves that the client eventually becomes live and converges with the writers.

## Purpose / Big Picture

After this change, the registered `studiofs-e2e` runner will expose a non-default SFS-716 scenario that exercises the real mounted PostgreSQL synchronization path with at least 100,000 small namespace or metadata mutations. A user can list the scenario, run its disabled/planned contract locally without infrastructure, or run the heavy mounted scenario with the existing platform prerequisites. The retained summary will show the generated mutation count, checkpoint and startup target, per-session monotonic applied-version samples with the restart boundary, observed catch-up pages and event volume, restart evidence, moving-head evidence, phase durations, and final read-write convergence.

## Surprises & Discoveries

- The current long-history scenario performs only a small number of logical operations and its `LongHistorySummary` has no catch-up telemetry, so it cannot prove a large PostgreSQL history was traversed.
- The startup catch-up session is deliberately page-budgeted (`MAX_STARTUP_CATCH_UP_PAGES = 16`) and persists progress for later polling. SFS-716 must therefore observe real lifecycle transitions and resume behavior rather than treating one large timeout as proof.
- The public status command already exposes lifecycle, applied/target versions, checkpoint, and current/last page diagnostics through the mounted IPC path. The implementation should reuse that boundary and retain sampled evidence instead of adding a second synchronization API unless the existing fields are insufficient.
- A runner contract test can validate scenario registration and disabled artifacts without requiring PostgreSQL, object storage, or a mounted macFUSE/WinFSP environment. Such a test is necessary but is not evidence of native mounted correctness.
- The first sandboxed native attempt was correctly rejected at preflight because Docker/OrbStack and port checks were not available inside the sandbox. The same fresh release binary passed scenario 24 with the required native access; the retained report is the live acceptance evidence.
- A restart can legitimately make the next status sample lower than the last sample before the restart; the retained native sequence was `[32, 29, 50, 54]`. The summary now records the restart index and validates monotonicity within each mount session while still requiring the final sample to reach the startup target.
- The mounted status boundary exposes remote-head progress and the cold client's applied version, but not an exact per-operation PostgreSQL mutation counter. `remote_visible_mutations` therefore remains an expected workload count and is documented as contingent on the moving-head catch-up proof.

## Decision Log

- Decision: Implement SFS-716 as a new registered advanced-mounted scenario rather than inflating the existing small cold-observer scenario. Rationale: the ticket calls for an opt-in heavy workload and the existing scenario has a different purpose and artifact contract. Date/Author: 2026-09-17, Codex.
- Decision: Keep the heavy run opt-in and preserve the existing default scenario list behavior. Rationale: 100,000 mutations are intentionally unsuitable for the fast default suite. Date/Author: 2026-09-17, Codex.
- Decision: Use deterministic generated names and bounded observable-state polling; do not use fixed sleeps or retry loops as synchronization. Rationale: reproducibility and the repository E2E contract. Date/Author: 2026-09-17, Codex.
- Decision: Reuse `MultiClientController`, the mounted `status` command, existing lifecycle helpers, and `finish_advanced_mounted` where their contracts fit. Rationale: the smallest correct change is to compose existing lifecycle and validation machinery. Date/Author: 2026-09-17, Codex.
- Decision: Add only a scenario-scoped status parser and an opt-in bulk helper; do not add cumulative product-wide PG telemetry. Rationale: the existing mounted status boundary already exposes page, event, byte, checkpoint, target, and applied-version observations, while a general telemetry counter would expand SFS-716 beyond its E2E scope. The artifact names the page/event/byte values as observed. Date/Author: 2026-09-17, Codex.
- Decision: Validate applied-version monotonicity separately before and after the recorded restart index. Rationale: global monotonicity rejects the observed restart reset, while session-local monotonicity still detects rollback or cursor regressions inside one mount session and preserves backward-compatible fallback validation for summaries without the new index. Date/Author: 2026-09-19, Codex.
- Decision: Treat moving-head success as a joint observation: the warm client's remote head must advance after the moving writer completes, and the cold client's applied version must reach that observed head. Rationale: stopping at the first `Live` sample does not prove catch-up of mutations generated while the writer was still running. Date/Author: 2026-09-19, Codex.
- Decision: Skip the review's low-severity reusable-`PathBuf` optimization. Rationale: it changes the hot helper without a profile or benchmark showing allocator work is the bottleneck; the correctness fixes and existing native runtime evidence are sufficient for this task. Date/Author: 2026-09-19, Codex.

## Context and Orientation

The repository root is `/Volumes/Storage/dev/studiofs`. The feature branch is `feature/sfs-716-add-a-real-large-history-cold-bootstrap-e2e-scenario`. The `studiofs-e2e` crate is the registered scenario runner. `crates/studiofs-e2e/src/scenario/registry.rs` maps user-facing names and numeric list entries to scenario implementations. `crates/studiofs-e2e/src/scenario/workloads/advanced_mounted.rs` defines the advanced mounted scenario kinds, their properties, summaries, and validation. `crates/studiofs-e2e/src/scenario/workloads/advanced_mounted/runner.rs` owns real client creation, discovery, mounting, workload execution, cold discovery, remount/restart, and finalization.

`MultiClientController` in `crates/studiofs-e2e/src/client.rs` launches isolated `studiofs` client processes with separate metadata, cache, mount, log, and artifact roots. The mounted `studiofs status` command reports synchronization diagnostics through the same local/IPC boundary used by the product. A status sample is an observation of one client at one point in time; the scenario must preserve its sequence and assert that applied versions never move backwards.

The existing cold-observer scenario is the nearest reference. It initializes and mounts warm clients, creates a small history, then discovers and mounts a fresh client. SFS-716 extends that shape with a deterministic large history, a deliberately cold client, a bounded interruption and restart while that client is catching up, continued writer mutations that move the remote head, and an artifact containing enough evidence to diagnose liveness and checkpoint effectiveness. Applied-version samples are monotonic within each mount session; a lower first sample after restart is represented by `applied_version_restart_index` rather than treated as an in-session rollback.

## Validation and Acceptance

The focused contract test must fail before registration and pass afterward with a nonzero count. The scenario must appear in `cargo run -p studiofs-e2e -- list`, be absent from the default fast run selection unless explicitly requested, and write deterministic planned artifacts when real infrastructure is disabled.

The mounted acceptance requires all of the following in one retained run: at least 100,000 small metadata mutations visible to PostgreSQL; multiple catch-up pages and a cold client discovered from a bootstrap checkpoint; an interruption and restart while catching up; a per-session monotonically nondecreasing applied-version sequence with the restart boundary retained; active writers that move the remote head during catch-up; the cold client reaching the completed observed remote head; eventual `Live` lifecycle; and final read-write convergence through the existing validator. The summary must include checkpoint version, startup target, applied progression, restart index, observed page count and event rows/bytes, restart evidence, moving-head evidence, and wall-clock durations. Fixed sleep, blind timeout success, or a retry-only convergence claim is invalid evidence.

Package tests and checks prove runner contracts and compilation only. They do not prove macFUSE/WinFSP behavior, PostgreSQL replication, or object-storage publication. Those native/service-backed checks must be reported separately with their exact command and result.

## Idempotence and Recovery

The scenario uses a unique runner run ID and per-client roots, so rerunning it creates a new isolated artifact set. If a mounted run fails, use the runner cleanup command and inspect the retained summary/logs before rerunning; do not delete unrelated `target/e2e-runs` directories. The implementation must keep teardown in the existing finalizer and emergency cleanup paths. If a client restart fails, the run should fail with the current phase and client log path rather than silently retrying until the deadline.
