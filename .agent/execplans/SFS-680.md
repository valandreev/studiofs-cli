# Benchmark Windows metadata caching and make the Windows GO/NO-GO decision

This ExecPlan follows `.agent/PLANS.md`. Keep `Progress`, `Surprises & Discoveries`,
`Decision Log` and `Outcomes & Retrospective` current while the benchmark is being
executed.

## Purpose / Big Picture

SFS-680 decides whether the adaptive WinFSP metadata-cache policy is suitable as
the Windows production default. The decision must use comparable native Windows
measurements, not unit-test timings or a different machine. After this work, a
reader can inspect the retained raw reports and the decision document to see the
same metadata-heavy workloads measured against the pre-SFS-678 policy and the
current adaptive policy, together with callback, latency, CPU and memory evidence.

Correctness is a hard prerequisite. SFS-679 already supplied ten complete native
scenario sweeps, so this plan does not repeat that gate unless its evidence is
missing or the candidate binary changes during execution.

## Surprises & Discoveries

- The historical SFS-675 sample has no matching host/build identity for the
  supplied CSV and must not be used as the primary A/B comparison when a fresh
  baseline can be collected from the same machine.
- The baseline test is already present at `3e7cf531`, before SFS-678 changed the
  default policy. This makes that commit a reproducible pre-change fixture without
  changing the workload definition.
- The current branch is at `7cee40bc`, where an unset
  `STUDIOFS_WINFSP_METADATA_CACHE_POLICY` selects `adaptive`.

## Outcomes & Retrospective

The final native A/B collection completed successfully. The candidate improved
open/close but regressed the selected primary enumeration metric and two other
mandatory workloads, so the Windows decision is NO-GO. The adaptive implementation
and shared coherence infrastructure remain intact; production should retain the
conservative Windows policy until a follow-up measurement addresses the regressions.
The final medians were stat 45.169 ms versus 52.766 ms, open/close 55.834 ms
versus 49.612 ms, negative lookup 22.390 ms versus 23.645 ms, and enumeration
323.890 ms versus 350.939 ms (baseline versus candidate). Focused validation then
passed formatting, Clippy, 142 WinFSP unit tests and the architecture contract test.

## Context and Orientation

`crates/studiofs-winfsp/tests/mount_sanity/metadata_baseline.rs` mounts an isolated
local redb-backed VFS through real WinFSP and measures repeated stat, open/close,
negative lookup and complete 64-entry enumeration. Each workload performs 1000
operations per pass and the test performs three passes. It validates attributes,
NotFound behavior and enumeration contents on every operation, then records
elapsed nanoseconds and callback-entry deltas for security/name lookup, open,
file-info, directory, cleanup and close.

Before SFS-678, `3e7cf531` uses the SFS-675 defaults: `FileInfoTimeout=u32::MAX`,
directory/volume metadata timeout 1000 ms, kernel-mode opens disabled and cleanup
purge disabled. The current candidate uses the adaptive default: file-info remains
`u32::MAX`, while the adaptive metadata timeout is 60000 ms. Both sides leave the
policy and individual timeout overrides unset and inherit only the two required
mount-test values from the repository `.env`.

The native test is an integration process and must run alone because it installs a
global tracing subscriber to observe callbacks on dispatcher threads. The harness
uses a temporary tracked-source snapshot under `target`, separate log/artifact directories,
the same release profile and the same drive `Z:`. It removes only that temporary
snapshot after copying the raw reports; retained evidence remains under
`target/perf/sfs-680-*`.

SFS-679 is the correctness/stability prerequisite. Its Linear evidence records ten
sequential candidate sweeps over scenarios 1-25, 250/250 executions passed, and no
retry or manual reset. The repository's full integration suite remains an operator
gate and is not silently substituted by this benchmark.

## Plan of Work

Add `tools/perf/sfs-680-windows-metadata-ab.ps1`. The script will resolve the
repository, validate the baseline commit and candidate commit, read only the two
required non-secret settings from `.env`, clear policy/timeout overrides for both
children, and refuse an assigned mount drive. It will create a detached baseline
tracked-source snapshot under `target` with `git archive`, invoke the exact `metadata_baseline::winfsp_metadata_baseline`
test three times per side, and copy each reported CSV next to its stdout/stderr
log. While each cargo process is alive, it will sample the cargo process tree for
maximum working set and accumulated CPU time. It will write `environment.json`,
`results.json` and `summary.md` under a unique retained artifact directory.

Add `docs/perf/sfs-680-windows-metadata-decision.md` after collection. It will
identify both commits, machine/build/configuration, exact command, raw artifact
paths, per-workload medians, callback behavior, CPU/memory observations and the
decision. It will explicitly separate the measured A/B result from the SFS-679
correctness gate and state any missing controls or limitations.

Do not change production cache behavior as part of SFS-680. A GO decision may
justify a later cleanup of transition switches, but that is a separate change and
must not be inferred from noisy or incomplete measurements.

## Concrete Steps

From `E:\dev\studiofs-cli`, run the harness with the verified free drive:

    .\tools\perf\sfs-680-windows-metadata-ab.ps1 -MountPoint Z:

The script must fail if either side skips the test, if a test returns a non-zero
exit code, if a CSV is missing, if the CSV does not contain exactly 12 data rows,
or if the process-tree sampler cannot observe a running test process. A successful
run prints the retained artifact directory and writes the decision inputs there.

Use `Import-Csv` or an equivalent read-only analysis to calculate the median of
the three invocation medians for every workload and report all callback columns.
Do not pool callback counts across different workload boundaries or call the
timings CPU latency: close callbacks may cross boundaries, and enumeration timing
includes correctness assertions, allocation and sorting.

## Validation and Acceptance

Focused acceptance requires three completed baseline invocations and three
completed candidate invocations, each containing all four workloads and three
passes. Every row must report 1000 operations, all correctness assertions must
pass, and every run must unmount and release the fixture. `environment.json` must
show the same host, Rust/Cargo versions, mount point, override state and workload
definition for both sides; `command.txt` or the equivalent command field must
show the exact test invocation.

The decision is GO only if the candidate has the better point estimate on the
declared primary metric and no mandatory workload has a material regression,
while the SFS-679 10-run correctness evidence remains valid. A difference within
measurement noise may still be GO when the point estimate is better. If the
candidate regresses a mandatory workload materially, or the evidence is not
comparable/complete, record NO-GO and retain the conservative policy.

Run focused repository checks after documentation and harness edits:

    cargo fmt --all -- --check
    cargo test -p studiofs-winfsp --lib
    cargo test -p studiofs --test architecture_vocabulary_test configuration_contracts_match_executable_defaults -- --nocapture
    git diff --check

Do not run the full workspace suites in this task. Tell the operator to run the
repository's full non-ignored and ignored integration commands when promoting the
result.

## Idempotence and Recovery

Each invocation uses a unique artifact directory and a fresh temporary baseline
source snapshot. A failed attempt remains in `target/perf` for diagnosis and is never
counted as a successful result. Remove only a verified temporary source snapshot under
`target/sfs-680-*` after its CSVs and logs are copied. If the mount remains
assigned after a failure, inspect the saved logs and normal fixture cleanup before
retrying; do not delete an unknown drive or reset repository state.

The harness restores any pre-existing environment values it temporarily changes.
The source `.env` is never printed, committed or copied into the temporary
snapshot.

## Interfaces and Dependencies

The harness depends only on PowerShell 7, Git, Cargo/Rust, the existing
`studiofs-winfsp` native test fixture and an installed WinFSP runtime. It uses no
new Rust production interface and no remote service. The test fixture continues
to use the existing tracing callback counter and local VFS setup. The current
policy interface remains `WinfspMetadataCachePolicy` in
`crates/studiofs-winfsp/src/cache_policy.rs`; this issue measures it and does not
modify it.
