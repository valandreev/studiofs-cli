# SFS-717: Make mount consistency validation local-first

This ExecPlan is a living record for the implementation of Linear issue SFS-717. It follows `.agent/PLANS.md`.

## Purpose / Big Picture

An existing valid local PostgreSQL-backed volume must mount and serve its local `redb` view when PostgreSQL is slow or unreachable. Mount startup will validate the local format metadata only; PostgreSQL volume identity will still be checked before any remote replay or publication, so a recreated or wrong remote volume cannot exchange metadata with the client.

The behavior is observable through a focused mount metadata test: reading mount format information must work with a local-format capability that has no remote replication capability. Remote identity safety remains observable through the existing metadata lifecycle tests that gate pulls, publication, and `Live` promotion.

## Surprises & Discoveries

- SFS-706 already made transport failures tolerable at the CLI boundary, but the boundary still invokes a live PostgreSQL identity probe before mount admission. That still violates the stronger SFS-717 requirement for a local-only mount decision.
- `PgMetaEngine::ensure_remote_format_validated` is shared by remote pulls, event publication, checkpoint work, and metadata flush. The fix must not bypass that gate; it is the protection against applying or publishing to a mismatched remote volume.
- The local `FormatInfo` already contains the persisted volume UUID and PostgreSQL volume configuration needed by mount setup. `get_format_info()` is therefore the local validation seam; no new identity cache or abstraction is needed for this change.

## Decision Log

- Decision: Remove the `MetaReplication` requirement from the mount format-reader seam and have it read only local `MetaFormat` state. Rationale: the mount decision must not call a remote operation, and a capability boundary makes that regression structurally harder to reintroduce. Date/Author: 2026-09-20, Codex.
- Decision: Keep strict `check_consistency()` and the existing remote validation gate unchanged. Rationale: destroy/diagnostics and all remote replay/publication paths still need explicit identity verification; SFS-717 changes only OS mount admission. Date/Author: 2026-09-20, Codex.
- Decision: Do not add a new persisted identity type or new configuration. Rationale: `FormatInfo` is already persisted locally and the issue's safety invariant is enforced at the shared remote-operation boundary. Date/Author: 2026-09-20, Codex.

## Context and Orientation

`crates/studiofs/src/cli/mount/session.rs` opens the local metadata engine, reads `FormatInfo`, and prepares the mounted runtime. Its former `read_live_mount_format_info` path also called `MetaReplication::check_consistency_for_mount_admission`, which reaches PostgreSQL for a UUID check. `crates/studiofs-meta/src/pg_engine.rs` and `crates/studiofs-meta/src/pg_engine/metadata_sync.rs` own the separate remote validation gate used before replay and publication. The canonical lifecycle contract is in `docs/pg-sync-contract.md`: local serving readiness, remote catch-up, and mutation authority are independent.

## Validation and Acceptance

Acceptance is met when local mount format loading does not require a PostgreSQL or replication capability, an existing local PostgreSQL volume can proceed from its local metadata, and the existing identity-gate tests still prove that remote pulls/publication/`Live` promotion cannot proceed while remote identity is unvalidated. A UUID mismatch must remain a remote-operation failure, not become a mount-time remote query.

## Idempotence and Recovery

The change is limited to tests, the mount-session capability bound, and its living plan. It is safe to rerun focused Cargo commands. Do not reset or discard unrelated worktree state. If a test or lint exposes another caller that depends on the removed mount-only helper, inspect that caller and preserve its strict `check_consistency()` path rather than weakening the shared remote gate.

The mount reader should depend on `studiofs_meta::MetaFormat::get_format_info` only. Remote synchronization continues to depend on `studiofs_meta::MetaReplication::check_consistency` and `PgMetaEngine::ensure_remote_format_validated`, which validates PostgreSQL format and volume UUID under the existing validation lock before remote operations.
