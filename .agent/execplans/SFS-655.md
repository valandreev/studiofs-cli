# Make HandleTable registration atomic: Implementation Plan

> **For agentic workers:** Follow this plan task-by-task with TDD and fresh
> verification before claiming completion.

**Goal:** Prevent concurrent `HandleTable` open/close operations from observing
  a handle without its inode reference count and panicking the daemon.

**Architecture:** Keep the existing `RwLock<HandleTableData>` as the single
  owner of handles, inode indexes, and counts. Update all related state under
  that one write/read lock and leave the independent orphan marker unchanged.

**Tech Stack:** Rust 2024, `parking_lot::RwLock`, `HashMap`, `HashSet`, Cargo
  unit tests, and Clippy.

---

This ExecPlan is a living plan for SFS-655 and follows `.agent/PLANS.md`.

## Purpose / Big Picture

Rapid concurrent file open and close operations must not crash the StudioFS
daemon. The current `HandleTable` publishes a handle under one lock and its
inode reference counters under another lock, leaving a window in which
`close()` can observe a real handle without its counter entry. After this
change, handle publication, per-inode indexing, and open-counter updates will
be one atomic state transition. The behavior is observable through a focused
structural regression test for shared state and a concurrent open/close
characterization that completes without a panic.

## Surprises & Discoveries

- Observation: `HandleTable` currently has no `drain` method despite the issue
  description mentioning it; the active implementation only needs `open`,
  `close`, lookups, inspectors, and access-class collection updated.
  Evidence: `crates/studiofs-vfs/src/vfs/handle_table.rs` contains the complete
  current implementation and `rg` found no `HandleTable::drain` call.
- Observation: `OpenFile` is cloneable and carries its mutable per-handle
  state in its own `Arc`-protected fields, so moving only the inode counters
  does not change the lifetime or access semantics of returned handles.
  Evidence: `crates/studiofs-vfs/src/vfs/file_session.rs` defines
  `OpenFile` with `Arc<Mutex<...>>` and `Arc<RwLock<...>>` state.
- Observation: the repository lock-order validator covers named VFS
  subsystems, but `HandleTable`'s private parking_lot lock is not a separate
  registered tier. Unifying the two table states removes the local lock-order
  hazard rather than introducing another ordering rule.
  Evidence: `crates/studiofs-vfs/src/lock_order.rs` lists subsystem tiers and
  `handle_table.rs` currently acquires `handles` and `counts` separately.
- Observation: the structural regression test reproduces the missing unified
  state deterministically in the baseline rather than depending on scheduler
  luck.
  Evidence: `cargo test -p studiofs-vfs
  vfs::handle_table::tests::handle_counts_are_stored_with_handle_table_state
  --lib -- --exact --nocapture` failed with `no field counts` on
  `HandleTableData`.

## Decision Log

- Decision: Store `counts: HashMap<Ino, HandleCounts>` inside
  `HandleTableData`, protected by the existing `RwLock`.
  Rationale: this makes insertion, removal, indexing, and counter updates a
  single critical section and matches the solution proposed in SFS-655. It
  also avoids choosing or documenting an order for two locks that describe one
  invariant.
  Date/Author: 2026-08-27 / Codex.
- Decision: Preserve the existing invariant assertions for genuine
  impossible state, while making the reported concurrent interleaving
  impossible.
  Rationale: silently repairing a missing counter would hide corruption and
  change the existing contract; atomic state ownership addresses the race at
  its source.
  Date/Author: 2026-08-27 / Codex.
- Decision: Use a private-state structural regression test plus a bounded
  concurrent runtime characterization, without a test-only hook in
  `HandleTable`.
  Rationale: the structural test deterministically prevents the split state
  from returning, while the runtime test exercises real cross-thread open and
  close behavior. This keeps production code free of test synchronization
  methods and avoids relying on scheduler luck for the primary regression
  proof.
  Date/Author: 2026-08-27 / Codex.

## Context and Orientation

`crates/studiofs-vfs/src/vfs/handle_table.rs` owns the process-local map from a
numeric file handle (`fh`) to an `OpenFile`, an index from inode (`Ino`) to its
file handles, and per-inode counts of all open handles and write-capable open
handles. `StudioVfs::open_file_resolved` calls `HandleTable::open`; release
callbacks call `HandleTable::close`; foreground decisions call
`open_count()` and `write_open_count()`.

The invariant is that every entry in `HandleTableData.handles` has a matching
inode-index entry and contributes exactly one to that inode's `open` count and,
when its flags permit writing, exactly one to its `write` count. `close()` must
remove all of those representations as one transition. The existing
`orphans` set is a separate deferred-deletion marker and is not part of this
handle/count invariant.

## Plan of Work

First extend the unit-test module in `handle_table.rs` with a deterministic
structural regression test. It reads the counter map through the same
`HandleTableData` guard as the handle map, so the baseline implementation fails
to compile because the shared state does not yet own `counts`. Keep a second,
bounded runtime test that runs real open and close calls from separate threads
and verifies that all counters return to zero.

Next add `counts` to `HandleTableData` and remove the separate `HandleTable`
field. `open()` will update `handles`, `handles_by_inode`, and the relevant
`HandleCounts` while holding one write guard. `close()` will remove the handle,
clean the inode index, decrement the same counter entry, and remove an empty
counter entry while holding that guard. `open_count()` and
`write_open_count()` will read the counters through the same table read guard.
All other methods will continue using the existing table lock and the
independent `orphans` lock with no behavior changes.

Finally run the focused handle-table tests and the crate-level VFS library
checks that cover the changed private module. Run formatting and
`git diff --check`; do not run the full workspace test suite because the
repository instructions reserve that operation for the user.
