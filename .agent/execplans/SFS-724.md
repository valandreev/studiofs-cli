# Propagate Deferred Namespace Conflicts to Dependent Operations

This ExecPlan is a living document and follows `.agent/PLANS.md`. Keep its
Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective
sections current while completing SFS-724.

## Purpose / Big Picture

When two clients race to create the same directory entry, the losing deferred
create must fail without leaving an inode that has no directory entry. Later
operations based on that failed inode must also fail, while independent creates
from the same deferred batch must still commit. The behavior is demonstrated by
focused metadata and VFS tests: the missing inode stays missing, dependent
operations settle with an error, independent namespace entries persist, and the
VFS does not become degraded.

## Surprises & Discoveries

- Observation: a successful `SetAttr` on a missing inode is currently possible in the redb batch path.
  Evidence: `RedbMetaEngine::apply_namespace_mutations` replaces `InodeNotFound` with the queued attribute and then writes it.
- Observation: a namespace batch error identifies the operation index, and the VFS already retries the batch after removing a concurrent `EntryExists` create.
  Evidence: `namespace_entry_conflict_index` extracts that index; `drain_deferred_namespace_metadata` currently abandons only the one removed operation.
- Observation: current tests already protect retrying independent operations and avoiding mount degradation for an isolated create conflict. New coverage should extend those behaviors rather than replace them.
  Evidence: `deferred_namespace_entry_conflict_retries_nonconflicting_operations` and `deferred_namespace_entry_conflict_does_not_degrade_mount` both exist and pass before this change.
- Observation: the missing-inode redb regression returns a fabricated inode today.
  Evidence: the test failed at `unwrap_err()` because the operation returned `Ok([InodeAttr { ino: 42, ... }])`.
- Observation: both VFS regressions reproduce the two reported failures.
  Evidence: the file case found the orphan via `meta.get_attr(conflicted.ino)`, and the directory case received `InodeNotFound` for the child because its parent directory had already been removed.
- Observation: review findings about stale cache state and cross-batch dependencies are reproducible through the public VFS admission path.
  Evidence: a VFS lookup healed away the competing entry, and a child queued after a full 256-operation batch retried with `InodeNotFound`.
- Observation: the review document's batch-size and retry counts are stale.
  Evidence: the current constants are 256 operations and 3 retries; the cross-batch dependency still occurs beyond that boundary.
- Observation: a write through a deferred-create handle persists an empty draft attr in redb and buffers bytes in `MountedWriterStack` before the create batch settles.
  Evidence: the new regression failed after the conflict because the inode still had dirty writer-stack state; it also asserts the attr and queued upload exist before conflict settlement.
- Observation: synchronous inode cleanup from the namespace drainer can deadlock when a strict write owns the file-session gate while waiting for that same drain.
  Evidence: strict write paths call `flush_local_dirty_state` under `FileSessionOperation::Write`, and that helper waits for deferred namespace settlement.
- Observation: an explicit flush can wait for failed namespace metadata without holding the file-session gate, then wait for full inode cleanup before returning the namespace error.
  Evidence: `flush_fh_with_outcome_inner` checks deferred namespace metadata before acquiring its flush gate.

## Decision Log

- Decision: prune only later operations in the current batch that reference an abandoned inode, directly or through a create's parent inode; keep the relative order of every other operation.
  Rationale: deferred operation order is significant, and an abandoned directory can have descendants whose own inode references must be added transitively.
  Date/Author: 2026-09-22 / Codex.
- Decision: treat `SetAttr` for an inode absent from the redb transaction as the existing indexed `InodeNotFound` batch error.
  Rationale: attribute updates must not create inode identity; `SetAttr` owns no namespace entry.
  Date/Author: 2026-09-22 / Codex.
- Decision: retain the existing metadata error for the failed create as the error reported by its dependent operations.
  Rationale: it identifies the root conflict and avoids introducing a new error type or mapping.
  Date/Author: 2026-09-22 / Codex.
- Decision: remove queued dependents while holding the deferred queue lock and check the parent's retained error again during enqueue.
  Rationale: an operation can pass the earlier admission check before the conflict is recorded; the queue scan must catch it if it enqueues first, and the locked enqueue check must reject it if it enqueues later.
  Date/Author: 2026-09-23 / Codex.
- Decision: invalidate each abandoned create's dentry and bump affected parent generations before releasing the deferred queue lock; clear file payload/incarnation state and abandoned directory state as part of settlement.
  Rationale: lookups must not heal a stale optimistic dentry by deleting the competing metadata entry, and failed creates must not leave runtime state behind.
  Date/Author: 2026-09-23 / Codex.
- Decision: keep the indexed `?` propagation in the redb `SetAttr` arm and keep `Vec::split_off`.
  Rationale: the `?` preserves the same indexed error with less code than the suggested `match`, and the split is bounded by 256 operations with no profiling evidence for allocator pressure.
  Date/Author: 2026-09-23 / Codex.
- Decision: clean abandoned file inodes through the existing orphan-deletion lifecycle under `FileSessionOperation::Delete`, using a tracked background task.
  Rationale: this reuses graph/attr removal, upload cancellation, writer-stack and pending-payload cleanup while serializing with writers/materializers; background scheduling lets an inline namespace drain return to a strict writer that currently owns the same gate.
  Date/Author: 2026-09-23 / Codex.
- Decision: explicit flush/fsync waits for failed-file cleanup before returning the namespace error, while generic namespace waits return the error immediately.
  Rationale: local dirty flush may wait for namespace settlement while holding the write gate, so making every waiter await cleanup would recreate the gate/drainer deadlock.
  Date/Author: 2026-09-23 / Codex.
- Decision: queue VFS regression operations directly and start the drain only after creating the competing entry.
  Rationale: this deterministically exercises a single batch without racing the background drain scheduled by public admission methods.
  Date/Author: 2026-09-22 / Codex.

## Outcomes & Retrospective

The VFS abandons the conflicted create and every dependent operation in the
current batch and the remaining queue, including descendants whose parent was
itself abandoned. It rejects admissions that race with that settlement,
invalidates optimistic dentries, retires abandoned runtime state, and retries
independent operations in their original order. The redb transaction reports
indexed `InodeNotFound` for an attribute update to a missing inode and does not
create an inode record. Six metadata batch tests, 30 deferred-namespace VFS
tests, and the VFS lookup regression passed. VFS check, Clippy, formatting, and
diff checks also passed. No PostgreSQL service or mounted filesystem was needed
for this local transaction behavior. No commit or external Linear update was
made.

The follow-up written-create regression confirms that a losing create removes
its redb draft attr, writer-stack bytes, pending local-dirty payloads, and queued
upload state without disturbing the competing name winner. Cleanup waits for
the inode Delete gate; late writes through the failed handle keep returning the
namespace error. The cleanup task is tracked and included in shutdown draining.
The focused conflict regression, 30 deferred-namespace tests, and the existing
orphan writer-stack cleanup regression passed; VFS check and Clippy passed with
warnings denied, as did formatting and diff checks.

## Context and Orientation

`crates/studiofs-vfs/src/vfs/namespace_ops.rs` accepts metadata changes into a
local deferred queue. `drain_deferred_namespace_metadata` sends each batch to
`MetaEngine::apply_namespace_mutations`; when another client has created the
same parent/name pair, redb returns `MetaError::NamespaceBatchOperation` with
the failing index and `MetaError::EntryExists` source. Since the metadata batch
is transactional, the VFS removes the losing create and retries the remaining
operations.

`DeferredNamespaceOp` has `CreateFile`, `CreateDir`, and `SetAttr` variants. A
create refers to its target through `attr.ino` and to its parent through
`parent`; `SetAttr` refers to its target through `attr.ino`. If a create is
abandoned, later `SetAttr` on that inode and later creates whose parent inode
was itself abandoned cannot succeed. Descendant creates add more target inodes
to the abandoned set. Other operations in the same batch remain ordered and
should continue through the existing retry path.

`crates/studiofs-meta/src/redb_engine/fs_ops.rs` applies namespace mutations in
one redb write transaction. Its `SetAttr` arm must load the inode from that
transaction before applying fields. A missing inode is an ordinary metadata
error, not permission to reconstruct an inode from a possibly stale queued
attribute. No relevant namespace-conflict ADR was found under `docs/adr`; the
root and crate `AGENTS.md` contracts define the applicable local-metadata and
deferred-operation boundaries.

## Plan of Work

First add a focused metadata regression in
`crates/studiofs-meta/src/redb_engine/tests/fs_ops.rs`. Submit `SetAttr` for an
inode that does not exist and assert the indexed `InodeNotFound` result and that
`get_attr` still reports the inode absent. Run this test before editing
production code and confirm it fails because the current implementation
fabricates the inode.

Next add VFS regressions in `crates/studiofs-vfs/src/vfs/tests.rs`. Queue the
same deferred operations the production path queues, then create a competing
entry directly in the metadata engine before starting the drain. Cover a file
create followed by `SetAttr` plus an independent create, and a directory create
followed by a child create plus an independent create. Wait for settlement,
assert dependent operations fail and have no persisted inode/dentry, assert the
independent entry persists, and assert the deferred queue is not degraded. Run
each test first and verify the current behavior fails these assertions.

Then change the redb `SetAttr` arm to propagate missing-inode errors with the
current operation index. In the VFS conflict branch, record the failed create
inode, scan only the later suffix in order, and abandon operations targeting a
failed inode or creating under a failed parent. When an abandoned create is
removed, add its target inode to the failed set so nested descendants are also
removed. Pass the original conflict error to the existing abandonment routine
and retain independent operations in their original order for retry.

For an abandoned `CreateFile`, schedule the existing orphan-inode cleanup under
the per-inode Delete gate so a write or materializer already in flight finishes
before redb/runtime state is removed. Keep this cleanup off the namespace
drainer's stack because strict writers can hold that gate while waiting for the
drain. Explicit flush/fsync waits for cleanup before returning the recorded
namespace error, and subsequent writes check that error before mutating state.

## Validation and Acceptance

production changes and passing after them. The redb regression must return
`NamespaceBatchOperation { index: 0, source: InodeNotFound(ino) }` for a missing
target and leave `get_attr(ino)` in the missing state. In the VFS tests, each
conflicted create and every dependent operation settles with an error, no

and `deferred.degraded` remains false. Existing batch ordering and newer-inode
field preservation tests must remain green. `running 0 tests` is not validation.

## Idempotence and Recovery

The tests use isolated temporary metadata engines and do not alter user data or
external services. Re-running the focused commands is safe. A failed regression
run leaves only its isolated temporary fixture; no database migration or
recovery action is needed.
