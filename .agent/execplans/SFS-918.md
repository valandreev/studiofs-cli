# Diagnose the rare fsx data loss under FUSE writeback

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current. Maintain it according to `.agent/PLANS.md`.

## Purpose / Big Picture

Users must not lose bytes that remain below EOF after a sequence of writes, mapped writes, copies, and truncates. This investigation will identify which layer first returns or persists the wrong bytes, then either make the smallest proven correction or document the remaining kernel-side evidence needed. A human can observe progress by running the bounded `small` fsx profile on a live WSL FUSE mount and comparing the raw failed file with fsx's `.fsxgood` reference while preserving callback logs.

Evidence: the fresh red run reports `cache_policy="kernel"`, `capable_features=0x79fffdb`, and `enabled_features=0x15f809`; bit 16 is set in both masks.
- Observation: The fresh red run is a persisted content failure, not just a one-read page-cache discrepancy. Evidence: the copied file after unmount/remount has the same SHA-256 as the pre-unmount captured file and still differs from `.fsxgood` in 727 bytes, starting at `0x1150`.
- Observation: The fresh red does not match the simple hypothesis that the recorded write is truncated away. Evidence: fsx operation 99434 copies `0x89f` bytes to `0x1150`, the later truncate leaves EOF at `0x8a7d`, and the first bad `MAPREAD` starts at `0xbfc`; all are within the final file size.

Its `fuse_do_setattr` path waits for the writepage counter before sending `FUSE_SETATTR`, then applies the new size and invalidates page-cache ranges. This rules out a generic pending-writepage overtaking claim, but does not by itself explain the persistent copied bytes.
- Observation: The Linux adapter has no `copy_file_range`/`copy_range` callback in `crates/studiofs-linux-fuse/src/low_level.rs` or `crates/studiofs-linux-fuse/csrc/low_level_ops.c`. Evidence: `setattr(requested_size=54383)` returned size 54383 at `20:58:07.793625Z`; the next FUSE getattr, at `20:58:07.794304Z`, returned 63542. The raw copy before unmount was 54,383 bytes, but a read-only remount reported and copied 63,542 bytes.
