# Scratch Layer Conflicts with Replicated Entries and Orphaned Scratch Entries (SFS-1080)

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan is maintained in accordance with [PLANS.md](file:///E:/dev/studiofs-cli/.agent/PLANS.md).

## Purpose / Big Picture

StudioFS stores ignored temporary files and directories in a mount-local scratch layer that never publishes events to PostgreSQL or object storage. Because peers cannot see local scratch entries, concurrent peer activity replicated into this client can create a tracked entry under a name already occupied by a local scratch entry, rename a tracked parent directory holding scratch children, or remove a tracked parent directory that still holds local scratch files or subdirectories. After this change, foreign replay and snapshot or checkpoint restore resolve tracked-versus-scratch name collisions by giving the replicated tracked entry its requested name, renaming the colliding local scratch entry locally to `<name>.scratch-conflict-<n>` with a warning log and a persisted conflict record for `status` and zero emitted `event_log` rows, while foreign parent removal or snapshot restore crash-safely relocates affected scratch entries and full scratch directory subtrees out of the active namespace into `<cache>/scratch-orphans/<timestamp>/<old path>` with preserved metadata and payload objects protected from local garbage collection. Replicated parent renames preserve scratch children automatically via parent inode keying, and ADR 0012 concurrent same-name directory merges re-parent scratch children to the canonical directory inode. Exposed conflict and orphan APIs on `MetaEngineCore` and `StudioVfs` allow both mounted and offline tools (`status`, `scratch list --orphaned`, `scratch restore`) to inspect conflicts and enumerate or restore orphans.

## Surprises & Discoveries

- Observation: `RedbMetaEngine::apply_events_to_base_in_txn` and `lookup_merged_from_opened_tables` fall back to `BASE_DENTRIES_TABLE` when neither `DENTRIES_TABLE` nor `DENTRY_TOMBSTONES_TABLE` has a row for a key, and StudioFS uses case-insensitive name matching (`find_scratch_dentry_in_table` and `folded_dentry_prefix`) throughout foreground lookup rather than a per-volume toggle.
  Evidence: Inspected `crates/studiofs-meta/src/redb_engine/namespace_merge.rs` and `crates/studiofs-meta/src/redb_engine/scratch.rs`. Searching `studiofs-meta` for `case_sensitive` returned no matches.

- Observation: During a single replay batch containing `RemoveAttr` followed by `RemoveEntry` (or `rmdir` / multi-level tree deletion / snapshot replacement), intermediate tracked directory inodes and dentries are already deleted by the time tracked mutations finish.
  Evidence: Inspected `apply_events_to_base_in_txn` and `import_snapshot_with_mode_and_preserved_inodes`. Resolving volume-relative parent paths before the batch mutates tracked tables avoids losing `<old path>` for orphaned scratch entries.

- Observation: Local payload objects on disk live at `<cache_dir>/payload/objects/<shard_0:02x>/<shard_1:02x>/<object_id:016x>.object` where the two shard bytes come from `splitmix64(object_id)`.
  Evidence: Inspected `crates/studiofs-cache/src/payload_layout.rs` and `crates/studiofs-cache/src/payload_store.rs`.

## Decision Log

- Decision: Persist conflict records in `SCRATCH_CONFLICTS` (`u64 -> ScratchConflictRecord`) and orphan batches in `SCRATCH_ORPHANS` (`(timestamp_be8 + root_old_path) -> ScratchOrphanRecord`) inside redb rather than purely on disk.
  Rationale: Recording the removal of orphaned scratch rows from `SCRATCH_DENTRIES` / `SCRATCH_INODES` and the insertion of `ScratchOrphanRecord { materialized: false, ... }` inside the same redb write transaction that deletes the tracked parent makes relocation atomic: a crash before commit leaves the entry in the namespace, while a crash after commit leaves the complete metadata and payload references in `SCRATCH_ORPHANS` so reopen/bootstrap idempotently finishes disk materialization to `<cache>/scratch-orphans/<timestamp>/<old path>`.
  Date/Author: 2026-11-21 / Antigravity

- Decision: Move orphaned scratch overlay chunks, symlink targets, and xattrs into `ScratchOrphanEntry` and include `SCRATCH_ORPHANS` slice object IDs in `RedbMetaEngine::local_payload_roots(true)`.
  Rationale: This removes orphaned entries completely from active `SCRATCH_*` namespace tables (ensuring offline tools and VFS lookups see them as outside the namespace) while still protecting all orphan payload objects from local cache GC until `scratch clean` or `scratch restore`.
  Date/Author: 2026-11-21 / Antigravity

- Decision: Check local dentry tombstones (`DENTRY_TOMBSTONES_TABLE`) and effective merged serving state during Phase C conflict resolution rather than matching raw `BASE_DENTRIES_TABLE` blindly.
  Rationale: When a client locally unlinks a tracked entry and creates a scratch entry under that name before replication acknowledges the unlink, stale foreign attribute or base updates for that removed tracked entry must not override local authority or displace the local scratch entry.
  Date/Author: 2026-11-21 / Antigravity

## Context and Orientation

In this repository, the metadata engine lives in `crates/studiofs-meta` and the virtual filesystem lives in `crates/studiofs-vfs`. Local scratch metadata is stored in five redb tables defined in `crates/studiofs-meta/src/redb_engine/layout.rs`: `SCRATCH_INODES`, `SCRATCH_DENTRIES`, `SCRATCH_OVERLAY`, `SCRATCH_XATTRS`, and `SCRATCH_SYMLINKS`. Operations on those tables are implemented in `crates/studiofs-meta/src/redb_engine/scratch.rs`, while tracked-versus-scratch precedence in VFS foreground operations is implemented in `crates/studiofs-vfs/src/vfs/namespace_ops.rs` (`lookup` checks `lookup_scratch_entry` before `meta.lookup`, and `readdir_entries_and_attrs` deduplicates against tracked names). Replication from PostgreSQL replays foreign batches through `RemoteApplyCoordinator` in `crates/studiofs-meta/src/pg_engine/remote_apply.rs`, `apply_replay_page_atomically_locked` in `crates/studiofs-meta/src/pg_engine/metadata_sync.rs`, and base/serving helpers in `crates/studiofs-meta/src/redb_engine/replication.rs` and `crates/studiofs-meta/src/redb_engine/namespace_merge.rs`. Snapshot and checkpoint imports flow through `import_snapshot_with_mode_and_preserved_inodes` in `crates/studiofs-meta/src/redb_engine/snapshots.rs`.

## Plan of Work

First, add the mount-local redb tables `SCRATCH_CONFLICTS` and `SCRATCH_ORPHANS` in `crates/studiofs-meta/src/redb_engine/layout.rs` along with orphan key encode/decode helpers, and open those tables in writable `RedbMetaEngine::open_with_relaxed_interval`. Define `ScratchConflictRecord`, `ScratchOrphanEntry`, and `ScratchOrphanRecord` in `crates/studiofs-meta/src/engine.rs`, re-export them from `crates/studiofs-meta/src/lib.rs`, and add `list_scratch_conflicts`, `clear_scratch_conflict`, `list_scratch_orphans`, `restore_scratch_orphan`, `set_scratch_cache_dir`, and `scratch_orphans_dir` to `MetaEngineCore`. Implement these methods on `RedbMetaEngine` and forward them on `PgMetaEngine` (`crates/studiofs-meta/src/pg_engine/engine_core.rs`), `ReadOnlyMetaEngine` (`crates/studiofs-meta/src/read_only.rs`), and `RuntimeMetaHandle` (`crates/studiofs-vfs/src/runtime.rs`). Extend `RedbMetaEngine::local_payload_roots` in `crates/studiofs-meta/src/redb_engine/gc.rs` so `include_scratch == true` retains object IDs referenced by `SCRATCH_ORPHANS`.

Second, implement `capture_pre_mutation_scratch_context_in_txn`, `reconcile_scratch_after_tracked_mutations_in_txn`, `finish_scratch_reconciliation`, `materialize_pending_scratch_orphans`, and `restore_scratch_orphan` in `crates/studiofs-meta/src/redb_engine/scratch.rs`. Before any replay or snapshot write transaction mutates tracked tables, when `SCRATCH_DENTRIES` is non-empty, capture each tracked scratch-parent inode's volume-relative path from the pre-mutation merged namespace. After the transaction's tracked mutations (and prior to `txn.commit()`), perform three ordered reconciliation steps inside the same write transaction: Phase A re-parents scratch children from any ADR 0012 merged directory alias in `DIRECTORY_ALIASES_TABLE` onto its canonical directory inode; Phase B detects any tracked scratch parent that is no longer a live reachable directory from `ROOT_INO` and moves its direct scratch entries along with their complete scratch descendant subtrees atomically into `SCRATCH_ORPHANS` with `materialized = false`; Phase C inspects remaining live tracked parents and renames any scratch child whose name (under case-insensitive matching) collides with a winning live merged tracked entry to `<name>.scratch-conflict-<n>` with a warning log, a `ScratchConflictRecord` row, and kernel/VFS invalidation intents. Clean up stale `SCRATCH_CONFLICTS` rows whenever a scratch entry is unlinked, removed, renamed, or promoted.

Third, hook `capture_pre_mutation_scratch_context_in_txn`, `reconcile_scratch_after_tracked_mutations_in_txn`, and post-commit `finish_scratch_reconciliation` into all replay and snapshot paths across `replication.rs`, `remote_apply.rs`, `metadata_sync.rs`, and `snapshots.rs`, plus call `materialize_pending_scratch_orphans()` on writable `RedbMetaEngine::open_with_relaxed_interval` and `set_scratch_cache_dir`. Disk materialization stages directory trees, reconstructed file payloads (reading shard files from `<cache>/payload/objects/` when present), symlinks, and metadata sidecars under `<cache>/scratch-orphans/.staging-*`, atomically renames into `<cache>/scratch-orphans/<timestamp>/<old path>`, and marks `materialized = true` in redb. Wire `cache_dir` into `set_scratch_cache_dir` in `crates/studiofs-vfs/src/vfs/bootstrap.rs` and add VFS convenience accessors in `crates/studiofs-vfs/src/vfs/scratch_storage.rs`.

## Idempotence and Recovery

Redb table opens are idempotent and non-destructive. `materialize_pending_scratch_orphans` cleans up any leftover `.staging-*` directories from interrupted runs and idempotently replaces incomplete targets before marking `materialized = true`, so repeated invocations or restarts after crashes always converge cleanly.
