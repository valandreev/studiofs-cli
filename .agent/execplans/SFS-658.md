# Make reverse child-mapping cleanup generation-aware

This is a living ExecPlan for SFS-658. It follows `.agent/PLANS.md`; the
`Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes &
Retrospective` sections must be updated as the work proceeds.

## Purpose / Big Picture

`studiofs-vfs` keeps a reverse lookup from a child inode to the directory
snapshot that produced it. The snapshot has a `readdir_touch` generation. A
stale cleanup must not remove a newer mapping for the same child, because that
can make a valid foreground read look untracked and silently disable
directory prefetching.

After this change, every cleanup path in
`crates/studiofs-vfs/src/readahead.rs` will remove a reverse mapping only when
the stored `(directory inode, readdir generation)` still equals the generation
owned by the state being discarded. Directory eviction selected from an older
LRU observation will likewise remove state only when its observed access touch
is still current. Focused unit tests will cover direct matching removal,
generation mismatch, reassignment to another directory, LRU eviction, and a
barrier-controlled refresh/cleanup ordering without sleeps.

## Decision Log

- Decision: Use `DashMap::remove_if` for conditional reverse-map removal.
  Rationale: A separate `get` followed by `remove` allows a concurrent insert
  or reassignment between the comparison and deletion. `remove_if` evaluates
  the generation predicate and removes the matching entry while holding the
  shard lock.
  Date/Author: 2026-08-27 / Codex.
- Decision: Use `readdir_touch` for reverse-map cleanup identity and
  `last_touch` for conditional LRU state removal.
  Rationale: `readdir_touch` identifies a directory child snapshot, while
  `last_touch` is the value observed when an LRU victim was selected. They are
  distinct generations with distinct ownership contracts.
  Date/Author: 2026-08-27 / Codex.
- Decision: Keep the fix local to `readahead.rs` and its unit tests.
  Rationale: Linear's corrected scope names one tracker and all known cleanup
  paths are confined to this module; no broader abstraction is needed.
  Date/Author: 2026-08-27 / Codex.
- Decision: Keep deterministic interleaving controls behind `#[cfg(test)]` in
  the tracker.
  Rationale: The production API has no pause points. Test-only hooks let the
  tests hold the exact comparison/selection point and coordinate real map
  operations with barriers, without adding runtime state or sleeps.
  Date/Author: 2026-08-27 / Codex.

## Context and Orientation

`crates/studiofs-vfs/src/readahead.rs` contains two related concurrent maps.
`dirs` stores one `DirPrefetchState` per directory inode. Each state records
the child snapshot from a completed `readdir`, its `readdir_touch` generation,
and a `last_touch` value used to bound the number of tracked directories.
`child_to_dir` maps a child inode to `(directory inode, readdir_touch)` so a
child read can find the matching directory state.

The maps are `DashMap`s, which provide per-shard locking. A guard returned by
`get` or `get_mut` must not be held while calling another map operation on the
same map if that can deadlock. The required atomic operation is
`remove_if(key, predicate)`: it checks the current value and removes it only
when the predicate returns true under the map's lock.

The current unsafe pattern is:

    if get(child) == expected {
        drop(get_guard);
        remove(child);
    }

Between `drop` and `remove`, a readdir refresh or reassignment can install a
new value for the child. The unconditional `remove` then deletes the new
mapping. The same issue appears when cleanup loops remove every child from a
discarded directory without checking that the reverse mapping still belongs
to that discarded generation.

## Plan of Work

First add focused tests in the existing `dir_prefetch_tests` module. Preserve
the current tests, and add separately named cases for: matching conditional
removal; mismatched generation preservation; a child reassigned to another
directory preservation; LRU cleanup not deleting a newer mapping; and an
explicit directory eviction not deleting a newer mapping. Add a barrier-based
test that captures a stale mapping, synchronizes a cleanup attempt with a
refresh, and asserts the fresh mapping remains. The synchronization must wait
on barriers or another observable condition rather than sleeping. If a
test-only seam is needed to hold the old comparison point open, keep it under
`#[cfg(test)]` and make the test exercise the production helper's final
conditional removal.

Then replace the helper body with one `child_to_dir.remove_if` call whose
predicate compares the stored tuple to `expected`. Change every cleanup loop
to call that helper with `(discarded_dir_ino, discarded_state.readdir_touch)`.
For LRU selection, retain the observed `(victim_dir, victim_last_touch)` from
the map iteration and remove the directory with `dirs.remove_if`, accepting the
victim only when its current `last_touch` still equals the observed value. Only
after that conditional removal succeeds should its children be pruned, using
the removed state's `readdir_touch` for each reverse-map condition.

Finally run formatting and the smallest relevant test/build commands, inspect
the complete diff, and commit the plan plus implementation and tests. Do not
run the full workspace test suite.

## Validation and Acceptance

Acceptance is behavioral: after a stale directory snapshot, LRU victim, or
explicit directory eviction is discarded, a child mapping belonging to a
newer snapshot or another directory remains in `child_to_dir`. A mapping for
the exact discarded `(directory, readdir_touch)` pair is removed. A directory
state selected as an LRU victim is removed only if its `last_touch` has not
changed before the conditional removal.

The primary proof is:

    cargo test -p studiofs-vfs readahead --lib -- --nocapture

It must pass all tests in the `readahead` module and must not report
`running 0 tests`. `cargo check -p studiofs-vfs` proves the non-test library
path compiles, while `git diff --check` catches whitespace errors. Full
workspace tests are intentionally not run per repository instructions.
