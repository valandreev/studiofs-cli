# SFS-707: Decouple detached mount handshake from remote catch-up

## Purpose

Make detached mount startup report the child process and local mount lifecycle
independently from PostgreSQL catch-up. The persisted mount record remains the
single local handshake/status channel: `Starting` proves the child owns the
attempt, while the detached parent returns success only after `Mounted`,
`Live`, or `Degraded` proves that the native mount point is attached. A PG
lifecycle then distinguishes a mounted-but-not-live view from `Live` or
`Degraded` runtime state.

## Surprises & Discoveries

- `MountRuntimeGuard::launch_mount` currently persists the record immediately
  before calling the backend, so the existing record is not proof that a mount
  point is attached.
- The detached child performs `resolve_mount_meta_session` and constructs the
  VFS before `launch_mount`, which is why the parent timeout is coupled to
  remote startup work.
- `StudioVfs::sync_status()` already exposes the canonical PG lifecycle with
  the mount-local read-only authority override; the CLI can observe it without
  adding another metadata state machine.
- Native bridge APIs have explicit attach boundaries: WinFSP `host.mount`,
  Linux/macFUSE low-level session creation, and the FSKit `MFMount` completion.
- The review's suggestion to deserialize legacy records as `Mounted` is not
  compatible with repository history: the legacy writer persisted its record
  before entering the native serving call, so `Starting` is the safer meaning
  for records without an explicit status.
- A review test that exercises detached diagnostics reaches a Windows named-pipe
  permission boundary in this environment, while the mount lifecycle tests run
  with a writable client root.
- Windows readers can briefly overlap an atomic destination replacement; the
  monitor must retry a sharing violation instead of treating the first failed
  `persist` as terminal.

## Decision Log

- Keep the existing JSON mount record and lifecycle lock as the handshake and
  status channel; do not add a second daemon IPC protocol.
- Publish a backward-compatible `Starting` record as soon as the child owns
  the lifecycle lock, before metadata/VFS preparation can wait on PostgreSQL.
- Keep `Mounted` separate from `Live`: the native bridge callback is the only
  source of OS-mount readiness, while `StudioVfs::sync_status()` supplies PG
  lifecycle updates. The detached parent waits for this native-ready state;
  `Starting` is only an internal child-owned progress state.
- Treat PG `CatchingUp`, `TargetReached`, `AllocatorPending`, and `LocalReady`
  as mounted-but-not-live; map `Degraded` to `Degraded` and preserve transient
  remote loss as a runtime state rather than a daemon-process failure.
- Keep record updates instance-aware and stop the observer before VFS/runtime
  teardown so an old child cannot overwrite a later mount attempt.
- Replace records through a same-directory temporary file and `persist`, so
  readers see either the old complete JSON or the new complete JSON rather
  than a truncated intermediate file.
- Use a separate publication lock around the read-modify-write operation while
  releasing the state lock during file I/O; this preserves ordered status
  updates without holding the state mutex across synchronous disk work.
- Treat `Failed` as an observable transient diagnostic state for detached
  children. Detached preparation and serving failures retain the record after
  releasing the lifecycle lock so the parent can observe the explicit failure
  before the next mount's stale-state guard removes it. Foreground failures,
  successful unmount cleanup, and panic/drop cleanup remove the record.
- Keep failure text out of the JSON record because arbitrary backend errors can
  contain credentials or connection strings; detached wait errors include the
  daemon log path instead.
- Retry mount-record publication after transient Windows sharing/access errors,
  but stop when the record's instance ID proves that another mount owns the
  path. A transient failure is not evidence that the monitor should die.
- Preserve legacy records with no `instance_id` as active candidates when their
  lifecycle lock is held; current records with `Starting` remain non-ready.

## Outcomes & Retrospective

Implemented the detached lifecycle split in the CLI mount session and native
bridge boundaries. A child now owns a `Starting` record before metadata/VFS
preparation, while the parent waits for child liveness plus a matching
`Mounted`/`Live`/`Degraded` record instead of waiting for PG catch-up. The
record is later updated with canonical PG lifecycle state. Native callbacks are
one-shot and run only after the relevant dispatcher/invalidation setup. JSON
records are replaced atomically, and monitor teardown no longer waits for a
poll interval.

Validation passed:

- `mount_record` filter in an isolated target with a writable `STUDIOFS_CLIENT_ROOT` (11 passed), including instance replacement, record removal, dead-child, and explicit `Failed` regressions.
- `prepared_mount_launch_failure_removes_foreground_record` in the isolated target (1 passed).
- Earlier focused `pid_file`, `prepared_mount_launch`, and `mount_runtime_guard` filters remain green; the separate diagnostics attach test hit named-pipe `Access is denied`.
- `cargo check -p studiofs -p studiofs-winfsp -p studiofs-linux-fuse -p studiofs-macfuse`.
- `cargo clippy -p studiofs --all-targets -- -D warnings` in the isolated target.
- `cargo fmt --all -- --check`
- `git diff --check`

The default target's test-artifact directory also returned `Access is denied`,
so focused tests used `target-sfs707-review4` and an explicit writable client
root. A Linux-target check reached native cross-build tooling but could not
continue because `x86_64-linux-gnu-gcc` is unavailable.
Live WinFSP/FUSE/FSKit mount validation was not run because those native
prerequisites are not available in this Windows environment.

The follow-up review also passed `Failed`-state reporting through a dead-child
test, reused the record returned by the handshake instead of re-reading it,
aligned the WinFSP request callback API, and covered the legacy active-record
predicate. The monitor's transient retry path is exercised indirectly by the
launch lifecycle tests. The later detached-mount review keeps failed records
only for detached children (including the internal child environment marker);
foreground failures remove their records. Native file-sharing fault injection
remains Windows environment-specific.

Mount-record update tests cover instance replacement and external record
removal without a second disk read; the FSKit readiness callback now runs on a
short-lived worker and is joined before the dispatcher returns.

## Validation and Acceptance

- A detached child that remains `CatchingUp` does not cause the parent to fail
  because PostgreSQL work exceeds the old record-publication timeout, once the
  native mount has published `Mounted`.
- A detached child that dies while its record is still `Starting` produces a
  deterministic parent error rather than a false success.
- A dead child with a visible `Failed` record produces the explicit failure
  reason rather than the generic early-exit message.
- A child that exits before publishing `Starting`, or publishes `Failed`,
  produces a deterministic parent error.
- A record never reports `Mounted` before the platform attach boundary.
- `Mounted`/PG `CatchingUp`, `Live`, and `Degraded` are distinguishable in the
  persisted record.
- Existing record removal, lifecycle-lock release, unmount, and panic cleanup
  tests remain green.
- Native live-mount validation is environment-gated on WinFSP/FUSE/FSKit and
  will be reported separately if unavailable.

## Idempotence and Recovery

Record updates are overwrite-safe and keyed by the lifecycle instance ID. A
detached preparation or serving failure publishes `Failed` and releases the
lock so the detached parent can report it; the next mount reclaims that stale
record through the existing guard path. Foreground failures and successful
backend teardown remove the record directly.
