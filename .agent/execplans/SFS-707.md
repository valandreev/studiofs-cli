# SFS-707: Decouple detached mount handshake from remote catch-up

## Purpose

Make detached mount startup report the child process and local mount lifecycle
independently from PostgreSQL catch-up. The persisted mount record remains the
single local handshake/status channel: `Starting` proves the child owns the
attempt, `Mounted` plus a PG lifecycle identifies a mounted-but-not-live view,
and `Live`/`Degraded`/`Failed` expose subsequent runtime state.

## Surprises & Discoveries

- `MountRuntimeGuard::launch_mount` currently persists the record immediately
  before calling the backend, so the existing record is not proof that a mount
  point is attached.
- The detached child performs `resolve_mount_meta_session` and constructs the
  VFS before `launch_mount`, which is why the parent timeout is coupled to
  remote startup work.
- `StudioVfs::sync_status()` already exposes the canonical PG lifecycle with
  the mount-local read-only authority override; the CLI can observe it without
  adding another metadata state machine.
- Native bridge APIs have explicit attach boundaries: WinFSP `host.mount`,
  Linux/macFUSE low-level session creation, and the FSKit `MFMount` completion.

## Decision Log

- Keep the existing JSON mount record and lifecycle lock as the handshake and
  status channel; do not add a second daemon IPC protocol.
- Publish a backward-compatible `Starting` record as soon as the child owns
  the lifecycle lock, before metadata/VFS preparation can wait on PostgreSQL.
- Keep `Mounted` separate from `Live`: the native bridge callback is the only
  source of OS-mount readiness, while `StudioVfs::sync_status()` supplies PG
  lifecycle updates.
- Treat PG `CatchingUp`, `TargetReached`, `AllocatorPending`, and `LocalReady`
  as mounted-but-not-live; map `Degraded` to `Degraded` and preserve transient
  remote loss as a runtime state rather than a daemon-process failure.
- Keep record updates instance-aware and stop the observer before VFS/runtime
  teardown so an old child cannot overwrite a later mount attempt.

## Outcomes & Retrospective

Implemented the detached lifecycle split in the CLI mount session and native
bridge boundaries. A child now owns a `Starting` record before metadata/VFS
preparation, the parent accepts that child-owned local state without waiting
for PG catch-up, and the record is later updated with OS attach and canonical
PG lifecycle state. WinFSP's existing `mount_and_serve` API remains intact;
the callback uses a separate helper to avoid breaking existing request
struct-literal callers.

## Validation and Acceptance

- A detached child that remains `CatchingUp` does not cause the parent to fail
  because PostgreSQL work exceeds the old record-publication timeout.
- A child that exits before publishing `Starting`, or publishes `Failed`,
  produces a deterministic parent error.
- A record never reports `Mounted` before the platform attach boundary.
- `Mounted`/PG `CatchingUp`, `Live`, and `Degraded` are distinguishable in the
  persisted record.
- Existing record removal, lifecycle-lock release, unmount, and panic cleanup
  tests remain green.
- Native live-mount validation is environment-gated on WinFSP/FUSE/FSKit and
  will be reported separately if unavailable.

## Idempotence and Recovery

Record updates are overwrite-safe and keyed by the lifecycle instance ID. A
failed preparation or backend launch removes the record and releases the lock;
the next mount can reclaim stale state through the existing guard path.
