# Make CLI janitor cancellation drain safely

This living plan follows `.agent/PLANS.md` and records SFS-976. It covers only `studiofs janitor`; the mounted janitor remains unchanged.

## Purpose / Big Picture

When an operator presses Ctrl+C or a per-cycle runtime budget expires, the CLI janitor must stop admitting new work, finish any object delete it has already claimed, retain a restart-safe checkpoint, print a partial cycle summary, and release the global PostgreSQL advisory lock. The same safety applies to ordinary errors. A later run resumes from durable queue/checkpoint state and existing per-object fencing.

## Surprises & Discoveries

- SFS-974 and SFS-975 keep candidate processing serial, so a small admission stop signal can prevent new candidates while the current candidate drains.
- `process_orphan` wraps each DELETE in a timeout that drops its future. S3 cancellation can leave remote outcome uncertain; per-object fencing and canonical idempotent DELETE support restart, but this path does not satisfy graceful draining.
- The OpenDAL S3 adapter has bounded retry count/delay but no adapter-level hard request deadline. The existing pipeline timeout remains the only hard bound and may drop a stalled DELETE after 20 seconds; expanding lease/request-deadline design is outside this patch and remains an explicit safety limitation for transport timeout, distinct from Ctrl+C handling.
- The run loop holds a synchronous metadata session and advisory lock around `Runtime::block_on`; cleanup must happen only after that future returns.
- The registered `studiofs-e2e` runner lists 32 mounted filesystem scenarios and no standalone janitor scenario. The focused service checks therefore use the existing `studiofs` test harness rather than claiming mounted E2E acceptance.
- Docker named-pipe access required elevated native execution in this Windows session. The services ran in an isolated Compose project with a dedicated PostgreSQL volume and RustFS volume; tests targeted that local RustFS bucket rather than the workspace-configured endpoint.
- The combined regression can prove the real PostgreSQL lease and real S3 DELETE together by pausing the DELETE at a test adapter gate, cancelling the shared pipeline token, and then releasing the request. Its post-run query confirms the candidate was acknowledged; the test also runs the pipeline again to confirm no candidate is re-admitted.

## Context and Orientation

`crates/studiofs/src/cli/janitor.rs` owns the command loop, signal handling, and per-volume lock. `crates/studiofs/src/cli/janitor/pipeline.rs` lists candidates, claims each eligible object, deletes its canonical keys, finishes the claim, and persists the scan checkpoint after a drained cycle. `crates/studiofs-meta` persists checkpoint and fencing state. Existing SFS-974/SFS-975 behavior is a base contract, not reimplementation scope.

## Idempotence and Recovery

Checkpoint movement must represent only completed batches. A claimed object's remote delete is followed by fenced finish before graceful lock release. If the process is forcibly killed, the existing claim eventually expires; the remote result may be unknown and a later run may retry the canonical DELETE. This patch does not prove the remote outcome or add lease renewal for a request exceeding its existing timeout.
