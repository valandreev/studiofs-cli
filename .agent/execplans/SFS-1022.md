# Retain staged payload handles for SFS-1022

This ExecPlan follows `.agent/PLANS.md` and records the bounded cache fix for SFS-1022. On Windows, a cold cache miss can make a WinFSP read worker open a payload file synchronously. The task is to reuse the read-capable handle already created when staging and writing a payload, so newly committed payloads do not need a separate foreground open. This reduces the observed cold-read descriptor-open path; it does not establish that the whole-machine hang cycle is solved.

## Surprises & Discoveries

- Rust `File::try_clone` shares the same OS file object and current file position, while cache reads use positional reads. The simplest safe ownership is one `Arc<CachedReadHandle>` over the original staged `File`, not a second open. Windows buffered and no-buffering flags belong to the handle and cannot be changed by cloning.
- The default Windows mount reads unbuffered but writes buffered. The retained buffered writer is tagged as buffered and stored in the primary cache. `read_into` uses that exact handle for the buffered read path, so it does not depend on a separate fallback LRU entry remaining present.
- Retained staged handles and cache seeding are Windows-only; other platforms drop the writer at the same staging boundary as before and retain their existing read-open behavior.
- Holding every writer handle in a large batch would bypass the existing descriptor bound. Each staging operation now decides whether to retain its writer from its input index, dropping non-retained files before returning to the batch collector; only the last cache-capacity handles plus active workers can be open. Excess entries use existing cold-open behavior.

## Decision Log

- Decision: Carry the original read+write staging `File` into the read cache after a successful rename and tag its actual I/O mode. Rationale: this avoids opening the populated final path on the foreground read path and preserves Windows mode correctness. Date/Author: 2026-11-05, Codex.
- Decision: Keep the existing bounded LRU caches and invalidation; on Windows route buffered fallback through the retained primary handle when its actual mode is buffered. Rationale: this avoids a second descriptor and a cross-cache eviction race while old active readers keep their Arc after replacement, and preserves other platforms' current path. Date/Author: 2026-11-05, Codex.
- Decision: Retain no more than the existing primary-cache capacity of batch writer handles, selecting the last staged entries. Rationale: those are the entries sequential commit leaves resident, and the bound prevents large batches from retaining unbounded file handles. Date/Author: 2026-11-05, Codex.

## Context and Orientation

`crates/studiofs-cache/src/payload_store.rs` owns temp-file creation, payload staging, atomic commit, descriptor cache misses and positional payload reads. `crates/studiofs-cache/src/payload_platform.rs` supplies buffered and unbuffered creation and positional reads. Before this change, `StagedBatchPayload` retained only paths and borrowed payload data, while `create_new_buffered_write` and the Windows unbuffered writer both created read+write handles. Windows `pread` uses positional `seek_read`; it does not depend on the cursor shared by a cloned file object.

A cached handle's actual mode matters. Buffered handles can serve ordinary reads and are used when an unbuffered read request is not aligned. Unbuffered handles can serve only aligned direct reads. A handle's mode must therefore be represented, and it must never be mistaken for the other mode.

## Plan of Work

On Windows, change the staging helpers in `payload_store.rs` to return the temp path together with the still-open writer `File` and its actual I/O mode. Successful unbuffered writes return an unbuffered handle; a buffered write or an unbuffered-write fallback returns a buffered handle. Carry that handle in `StagedBatchPayload` through atomic rename. After successful commit, invalidate old cache entries and install the same `Arc` in the bounded primary cache if its actual mode can serve the configured read path. For buffered writers under the default Windows unbuffered-read policy, `read_into` detects the buffered tag and reads through that handle directly. During cross-device fallback, replace the retained handle with the handle writing the local-volume temp file before committing that file. Other platforms drop the staging writer before commit, preserving their existing behavior.

Add a regression that opens a Windows-mode store, puts and batch-puts payloads, reads them, and confirms the descriptor miss counter does not increase. Also verify that an already-held old handle still reads old bytes after replacement while a new lookup reads the replacement; existing bounded-cache and removal tests cover ownership cleanup. Do not add retries, timeouts, capacity changes, or a second path open.

## Idempotence and Recovery

The change is process-local and uses the existing bounded cache. If staging or commit fails, its retained handle drops with the staged object; do not seed the cache before commit. On cross-device fallback, remove the original staged file using its existing share-delete behavior and retain the local-volume writer handle instead. Reverting the code requires removing the staged handle field and restoring the current path-open-on-cache-miss behavior.

## Interfaces and Dependencies

The implementation adds a private `PayloadFileIoMode` with buffered and unbuffered variants, a private staged temp-file value containing `PathBuf`, `File`, and mode, and an actual-mode field on `CachedReadHandle`. The three write helpers return the staged temp-file value (the unbuffered helper returns `Option` of that value). No dependency changes are needed. On Windows, a successful unbuffered write is seeded only for an unbuffered reader; buffered writers are usable by buffered readers and by the default Windows unbuffered-read fallback. Other platforms drop staged writers and retain their existing read-open behavior.

Plan note (2026-11-05 11:18Z): a rejected design opened the staged temp path for reading after writing; it was discarded because that merely moved the same native open into the foreground staging/fetch operation. The accepted design retains the original writer handle instead and distinguishes its actual buffered/unbuffered mode on Windows. Later refinements read directly through the buffered primary handle on Windows fallback and cap retained batch handles at the existing cache capacity.
