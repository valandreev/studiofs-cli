# Batch pending-deletion markers during deleted-inode graph cleanup

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date in accordance with `.agent/PLANS.md`.

## Purpose / Big Picture

When StudioFS removes a regular-file inode, it first removes the inode's payload graph and then records each removed object for later object-store garbage collection. Before this change, the two VFS cleanup paths called the scalar marker operation once per object. Each scalar call opened and committed its own local redb write transaction, appended one event, and made the PostgreSQL-backed adapter perform its mutation bookkeeping once. Large files therefore made unlink or last-close cleanup slower and serialized unrelated local metadata writers more often than necessary.

After this change, both deleted-inode cleanup paths submit all unique removed object IDs in one batch. Redb commits all marker rows atomically in one write transaction while retaining one `AddPendingDeletion` event per object, so existing event consumers remain compatible. The existing scalar method remains available for unrelated callers and older implementations. The behavior is observable through focused meta tests and VFS tests that exercise both immediate unlink cleanup and open-unlink last-close cleanup.

## Surprises & Discoveries

- The audit's original claim that PostgreSQL executes one foreground transaction per object is incorrect. `PgMetaEngine` mutates local redb and signals asynchronous replication; batching is still valuable because it reduces local redb transactions and mutation bookkeeping.
- `remove_regular_file_graph` already collects object IDs in a `BTreeSet`, so the VFS cleanup input is already unique and ordered. The batch API must not add a second deduplication policy.
- `NamespaceDeleteTxn::queue_pending_deletions_in_txn` already contains the correct atomic row-insertion and per-object event sequence. The new redb batch implementation will centralize that logic and make the namespace transaction call the same helper.
- `AddPendingDeletion` is a local garbage-collection bookkeeping event. Replica base application intentionally does not project it into remote base state, so compatibility is verified by decoding the local event log rather than changing event formats or replay semantics.
- The orphan cleanup path performs six local write transactions for the two-object fixture after batching: the marker batch plus the path's other metadata writes. The extra write beyond the initially expected five is part of deferred-cleanup bookkeeping, not an additional marker transaction.

## Decision Log

- Decision: Add `MetaGc::add_pending_deletions(&[(u64, i64)])` while retaining the scalar `add_pending_deletion` method.
  Rationale: The VFS paths need a batch boundary, while fsck, recovery, truncate cleanup, and stale-upload cleanup still use scalar calls. A default trait implementation preserves compatibility for other implementations.
  Date/Author: 2026-08-27 / Codex.
- Decision: Use one redb write transaction for all rows and append one existing `MetaEvent::AddPendingDeletion` per input marker.
  Rationale: This is the requested performance change without changing persisted event wire format or per-object event semantics.
  Date/Author: 2026-08-27 / Codex.
- Decision: Leave non-VFS scalar loops unchanged.
  Rationale: SFS-659 explicitly targets the two deleted-inode VFS cleanup paths; preserving the scalar entry point avoids broad, unrelated behavior changes.
  Date/Author: 2026-08-27 / Codex.
- Decision: Test rollback by invoking the shared in-transaction helper and dropping its write transaction before commit.
  Rationale: redb has no need for a production-only failure hook; dropping an uncommitted write transaction is the real atomic rollback boundary and verifies both rows and events remain absent.
  Date/Author: 2026-08-27 / Codex.
- Decision: Handle empty batches in `PgMetaEngine` rather than adding a second VFS guard.
  Rationale: `MetaGc` batch callers already pass through the backend boundary; the PgMeta guard avoids the pending-state lock, while an additional caller guard would duplicate the no-op policy. `Vec::new()` for an empty iterator does not allocate heap storage.
  Date/Author: 2026-08-28 / Codex.
- Decision: Do not batch event-table handles or add a same-timestamp batch API from this review.
  Rationale: SFS-659 requires one durable transaction and one existing event per object; the proposed changes optimize internal redb operations and add API surface without a benchmark proving the need.
  Date/Author: 2026-08-28 / Codex.

## Context and Orientation

The repository is `/Volumes/Storage/dev/studiofs`, a Rust workspace. `MetaGc` in `crates/studiofs-meta/src/engine.rs` is the metadata garbage-collection interface. `RedbMetaEngine` in `crates/studiofs-meta/src/redb_engine` owns the local durable redb database and its append-only event log. `PgMetaEngine` in `crates/studiofs-meta/src/pg_engine` wraps local metadata and schedules asynchronous PostgreSQL replication. `ReadOnlyMetaEngine` and `RuntimeMetaHandle` are adapters that must expose the same capability. `VfsMeta` in `crates/studiofs-vfs/src/runtime.rs` includes `MetaGc`.

The two target call paths are in `crates/studiofs-vfs/src/vfs/deletion_cleanup.rs`. `collect_deleted_inode_cleanup` handles an inode whose last link is removed without open handles and calls `queue_pending_deletions_for_object_ids`. `collect_orphan_deleted_inode_cleanup` handles an inode unlinked while a handle remains open and runs the cleanup when the last handle closes. Both receive the unique object IDs returned by `remove_regular_file_graph`.

The pending-deletion table is local redb bookkeeping. A pending marker stores an object ID and timestamp until the object-store garbage collector can safely delete the object. Each marker currently emits the persisted `MetaEvent::AddPendingDeletion { object_id, timestamp }`; this event shape and ordering must remain unchanged.

The existing `NamespaceDeleteTxn::queue_pending_deletions_in_txn` in `crates/studiofs-meta/src/redb_engine/fs_ops.rs` demonstrates the required transaction order: insert all pending rows, release the table handle, then append the existing per-object events before one outer transaction commits. The new helper should live with the redb GC implementation and be reused by that namespace transaction.

Add a PgMeta unit test using the existing local-redb test fixture to prove the PgMeta batch applies markers and preserves the event sequence. Then extend `MetaGc` with the batch method and a scalar-compatible default. In `crates/studiofs-meta/src/redb_engine/gc.rs`, centralize insertion of all rows and one event per marker in an in-transaction helper, implement the public batch method with one `begin_write_txn`/`commit`, and keep scalar behavior compatible. Replace the duplicate namespace transaction logic in `fs_ops.rs` with the shared helper. Implement the batch method in `PgMetaEngine` as one `mutate` call, return the normal read-only error from `ReadOnlyMetaEngine`, and forward the method through `RuntimeMetaHandle`.

Finally, change only the two VFS cleanup paths. The immediate cleanup helper will build one `(object_id, timestamp)` slice, submit it once, and retain per-object diagnostics after success. The orphan cleanup closure will submit the same kind of batch once with its existing timestamp. Do not change the unrelated recovery, fsck, truncate, or stale-upload scalar callers.
