# Persist scratch entries on their creating client

This living ExecPlan follows .agent/PLANS.md.

## Purpose / Big Picture

Provide storage for local temporary files. A caller can create a scratch entry,
store file blocks and reopen the same metadata and payload cache with the entry
intact. Namespace routing and promotion belong to SFS-1077.

## Surprises & Discoveries

The normal payload adapter also creates upload staging links. Scratch can reuse
its payload store batch implementation through a local-only admission mode.

The process-exit regression exposed that startup cleanup uses global
reachability, which deliberately excludes scratch. The startup cache query now
includes both the scratch table and the original shared snapshot roots. The
local retired-payload sweep uses a cache query that only reads local metadata.

## Decision Log

- Decision: Persist payload before committing the scratch block reference.
  Rationale: A crash must leave either the prior metadata or a reference to a
  durable local file. Date/Author: 2026-11-20 / Codex.
- Decision: Store scratch as a distinct payload origin with no pending upload
  and with eviction disabled. Rationale: Pressure passes, startup upload replay
  and cache budgeting can use persisted state without runtime pins.
  Date/Author: 2026-11-20 / Codex.
- Decision: Accept complete volume blocks at the storage boundary. Rationale:
  SFS-1077 owns namespace routing and assembly of partial mounted writes.
  Date/Author: 2026-11-20 / Codex.

## Outcomes & Retrospective

The storage API durably writes regular-file blocks and scratch metadata. A
process-exit test recovered the inode, name, xattr and payload with zero
additional journal rows and upload submissions. A quota of one byte did not
constrain scratch. The budget and physical pressure test reclaimed ordinary
downloaded objects while preserving scratch. Mounted integration remains in
SFS-1077.

## Review Outcomes (2026-11-20)

A review of `main..e547d384` checked spec conformance, durability, eviction,
accounting, compatibility, lock order and tests. No product code changed.

- Open, design (medium): `write_scratch_block` uses the normal payload store,
  object allocator and `<id>.object` format, but bypasses the writer stack
  (`LocalPayloadWriterPort`/`OverlayCommitPort`). Each call allocates and
  fences an object ID, fsyncs the payload and commits redb durably. SFS-1077
  can reuse `put_scratch_batch` and `commit_scratch_block` as the overlay
  commit for writer-page flushes, but must not call `write_scratch_block` from
  `write` callbacks: that adds fsync to `write` and breaks the separate
  `write`/`flush`/`fsync` contracts. ADR 0014 promote also expects writer pages.
- Confirmed durable ordering: allocator fence, then payload and directory fsync,
  then the cache index commit (redb `Immediate`), then the immediate metadata
  commit. The displaced object is removed only after the commit. The Write file
  session permit excludes concurrent reads of the same inode.
- Rejected: removing the new object when `commit_scratch_block` fails. A redb
  commit error can be ambiguous, and removal could leave a dangling mapping.
  Startup cleanup reclaims the unreferenced object through
  `get_cache_referenced_object_ids`.
- Confirmed eviction exclusion: budget eviction, foreground admission and
  physical pressure select only `Uploaded` rows with `evictable` set. Physical
  pressure also requires `Downloaded` origin. Scratch rows have no checksum, so
  scrub skips them. No path calls `mark_uploaded` on a scratch object.
- Confirmed tracked writes are unchanged: with no scratch rows,
  `budgeted_bytes()` equals `current_bytes`, and the non-scratch branch of
  `put_batch_with_mode` matches the previous `put_batch`.
- Rejected: the read-only snapshot engine lacks scratch tables. Read-only mounts
  skip startup cleanup, and snapshot export enumerates its tables, so it
  excludes scratch.
- Confirmed compatible: new metadata tables are created at open, after the
  format check, so an unsupported database still gets no tables. The cache
  index adds the `scratch_bytes` counter at open.
- Skipped, noted: an older binary cannot decode origin `3` once scratch rows
  exist. Downgrade is not supported, and no cache index format bump was added.
  Future `InodeAttr` format migrations must also rewrite `scratch_inodes`.
- Skipped, follow-up: budget eviction scans skip scratch rows in access order.
  The cost grows with scratch row count, as it already does for dirty rows.
- Skipped, cosmetic: scratch codec errors map to `MetaError::Storage` instead of
  `Serialization`. A failed `store_scratch_entry` does not return its reserved
  inode number.
- Test gaps fixed: `scratch_admission_reads_only_the_cached_reserve_sample`
  covers the reserve boundary, the case with no sample, a tracked write under
  pressure, and zero native space queries.
  `scratch_overwrite_releases_the_displaced_payload` covers removal of the
  replaced object and the reachability set. `docs/cache.md` documents scratch
  payload accounting.

## Context and Orientation

The redb metadata engine stores tracked metadata and commits replication events.
The cache runtime materializes payload objects and indexes their lifecycle.
Scratch uses new tables and the same inode and object ID allocators.

## Plan of Work

First add local-only table operations to studiofs-meta and forward them through
the PostgreSQL engine to local redb. Then extend the studiofs-cache batch writer
to persist protected scratch objects without staging upload work. Expose block
storage through StudioVfs and verify the complete path.

## Concrete Steps

From the repository root run the focused scratch storage and cache tests, then
run crate-scoped check and Clippy for studiofs-meta, studiofs-cache and
studiofs-vfs. Run cargo fmt --all -- --check and git diff --check.

## Idempotence and Recovery

Add the tables when opening existing databases without a format bump. Allocate
new object IDs before replacing mappings so a failed replacement preserves the
old payload. The object allocator state is synced before a payload is written.
Startup cache cleanup considers a committed scratch mapping a live reference
and can reclaim orphan objects left by interrupted writes.

## Artifacts and Notes

The storage entry points can be exercised without mounting a filesystem.

## Interfaces and Dependencies

MetaEngineCore supplies local scratch operations. StudioVfs exposes
store_scratch_entry, write_scratch_block and read_scratch_block. The cache
runtime owns the cached free-space sample and persists scratch through its
existing object batch writer. The scratch API uses exact byte names. The
namespace integration owns name policy, partial writes, unlink and promotion.
