# Snapshot v2 implementation plan

This is the living ExecPlan for SFS-650. It is the implementation contract for the Snapshot v2 work described by SFS-35, SFS-36, SFS-39, SFS-37, SFS-38, SFS-649, SFS-40, SFS-651, SFS-652, and SFS-41. SFS-650 authorized the plan; each implementation ticket records its own bounded code, test, documentation, and Git evidence here.

## Purpose / Big Picture

StudioFS is a local-first virtual filesystem (VFS) backed by PostgreSQL (PG, the shared metadata authority) reached through a data source name (DSN), an embedded redb database for local metadata, and object storage compatible with Amazon Simple Storage Service (S3). PostgreSQL schema text is data definition language (DDL). Platform bridges use Filesystem in Userspace (FUSE), macFUSE, and Windows File System Proxy (WinFSP). End-to-end (E2E) evidence exercises the real product binary and those external services. Snapshot v2 provides a whole-volume, point-in-time, immutable, read-only view that can restore a deleted file into the continuing live volume.

The public command-line interface (CLI) uses a time to live (TTL) duration and an Internet Assigned Numbers Authority (IANA) timezone where shown; an omitted policy timezone is persisted as UTC. It has exactly these eight forms:

    studiofs snapshot create [--ttl <duration>]
    studiofs snapshot list
    studiofs snapshot inspect <snapshot-id>
    studiofs snapshot delete <snapshot-id>
    studiofs snapshot policy set --daily-at <HH:MM> [--timezone <IANA zone>] --retention <duration>
    studiofs snapshot policy show
    studiofs snapshot policy cancel
    studiofs smount <volume> <snapshot-id> <mountpoint>

Create, list, and policy commands resolve the creator's one current live volume implicitly. Inspect and delete use only SnapshotId after resolving the creator's volume context. Only smount has a volume positional argument. No public command accepts a root inode, caller-selected snapshot name, caller-selected snapshot ID, writable snapshot mode, or a hidden worker-restart command.

The public cut vocabulary is exactly one cut_version and one capture time, captured_at. Retained checkpoint and event-range boundaries are internal descriptor inputs used to reconstruct that cut; they are not content identity. PostgreSQL allocates SnapshotId and cut_version in one transaction. The human-readable public SnapshotId is exactly `<volume-name>.<UTC-cut-timestamp>`, where UTC-cut-timestamp is captured_at rendered as `YYYY-MM-DDTHH-mm-ss.SSSZ` in UTC, for example `projectfs.2026-08-12T14-07-09.482Z`. A same-volume collision receives the deterministic PostgreSQL-allocated suffix `-2`, then `-3`, and so on. SnapshotId is scoped by verified volume identity; every remote artifact namespace and cache key must carry the immutable volume UUID as well as the numeric volume context, because volume names can be reused. A snapshot is not Ready until its immutable metadata artifact and every payload reachable from the cut are durable, checksum-verified, and published through a compare-and-set (CAS) state transition.

The implementation follows the dependency direction domain <- ports <- application <- adapters/runtime/application programming interface (API). Materialization is a reusable application service in crates/studiofs-vfs/src/snapshot_worker.rs. A mounted client starts that worker with the existing startup-worker lifecycle, and the CLI create command uses the same service. A force-killed CLI claimant therefore leaves a durable job that another mounted client can claim after the PostgreSQL lease expires.

## Surprises & Discoveries

- Surprise: the current snapshot CLI is a local redb/root-inode surface, not a PostgreSQL catalog operation.
  Evidence: crates/studiofs/src/cli/snapshot.rs currently opens local metadata and exposes root-based creation/list behavior.
- Surprise: startup workers already have a tracked shutdown mechanism that the snapshot worker can reuse.
  Evidence: crates/studiofs-vfs/src/vfs.rs contains spawn_startup_workers, background task tracking, and a shared shutdown token.
- Surprise: the existing E2E runner already owns the isolation and cleanup contract that Snapshot v2 needs.
  Evidence: crates/studiofs-e2e/src/cli.rs exposes run with --root, --run-id, --studiofs-bin, --platform, --retain, and --port-range; crates/studiofs-e2e/src/runner.rs writes the sandbox manifest and records the unique Compose project, allocated ports, client roots, cleanup allowlist, and mount metadata.
- Surprise: the Compose file's named volumes are Docker-managed resources rather than files below the repository target root.
  Evidence: crates/studiofs-e2e/src/infra.rs derives a unique studiofs-e2e-<run-id> project and its teardown removes volumes only through that runner-owned project; target/snapshot-v2 remains the host-file sandbox, while the manifest is the ownership proof for Docker volumes and platform mount points.
- Surprise: local payload metadata cannot be allowed to decide object lifetime.
  Evidence: crates/studiofs-meta/src/redb_engine/payload_objects.rs is local state, while shared reachability and janitor decisions must survive client loss in PostgreSQL.
- Surprise: one published metadata batch has one batch_version, not one independently assigned version per event.
  Evidence: crates/studiofs-meta/src/pg_engine/metadata_io.rs push_projected_event_log_batch_locked calls BUMP_METADATA_VERSION once, inserts every event in events_vec with that batch_version, and commits the projection in the same PostgreSQL transaction.
- Surprise: the current published regular-file event already carries the full after-image needed for exact reference derivation.
  Evidence: crates/studiofs-meta/src/events.rs MetaEvent::PublishRegularFileBaseSlices contains an inode and the final chunk_slices; crates/studiofs-meta/src/schema.rs SliceRecord contains an optional PayloadRef plus PayloadRefState, and only Published is remote-visible.
- Surprise: the current layer map put a PostgreSQL adapter in the application layer.
  Evidence: crates/studiofs-vfs/Cargo.toml depends on studiofs-meta and studiofs-data, while crates/studiofs-meta/Cargo.toml has no dependency on studiofs-vfs; the reusable application service can therefore live in studiofs-vfs, but crates/studiofs-meta/src/pg_engine/ remains an adapter below it.
- Surprise: the current studiofs-e2e port preflight binds and immediately releases a candidate port.
  Evidence: crates/studiofs-e2e/src/infra.rs port_check uses TcpListener::bind and drops the listener before Compose startup; this can detect an early conflict but cannot reserve a port, prove later ownership, or replace post-start Docker port inspection.
- Surprise: the local FormatInfo record contains the PostgreSQL volume_id but the existing shared identity check is remote.
  Evidence: crates/studiofs-meta/src/schema.rs FormatInfo carries PostgresConfig.volume_id, while crates/studiofs-meta/src/pg_engine.rs PgMetaEngine::fetch_remote_uuid queries the PostgreSQL volumes table by vol; the resolver must use local format only to discover context and must validate the complete identity through that PostgreSQL seam.
- Surprise: the workspace already standardizes error derivation and owned-secret erasure without a secrecy dependency.
  Evidence: Cargo.toml provides workspace thiserror and zeroize, the affected crates consume them through workspace dependencies, and crates/studiofs-meta/src/schema.rs and crates/studiofs-meta/src/pg_dsn.rs already implement custom redacted Debug output.

## Decision Log

### 1. Authority and cut identity

Decision: PostgreSQL is authoritative for SnapshotId, cut_version, captured_at, catalog lifecycle, creation jobs, leases, policy slots, and payload reachability.

Rationale: A mounted client can disappear at any time; local redb state cannot safely decide shared retention, cleanup, or takeover.

Date/Author: 2026-08-12 / SFS-650 plan author.

### 2. Public cut vocabulary

Decision: Public and domain-facing snapshot identity uses only volume identity, cut_version, and captured_at; retained checkpoint and event-range boundaries are descriptor inputs only.

Rationale: One stable cut vocabulary prevents callers from confusing serving checkpoints or replay boundaries with snapshot content identity.

Date/Author: 2026-08-12 / Standards review correction.

### 3. Snapshot origin

Decision: SnapshotOrigin has exactly Manual and Automatic, and the origin is carried in catalog rows and the list and inspect projections.

Rationale: Operators must distinguish a user request from a policy-created snapshot without inferring origin from timing or nullable fields.

Date/Author: 2026-08-12 / Spec review correction.

### 4. Catalog lifecycle and job execution state

Decision: SnapshotLifecycle is Creating, Ready, Failed, Deleting, or Deleted; SnapshotCreationState is Queued, Running, RetryWait, Completed, or Failed and is exclusively the creation-job execution state.

Rationale: The catalog lifecycle answers admission and deletion questions, while SnapshotCreationState answers worker progress and retry questions. The two state machines must not be conflated.

Date/Author: 2026-08-12 / Standards review correction.

### 5. Materializer location and lifecycle

Decision: SnapshotMaterializer, SnapshotWorker, and SnapshotPolicyEvaluator are reusable application services in crates/studiofs-vfs/src/snapshot_worker.rs; StudioVfs::spawn_snapshot_worker and StudioVfs::spawn_snapshot_policy_evaluator are called by crates/studiofs-vfs/src/vfs.rs spawn_startup_workers and use tracked shutdown.

Rationale: Mounted clients already own the durable creation-worker and policy-evaluator lifecycle, so takeover and future policy slots are automatic and no hidden command is needed.

Date/Author: 2026-08-12 / Spec review correction.

### 6. CLI claimant behavior

Decision: crates/studiofs/src/cli/snapshot.rs create uses the same materializer service to claim-or-follow its durable SnapshotId and waits for Ready.

Rationale: Manual create must provide a readiness barrier while still leaving the committed job available to a mounted client if the CLI claimant dies.

Date/Author: 2026-08-12 / Spec review correction.

### 7. Implicit volume resolution

Decision: SnapshotVolumeResolver in crates/studiofs/src/cli/snapshot.rs uses get_client_root, default_meta_dir_in_client_root, FormatInfo, and read_format_info_readonly only to discover one local context hint, then obtains and transactionally validates one SnapshotVolumeContext through PgMetaEngine and the PostgreSQL volumes authority before any snapshot catalog read or mutation. It compares volume_id, name, and UUID exactly and fails with a redacted actionable error on zero or multiple local hints, corrupt or stale local state, remote mismatch, or PostgreSQL unavailability.

Rationale: The exact CLI has no volume positional for snapshot and policy commands, so client_root is required for discovery, but local redb cannot establish shared volume identity. One PostgreSQL-verified context prevents a stale or copied local database from selecting the authority used for catalog and mutation operations. smount remains explicit.

Date/Author: 2026-08-12 / Standards review correction.

### 8. Reachability authority and interval shape

Decision: Add apply_object_lifetime_changes in crates/studiofs-meta/src/pg_engine/snapshot_reachability.rs and call it once from crates/studiofs-meta/src/pg_engine/metadata_io.rs push_projected_event_log_batch_locked after the batch_version is assigned and before that same PostgreSQL transaction commits. Store one half-open lifetime interval per never-reused object.

Rationale: Reachability must describe the shared published history at the exact revision where a mapping changes. Local crates/studiofs-meta/src/redb_engine/payload_objects.rs must never be authoritative.

Date/Author: 2026-08-12 / Standards review correction.

### 9. Automatic scheduling transaction

Decision: Automatic scheduling claims the unique policy generation and slot and inserts or reuses its catalog Creating row and SnapshotCreationState job in one PostgreSQL transaction. The catalog row and job are the durable queue.

Rationale: A separate claim and enqueue operation creates a crash window in which a slot is consumed but no durable work exists. One transaction removes that gap and permits lease takeover.

Date/Author: 2026-08-12 / Spec review correction.

### 10. Retention timing

Decision: Manual time to live (TTL) and automatic policy retention begin at ready_at, not request time or cut capture time.

Rationale: Materialization time must not consume user-visible retention, and every expiration must derive from one durable Ready transition.

Date/Author: 2026-08-12 / Spec review correction.

### 11. Read-only artifact policy

Decision: Snapshot artifacts are immutable and mounted read-only; artifact encryption is outside this plan unless a separate security contract is approved.

Rationale: The reviewed behavior requires integrity, checksum verification, and mutation rejection. Inventing an encryption protocol would expand scope without an accepted key-management contract.

Date/Author: 2026-08-12 / Standards review correction.

### 12. Temporary-file root

Decision: Every materializer attempt file, test fixture, report, local database, downloaded artifact, runner sandbox, and other disposable host file is below target/snapshot-v2/. Docker named volumes and Windows WinFSP drive-letter mount points are not target children; the unique runner manifest must own and clean them.

Rationale: A single repository-local root makes cleanup bounded, reviewable, and safe. Production client cache files are product state and are not test temporary files; tests must never place disposable files beside them.

Date/Author: 2026-08-12 / Standards review correction.

### 13. Recovery and rollback

Decision: Implementation is committed per ticket with a repository-format feat: subject, the SFS ticket in the commit body or metadata, and only an explicit reviewed file list staged. Development rollback uses git revert on the named ticket commit, and cleanup removes only runner-manifest-owned resources plus the validated target/snapshot-v2 root.

Rationale: Reversible ticket-level history preserves unrelated work and avoids destructive reset or broad cleanup commands.

Date/Author: 2026-08-12 / Standards review correction.

### 14. E2E and Compose ownership

Decision: All mounted Snapshot v2 scenarios run through cargo run -p studiofs-e2e -- run with an explicit fresh --studiofs-bin, unique --run-id, target/snapshot-v2/e2e-runs root, explicit --port-range, and retained runner manifest. No direct fixed-project docker compose up/down flow is part of Snapshot v2 validation.

Rationale: crates/studiofs-e2e already proves ownership of its unique studiofs-e2e-<run-id> project, allocated ports, client roots, mount points, and cleanup allowlist. Direct fixed-project down --volumes cannot prove exclusive ownership.

Date/Author: 2026-08-12 / fresh Standards review correction.

### 15. Schema replacement

Decision: crates/studiofs-meta/src/pg_engine/schema.rs exports one canonical v2 schema version, SQL function, and ensure function used by crates/studiofs/src/cli/init.rs, crates/studiofs/src/cli/dump_load.rs, and crates/studiofs-meta/src/pg_engine/tests/mod.rs. The old snapshots table and old snapshot events are removed with no v1 migration or compatibility path.

Rationale: duplicated DDL has already drifted across the three callers, and retaining a legacy table or replay path would create two snapshot authorities.

Date/Author: 2026-08-12 / fresh Spec review correction.

### 16. Artifact-key boundary

Decision: crates/studiofs-data/src/snapshot_key.rs owns a validated SnapshotArtifactKey and SnapshotArtifactPrefix API, and every snapshot put/get/delete/list call accepts those types rather than raw strings. Their rendered object paths include the canonical immutable volume UUID namespace in addition to the configured prefix, volume context, SnapshotId, and artifact component.

Rationale: custom data prefixes are a security and lifecycle boundary; validated keys prevent traversal, wrong-volume deletion, and bypass of the configured prefix. `volumes.name` is neither unique nor never-reused, so a public SnapshotId alone cannot isolate artifacts from two volume identities captured in the same UTC second.

Date/Author: 2026-08-12 / fresh Standards review correction.

### 17. Cross-crate ownership

Decision: domain values and async port traits live in studiofs-meta; PostgreSQL implementations remain adapters in crates/studiofs-meta/src/pg_engine/; SnapshotWorker application orchestration and DataStore wrapper adapters live in studiofs-vfs; the studiofs CLI and platform bridges remain runtime adapters above studiofs-vfs.

Rationale: studiofs-vfs already depends on studiofs-meta and studiofs-data. Reversing that dependency or calling pg_engine an application service would violate the repository dependency direction.

Date/Author: 2026-08-12 / fresh Standards review correction.

### 18. Secret and validation evidence

Decision: secret safety is proved with sentinel credential and DSN tests that assert raw sentinel values are absent from typed errors, reports, and transcripts. Source-code identifier searches are not evidence of redaction.

Rationale: legitimate code must name secret-bearing environment variables; only rendered output can leak their values.

Date/Author: 2026-08-12 / fresh Standards review correction.

### 19. Explicit exclusions

Decision: Snapshot v2 includes no product rollback, v1 migration or compatibility, offline snapshot creation or mounting, general cron framework, or multiple active policy generations. git revert is development-history recovery only.

Rationale: these capabilities are outside the accepted tickets and would add conflicting authorities or speculative scheduling and migration behavior.

Date/Author: 2026-08-12 / fresh Spec review correction.

### 20. Canonical policy spelling and public SnapshotId

Decision: The policy setter is exactly `snapshot policy set --daily-at <HH:MM> [--timezone <IANA zone>] --retention <duration>`. SnapshotId is exactly `<volume-name>.<UTC-cut-timestamp>` with captured_at formatted in UTC as `YYYY-MM-DDTHH-mm-ss.SSSZ`; PostgreSQL appends deterministic same-volume collision suffixes `-2`, `-3`, and onward.

Rationale: One parser spelling and one human-readable, transactionally unique identifier prevent client-side aliases and nondeterministic collision handling.

Date/Author: 2026-08-12 / confirmed contract correction.

### 21. Uploaded-fragment reconciliation authority

Decision: PostgreSQL records one row per uploaded payload object and fragment, and crates/studiofs-vfs/src/vfs/workers.rs StudioVfs::background_janitor reconciles one bounded leased page per cycle through crates/studiofs-meta/src/pg_engine/snapshot_reachability.rs while holding the existing PostgreSQL janitor authority. No snapshot row stores an object or fragment array.

Rationale: A client can die after remote upload but before publication. Durable per-object/per-fragment rows, a cursor, fencing, and idempotent validation/deletion close that gap without reintroducing thick snapshot payload state.

Date/Author: 2026-08-12 / confirmed contract correction.

### 22. Snapshot artifact cache identity

Decision: Snapshot artifact cache identity is exactly the composite `(volume identity, SnapshotId, checksum)`; every lookup, filename/path derivation, lease record, hit/miss decision, eviction record, and test uses all three fields, and checksum verification remains mandatory before open.

Rationale: A checksum alone proves bytes but does not establish the catalog and volume ownership needed for safe cache admission, sharing, and cleanup.

Date/Author: 2026-08-12 / confirmed contract correction.

### 23. Persisted states and typestate

Decision: Persisted SnapshotLifecycle and SnapshotCreationState remain enums with explicit validated transition functions and PostgreSQL compare-and-set updates. This plan rejects a generic `Snapshot<State>` typestate requirement; no typestate abstraction is added unless a later concrete compile-time invariant cannot be expressed by the persisted state machine and SQL fence.

Rationale: Lifecycle and job states are deserialized after restart, observed and changed by different clients, and enforced at the shared PostgreSQL authority. A process-local generic state parameter cannot prove the cross-process state at an await or transaction boundary and would duplicate, rather than strengthen, the authoritative fences.

Date/Author: 2026-08-12 / code-review response.

### 24. Existing secret-handling contract

Decision: Do not add a secrecy dependency for Snapshot v2. Preserve custom redacted Debug implementations, typed RedactedSnapshotMessage values, sentinel leak tests, and the workspace zeroize dependency for owned key material; apply zeroize to any newly owned secret buffer, but do not add secrecy merely as a review recommendation.

Rationale: The repository already has an explicit redaction and erasure contract, and the new snapshot domain/ports need not own long-lived secret values. Adding a second wrapper system without a concrete missing invariant would increase conversion and logging risk without improving the CLI boundary proof.

Date/Author: 2026-08-12 / code-review response.

### 25. Redacted error boundary

Decision: Every new Snapshot v2 domain and adapter error derives the workspace thiserror::Error. Backend errors are classified into typed redacted variants before crossing an adapter boundary; no new CLI-facing variant uses `#[error(transparent)]`, and no raw PostgreSQL, object-store, I/O driver, credential, request-header, or DSN source string reaches Display, Debug, reports, or transcripts.

Rationale: Structured variants retain actionable operation and retry classification while preventing convenient source chaining from bypassing the established redaction contract.

Date/Author: 2026-08-12 / code-review response.

### 26. Transaction-reusable PostgreSQL helpers

Decision: Every PostgreSQL query helper in crates/studiofs-meta/src/pg_engine/ that participates in a Snapshot v2 transaction is generic over `C: tokio_postgres::GenericClient + Sync`, and the same helper is compile-tested with both Client and Transaction. Domain ports remain backend-agnostic and expose no tokio-postgres type.

Rationale: Reusing the exact query and validation logic inside and outside a transaction avoids a second subtly different authority path while keeping the database adapter below the application boundary.

Date/Author: 2026-08-12 / code-review response.

### 27. Automatic policy timezone and DST mapping

Decision: If `--timezone` is omitted, persist UTC; never use the host's local timezone. Resolve each daily slot from its local calendar date, `HH:MM`, and the persisted IANA zone. A nonexistent local time in a spring-forward gap records one durable `SkippedDstGap` slot and advances to the next local date without shifting the time. An ambiguous local time in a fall-back repeat resolves to the earlier UTC occurrence (the pre-transition offset); the unique slot identity remains generation plus local date plus local `HH:MM`, so the second occurrence cannot create a duplicate. Invalid IANA zones are rejected before the policy transaction commits. Downtime creates at most one catch-up for the latest eligible, non-skipped slot.

Rationale: UTC as the default is deterministic across hosts, and explicit gap/ambiguity mapping prevents different clients from allocating incompatible slot identities or duplicate automatic snapshots.

Date/Author: 2026-08-12 / receiving-code-review correction.

### 28. Mounted policy-evaluator lifecycle

Decision: Add a tracked `SnapshotPolicyEvaluator` application service alongside `SnapshotWorker` in crates/studiofs-vfs/src/snapshot_worker.rs. `StudioVfs::spawn_startup_workers` starts exactly one evaluator for the verified mounted volume, using a PostgreSQL per-volume evaluator lease and fencing token. The loop claims or renews that lease, invokes the due-slot transaction, and sleeps until the returned next due instant, the lease-renew deadline, or a maximum 30-second poll interval, whichever comes first. Cancellation is selected at every sleep and database await; it stops new evaluations, releases the lease when ownership is certain, otherwise lets the fenced lease expire, and awaits the owned task during shutdown. The evaluator starts before the startup worker set is considered ready, so a committed `snapshot policy set` is observed by the next bounded poll even when no notification is delivered; no mounted client means no automatic job is expected. The due-slot transaction locks the active generation, records a gap skip or claims the unique generation-plus-local-slot, inserts/reuses the catalog Creating row and job, and commits them atomically. A later mounted client takes over only after the recorded lease expiry.

Rationale: `SnapshotWorker` only drains durable creation jobs; a separate tracked evaluator is required to turn a stored future policy into the first durable job and to keep evaluating later slots without a hidden command or process-local scheduling authority.

Date/Author: 2026-08-12 / receiving-code-review correction.

### 29. Immutable captured source checkpoint

Decision: The capture transaction copies the exact serving checkpoint bytes at or before the captured cut into an immutable per-snapshot source-checkpoint row, including checkpoint version, bytes, schema version, and checksum. `SnapshotSourceDescriptor` references that retained row plus its event-range boundaries; materialization never rereads the replaceable `metadata_state` row to reconstruct an already captured cut. The retained row is immutable and remains until the snapshot is deleted after all creation/takeover work has fenced out.

Rationale: the serving `metadata_state` row is a single mutable upsert; retaining only its version or identifier cannot reconstruct a cut after another client advances the serving checkpoint. Copying or versioning the bytes in the capture transaction makes delayed and takeover materialization independent of later serving-state replacement.

Date/Author: 2026-08-12 / receiving-code-review correction.

## Context and Orientation

The first use of important terms is explicit here. An application programming interface (API) is a callable boundary between layers. A command-line interface (CLI) is the user-facing executable surface. A data source name (DSN) is the PostgreSQL connection string. A time to live (TTL) is a duration measured from Ready publication. The Internet Assigned Numbers Authority (IANA) timezone is a named zone such as Europe/Kyiv. End-to-end (E2E) means a scenario that exercises the real product binary, PostgreSQL, object storage, mount, and peer client. Multiversion concurrency control (MVCC) is PostgreSQL's transaction visibility model. Filesystem in Userspace (FUSE) is the user-space filesystem bridge. Windows File System Proxy (WinFSP) is the Windows filesystem bridge. Compare-and-set (CAS) means an update whose predicate includes the state, owner, or version being replaced. The data definition language (DDL) is the Structured Query Language (SQL) schema initialization text. Garbage collection (GC) means cleanup of resources that no longer have a live owner or retained cut. Coordinated Universal Time (UTC) is the timestamp standard stored for durable events. Secure Hash Algorithm 256 (SHA-256) is the artifact and recovered-file checksum algorithm. JavaScript Object Notation (JSON) is used only for Compose inspection and redacted reports. Input/output (I/O) means filesystem or network reads and writes.

The domain and port seams are:

    domain: crates/studiofs-meta/src/snapshot.rs
        <- ports: crates/studiofs-meta/src/snapshot_ports.rs
        <- application: crates/studiofs-vfs/src/snapshot_worker.rs
    port implementations -> ports: crates/studiofs-meta/src/pg_engine/ and the DataStore adapter in crates/studiofs-vfs/src/snapshot_worker.rs using crates/studiofs-data/src/snapshot_key.rs
    runtime/API -> application: crates/studiofs/src/cli/snapshot.rs, crates/studiofs-e2e/src/, and the FUSE, macFUSE, and WinFSP bridges

## Idempotence and Recovery

- If the CLI exits after the capture transaction, the catalog/job remains durable. crates/studiofs-vfs/src/snapshot_worker.rs can follow or claim the same SnapshotId; it never captures a replacement cut.
- If a worker loses its lease, a current worker takes it through CAS after expiry. Fencing prevents the old owner from changing SnapshotCreationState, descriptor, or Ready.
- If claim fails before commit, no lease exists and the Creating catalog/job remains Queued or RetryWait. If the claim response is lost after commit, only the recorded lease owner/fence is authoritative.
- If cancellation occurs during a PostgreSQL await, the transaction either commits its complete fenced transition or is dropped/rolled back; code re-reads authoritative state before any later side effect and never assumes an uncertain commit result.
- If renewal is unavailable or its result is uncertain, the worker performs no descriptor/Ready publication. The recorded lease remains until expiry, after which another mounted startup worker may take over.
- If cancellation occurs before object I/O, the pre-I/O Uploading or CleanupPending row remains; if it occurs during or after an uncertain PUT/delete, the same fenced row exposes the possible orphan for exact stat/read/checksum validation and idempotent close/delete. Shutdown propagates cancellation and awaits every owned task.
- If immutable final upload completes but descriptor publication does not, catalog stays Creating and smount rejects it. The attempt is CleanupPending; a later claimant either verifies and reuses the exact key/checksum or proves no Ready descriptor references it and deletes the orphan.
- If Ready CAS fails or loses its fence, no partial descriptor/proof publication is visible. Job state remains Running/RetryWait as committed, never Ready.
- If an attempt fails, its file below target/snapshot-v2/materializer/<snapshot-id>/attempts/ remains retryable until the cleanup pass removes it. Cleanup retries five times and records failure without deleting an immutable Ready artifact.
- If PostgreSQL or object storage is unavailable, catalog, job, policy slot, and reachability changes remain transactional; network work is retried outside the control transaction.
- If policy transaction work fails, both the unique slot claim and catalog/job insertion roll back together. A later evaluator can claim the same slot.
- If a publish or Ready CAS loses to delete, the worker stops and cleans only its own temporary path.
- If a mount lease expires, the session closes before payload or artifact cleanup can proceed. A later mount must reacquire a lease and reverify the checksum.
- If an object delete returns not-found, cleanup records success. Other object failures remain retryable.
- If a payload fragment PUT starts but the client dies before confirmation or publication, its PostgreSQL Uploading/Uploaded row remains discoverable. The next janitor owner resumes after the 60-second row lease, revalidates the exact fragment, and records Published, RetryWait, or Deleted through the current fence. Cursor replay and NotFound deletion are idempotent.
- If publication races reconciliation, the PostgreSQL object-state CAS decides ownership: Published prevents remote deletion; DeletePending prevents publication and requires a new never-reused object ID. A stale lease or fence can change neither state nor remote data.
- If a cached artifact is revisited, lookup requires the same volume identity, SnapshotId, and checksum and then revalidates checksum/length before open. A differing component creates a separate cache identity and cannot borrow the existing mount lease or eviction timestamp.
- If the process restarts during Deleting, the durable catalog row resumes cleanup; no local redb table can resurrect a deleted snapshot or extend a shared payload lifetime.
- The only development rollback is per-ticket git revert followed by exact target/snapshot-v2 cleanup. No destructive history rewrite is part of this plan.

## Artifacts and Interfaces

The domain interface contains:

- SnapshotId: validated public text exactly `<volume-name>.<UTC-cut-timestamp>`, where UTC-cut-timestamp is `YYYY-MM-DDTHH-mm-ss.SSSZ`, with optional PostgreSQL-allocated `-2`, `-3`, and onward suffix.
- SnapshotOrigin: Manual or Automatic.
- SnapshotVolumeIdentityHint: locally discovered, backend-agnostic volume_id, volume_name, and volume_uuid; it carries no credential or authority claim.
- SnapshotVolumeContext: the transactionally verified PostgreSQL volume_id, volume_name, and volume_uuid required by every catalog read and mutation.
- SnapshotCut: volume_id, cut_version, and captured_at only.
- SnapshotSourceCheckpoint: immutable per-snapshot checkpoint bytes, checkpoint version, schema/format version, and SHA-256 retained by the capture transaction until deletion.
- SnapshotSourceDescriptor: a reference to SnapshotSourceCheckpoint plus event-range inputs, schema/format version, and replay proof; these inputs do not redefine SnapshotCut and the descriptor never points only at mutable `metadata_state`.
- SnapshotLifecycle: Creating, Ready, Failed, Deleting, Deleted.
- SnapshotCreationState: Queued, Running, RetryWait, Completed, Failed; this is creation-job execution state distinct from SnapshotLifecycle.
- SnapshotPolicyEvaluatorError: a typed redacted evaluator failure with retry/cancellation classification; it never carries raw PostgreSQL, credential, or DSN text.
- validate_snapshot_lifecycle_transition and validate_snapshot_creation_transition: explicit enum transition functions mirrored by expected-state/owner/fence SQL CAS; persisted states are revalidated after every read rather than represented by a process-local generic typestate.
- SnapshotCatalogEntry: SnapshotId, volume, origin, SnapshotCut, lifecycle, retention, ready_at, expires_at, artifact descriptor, redacted failure status.
- SnapshotCreationJob and SnapshotCreationLease: durable work, retry count, claimant, lease expiry, fencing version, and next retry time.
- SnapshotPolicyEvaluatorId, SnapshotPolicyEvaluatorLease, and SnapshotPolicyEvaluation: per-volume evaluator owner/fence state and the transaction result containing a created/skipped/followed outcome plus the next wake-up instant.
- SnapshotMountLease: Ready snapshot, mount owner, the exact SnapshotArtifactCacheKey composite, lease expiry, heartbeat, fencing version, and release state.
- SnapshotArtifactDescriptor: immutable final object key, format/schema version, checksum, byte length, SnapshotCut, and verification time.
- SnapshotReachabilityInterval: object identity, start_cut_version, nullable end_cut_version, and unique object constraint.
- SnapshotArtifactCacheKey: exactly volume identity, SnapshotId, and checksum; equality/hash/path derivation use all three.
- PayloadUploadOwnerId, UploadedFragmentReconcileOwnerId, UploadedPayloadObject, UploadedPayloadFragment, UploadedFragmentCursor, UploadedFragmentClaim, UploadedFragmentProof, and UploadedFragmentReconcilePage: PostgreSQL-owned upload/reconciliation values keyed by volume/object/fragment, never by a SnapshotId array.

The evaluator claims its lease before evaluating, renews before the lease-renew deadline, and stops before any due-slot transaction when renewal is uncertain. After `evaluate_due_slot` it selects cancellation, lease renewal, the returned next due instant, and a maximum 30-second fallback poll; the fallback makes a committed policy observable even if no cross-process notification exists. `snapshot policy set` therefore need not own a process-local wake channel, and a policy stored while no mounted client exists remains durable but does not create a job until a mounted evaluator starts.

StudioVfs owns the Arc<SnapshotWorker> and Arc<SnapshotPolicyEvaluator>. crates/studiofs-vfs/src/vfs.rs adds the exact private lifecycle seams `fn spawn_snapshot_worker(self: &Arc<Self>)` and `fn spawn_snapshot_policy_evaluator(self: &Arc<Self>)`, both called once by spawn_startup_workers. Each clones its service, derives a child from ShutdownState.background_shutdown_token, uses tokio::spawn, passes the JoinHandle to track_background_task, and records only redacted terminal errors. CLI create constructs the same SnapshotWorker service from the same ports and calls claim_or_follow; it does not duplicate materialization or policy scheduling. Cancellation stops new I/O, releases or lets the relevant lease expire according to the last certain PG state, awaits owned child work, and never detaches. Every public trait, type, constructor, and method above requires Rust triple-slash documentation stating authority, ownership, cancellation behavior, invariants, and an Errors section; error docs explicitly promise redaction.
