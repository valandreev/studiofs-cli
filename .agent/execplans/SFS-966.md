# Make the CLI janitor fail closed

This ExecPlan is a living document maintained under `.agent/PLANS.md`. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current.

## Purpose / Big Picture

The standalone `studiofs janitor` command removes old data objects that metadata no longer references. A wrong local volume file, missing PostgreSQL reachability state, unfinished sync, or unavailable backend must never be interpreted as evidence that an object is orphaned. After this change, the CLI checks those conditions without writing metadata, holds the per-volume PostgreSQL janitor lock while it reads protection data and scans storage, and stops before object listing or deletion when safety is uncertain. A healthy PostgreSQL volume continues to make progress. Mounted background janitor behavior remains unchanged.

## Surprises & Discoveries

- Observation: normal PostgreSQL engine startup cannot serve `--dry-run` because it opens redb writable and may update recovery markers, visibility filters, client slots, and background workers.
  Evidence: `PgMetaEngine::open_with_options` calls `RedbMetaEngine::open`, changes counters/filter state, and starts poll/checkpoint workers unless disabled.
- Observation: the remote checkpoint stores the full `FormatInfo`, including the immutable data bucket and prefix, and `studiofs init` seeds that information with the initial remote checkpoint.
  Evidence: `crates/studiofs/src/cli/init.rs::seed_pg_metadata_state` writes serialized `FormatInfo`; later checkpoint publication updates the same `metadata_state.format_info` field.
- Observation: `snapshot_reachability_bootstrap` is inserted only after the version-checked backfill transaction completes; its absence means janitor pins are unknown.
  Evidence: `crates/studiofs-meta/src/pg_engine/snapshot_reachability.rs::backfill_current_reference_ledger_once` and the existing `load_pg_global_snapshot_pins` guard.
- Observation: the CLI's effective object prefix also depends on the volume name when the persisted data prefix is empty.
  Evidence: `crates/studiofs/src/cli/janitor.rs::normalize_prefix`; the remote binding check therefore compares the volume name alongside endpoint, bucket, prefix, and UUID.
- Observation: the standalone safety session can acquire a PostgreSQL lock and read its protection snapshot without changing local redb bytes.
  Evidence: the focused PostgreSQL integration test compares local database bytes around successful and unsafe read paths and checks lock contention/reacquisition.

## Decision Log

- Decision: Use a janitor-only read-only metadata session instead of opening the regular PostgreSQL metadata engine.
  Rationale: the regular engine has local repair, replication, and worker side effects that violate dry-run's no-metadata-write requirement. A separate narrow reader keeps mounted startup behavior unchanged.
  Date/Author: 2026-11-09 / Codex.
- Decision: Treat the published remote `metadata_state.format_info` as the storage binding; do not add columns or copy a local binding into PostgreSQL during janitor execution.
  Rationale: init and checkpoint publication already store the binding on trusted paths. Older rows with no usable binding must fail closed until initialized through a trusted path.
  Date/Author: 2026-11-09 / Codex.
- Decision: Require PostgreSQL metadata for standalone destructive janitor work; do not authorize deletion from a local-only metadata backend.
  Rationale: local metadata alone cannot prove that no shared reference or snapshot pin exists.
  Date/Author: 2026-11-09 / Codex.
- Decision: Keep PostgreSQL failure strings bounded and redacted at the janitor API boundary.
  Rationale: transport or server errors must not reveal a stored PostgreSQL URL through CLI errors.
  Date/Author: 2026-11-09 / Codex.

## Context and Orientation

`crates/studiofs/src/cli/janitor.rs::run` coordinates metadata access, the global lock, the loop, and object listing/deletion through `pipeline.rs`. `crates/studiofs-meta/src/redb_engine.rs::open_read_only` reads local metadata without creating or repairing rows. `crates/studiofs-meta/src/pg_engine/janitor.rs` already defines the PostgreSQL advisory-lock key and queries global snapshot pins; `snapshot_reachability.rs` owns PostgreSQL current-reference reads. `metadata_state.format_info` is the serialized, checkpointed volume configuration. A “protection snapshot” is the set of locally and remotely referenced object IDs, active snapshot pins, and pending deletion timestamps that the CLI passes to the object cycle.

The janitor lock is a PostgreSQL session advisory lock keyed by volume ID. It coordinates janitor processes for that volume. “Fail closed” means the command returns a stable safety/backend error before listing or deleting objects whenever it cannot prove the required metadata state.

## Plan of Work

Add the narrow read-only janitor metadata API to `studiofs-meta`. It reads the local `FormatInfo` and redb state through read-only handles, retains a bounded PostgreSQL connection for the existing per-volume advisory lock, and checks remote UUID and checkpointed storage binding, current metadata head versus local applied version, local unflushed event/recovery state, metadata format, and snapshot reachability bootstrap. With the lock held, it reads PostgreSQL current references and snapshot pins and combines those with local references and pending deletion timestamps. It must expose no metadata mutation operation and must release/close its PG session on success and every error path.

Change only the standalone CLI janitor to use this session. It must acquire the remote lock before reading the protection snapshot or listing object storage, keep the lock through object work, and release it after each cycle. A busy lock is a distinct skip result; unknown or unsafe metadata state and backend unavailability are distinct surfaced errors. Do not alter VFS janitor code.

Add small tests for each gate and for cycle ordering. Fake unsafe state, lock contention, and backend failure must make zero list/head/delete calls. A healthy fake adapter must list and process an old orphan. A dry-run must report candidates without metadata writes or delete requests. Add an adapter-level test proving the real reader is built from read-only redb and does not expose a write path; use a focused ignored PostgreSQL integration test only when it can prove lock and binding wiring without broad services.

## Validation and Acceptance

Unsafe binding, mismatch, missing snapshot bootstrap, a stale/ahead local metadata version, unflushed local events, pending recovery, or a failed PostgreSQL query must stop the CLI before the fake object store receives a list request. Busy lock must also stop before listing but remain distinguishable from unsafe state. With matching identity, equal local/remote head, no pending recovery or event work, and complete snapshot reachability, the CLI must list and process an old orphan while protecting the union of local references, PostgreSQL references, and snapshot pins. Dry-run may issue object-store list/head calls, but sends no delete request and performs no metadata writes.

## Idempotence and Recovery

The implementation is read-only with respect to metadata. A failed PG check or object-store operation must close the held connection so PostgreSQL releases the advisory lock; a subsequent janitor invocation can retry safely. Missing legacy `metadata_state.format_info` is reported as unsafe and is never backfilled by the janitor.

## Artifacts and Notes

No schema migration is planned because init and checkpoint publication already persist the immutable volume binding. Existing `studiofs-vfs` background janitor behavior and SFS-967 per-object deletion fencing remain out of scope.

## Interfaces and Dependencies

Reuse existing `redb`, `tokio-postgres`, transport, and timeout dependencies. Keep a small public metadata API for the standalone CLI and private internal helpers for connection lifecycle, identity checks, and protection reads. The API should return `FormatInfo`, lock acquisition state, and a `JanitorProtection` snapshot without granting the caller write access to redb or PostgreSQL metadata.
