# Prepare the v0.2.0 publication gate and release builds

This living ExecPlan follows `.agent/PLANS.md`. Keep Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective current.

## Purpose / Big Picture

The maintainer has selected version 0.2.0 and wants downloadable GitHub Releases builds for Windows x86-64/ARM64, Linux x86-64/ARM64 and macOS ARM64. Native GitHub runners will run the equivalent of `cargo build -p studiofs --release --locked` for each target. Archives must carry licenses, installation requirements and the exact source/build identity. A tag build can prepare a draft release; publication still depends on the final compliance decision.

## Surprises & Discoveries

The first push was rejected because the remote SFS-854 branch retained the initial report commit `033e69b1172490c790576cb0ed17da8af0894699`. A normal merge preserves that history; its only add/add conflict is resolved with the refreshed report and an immutable link to the initial assessment. No force push is needed.

All five prerequisite issues are Done, but their reports retain release conditions. The notice generator exits 1 in release mode for 65 packages. The existing `release: published` compliance workflow runs after publication and does not assemble binary archives. macOS automatically links experimental MFMount when installed, so release builds must point `STUDIOFS_MFMOUNT_FRAMEWORK_DIR` to an empty directory and inspect the executable. Current GitHub documentation lists native ARM64 hosted runners for both private and public repositories.

## Decision Log

Use native runners for all five targets rather than add cross-compilers and sysroots. Interpret the requested x86 builds as x86-64; no 32-bit products were requested explicitly. Pin Rust 1.95.0 and existing immutable action revisions. Use the current package's default features, with the existing macOS environment override required by the platform distribution policy. Preserve the historical dependency/provenance inventories rather than silently refreshing their evidence.

Prepare a draft release only after all package jobs and strict notice checks succeed. This makes the requested downloads reviewable without publishing an unresolved legal condition. A manual branch run prepares CI artifacts; an existing version tag prepares the draft. No tag, release publication, repository visibility change or full suite is part of this local preparation.

## Concrete Steps

From the repository root run the packaging unit checks, `cargo metadata --locked --offline --no-deps --format-version 1`, the existing notice self-test, `cargo deny --locked check licenses`, and strict notice generation under `target/sfs-854/`. Run actionlint on the new workflow and `git diff --check`. Use authenticated `gh` reads for GitHub state. Commit and push only after inspecting these results. No product or workspace-wide test suite is required for metadata, packaging and workflow changes.

## Validation and Acceptance

Packaging checks must exercise actual ZIP/tar output, binary hashes, both naming formats and rejection of unresolved notices. The workflow must check the version/tag identity, use five native targets, forbid MFMount in macOS linkage, preserve separate driver installation and create a draft only after all jobs pass. A deliberately unresolved notice bundle must fail packaging. Native runner evidence and public source access are still required before the final GO decision.

## Idempotence and Recovery

Temporary tools and artifacts stay in ignored `target/`. Re-running a tag workflow may update an existing draft, but must reject an already published release. It must not create an absent Git tag or overwrite published assets. Existing historical inventories remain immutable audit baselines.
