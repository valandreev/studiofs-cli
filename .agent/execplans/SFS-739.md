# Keep metadata shutdown responsive and retain the sync owner

This ExecPlan follows `.agent/PLANS.md` and remains a living document.

## Purpose / Big Picture

SFS-739 requires VFS shutdown to keep Tokio tasks responsive while local metadata
sync stalls. The configured metadata timeout must return a failed shutdown result
without abandoning the operation that owns redb. A successful shutdown must leave
no metadata worker preventing immediate reopen after the VFS is dropped.

## Surprises & Discoveries

`run_sync_with_timeout` in `crates/studiofs-vfs/src/vfs.rs` unconditionally joins
its OS thread on success, timeout, and disconnect. The comment claims a secondary
cap that does not exist. Its only production caller is `StudioVfs::shutdown` in
`crates/studiofs-vfs/src/vfs/upload_lifecycle.rs`.

The local sync is a synchronous redb durability transaction. It cannot be safely
interrupted halfway through persistence. Tokio's blocking-task documentation also
states that an already running `spawn_blocking` task cannot be aborted.

The responsiveness regression failed against the original implementation after
its bounded channel watchdog expired (the sibling Tokio task could not release the
operation). With the async wait, it passes; the timeout path now also retains the
same handle and does not start a duplicate operation.

## Decision Log

- Decision: use the existing Tokio blocking pool, retaining its join handle in
  `ShutdownState` and awaiting it by mutable reference under an async mutex.
  Rationale: deadline or caller cancellation leaves the same operation owned;
  no second thread, receiver, or cancellation protocol is needed.
  Date/Author: 2026-09-29, Codex.
- Decision: metadata deadline exhaustion is a terminal failed VFS shutdown,
  replayed to concurrent and repeated callers. The retained worker keeps its
  metadata reference until the actual sync finishes; this is not permission to
  reopen the database or claim crash-safe recovery.
  Rationale: local sync has no cooperative cancellation API. Returning failure
  permits shutdown progress while preserving the storage owner. Default Tokio
  runtime destruction may still wait for an in-progress blocking operation.
  Date/Author: 2026-09-29, Codex.

Known boundary: Tokio cannot abort a running blocking task. Shutdown returns its
terminal timeout without blocking a Tokio worker, but destroying a Tokio runtime
may still wait for an in-flight blocking task. The sync retains its metadata owner
until it completes; timeout is not a safe signal to reopen redb early.

## Context and Orientation

`StudioVfs` stores synchronous metadata behind `MetaExecutor`. `ShutdownState`
serializes shutdown ownership and retains background task handles. The shutdown
owner drains accepted local state, stops remote workers, performs local metadata
sync, persists the cache, then records an immutable success or failure for all
callers. A cancelled owner marks shutdown aborted so a later caller can resume.
The metadata barrier must therefore keep its task in shared state even if its
waiting future is dropped. redb is the local metadata database; reopening it
while any owner remains is rejected by its file lock.

## Plan of Work

First add a current-thread Tokio regression beside the helper tests in
`crates/studiofs-vfs/src/vfs/tests.rs`. Block the sync closure on a channel with a
bounded watchdog, and let a sibling Tokio task release it. The old implementation
prevents the sibling from running before the watchdog.

Then change the helper to an async function. Add one metadata task slot to
`ShutdownState`, populate it with `spawn_blocking` once, and apply a Tokio timeout
to the borrowed handle. Remove the slot only after the task has finished. Await
the helper from shutdown and correct the timeout log. Use the same slot on retry
after either deadline expiry or caller cancellation.

Finally replace the old sleep-based timeout check with channel-controlled
ownership checks. Exercise the real shutdown caller with a controlled redb sync
and check its terminal error/snapshot. A separate successful shutdown must allow
immediate metadata reopen while the runtime remains alive. Keep new test setup
under `target/` using the existing workspace temporary-directory helper.

sleeping or retrying.
