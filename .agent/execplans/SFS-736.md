# Add conservative local redb compaction scheduling

This ExecPlan is a living record for SFS-736. Maintain `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` according to `.agent/PLANS.md`.

## Purpose / Big Picture

Mounted clients reclaim local metadata space with one best-effort compaction during startup and additional threshold-gated compaction after sustained quiet. A PostgreSQL janitor lease, network access, and object storage are not prerequisites. Shutdown does not trigger compaction. Operators can see attempts in structured logs and read the existing redb result, duration, and physical-size metrics.

## Surprises & Discoveries

- Observation: Production already calls `compact_local_storage()` during startup, before it spawns the background workers. This can delay startup while redb holds exclusive database access. Evidence: `crates/studiofs-vfs/src/vfs.rs`, `StudioVfs::spawn_startup_workers` and `run_startup_local_metadata_compaction`.
- Observation: `background_gc()` acquires the PostgreSQL janitor lease before object cleanup, so placing local compaction inside its leased portion would incorrectly couple per-client local maintenance to the global lease. Evidence: `crates/studiofs-vfs/src/vfs/workers.rs`, `StudioVfs::background_gc`.
- Observation: In the SFS-733 Windows workload, physical size reached 6,320,128 bytes. At the final pre-compaction checkpoint redb reported 1,786,496 fragmented bytes; explicit compaction reduced the file to 4,255,744 bytes in 184,071,000 ns. The initial 1,056,768-byte database reported 1,007,924 fragmented bytes, showing why a percentage-only trigger would compact small databases. Evidence: the targeted `local_metadata_churn_redb_growth_workload` output on 2026-09-27.
- Observation: Context7's redb documentation confirms `Database::compact()` requires exclusive access, returns an error for active transactions, and iterates until no more pages can be compacted. Once started, its duration cannot be interrupted by the scheduler.
- Observation: An async metadata call can start and finish between scheduler polls. Tracking only active calls misses that quiet-window break, so the activity generation is incremented before dispatch to the blocking pool; the local maintenance path is explicitly excluded from that generation.
- Observation: Foreground I/O can become inactive between a scheduler check and its metadata diagnostic/compaction closures. Failed admission resets the quiet window, so a transient request cannot inherit an older idle interval.
- Observation: `foreground_io_active()` also includes handle-lifetime counts for OS-cache readers and open writers. Compaction now uses only in-flight/recent foreground read scopes; recorded metadata activity and redb's exclusive lock remain separate admission signals.
- Observation: `upload_user_idle_grace_ms` is user-configurable and not clamped by `normalize_vfs_config()`. The compaction read gate now uses its own two-minute grace, above the one-minute polling interval and independent of upload tuning.
- Observation: An RDWR handle starts in a read-capable access class and becomes a writer class after `write_fh()`. The compaction gate intentionally excludes that handle-lifetime count; the write operation advances the foreground generation and resets the quiet window.
- Observation: `Notify::notify_waiters()` is non-sticky and can be missed while the worker awaits blocking maintenance. The worker also selects on the sticky background shutdown token, so cancellation remains observable on its next poll.
- Observation: `MetaExecutorActivitySnapshot.active_calls` covers calls holding an explicit executor activity guard. `foreground_view()` records activity once when returning its `Arc`; it does not guard the full duration of later view use.
- Observation: The user confirmed startup can tolerate the existing synchronous compaction delay and requested restoring that behavior alongside the idle scheduler.
- Observation: The upload-stats loop read replication backlog through `sync_meta()`, and other recurring worker calls used `run_meta()`, so they continually advanced the foreground generation and prevented the 15-minute idle window from accumulating. A real VFS runtime-stats regression reproduced two extra generation increments (1 to 3) before the fix.
- Observation: A successful diagnostic response may still have incomplete page statistics when redb's nonblocking page-stat sample cannot refresh. This is different from a complete sample below the compaction thresholds and now retries on the next normal poll.
- Observation: A read-only VFS may wrap an engine whose default local compaction result is `NoWork`; invoking startup compaction still counted as executor activity even though the mount cannot compact.
- Observation: Writable startup compaction was still routed through `run_sync()`, so it advanced the foreground activity generation once before workers started. A focused regression reproduced the extra increment (1 to 2) even though startup work is maintenance.
- Observation: `known_file_lock_lease_snapshot()` requested two foreground views back-to-back for one metadata check, and the compaction attempt closure cloned `MetaExecutor` separately despite already capturing the VFS.

## Decision Log

- Decision: Run local metadata compaction in one separately tracked VFS worker, outside `background_gc()` and the PostgreSQL janitor lease. Rationale: each client owns its database and must be able to maintain it independently.
- Decision: Keep one best-effort synchronous startup compaction before spawning VFS workers. Rationale: the user explicitly accepts startup delay; this preserves cleanup on startup while the idle scheduler handles later accumulated fragmentation.
- Decision: Require a physical file size of at least 4 MiB, at least 1 MiB reported fragmentation, and fragmentation of at least one quarter of the file. Rationale: all three conditions admit the measured 6.32 MiB plateau where compaction reclaimed about 2.06 MiB, while rejecting the 1.06 MiB initial database whose fragmentation statistic was nearly the whole file. These are evidence-based initial thresholds, not a claim that `fragmented_bytes` is an exact garbage estimate.
- Decision: Require 15 minutes without recorded foreground metadata activity or a foreground read seen within the compaction-owned two-minute grace; open idle handles do not hold the quiet window open. Writer handle classes are excluded as lifetime counts, while actual writes advance the activity generation. Poll at a fixed interval and enforce a cooldown after an attempt. Busy attempts retry after a fixed bounded delay; success/no-work and errors use longer delays. Rationale: SFS-733 does not measure idle timing, so these are conservative scheduling safeguards rather than churn-derived thresholds. Keep the durations internal and shared across platforms.
- Decision: Use the existing metadata diagnostics for compaction result/duration/bytes and emit one structured attempt log with the threshold reason, idle duration, and foreground-arrival signal. Rationale: this adds no second telemetry surface or persistent scheduler schema.
- Decision: Count foreground metadata requests that use activity-recording executor paths in the generation; run background workers and telemetry through generation-neutral maintenance APIs. `active_calls` excludes concurrent calls only when they hold an executor activity guard; a returned `foreground_view()` is not guarded for its full use. Redb's exclusive `try_write()` remains the lock-based arbiter for active database transactions.
- Decision: Retry incomplete diagnostics after one normal poll and complete below-threshold diagnostics after one hour. Rationale: sampling contention is transient and should not receive the no-work backoff.
- Decision: Skip the synchronous startup attempt on read-only mounts. Rationale: the read-only metadata view cannot compact; retaining a no-op executor call only adds startup work and activity.
- Decision: Keep `SeqCst` ordering for the admission counters and leave the local `(bool, Option<Diagnostics>)` probe result. Rationale: no measured benefit justifies weakening the shared admission signal, and a one-use enum would add code without clarifying another caller.
- Decision: Borrow the activity guard and name the 25% ratio denominator; flatten the attempt result match. Rationale: these are local reductions that preserve the existing policy and behavior.
- Decision: Run startup compaction through `run_sync_maintenance()` while retaining its active-call guard. Rationale: startup compaction stays synchronous but must not be observed as foreground user activity.
- Decision: Emit stable lowercase structured result labels and keep the combined `NoWork`/`SkippedBusy` debug arm. Rationale: log consumers receive one consistent field format without duplicating fields.
- Decision: Keep one foreground view for the file-lock lease snapshot, reuse the captured VFS executor in the compaction closure, and add focused rustdoc/cooldown coverage. Rationale: remove verified redundant work and make the scheduling boundary explicit.

## Context and Orientation

`RedbMetaEngine::compact_local_storage()` lives in `crates/studiofs-meta/src/redb_engine/gc.rs`. It already uses a nonblocking database write-lock acquisition, maps active transactions to `SkippedBusy`, and records outcome, duration, and successful before/after file sizes in `LocalStorageDiagnostics`. `PgMetaEngine` forwards that local-only operation through its local engine. Startup invokes it synchronously before worker creation; `background_gc()` remains separate PG/object maintenance gated by a global janitor lease.

`MetaExecutor` in `crates/studiofs-vfs/src/runtime.rs` is the shared VFS boundary for synchronous and asynchronous metadata operations. Activity-recording calls advance the generation; maintenance execution tracks active calls only while they hold an explicit guard. A returned `foreground_view()` records one access but does not guard later use of its `Arc`. The compaction worker has a dedicated tracked join handle; it selects on the sticky shutdown token and checks shutdown again immediately before invoking redb.

## Idempotence and Recovery

Both startup and scheduled admission are best-effort. Writable startup logs and continues if compaction fails or redb is busy; read-only mounts skip the call. Missing or incomplete scheduled diagnostics retry after the normal 60-second poll, while complete samples below thresholds wait for the one-hour recheck. `SkippedBusy` is not an error and retries after the bounded delay. A sticky token stops future attempts even if the one-shot notification is missed during a blocking operation. The compaction worker has a dedicated shutdown join outside the generic two-second background-task budget; shutdown waits for an in-progress blocking attempt to return before proceeding. If that join exceeds two seconds, shutdown logs that it is still waiting and logs its final elapsed time; cancellation errors are ignored like those from sibling joins. Other background tasks retain the existing bounded join. No persistent schema or database migration is introduced.
