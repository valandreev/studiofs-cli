# Add local-first logical volume quotas

This ExecPlan is living documentation governed by `.agent/PLANS.md`. Keep its progress, discoveries, decisions, outcomes and revision note current. The feature lets an administrator bound logical file data in a volume and lets applications see the configured capacity, while preserving autonomous local writes. Each client admits against its local authority; concurrent clients may temporarily overshoot the aggregate cap.

## Purpose / Big Picture

Users can configure a volume-wide logical byte limit, see total/free capacity, and receive a consistent disk-full result when local admitted usage reaches that limit. A two-client mounted scenario demonstrates the deliberately soft distributed guarantee. This is not a strict shared reservation system and does not cap S3 billing.

## Decision Log

- Decision: charge each reachable regular-file inode once by logical length; holes count, hard-link aliases do not multiply usage, trash remains charged until actual removal, and snapshot-only physical retention is excluded.
  Rationale: this gives one stable logical namespace measure without pretending to estimate provider storage or billing.
  Date/Author: 2026-11-17, Codex.
- Decision: a locally open orphan stays charged through reclamation after final close.
  Rationale: an open handle can continue growing a file after unlink, so releasing its charge early permits unlimited temporary-file growth.
  Date/Author: 2026-11-17, Codex.
- Decision: test soft overshoot through a registered two-client mounted scenario after implementation provides policy configuration and usage observability; do not create a speculative test against nonexistent interfaces.
  Rationale: the shared checkout has no quota API yet, so an invented test would not compile or validate product behavior.
  Date/Author: 2026-11-17, Codex.

## Context and Orientation

The volume is the shared filesystem namespace. A logical byte is a file's visible length, including sparse holes. An inode is the underlying file identity that may have multiple hard-link names. A reservation is growth already accepted by a local writer but not yet reflected in committed metadata. PostgreSQL replication is asynchronous; `redb` is the foreground local authority. `USED_SPACE` describes referenced payload storage and cannot be reused as logical usage. The current high-level feature sequence is in `docs/superpowers/plans/2026-11-12-qol-023.md`, Milestone 5. Detailed user-facing semantics are in `docs/logical-volume-quota.md`.

## Plan of Work

First trace the actual write, append, truncate/setattr, create, unlink, restore, purge and replay paths, along with statfs consumers and bridge errno mapping. Persist an optional, versioned volume policy via the supported atomic metadata path and define authorized updates and stale-peer propagation. Track committed logical lengths by inode and reserve local accepted growth across concurrent handles. Reconcile reservations on failure, shrink, close and restart without double-counting replay or hard links. Update capacity reporting and map quota exhaustion consistently while allowing reads, in-place overwrite, shrink, delete, durability barriers and shutdown.

Add focused unit/integration tests for the accounting rules and failure rollback. Add a registered two-client mounted scenario under `crates/studiofs-e2e/src/scenario/` using separate client roots and bounded observable-state polling. With a quota Q and initial local usage U, isolate peer propagation, let each client independently accept growth no greater than Q-U, reconnect, and wait until both files are visible. Assert each local admission succeeded and converged aggregate logical usage exceeds Q. The scenario must not claim that overshoot is bounded to one operation or that all timing schedules overshoot. Add the scenario to registry/listing and runner contract tests following existing workload conventions.

## Validation and Acceptance

Verify that sparse length is charged, hard links count once, truncate releases only the removed length, unlink followed by append still enforces quota until orphan reclamation, retained trash stays charged until purge/expiry, restore does not double-charge, and snapshots affect physical retention rather than quota usage. Exercise concurrent local handles and failed operations to show reservations are neither double-spent nor leaked. Verify restart/replay, lowered-quota zero-free reporting, bridge error consistency, and continued reads/overwrite/shrink/delete/fsync/shutdown.

The two-client scenario passes when each client admits growth using stale local usage, replication converges, both files remain readable, and aggregate logical usage exceeds Q; it fails if a foreground remote quota wait is introduced or if it asserts a strict shared cap. Native mounted capacity/error behavior is separate evidence.
