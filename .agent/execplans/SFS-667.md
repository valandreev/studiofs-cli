# Upgrade Tokio to 1.53.1 with runtime and cross-platform validation

This ExecPlan is a living document and follows `.agent/PLANS.md`.

## Purpose / Big Picture

StudioFS will resolve Tokio 1.53.1 while keeping its existing runtime feature
set and runtime topology. The user-visible result is a newer maintained async
runtime in the shipped workspace, with evidence that the synchronous bridge,
PostgreSQL runtime, local-cache blocking paths, prefetch workers, and shutdown
behavior remain compatible. The change is a dependency-hardening update; it
must not be described as a performance improvement unless repeated mounted
measurements prove one.

The repository is currently being executed from Windows 11. Cross-platform
macFUSE and libfuse3 validation must be run on their native hosts before this
issue can be called fully accepted. The repository instructions prohibit
running the full test suites in this agent session, so the final plan records
the exact commands for the operator/CI gate instead of claiming those checks
from focused local tests.

## Surprises & Discoveries

- Observation: The workspace manifest already permits compatible Tokio 1.x releases with `tokio = { version = "1", features = [...] }`.
  Evidence: `Cargo.toml:34` declares the existing feature set; no manifest minimum needs to change merely to resolve 1.53.1.
- Observation: The current code deliberately uses more than one runtime shape. The bridge runtime is an implicit-size multi-thread runtime; PostgreSQL execution has a dedicated current-thread runtime; the janitor lock uses a one-worker multi-thread runtime.
  Evidence: `crates/studiofs/src/runtime_bridge.rs`, `crates/studiofs-meta/src/pg_engine/runtime.rs`, and `crates/studiofs-meta/src/pg_engine/janitor.rs`.
- Observation: Foreground cache reads use `block_in_place`, while unavoidably blocking cache maintenance uses `spawn_blocking`; Tokio documentation says the former requires a multi-thread runtime and the latter cannot cancel already-started blocking work.
  Evidence: `crates/studiofs-vfs/src/runtime.rs:706-764` and the official Tokio API documentation retrieved through Context7.
- Observation: The baseline dependency metadata command attempted to access an unavailable Cargo registry source directory and failed with access denied, but the lockfile and `cargo tree --locked` independently provided the resolved versions, and focused tests used the already-built dependency artifacts.
  Evidence: baseline metadata command reported `failed to create directory ... ab_glyph-0.2.32: Access is denied`; `cargo tree --locked -i tokio` resolved Tokio 1.49.0 and the focused tests passed.
- Observation: No mounted StudioFS benchmark was started from this Windows session yet. The existing benchmark scripts require an active native mount and write artifacts under `target/perf`; a non-mounted invocation is not performance evidence.
  Evidence: `tools/perf/validate-bench-windows.ps1` requires `-MountPoint` and `studiofs devbench` resolves an active mount before running.
- Observation: The targeted resolver changed five package versions and added one package record: Tokio, tokio-macros, mio, socket2, and libc moved versions, and syn 3.0.4 was added. It also rewrote eight `windows-sys` dependency references in otherwise unchanged package records to older already-locked variants; the updated socket2 record separately moved its own `windows-sys` edge from 0.60.2 to 0.61.2, without changing any `windows-sys` package version.
  Evidence: `git diff -- Cargo.lock` and package-key comparison show only `libc@0.2.182 -> 0.2.189`, `mio@1.1.1 -> 1.2.2`, `socket2@0.6.2 -> 0.6.5`, `tokio@1.49.0 -> 1.53.1`, `tokio-macros@2.6.0 -> 2.7.2`, and added `syn@3.0.4`; the eight otherwise unchanged package references occur in `dirs-sys`, `errno`, `jiff`, `nu-ansi-term`, `quinn-udp`, `rustix 1.1.3`, `tempfile`, and `winapi-util`.
- Observation: Tokio 1.53.1 carries cross-platform and synchronization fixes, while the 1.52.x history includes reverts for a `spawn_blocking` hang regression and LIFO slot-stealing performance impact. The candidate therefore needs repeated measurements and must not be presented as an automatic speedup.
  Evidence: `tokio-1.53.1/CHANGELOG.md` lists the Windows signal fix, mpsc receiver/permit wake fixes, the 1.52.1 `spawn_blocking` revert, and the 1.52.2 LIFO slot-stealing revert.

## Context and Orientation

The repository is `E:\dev\studiofs-cli`, a Rust 2024 workspace. The root
`Cargo.toml` owns the workspace Tokio dependency and currently requests the
features `rt-multi-thread`, `time`, `sync`, `macros`, `fs`, `io-util`, `net`,

1.49.0 and the candidate lockfile resolves Tokio 1.53.1.

The runtime-critical source paths are:

- `crates/studiofs/src/runtime_bridge.rs` creates the shared multi-thread
  runtime used by synchronous platform bridge entry points.
- `crates/studiofs-meta/src/pg_engine/runtime.rs` creates the named
  current-thread PostgreSQL runtime and adapts synchronous calls with
  `block_in_place` when the caller is already on a multi-thread runtime.
- `crates/studiofs-meta/src/pg_engine/janitor.rs` creates a one-worker
  multi-thread runtime for the PostgreSQL janitor advisory-lock session.
- `crates/studiofs-vfs/src/runtime.rs` uses `block_in_place` for foreground
  reads whose output buffer cannot be moved and `spawn_blocking` for cache
  operations that can move to Tokio's blocking pool.
- `crates/studiofs-vfs/src/vfs/prefetch.rs` uses an MPSC ingress queue, a
  semaphore, and a `JoinSet` to bound and drain prefetch work.
- `crates/studiofs/src/cli/bench.rs` creates a default multi-thread Tokio
  runtime around the mounted benchmark workload.
- `crates/studiofs-vfs/src/vfs/config.rs` and `crates/studiofs-vfs/src/vfs.rs`
  define the unchanged StudioFS runtime tuning defaults: 300 MiB read buffer,
  prefetch concurrency 16, readahead width 64, minimum prefetch 16, prefetch
  ingress capacity 256, foreground reserve 16, QoS accept/materialize/commit/
  fetch slots 64/2/4/200, and upload worker count 20.

The baseline host is Windows 11 (`Microsoft Windows NT 10.0.26200.0`) with
Rust/Cargo 1.98.0, 24 reported processors, and PowerShell 7.6.5. The baseline

## Milestones

### Milestone 1: Freeze the baseline and build two identifiable candidates

This milestone creates two source trees and two release binaries without
changing the operator's current checkout. The baseline is the clean commit
`61c9abc74620f78081c8f47e71c8c1f02a010acc`; the candidate is the commit at the
current checkout when the commands begin. Separate Cargo target directories
prevent one build from overwriting the other, and separate worktrees let the
benchmark script record the correct git revision.
This is the first milestone of the native gate and is executed after the
candidate lockfile update and focused validation described in Milestones 2 and
3; Concrete Step 6 reaches it after Steps 1-5.

On Windows PowerShell, run from `E:\dev\studiofs-cli`:

       $repoRoot = (Get-Location).Path
       $baselineCommit = '61c9abc74620f78081c8f47e71c8c1f02a010acc'
       $candidateCommit = (git rev-parse HEAD).Trim()
       $candidateStatus = @(git status --porcelain)
       if ($candidateStatus.Count -ne 0) { throw 'candidate checkout must be clean before the A/B run' }
       $baselineWorktree = Join-Path $repoRoot 'target\sfs-667-baseline-worktree'
       $candidateWorktree = Join-Path $repoRoot 'target\sfs-667-candidate-worktree'
       $baselineTargetDir = Join-Path $repoRoot 'target\sfs-667-baseline-cargo'
       $candidateTargetDir = Join-Path $repoRoot 'target\sfs-667-candidate-cargo'
       $baselineArtifactRoot = Join-Path $repoRoot 'target\perf\sfs-667-baseline'
       $candidateArtifactRoot = Join-Path $repoRoot 'target\perf\sfs-667-candidate'
       $requiredFreshPaths = @($baselineWorktree, $candidateWorktree, $baselineTargetDir, $candidateTargetDir, $baselineArtifactRoot, $candidateArtifactRoot)
       $existingPaths = @($requiredFreshPaths | Where-Object { Test-Path -LiteralPath $_ })
       if ($existingPaths.Count -ne 0) {
           throw ('benchmark path already exists: ' + ($existingPaths -join ', ') + '; choose fresh target paths or verify and reuse it explicitly')
       }
       git worktree add --detach $baselineWorktree $baselineCommit
       git worktree add --detach $candidateWorktree $candidateCommit
       cargo build --locked --release --manifest-path (Join-Path $baselineWorktree 'Cargo.toml') --target-dir $baselineTargetDir --package studiofs --bin studiofs
       cargo build --locked --release --manifest-path (Join-Path $candidateWorktree 'Cargo.toml') --target-dir $candidateTargetDir --package studiofs --bin studiofs
       $baselineBinary = Join-Path $baselineTargetDir 'release\studiofs.exe'
       $candidateBinary = Join-Path $candidateTargetDir 'release\studiofs.exe'
       if (($baselineBinary -eq $candidateBinary) -or ($baselineArtifactRoot -eq $candidateArtifactRoot)) { throw 'baseline and candidate paths must remain distinct' }
       if (-not (Test-Path -LiteralPath $baselineBinary -PathType Leaf)) { throw 'baseline release binary was not produced' }
       if (-not (Test-Path -LiteralPath $candidateBinary -PathType Leaf)) { throw 'candidate release binary was not produced' }
       if ((git -C $baselineWorktree rev-parse HEAD).Trim() -ne $baselineCommit) { throw 'baseline worktree revision mismatch' }
       if ((git -C $candidateWorktree rev-parse HEAD).Trim() -ne $candidateCommit) { throw 'candidate worktree revision mismatch' }
       & $baselineBinary --version
       & $candidateBinary --version

The observable acceptance is that both revision checks match their declared
