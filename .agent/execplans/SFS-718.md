# Benchmark and tune catch-up page and checkpoint thresholds

This is a living ExecPlan for SFS-718. It covers measured tuning of the
PostgreSQL catch-up page and bootstrap-checkpoint freshness policies while
preserving the bounded, resumable replay and local-first serving contracts.

## Purpose / Big Picture

After this change, the existing opt-in large-history mounted scenario can be
run as a repeatable parameter matrix. Retained artifacts will contain page
fetch/apply/end-to-end timings, response bytes and event counts, checkpoint
serialization/publication timings and payload size, client/runner working-set
high-water marks, and PostgreSQL container memory samples. Production defaults
will be changed only where the retained measurements justify the change, with
the rationale and configuration knobs documented.

The benchmark is evidence collection, not a liveness replacement: a run is
successful only when the existing scenario reaches its normal mounted
convergence gates. No fixed sleep, retry-only success, synchronous remote work
on the foreground path, or checkpoint-format redesign is in scope.

## Surprises & Discoveries

- The current production page defaults are 64 complete batches and 8 MiB of
  estimated response bytes; checkpoint freshness defaults are 10,000 versions,
  64 MiB of encoded event payload, and one hour of changing-volume age.
- SFS-716 deliberately overrides the cold client to one batch per page and its
  default fixture currently exposes 32 replay batches. That is useful for
  liveness but insufficient to compare the full production matrix, so the
  benchmark profile must be opt-in and must not silently alter ordinary E2E
  acceptance semantics.
- The existing mounted `status` boundary already carries page and checkpoint
  diagnostics through the VFS snapshot. Extending those typed diagnostics is
  smaller and safer than adding a separate benchmark-only IPC protocol.
- Docker was initially inaccessible inside the default sandbox, but the
  elevated read-only engine check succeeded (`29.7.2`); native benchmark
  execution remains an environment-gated validation step.
- The first matrix showed two deterministic page=1 mounted-tree snapshot
  timeouts and one page=64 validation miss caused by sampling the cold client
  after it had already completed initial replay. The retained reports identify
  the exact phases; the harness now applies an explicitly selected benchmark
  page profile to both warm and cold clients, while the default scenario keeps
  the original warm/default and cold/page=1 behavior.
- In the corrected page matrix, page=64 completed the large-history phase in
  16.2--16.7 seconds with a largest observed response of 1.70 MiB. A 2 MiB
  byte-cap control had the same four-page shape and 16.4--17.1 second wall
  time, while a 1 MiB cap added pages and had a less stable tail.
- Triggered checkpoint measurements showed a 344,883-byte production payload.
  Version-lag 32 publication totaled 74.6--79.8 ms, while 1 MiB event-byte
  and one-second age triggers had materially larger build tails and, for the
  byte trigger, an 817 MiB client working-set high-water mark.

## Decision Log

- Decision: Keep benchmark controls in the existing SFS-716 runner and expose
  them through opt-in `STUDIOFS_E2E_*` environment variables. Rationale: the
  scenario already owns isolated fixture creation and retained status samples;
  a second workload would duplicate the hardest lifecycle logic. Date/Author:
  2026-09-21, Codex.
- Decision: Record page `query_duration_us`, `apply_duration_us`, and
  `total_duration_us` on the existing page diagnostic. Rationale: these values
  identify PostgreSQL/round-trip overhead versus local redb replay cost without
  changing the replay transaction boundary. Date/Author: 2026-09-21, Codex.
- Decision: Record successful checkpoint payload bytes plus build, publish, and
  total durations alongside checkpoint freshness diagnostics. Rationale: SFS-720
  explicitly needs monolithic checkpoint size/latency evidence, and the values
  can be updated only after the existing fenced publication path succeeds.
  Date/Author: 2026-09-21, Codex.
- Decision: Tune page batch/byte budgets and checkpoint lag/byte/age policies
  from repeated release runs on the bounded low-resource profile; do not infer a
  production value from one synthetic sample or localhost-only timing. Rationale:
  this is the SFS-718 acceptance boundary. Date/Author: 2026-09-21, Codex.
- Decision: Measure memory in the harness (runner/client process tree and the
  labeled PostgreSQL container), not by adding a product-wide allocator
  profiler. Rationale: sampled/native working-set evidence is sufficient for
  threshold selection and keeps runtime overhead out of the mount hot path.
  Date/Author: 2026-09-21, Codex.
- Decision: Apply an explicitly selected benchmark page/byte profile to both
  warm and cold clients, but preserve the original default warm/cold split when
  no benchmark environment is present. Rationale: page samples from the warm
  client must use the same budget as the measured cold client, while SFS-716's
  normal acceptance path intentionally keeps its warm client on production
  defaults. Date/Author: 2026-09-21, Codex.
- Decision: Keep the 64-batch default and reduce the default estimated response
  byte budget from 8 MiB to 2 MiB. Rationale: repeated passing runs showed the
  64-batch path had the shortest complete catch-up wall time, and a 2 MiB
  control covered the observed 1.70 MiB maximum response without binding this
  fixture. Date/Author: 2026-09-21, Codex.
- Decision: Keep checkpoint freshness defaults at 10,000 versions, 64 MiB of
  event payload, and 3,600 seconds. Rationale: lower trigger controls were
  useful measurement probes but caused more frequent checkpoint work and had
  materially worse build/memory tails; the measured payload and publication
  path remain bounded without lowering the production thresholds. Date/Author:
  2026-09-21, Codex.

## Plan of Work

First add focused tests around the public diagnostic/status boundaries. The
tests must verify that zero/default telemetry remains serializable, that the
human status format remains parseable with timing tokens, and that the page
diagnostic preserves existing batch/byte semantics. Tests should use
`..Default::default()` for unrelated fields so future telemetry additions do
not force broad fixture churn.

Add the page timings in `pg_engine::metadata_sync` around the existing bounded
PostgreSQL page fetch and local decode/apply path. Keep the PostgreSQL
transaction and redb atomic commit boundaries unchanged. Record the selected
page only after fetch and record it as the last page only after local commit;
failed pages must not look successfully applied.

Add checkpoint performance state to the existing diagnostics. Measure local
checkpoint export/serialization/hash work separately from the fenced PostgreSQL
publication call. Record only a successful publication, preserve the latest
measurement when freshness observations refresh the policy fields, and expose
no DSN, credentials, payload contents, or other secrets.

Make the large-history fixture's replay-batch count and cold-client page/byte
budgets overridable only for benchmark runs, with positive-value validation and
the current SFS-716 defaults retained when the variables are absent. Extend the
retained page samples and summary with the new timing fields and checkpoint
performance values. Keep the normal scenario's restart, moving-head, marker,
stable-head, and final read-write gates unchanged.

Add `tools/perf/sfs-718-pg-sync.ps1`. It will:

1. accept an explicit release `studiofs`/`studiofs-e2e` binary, output root,
   repeat count, and optional one-CPU/6-GB PostgreSQL constraint;
2. run a fixed matrix of complete-batch page budgets, byte budgets, and
   checkpoint lag/byte/age profiles using unique run IDs;
3. capture the exact command and non-secret environment knobs;
4. sample the runner/client process-tree working set and the labeled PostgreSQL
   container while the native scenario is running;
5. retain the scenario report, status NDJSON, samples, raw stdout/stderr, and a
   derived `summary.json`/`results.json` with medians and tail values; and
6. fail a matrix cell if the scenario itself fails, if the page tail is not
   bounded, or if required telemetry is absent.

Document the benchmark command and interpretation in `tools/perf/README.md`
and a dedicated `docs/perf/sfs-718-pg-sync-thresholds.md`. The document will
separate measured facts from selected defaults, record machine/build/service
identity, state the unavailable native gates explicitly, and preserve prior
artifacts rather than overwriting them.

## Validation and Acceptance

The implementation is complete only when the benchmark harness is repeatable,
retains exact non-secret commands and artifacts, and at least one native/service
run produces nonzero page and checkpoint observations. The selected defaults
must be justified by medians/tails from repeated release runs, not by a guessed
constant. Every run must retain enough evidence to distinguish page query time,
local apply time, end-to-end page time, checkpoint build/publication time,
payload size, client memory high-water, and PostgreSQL memory high-water.

Focused Rust tests, package checks, formatting, and diff hygiene prove the
diagnostic and harness contracts only. They do not prove WinFSP, PostgreSQL,
RustFS, or low-resource native behavior; those gates must be reported
separately with the retained run paths and exact commands.

## Idempotence and Recovery

Each matrix cell uses a unique run ID and non-overwriting `target/perf` and
`target/e2e-runs` paths. A failed cell retains its logs and diagnostics before
the next cell starts. Cleanup is limited to runner-owned resources; no broad
workspace or Docker cleanup is allowed. If the native prerequisite is missing,
stop the live matrix at the preflight boundary and report the missing gate
instead of fabricating results or changing defaults.

## Artifacts and Notes

The primary benchmark artifact is a timestamped directory under
`target/perf/sfs-718-pg-sync-*` containing `command.txt`, `matrix.json`, one
subdirectory per cell/repetition, sampled memory data, raw runner output, and
derived `summary.json`/`results.json` files. The decision document under `docs/perf/` links the selected
artifact paths and records the exact release binary identity, host/service
identity, page/checkpoint settings, and defaults selected from the evidence.

## Interfaces and Dependencies

Use the existing `PgSyncDiagnostics`/`PgSyncPageDiagnostics` public snapshot,
`studiofs status`, `MultiClientController`, SFS-716 scenario registry, Docker
labels, and PowerShell/.NET process APIs. Do not add a new runtime dependency,
change the checkpoint schema, or move PostgreSQL into the foreground serving
path. Context7 is not needed unless a changed third-party API requires current
documentation; this task is primarily repository code and measurement.
