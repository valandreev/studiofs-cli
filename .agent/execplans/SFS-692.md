# Optimize the generation-safe negative lookup fast path on Windows

This ExecPlan is a living document and follows `.agent/PLANS.md`. The
`Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes &
Retrospective` sections must be updated as work advances.

## Purpose / Big Picture

Repeated Windows metadata probes for a missing path should remain as correct as
they are now while doing less work after the negative full-path shortcut is
warmed. A successful result is observable in two ways: focused VFS tests keep
returning the exact missing component and reject stale generations, and the
release WinFSP interleaved benchmark reports lower negative-lookup latency (or
honestly records that the measured change did not improve it) without a
material regression in positive stat/open or enumeration.

## Surprises & Discoveries

- The WinFSP negative workload enters `get_security_by_name`, calls
  `resolve_path`, and reaches the already-warmed full-path shortcut. The
  current shortcut is generation- and namespace-epoch-validated before the
  cached result is used.
- A negative shortcut currently owns `Arc<[u8]>` for the missing component.
  `TwoTierCache::get_borrowed` clones the cached value on every hit, so the
  hot negative hit performs an atomic reference-count operation even though
  the path key already identifies the normalized components. The cached hit
  then constructs the required owned `String` for `MetaError::EntryNotFound`.
- The current `NormalizedPath` already performs one normalization/encoding
  pass and retains borrowed component slices. The optimization must reuse that
  representation rather than reintroducing a `Vec<String>` on a Windows
  shortcut hit.
- The existing SFS-690 instrumentation is intentionally untimed for hot-path
  attribution. Cache counters are useful evidence, but they are not a
  one-to-one callback count because Windows can issue multiple metadata calls.
- The mount-only sentinel removes the repeated
  `String::from_utf8_lossy(...).into_owned()` on a valid negative shortcut hit,
  but the 10-run native result shows that this allocation is not the dominant
  end-to-end latency component; path normalization, generation/cache locking,
  ACL work, and WinFSP callback overhead remain in the timed path.

## Decision Log

- Decision: Represent a negative full-path shortcut by its parent inode and the
  index of the missing normalized component, rather than owning a second
  `Arc<[u8]>` name.
  Rationale: the normalized path/key already contains the component bytes; an
  index makes the cache value cheap to copy, removes the negative-entry name
  allocation, and keeps the cache key and parent-generation metadata as the
  validity boundary.
  Date/Author: 2026-09-07 / Codex.
- Decision: Resolve the component name from the current normalized components
  at the cache-hit boundary and fall back to the existing component walk if an
  impossible index mismatch is observed.
  Rationale: this preserves the existing `EntryNotFound { parent, name }`
  error contract without allocating all components on the hot path, while
  avoiding an unsafe `unwrap` in production code.
  Date/Author: 2026-09-07 / Codex.
- Decision: Do not add another cache, change the epoch/generation scheme,
  bypass ACL checks, or change WinFSP error mapping.
  Rationale: SFS-692 explicitly requires the existing coherence contract and
  conservative fallback; the measured target is the cost of the existing
  negative shortcut, not a new source of cached truth.
  Date/Author: 2026-09-07 / Codex.
- Decision: Add a mount-only `CachedPathNotFound` error and resolver entry
  point for a generation/epoch-validated negative shortcut hit.
  Rationale: WinFSP only needs the existing `NotFound` status on this path;
  avoiding construction of the detailed metadata error removes a confirmed
  temporary allocation while leaving the ordinary VFS error contract and the
  bridge status mapping unchanged.
  Date/Author: 2026-09-07 / Codex.

## Outcomes & Retrospective

The implementation is correctness-safe and committed, but the latency
acceptance is not met by the retained native evidence. Focused tests pass, and
the optimized value is `Copy` with a normalized component index; the
generation/epoch checks, ACL path, deferred-directory fallback, and invalidation
paths are unchanged.

Native artifact `target/perf/sfs-680-windows-metadata-ab-20260907-175436`
contains 10 interleaved runs per side (30 samples per workload) comparing
baseline `7a38f2f8c091def4ba3c29fef677339e7aabeed9` with candidate
`16c2836a5eee395daca0be6f173b34a2e1c8a641`. For `negative_lookup`, baseline
was 22.253 ms p50 / 32.327 ms p95; candidate was 22.656 ms p50 / 31.849 ms
p95: p50 regressed 1.8% while p95 improved 1.5%. No IQR outliers were
reported on either side. The earlier 5-run artifact
`target/perf/sfs-680-windows-metadata-ab-20260907-174948` showed the same
direction: +0.4% p50 and -3.8% p95. The separate candidate attribution run
retained 2,000 path-shortcut hits, zero misses, 1,000 ACL checks, and 1,000
attribute-cache hits for the negative workload.

The candidate did not materially regress stat/open or enumeration in the
10-run confirmation (`stat` +0.4%, `open_close` 0.0%, `enumeration` -0.5%),
but SFS-692 should remain In Progress rather than be closed until a follow-up
optimization demonstrates a repeatable negative-lookup median improvement or
the issue owner explicitly accepts the p95-only result.

## Context and Orientation

`crates/studiofs-winfsp/src/context.rs` converts the UTF-16 WinFSP path and
calls the platform-neutral `NamespaceResolver::resolve_path_for_mount`. That
resolver in
`crates/studiofs-vfs/src/vfs/namespace.rs` normalizes separators, `.`/`..`,
and Windows trailing dots/spaces; it encodes the result as a full-path cache
key and validates cached entries against the namespace epoch and every captured
parent directory generation.

On a cache miss, the resolver walks components through
`StudioVfs::lookup_component_impl` in `namespace_ops.rs`. That function keeps
the existing ordering for access checks, ignored entries, deferred local
directories, dentry cache lookup, metadata lookup, and observed cache
admission. A cached negative path must continue to produce
`MetaError::EntryNotFound` for the same parent and normalized missing
component.

The shared `TwoTierCache` updates recency on a hit. The proposed change makes
the negative path-shortcut value cheap to copy; it does not remove recency
updates, cache locking, parent-generation validation, or namespace-epoch
validation.

## Plan of Work

First add a unit test in `crates/studiofs-vfs/src/vfs/namespace.rs` that
requires `PathShortcutCacheValue` to be copyable and verifies that a cached
negative path whose missing component is not the final component still reports
the same parent and component after a warm hit. Run the new test before the
production change and record the expected compile failure for the copyability
assertion. Keep the existing negative-hit, stale-generation, reset, rename,
delete-subtree, Windows normalization, ACL-hidden, and deferred-directory
tests as the semantic safety net.

Then change the negative `PathShortcutCacheValue` payload to store
`component_index: usize` instead of an owned name and derive `Copy` for the
cache value. Pass the component index while the resolver walks components, and
remove the negative-name ownership from the cache charge calculation. Add a
small `NormalizedPath` accessor for borrowed component bytes. Update the
cached-result helper so it reconstructs the missing name from the current
normalized components; if the index is unavailable, return `Ok(None)` so the
caller performs the existing full component resolution and re-establishes a
valid cache entry.

Use the borrowed normalized component slices in `resolve_path` before calling
`into_components()`. The fallback path may still materialize owned components
because the component resolver requires them, but a valid positive or negative
shortcut hit must not do so. The component-based resolver used by
`resolve_parent` must use the same index contract and preserve its existing
behavior.

Finally update direct cache fixtures and charge tests, format the changed Rust
files, run focused tests and Clippy, inspect the diff, and run the native
benchmark only after the product/test binary has been rebuilt. Keep the native
benchmark as the final acceptance gate because unit tests cannot prove the live
WinFSP path or its latency.

## Validation and Acceptance

The focused tests must prove that repeated missing paths remain NotFound,
intermediate missing components retain the same error parent/name, a create or
rename makes the old negative entry unusable, stale parent generations and
namespace resets reject old entries, ACL-hidden and deferred local directories
retain their existing semantics, and positive path behavior is unchanged.

The native result is accepted only as evidence from the rebuilt candidate
binary with interleaved ordering and retained artifacts. Compare paired
negative-lookup medians, p95/tail samples, and the cache attribution counters;
also verify that positive stat/open and enumeration do not materially regress.
If repeated measurements do not improve negative lookup, keep the correctness
and allocation reduction if it is independently justified, record the lack of
latency improvement, and do not overstate the optimization.

## Interfaces and Dependencies

`PathShortcutCacheValue::Negative` must contain the missing parent inode and a
normalized component index. `PathShortcutCacheValue` should be `Copy` so a
cache hit does not clone a heap-owned negative name. `NormalizedPath` must
provide a borrowed component-byte view for that index. Cache lookups continue
to receive the current namespace epoch and the directory-generation lookup
closure, and `PathShortcutCachePolicy::is_stale` remains unchanged.

No new dependency, metadata schema, native cache policy, or remote foreground
call is permitted by this plan. The mount-only resolver/error entry point is a
narrow adapter-facing crate-boundary hook; it does not change the existing
`resolve_path` or WinFSP status contract.
