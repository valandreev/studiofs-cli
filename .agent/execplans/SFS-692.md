# Optimize the generation-safe negative lookup fast path on Windows

This is a living ExecPlan. Keep the purpose, decisions, validation evidence,
and open acceptance state current while SFS-692 remains In Progress.

## Purpose

Reduce repeated WinFSP metadata latency for a missing path without weakening
the namespace epoch/parent-generation validation, ACL and ignored-entry rules,
deferred-directory behavior, or mutation invalidation. The result must retain
the existing ordinary VFS `EntryNotFound { parent, name }` contract and report
native A/B evidence rather than assuming a micro-optimization helped.

## Findings and decisions

- The full-path cache is generation- and namespace-epoch-validated before a
  cached value is used; this boundary remains unchanged.
- `NormalizedPath` already performs one normalization/encoding pass and keeps
  borrowed components. The negative value now indexes that representation
  instead of owning another `Arc<[u8]>` name.
- The ordinary resolver still constructs the detailed metadata error. The
  mount resolver returns the existing I/O `NotFound` category on a valid
  negative shortcut hit, avoiding a new public error variant and bridge arm.
- No second cache, ACL bypass, generation/epoch change, remote foreground call,
  retry, sleep, or native-cache policy change is allowed by this plan.

## Outcome

Focused validation is green. The retained native artifact
`target/perf/sfs-680-windows-metadata-ab-20260907-175436` used 10 interleaved
runs per side and 30 samples per workload, comparing baseline
`7a38f2f8c091def4ba3c29fef677339e7aabeed9` with candidate
`16c2836a5eee395daca0be6f173b34a2e1c8a641`.

For `negative_lookup`, baseline was 22.253 ms p50 / 32.327 ms p95 and the
candidate was 22.656 ms p50 / 31.849 ms p95: p50 +1.8%, p95 -1.5%, with no
IQR outliers. Stat/open/enumeration did not materially regress in that run.
The separate attribution run retained 2,000 path-shortcut hits, zero misses,
1,000 ACL checks, and 1,000 attribute-cache hits. The review simplification
preserves the same WinFSP status path; its post-review binary has not been
rerun natively yet.

SFS-692 should remain In Progress until a follow-up optimization demonstrates
a repeatable negative-lookup median improvement or the issue owner explicitly
accepts the p95-only result.
