# Reduce exact-key rename reconciliation work

This living ExecPlan follows `.agent/PLANS.md`.

## Purpose / Big Picture

SFS-899 reports that eight processes renaming files in separate directories are slower in aggregate than one process. The acceptance gate is a mounted Linux comparison with eight-process throughput above single-process throughput and no increase in PostgreSQL poll-worker CPU per rename. Local redb is the foreground metadata authority; its single writer serializes foreground mutations and replication apply. Remove only demonstrated unnecessary work inside that writer, preserving exact namespace identity and newer local overlays.

## Surprises & Discoveries

`run_sync_future_with_admission` already reuses `mount_runtime`, so SFS-887's per-operation runtime creation is fixed on this baseline. `RedbMetaEngine::begin_write_txn` acquires `write_txn_lock` before starting the existing begin-write metric; that metric does not measure mutex wait. Do not present it as off-CPU evidence.

`PgMetaEngine::rename_atomic` calls `mutate`, then `mutate_with_hint` (`pg_engine.rs`), which holds the shared `pending_state` mutex across the local mutation and its event-sequence reads. Thus parallel PostgreSQL-backed namespace mutations also serialize there before entering redb. That lock protects the read/apply window from overwriting unobserved local mutations; removing it without a proven replacement would violate local authority. VFS `rename_inner` performs access checks, lookups, lock checks, then synchronous `meta.rename_atomic`; no VFS namespace guard spans that entire ordinary rename path. These are source-level observations, not measured wait attribution.

`reconcile_serving_dentries_from_base_in_txn` receives exact event keys, but uses `lookup_in_opened_dentry_table`, which scans every entry in the parent on an exact miss and can resolve another spelling. The existing `lookup_exact_in_opened_dentry_table` preserves error propagation and avoids that fallback. Existing SFS-890 test counters measure directory fallback scans deterministically.

The shell reports `ls: cannot access '/dev/fuse': No such file or directory`. Mounted acceptance, poll-worker CPU attribution, and off-CPU comparison cannot be established in this environment. The Linear shared-notes tool is advertised but returns `Tool get_agent_context not found`; issue reads and comments work.

## Decision Log

Limit implementation to the demonstrated exact-key reconciliation defect and its regression. Do not change FUSE workers, runtime policy, lock ordering, transaction batching, or public metrics without mounted evidence. Keep SFS-899 open until its throughput and wait-time requirements are measured.

Review follow-up: `base_dentry_keys_for_rename_entry` also checked exact by-inode index keys with the case-insensitive helper; on a stale index key it matched a differently cased base dentry, so a replica rename preserved the old binding as a duplicate. It now uses the exact helper. The replica `RenameEntry` source check (`lookup_in_write_table` on `BASE_DENTRIES_TABLE`) and the foreground merged-readdir lookups in `txn.rs` still use case-insensitive lookup; The foreground merged-readdir lookups are left unchanged.

Second review follow-up: the replica `RenameEntry` source check now uses the exact helper; a case-variant source is resolved by the exact by-inode prior-key path. `BatchMerge::dentry` and `is_replayed_entry` keep case-insensitive base lookup: foreground lookup has no case-sensitive mode, so concurrent `Docs`/`docs` directories must still merge. Stale by-inode index rows are skipped, not deleted, because the prior-key helper is read-only; index readers other than this helper were not audited, and the index is rebuilt by snapshot restore. The remote-apply overlay pre-pass reads merged state while reconcile reads base; sharing them is an unmeasured micro-optimization and is deferred to the mounted measurement.

## Context and Orientation

`crates/studiofs-meta/src/redb_engine/replication.rs` reconciles replicated base namespace entries into the local serving view. Both the public `reconcile_serving_dentries_from_base` wrapper and `RemoteApplyCoordinator` in `pg_engine/remote_apply.rs` call the transaction-level method. The coordinator protects keys belonging to newer local overlay state. `redb_engine/txn.rs` provides both exact and case-insensitive lookup helpers; foreground case-insensitive semantics remain unchanged. `redb_engine/tests.rs` owns thread-local scan counters and local test fixtures. No schema, fixtures, exports, dependencies, or platform adapter changes are needed.
