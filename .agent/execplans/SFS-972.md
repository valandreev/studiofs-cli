# Build a PostgreSQL-first keyset-paginated GC candidate queue

This ExecPlan follows `.agent/PLANS.md` and is a living document. It describes a CLI-only path for consuming durable PostgreSQL candidates before the existing bounded S3 orphan sweep. Mounted background Janitor behavior remains unchanged.

## Purpose / Big Picture

The CLI janitor can clean objects already known to have lost their final current reference without first discovering every key in object storage. A PostgreSQL queue records candidates when replicated metadata closes the final current-reference interval. The CLI processes bounded keyset pages, rechecks A04/A05 protections, uses the existing fenced per-object deletion claim, acknowledges only confirmed deletion, and retains retryable work. S3 discovery remains the fallback for legacy or untracked objects.

## Surprises & Discoveries

- `snapshot_payload_upload_objects` already owns upload and deletion fencing, but a committed object's last-reference close only closes `snapshot_object_reachability`; the object ledger remains `published`. Thus the ledger does not itself queue ordinary superseded payloads.
- `delete_pending` is a terminal publication fence and `FINISH_UPLOADED_OBJECT_DELETION_SQL` keeps that state after either successful or retryable remote deletion. Reusing that state as candidate membership would alter publication behavior and cannot represent retry acknowledgement safely.
- The CLI's exact delete cap and bounded scan work are already present on `main` through PR #967; the canonical claim and key validation path is present through PR #961.
- Candidate page timestamps are represented as signed PostgreSQL epoch microseconds for an exact `(eligible_at, object_id)` keyset cursor; the CLI converts only the age check to whole seconds. Rust SQL bindings cast these `BIGINT` values explicitly before calling `to_timestamp`.
- Legacy successful deletion fences and partial deletions are both represented as `delete_pending` by older code. Candidate rows therefore retain an `acknowledged_at` tombstone after confirmed deletion so bounded backfill cannot enqueue a completed deletion forever. Acked rows are excluded by a partial page index.
- A candidate can also be encountered in the later S3 fallback after its queue attempt failed or was too young. The batched PostgreSQL A04 result carries queue retry/age state so fallback cannot bypass its retry delay or conservative close timestamp.

## Decision Log

- Decision: Add a separate advisory candidate table instead of overloading the upload ledger's terminal deletion state.
  Rationale: Candidate discovery must include published objects with closed current-reference intervals, while `delete_pending` must remain an irreversible publication fence. Candidate presence itself never authorizes deletion; A04/A05 eligibility and the fenced claim remain authoritative.
  Date/Author: 2026-11-09 / Codex.
- Decision: Create candidates in the same PostgreSQL transaction that applies the metadata event closing the final current reference, using a stable eligibility timestamp and idempotent `(vol, object_id)` identity.
  Rationale: A replicated local-first deletion becomes discoverable only after PG applies the event and its shared reference state; inserting in that transaction avoids a gap and duplicate events preserve the original age.
  Date/Author: 2026-11-09 / Codex.
- Decision: Treat this additive repeatable DDL as SFS-980's early schema design; do not introduce a general migration framework or pre-0.2.5 compatibility layer.
  Rationale: SFS-980 explicitly asks for schema design before finalization and implementation later; the current storage contract already uses repeatable `CREATE TABLE IF NOT EXISTS` DDL.
  Date/Author: 2026-11-09 / Codex.
- Decision: Backfill `delete_pending` rows in bounded, lock-skipping batches and convert only the two exact historical remote-deletion retry markers from `retry_wait` to terminal `delete_pending`.
  Rationale: The candidate table is advisory and A04/A05 claims remain authoritative; exact legacy failure markers prove a partial remote delete was underway, while ambiguous upload retries remain protected. The backfill repeats safely and the acknowledgement tombstone prevents completed candidates from returning.
  Date/Author: 2026-11-09 / Codex.
- Decision: Keep a durable `acknowledged_at` tombstone instead of physically deleting an acknowledged candidate row.
  Rationale: Legacy terminal ledger rows cannot distinguish a completed delete from a pending candidate. The tombstone prevents repeatable backfill from re-enqueueing successful work and a partial page index keeps acknowledged rows out of ordinary scans.
  Date/Author: 2026-11-09 / Codex.

## Context and Orientation

`crates/studiofs-meta/src/pg_engine/snapshot_reachability.rs` applies replicated metadata events to `snapshot_current_references` and `snapshot_object_reachability`. It computes `closed_object_ids` when an object loses its last current reference. `crates/studiofs-meta/src/pg_engine/schema.rs` contains repeatable PostgreSQL schema DDL. `crates/studiofs-meta/src/pg_engine/janitor.rs` owns the CLI janitor's PostgreSQL session, advisory lock, safety validation, batch A04 protections, and fenced deletion claims. `crates/studiofs/src/cli/janitor.rs` orchestrates local pending candidates and S3 discovery. An advisory candidate is a hint to try deletion, not proof that deletion is safe.

The queue key is `(vol, object_id)`, with `eligible_at`, retry eligibility, and a last error. Pages are ordered by `(eligible_at, object_id)` and continue after a cursor, so memory and SQL result sizes stay bounded. A successful delete is acknowledged only after remote deletion and PG claim completion both succeed. A failed or ambiguous operation stays durable for a later retry. Existing A04/A05 validation protects current references, snapshots, uploads, and claims.

## Idempotence and Recovery

Candidate insertion uses `(vol, object_id)` conflict handling that never resets an older eligibility time. Restart resumes from the first eligible keyset page; no in-memory cursor is treated as durable progress. Candidate rows are marked acknowledged only after confirmed S3 deletion and successful claim completion; ambiguous deletion or PG completion errors retain unacknowledged rows for safe retry. Unsupported or incomplete schema state must fail closed before any S3 deletion. Global schema-versioning, dump/load proof, and rollback instructions remain SFS-980 acceptance work.
