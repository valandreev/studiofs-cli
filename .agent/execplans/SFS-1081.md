# Scratch Layer Automatic Promotion When a Rule Is Removed (SFS-1081)

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan is maintained in accordance with [PLANS.md](file:///E:/dev/studiofs-cli/.agent/PLANS.md).

## Purpose / Big Picture

When a user or peer edits or removes `.studiofsignore` rules so existing scratch files or scratch directories under a tracked parent directory no longer match any scratch rule, StudioFS should automatically promote those entries into the tracked namespace without requiring a manual rename or copy. After this change, a bounded, rate-limited background worker subscribed to the ignore-rule "rules changed" broadcast scans affected tracked-parent scratch entries, promotes open-handle entries immediately while preserving their inode numbers and active writer state, promotes closed entries through the zero-copy promote path (`LocalDirty -> Namespace -> Upload`), checks the local base before promoting files and conflict-renames colliding files to `<name>.scratch-conflict-<client>`, leaves scratch entries inside still-scratch directories untouched, leaves directories exceeding `STUDIOFS_SCRATCH_PROMOTE_ENTRY_LIMIT` in scratch while surfacing them in `status` (`exceeds promote limit; run \`studiofs scratch promote\``), and ensures concurrent automatic promotion across clients resolves cleanly under ADR 0012 (directories merge, files resolve by last writer).

## Surprises & Discoveries

- Initial inspection: `promote_scratch` emits `RenameEntry` for the root entry, whereas ADR 0012 directory merge (`BatchMerge::rewrite` in `crates/studiofs-meta/src/redb_engine/namespace_merge.rs`) merges concurrently created directories on `AddEntry` (`AddEntry` for the directory before any `AddEntry` / `SetAttr` / `SetXattr` for its children). Therefore, automatic promotion (`promote_scratch_auto`) must emit pre-order `SetAttr` + `SetAttr(parent)` + `AddEntry` for the root entry before children, and `SetXattr` after `AddEntry`, rather than emitting `RenameEntry`.
- Sparse regular files on promotion: `apply_regular_file_overlay_mutation_in_txn` returns `(None, false)` when a non-zero-size regular file has no slice chunks (`chunks.is_empty()`), so `attr.content_epoch = attr.content_epoch.max(1)` must be applied BEFORE `Self::set_inode_in_txn(&txn, &attr)?` so `INODES_TABLE` matches the emitted `SetAttr` event.
- Foreign replication splits base tables from serving overlays: `apply_replica_serving_state` clears stale serving overlays on `PublishRegularFileBaseSlices`, while `apply_replica_events_to_base` writes `REGULAR_FILE_BASE_TABLE`. Simulating a peer `.studiofsignore` edit requires updating both before calling `drain_semantic_invalidations()`.
- Pre-promotion lookup precedence: `StudioVfs::lookup_component_impl` resolves scratch entries before tracked entries when both exist temporarily prior to promotion; after auto-promotion renames the colliding scratch entry to `<name>.scratch-conflict-<client>` and invalidates the old dentry cache entry without inserting a negative marker, lookups resolve cleanly to the tracked winner.

## Decision Log

- Decision: Add a dedicated `promote_scratch_auto` metadata operation emitting `AddEntry` (instead of `RenameEntry`) and checking for tracked name collisions inside the same redb write transaction using `<name>.scratch-conflict-<client>` (with `-2`, `-3`, ... fallback if needed).
  Rationale: Emitting `AddEntry` in pre-order guarantees two-client concurrent automatic promotion of a shared directory merges cleanly via ADR 0012 (`BatchMerge::rewrite`) and satisfies `RemoteApplyCoordinator::project_local_batch` hidden-draft semantics.
  Date/Author: 2026-11-21 / Antigravity

- Decision: Run automatic promotion in a background worker (`background_scratch_auto_promote`) subscribed to `IgnoreRules`'s `rules changed` broadcast channel, prioritizing open-handle entries immediately while pacing closed entries with a token bucket (`AutoPromoteRateLimiter`) and `qos.wait_foreground_local_io_idle()`.
  Rationale: Foreground operations never block on promotion, open handles stay valid with the same inode number and writer state, closed backlogs are bounded and rate-limited, and shutdown cancels `background_shutdown_token` and joins the worker before local dirty drain and redb close.
  Date/Author: 2026-11-21 / Antigravity

- Decision: Track `last_rule_generation` on `VfsScratchAutoPromoteSnapshot` (sampled from `IgnoreRules::rule_generation` at pass start) and emit `status` over-limit lines (`Scratch dir ... exceeds promote limit; run \`studiofs scratch promote\``) in both mounted and offline paths.
  Rationale: Waiting on `last_rule_generation` avoids pass-count races when rule-change notifications coalesce, while keeping mounted and offline CLI diagnostics aligned on the same `ScratchPromoteOverLimitEntry` structure.
  Date/Author: 2026-11-21 / Antigravity

- Decision (review follow-up): The local-base conflict rename applies only to non-directories. A scratch directory whose name is a tracked directory merges into it (ADR 0014 "Conflicts and orphans", ADR 0012): `merge_auto_promote_directory` moves its children as scratch rows (no events), merges nested directory collisions recursively, renames any other colliding child to `<name>.scratch-conflict-<client>`, and removes the emptied scratch directories. The pass then promotes the moved children as ordinary candidates. Descendants that still match a rule stay scratch when their directory is promoted.
  Rationale: The outcome no longer depends on timing (sequential = conflict copy, concurrent = merge); directories merge in both cases.
  Date/Author: 2026-11-21 / Claude

- Review follow-ups filed: SFS-1125 (shared promote path), SFS-1126 (`TOTAL_INODES` in explicit promote), SFS-1127 (`studiofs scratch promote` command), SFS-1128 (pass after mount), SFS-1129 (stale over-limit status).

## Validation and Acceptance

Focused nonzero tests must verify: rule removal promotes scratch entries without copying payload and with unchanged inode numbers; open handles promote immediately and continue writing/flushing; adding a rule never modifies existing tracked entries; partial rule changes leave still-ignored entries and entries inside still-scratch directories untouched; peer rule removal via foreign apply triggers promotion; directories exceeding the promote limit stay scratch and appear in both mounted and offline `status` (`exceeds promote limit; run \`studiofs scratch promote\``); taken names rename to `<name>.scratch-conflict-<client>`; a two-client ADR 0012 test converges both clients' concurrently auto-promoted directories and files; and progress is observed via `watch`/`broadcast` channels with zero fixed sleeps.

## Idempotence and Recovery

All redb transactions for `promote_scratch_auto` are atomic: on failure or `TargetChanged`, scratch tables and tracked tables remain untouched; on commit before upload submission, startup recovery (`StartupReplayCoordinator`) enqueues existing local objects because `attr.upload_state` and overlay metadata are persisted inside the same transaction.
