# Read cold ranges from compressed payload objects

This living ExecPlan follows `.agent/PLANS.md`. Keep Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective current.

## Purpose / Big Picture

A cold random read of up to 256 KiB within one logical block can retrieve the requested bytes from a compressed remote fragment without downloading or decoding the whole fragment. The data-store tests measure remote byte ranges and compare returned bytes with the original payload.

## Surprises & Discoveries

The legacy range reader can locate target ciphertext from the fixed envelope prefix and the requested logical offset. In v3 the stored offset depends on preceding chunk lengths in the encrypted seek table. The reader learns those lengths after it authenticates the first frame.

## Decision Log

- On 2026-11-23, use the existing SFEC frame authentication and STFS seek-table validation. The format already carries the lengths and offsets needed for a bounded fetch.
- On 2026-11-23, correct ADR 0015's description of v3 request ordering. Extending the frame-zero GET to an adjacent target would require the stored offsets before their authenticated source has arrived. Reuse frame-zero bytes and issue the optional target GET after validation. Keep the v2 merge and concurrent-read behavior.

## Outcomes & Retrospective

Canonical v3 reads use two GETs when all selected stored bytes are in frame zero and three otherwise. The tests compare the exact bytes transferred with the union of ciphertext frames needed to serve the read. They also verify that adjusting authenticated frame geometry, corrupting the seek table or a selected frame, and supplying an authenticated malformed table cause the expected failures.

The production writer uses 64 KiB frames for v3. A v3 object made outside that writer with legacy 1 MiB framing can incur a speculative GET from the v2 optimization. The complete reader supports both frame sizes. Validation used an in-memory object store on Windows. Mounted testing belongs to the separate mounted compression scenario.

## Context and Orientation

`crates/studiofs-data/src/store.rs` implements the remote data-store entry point `DataStore::get_payload_range_by_key_with_stats`. SFEC is the encrypted envelope with a fixed 40-byte prefix followed by a variable header and independently authenticated frames. STFS is the object inside that envelope. Version 2 stores logical bytes directly. Version 3 puts a seek table after the STFS header. The table describes each chunk's stored length and whether it uses raw bytes or Zstd. The version 3 writer uses 64 KiB SFEC frames, so frame zero holds the entire seek table. `crates/studiofs-data/src/object.rs` defines and validates that table. `crates/studiofs-data/src/compression.rs` owns chunk decoding.

## Validation and Acceptance

Read 4 KiB at the start, middle, end, and across a chunk boundary. Compare each result with the source and observe at most three reads. The transfer consists of the prefix, header tail, first frame, and any additional frames covering the selected stored chunks. A partial read of a sufficiently large object transfers fewer bytes than a complete fetch. Tampered seek-table ciphertext, a selected frame, or the envelope's frame size cause an authentication failure. Existing range tests cover v2 offsets, boundary clamping, and transfer bounds.
