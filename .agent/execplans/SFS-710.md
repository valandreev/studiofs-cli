# SFS-710: Expose PG catch-up and checkpoint progress diagnostics

## Purpose

Expose the existing PostgreSQL synchronization state through structured,
read-only diagnostics and `studiofs status`, so a long catch-up is observable
without inspecting the database while preserving the local-first serving and
write-authority contracts.

## Surprises & Discoveries

- `PgSyncStatus` already supplies the lifecycle and allocator gate, so it
  should remain a small `Copy` value used by mutation enforcement.
- `MetadataCheckpointFreshnessDiagnostics` already contains checkpoint/head,
  lag, refresh state, and refresh reason; the new snapshot can reuse it instead
  of duplicating those fields.
- `VfsSynchronizationStateSnapshot` is already serialized by live diagnostics,
  so one additional field reaches the existing JSON surface without a second
  diagnostics subsystem.
- Catch-up page metadata is already available in `ForeignEventPage`; progress
  tracking only needs a small in-memory state record and must not scan the event
  log.

## Decision Log

- Keep `PgSyncStatus` unchanged and add a separate `PgSyncDiagnostics` value.
  Rationale: diagnostics need owned strings/page history while lifecycle gates
  must stay cheap and copyable.
- Store only typed, redacted failure categories and safe version/count data;
  never expose PostgreSQL URLs, credentials, or raw remote error text.
- Record the selected page as current and the successfully applied page as the
  last page. Clear the current page only after the local apply succeeds.
- Rate-limit page progress logs by monotonic time while retaining the first,
  final, and materially progressing snapshot data.
- Use the existing `MetaReplication` and VFS snapshot boundaries. Do not add
  event-log scans, a new worker, a polling loop, or synchronous remote work to
  the status path.
- Keep rebootstrap ownership with the existing replay-gap recovery state; the
  diagnostics surface reports that state but does not implement SFS-711.

## Outcomes & Retrospective

Implemented a low-cost `PgSyncDiagnostics` snapshot in `studiofs-meta` and
forwarded it through the runtime metadata facade and VFS synchronization
snapshot. The snapshot reports lifecycle, local/frozen/remote versions, lag,
checkpoint freshness, current/last replay pages, allocator authority, safe
last-error categories, source connectivity, sync error count, and
rebootstrap-required state. `studiofs status` now renders the PostgreSQL sync

## Context and Orientation

`studiofs-meta` owns `PgMetaEngine`, the startup lifecycle, page fetch/apply,
checkpoint freshness, and typed sync errors. `MetaReplication` is the existing
capability boundary consumed by `studiofs-vfs`. `StudioVfs` exposes a runtime
synchronization snapshot, which `studiofs` includes in live diagnostics. The
CLI status command opens the metadata engine and is the user-facing status
surface for an unmounted database.

The relevant contracts are `docs/pg-sync-contract.md`,
`docs/diagnostics-workflows.md`, and the scoped `AGENTS.md` files for
`studiofs-meta` and `studiofs-vfs`.

## Validation and Acceptance

- The snapshot identifies every lifecycle named by the issue, including
  allocator-pending, degraded, and replay-gap/rebootstrap-required state.
- Applied and page progress are observable and monotonic for a long catch-up.
- A meaningful typed sync failure is visible, redacted, and cleared or replaced
  after a successful sync.
- Checkpoint version, refresh-needed state, and refresh reason are visible.
- Status collection performs only local atomic/mutex reads; no remote query or
  event-log scan is added.
- Focused tests are nonzero and pass; package check, Clippy, formatting, and
  diff checks pass.
- PostgreSQL-backed ignored tests and mounted FUSE validation remain separate
  environment gates and are reported as such if unavailable.

## Idempotence and Recovery
