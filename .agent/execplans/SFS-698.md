# Remove remote catch-up from `PgMetaEngine` open

This ExecPlan is a living document and follows `.agent/PLANS.md`.

## Purpose / Big Picture

Opening a valid local PostgreSQL-backed metadata database must return a usable
local serving engine without replaying an arbitrarily large PostgreSQL event
tail. After this change, a stale local client can open from its persisted
`redb` state, report a non-live synchronization lifecycle, and let the
existing background/manual replication path catch up later. The behavior is
observable through a focused PostgreSQL lifecycle test that holds the event-log
table locked: `open()` must return without performing the old repeated
event-tail timeout sequence.

## Surprises & Discoveries

- Observation: `sync_metadata_to_current_head` is also used by snapshot-reachability backfill, so the helper itself must remain; only its startup callers can be removed.
  Evidence: `crates/studiofs-meta/src/pg_engine/snapshot_reachability.rs` calls the helper independently of `open_with_options`.
- Observation: `open_with_options` currently performs more than event replay: it may import a startup checkpoint, reserve a fresh-client slot, bootstrap allocator state, and backfill snapshot reachability.
  Evidence: `crates/studiofs-meta/src/pg_engine.rs:929-1075`.
- Observation: the lifecycle already has `CatchingUp` and the background poll already calls `sync_metadata_with_source`, so SFS-698 can reuse those seams without adding a new worker or abstraction.
  Evidence: `crates/studiofs-meta/src/pg_engine/lifecycle.rs:242-295` and `crates/studiofs-meta/src/pg_engine/replication_api.rs:42-45`.
- Observation: the locked-event-log regression still incurs one bounded wait in the open path, but the old repeated replay incurred two waits and exceeded the test bound.
  Evidence: the pre-change test failed at 2.212 seconds; the post-change focused test passed with the same 1-second command timeout and 1.5-second assertion bound.

## Decision Log

- Decision: Keep the `sync_metadata_to_current_head` helper for non-startup callers and remove only its calls from engine construction.
  Rationale: deleting the helper would break the existing snapshot-reachability path and would expand SFS-698 beyond startup behavior.
  Date/Author: 2026-09-11 / Codex with user approval.
- Decision: Observe the remote metadata head at most once during open, but never query `event_log` from the constructor.
  Rationale: one bounded head observation lets an existing stale client enter `CatchingUp`; event-tail replay remains a later replication operation.
  Date/Author: 2026-09-11 / Codex with user approval.
- Decision: Preserve the repair snapshot import as a local-serving recovery prerequisite, but do not replay the event tail or backfill remote reachability during open.
  Rationale: a repair marker means the local graph is not yet trusted, while remote replay is explicitly outside the open boundary.
  Date/Author: 2026-09-11 / Codex with user approval.
- Decision: Run snapshot-reachability ledger backfill after successful background replication instead of during construction.
  Rationale: removing the startup call must not remove the existing conservative janitor bootstrap; the background poll is already the explicit non-constructor replication seam.
  Date/Author: 2026-09-11 / Codex.

longer replays the remote event tail, reserves fresh-client authority, or
backfills snapshot reachability during construction. Reachability backfill is

## Context and Orientation

`crates/studiofs-meta/src/pg_engine.rs` owns `PgMetaEngine::open_with_options`.
It opens the local `RedbMetaEngine`, validates local/remote format information,
restores persisted replay cursors, constructs the wrapper, and currently runs
remote snapshot/catch-up work before returning. `PgSyncLifecycle` in
`crates/studiofs-meta/src/engine.rs` distinguishes local readiness from
catch-up and write authority. `crates/studiofs-meta/src/pg_engine/lifecycle.rs`
starts the background polling worker, while
`crates/studiofs-meta/src/pg_engine/metadata_sync.rs` applies foreign event
batches.

The local replay cursor is the last remote event-log batch version applied to
local `redb`. The remote head is the current `metadata_state.version`. A stale
client has a local cursor below that observed head. `CatchingUp` permits local
reads but does not grant new mutation authority.

## Plan of Work

First add one ignored PostgreSQL regression in
`crates/studiofs-meta/src/pg_engine/tests/lifecycle.rs`. It creates a test
volume, seeds an existing local database with a persisted client slot and an
older local cursor, advances the remote metadata head, and holds an
`ACCESS EXCLUSIVE` lock on `event_log`. The old implementation blocks through
repeated bounded operations in `sync_metadata_to_current_head`; the test
therefore fails before the production change. It will assert that
opening returns promptly, that the stale engine is `CatchingUp`, and that local
state remains available. The test must use a readiness channel for the SQL
lock, not a coordination sleep.

Then update `PgMetaEngine::open_with_options` in
`crates/studiofs-meta/src/pg_engine.rs`:

1. Keep local redb opening, format/schema validation, persisted cursor loading,
   and required identity/client-slot checks.
2. Keep the repair-only checkpoint import needed to rebuild an unsafe local
   graph, but remove its event-tail replay and remote reachability backfill.
3. Keep the bounded startup checkpoint import for a zero-version local state,
   but remove `sync_metadata_to_current_head` from the normal branch.
4. After the engine exists, make one best-effort bounded remote-head
   observation. Store that head and transition an established client to
   `CatchingUp` when its local cursor is behind. If the observation is
   unavailable, preserve valid existing-client local/offline behavior.
5. Keep a fresh client non-live while its durable pending marker remains. Do
   not reserve its client slot, mint allocator state, clear the marker, or
   mark it live from the open path; those gates belong after catch-up.
6. Continue restoring pending local event state and starting the existing
   background workers. The existing `sync_metadata_with_source` path remains
   the runtime replication entry point.

The helper in `metadata_sync.rs` remains unchanged unless compilation or a
focused test proves that a separate startup-only wrapper is needed. Update
comments that still describe the old transitional fast-forward behavior.

## Validation and Acceptance

The regression is accepted when a stale local database opens while the
`event_log` table is locked within the focused 1.5-second bound, and its
lifecycle is `CatchingUp` rather than `Live`. Existing local metadata must
remain readable. The focused lifecycle suite must retain the existing repair
marker and fresh-client write-gate behavior. No constructor path may call
`sync_metadata_to_current_head`, and the helper must remain available only to
explicit non-constructor operations.

## Idempotence and Recovery

The test creates a unique PostgreSQL volume and temporary local database, then
removes the volume through the existing `PgTestVolume` cleanup. If a test
fails while holding the SQL lock, release the channel and join the lock thread
before retrying. No repository reset or destructive checkout is needed; all
changes are confined to the plan, metadata engine, and focused tests.
