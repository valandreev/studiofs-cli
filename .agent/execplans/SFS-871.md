# Make fsck orphan graph cleanup atomic with GC scheduling

This living ExecPlan follows `.agent/PLANS.md`.

## Purpose / Big Picture

An interrupted fsck repair must retain the object identifiers needed for garbage collection (GC). The repair currently commits removal of the regular-file graph (the inode's payload references) before writing pending-deletion markers. A failed marker write loses that information. The new operation commits graph removal and every marker together in the local redb database; an error leaves the graph available for retry.

## Surprises & Discoveries

The existing graph-only operation and pending-deletion markers intentionally create no PostgreSQL remote backlog. VFS and undo recovery still schedule deletion separately and retain the same pre-existing crash window. This is a deferred correctness issue, not a mitigation: migrate orphan-handle cleanup and undo recovery to timestamped removal in a separate lifecycle change, and retain the fallback-ID scheduling needed by the mixed VFS cleanup path. SFS-871 guarantees atomic GC scheduling only for timestamped calls. Linear's optional get_agent_context tool is advertised but unavailable; the issue and repository remain readable.

## Decision Log

The subsequent static review is recorded with dispositions in `docs/code-reviews/SFS-871-fsck-orphan-gc-atomicity.md`. Preserve the user's explicit Option API and deleted passthrough/stub tests. Move the fsck GC report count after inode-removal success; do not change the existing count of successfully handled orphan attempts or introduce a new USED_SPACE accounting policy. Correct the test name and remove dependence on redb's internal corruption-error wording. Defer the pre-existing clock fallback and USED_SPACE repair issues with the non-atomic runtime/recovery paths. Do not split the atomic repair into transactions to address speculative live-mount latency: fsck's writable redb open excludes an active writer for the same database.

Use `MetaPayloadObjects::remove_regular_file_graph(ino, deletion_timestamp: Option<i64>)`. Fsck passes `Some(timestamp)` to queue unique object IDs before commit. Existing graph-only callers pass `None`. This supersedes the initially implemented dedicated aggregate capability after review requested less API scaffolding. There is no new trait method or new adapter implementation. Existing PostgreSQL/read-only implementations and the VFS runtime forward the argument. Remove passthrough/stub/reopen tests requested by review; keep the meaningful marker-insertion fault regression and combine fsck failure and success checks in one fixture. No schema, event codec, dependencies or mounted callback behavior changes are needed.

## Validation and Acceptance

An injected failure at the pending-deletion table must leave graph rows, object reference counts and local event position unchanged. After removing the failure, retry must remove the graph and persist one marker per unique object ID. CLI tests must show repair counters advance only on successful graph-and-marker completion. Existing graph-only PostgreSQL backlog tests must retain their behavior; the new operation must persist local GC bookkeeping without creating remote backlog, through the normal adapter mutation path.

## Idempotence and Recovery

The write transaction rolls back all graph and marker mutations on failure. Retrying after success sees an empty graph and queues no additional IDs. Temporary failure backends and databases are test-only; no production fault hook is added. Unrelated user changes must be preserved.
