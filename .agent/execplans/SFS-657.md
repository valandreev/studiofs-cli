# Avoid repeated full-map scans during directory tracker eviction

This is a living ExecPlan for SFS-657. It follows `.agent/PLANS.md`; the
`Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes &
Retrospective` sections must be kept current until the implementation is
complete.

## Purpose / Big Picture

`studiofs-vfs` keeps a bounded in-memory tracker for directory read-ahead.
When a new directory would exceed the cap, the tracker evicts the least
recently touched directories. The current implementation finds one victim by
scanning the complete concurrent map, removes it, and repeats. A concurrent
burst can therefore perform one full scan for every excess directory.

After this change, one oversubscribed eviction pass will select all currently
needed victims in a single map traversal, while retaining the exact
generation-aware reverse-map cleanup implemented by SFS-658. The capacity
limit and least-recently-used behavior remain observable through focused unit
tests, including concurrent directory registrations. The result is entirely
platform-neutral and does not require FUSE, WinFSP, macFUSE, PostgreSQL, or
object storage.

## Surprises & Discoveries

- Observation: the current `DirAccessTracker` type already contains the
  generation-safe SFS-658 cleanup paths, so SFS-657 can reuse them without
  changing reverse-map identity.
  Evidence: `remove_child_mapping_if_same` uses `child_to_dir.remove_if`, and
  both readdir refresh and LRU cleanup pass `(dir_ino, readdir_touch)` to it.
- Observation: a normal sequential registration exceeds the cap by one, but
  concurrent registrations can leave several excess entries before any one
  eviction caller finishes.
  Evidence: `on_readdir_entries` inserts the new directory before calling
  `evict_lru_if_needed`; the current eviction loop calls
  `dirs.iter().min_by_key(...)` on every iteration.
- Observation: a bounded heap is sufficient for the required victim set and
  avoids allocating or sorting the complete map when the overshoot is small.
  Evidence: selecting the oldest `K` entries needs at most `K` heap entries;
  replacing the newest selected entry keeps the heap bounded while scanning
  the map once.
- Observation: the red regression can observe selection-pass count through
  the existing test hook without adding production counters.
  Evidence: the initial eight-directory red fixture with a temporary cap of
  two made the old loop invoke the hook six times; the final fixture uses
  1,024 directories and still requires one invocation for its 1,022 victims.
- Observation: the existing LRU race remains compatible with batched removal;
  a touched candidate is skipped and the next current victim is selected.
  Evidence: the focused `readahead` filter passed with both
  `test_lru_cleanup_does_not_remove_recently_touched_directory` and the new
  batching regression green.
- Observation: the LRU race from SFS-658 remains valid after adding an
  eviction coordinator because `on_child_read_limited` still updates
  `last_touch` without taking the coordinator.
  Evidence: the coordinator is acquired only inside `evict_lru_if_needed`,
  while foreground child reads mutate the per-directory DashMap entry directly.

## Decision Log

- Decision: serialize only `evict_lru_if_needed` with a
  `parking_lot::Mutex<()>`.
  Rationale: concurrent eviction callers should coalesce an overshoot and
  avoid duplicate selection work, but ordinary child reads must not acquire a
  global lock or pay eviction contention. A fast capacity check returns before
  locking when no eviction is needed; the loop rechecks after lock acquisition
  because another caller can repair the overshoot first.
  Date/Author: 2026-08-28 / Codex.
- Decision: select victims with a bounded `BinaryHeap<(u64, Ino)>` keyed by
  `(last_touch, dir_ino)`.
  Rationale: the heap keeps only the oldest `K` candidates, where `K` is the
  current excess. The inode tie-breaker makes equal-touch selection stable
  without changing the primary LRU ordering.
  Date/Author: 2026-08-28 / Codex.
- Decision: retain conditional state removal and retry only after a selected
  candidate is no longer current, or after concurrent insertion leaves the map
  over capacity.
  Rationale: a `last_touch` change means a foreground read won the race and
  the candidate must not be deleted from the observed snapshot. A fresh
  selection is then required to preserve the hard cap.
  Date/Author: 2026-08-28 / Codex.
- Decision: do not add a maintained LRU index in this issue.
  Rationale: SFS-657 specifically requires eliminating repeated full scans in a
  K-entry overshoot. A maintained index would add update and cleanup coupling
  to every directory read; it is justified only by release measurements that
  show one bounded selection scan remains materially expensive.
  Date/Author: 2026-08-28 / Codex.

## Context and Orientation

The only production file expected to change is
`crates/studiofs-vfs/src/readahead.rs`. `DirAccessTracker` owns two DashMaps:
`dirs` stores one `DirPrefetchState` per tracked directory, and `child_to_dir`
maps a child inode to the directory and `readdir_touch` generation that
registered it. `last_touch` is a separate monotonic stamp used only for LRU
recency. SFS-658 made all reverse-map cleanup conditional on the generation;
that contract must not be weakened.

`on_readdir_entries` replaces a directory snapshot, registers its children,
and then calls `evict_lru_if_needed`. `on_child_read_limited` updates
`last_touch` for a foreground read and must remain free of the eviction lock.
`evict_dir` and readdir refresh continue to remove reverse mappings through
`remove_child_mapping_if_same`.

The implementation will use `parking_lot::Mutex<()>` as a slow-path
coordinator. It protects the eviction selection/removal sequence from another
eviction caller, not from foreground reads. A bounded max-heap stores the
newest member among the currently selected oldest candidates. For each map
entry, a candidate replaces that heap member only when its `(last_touch,
dir_ino)` key is older. The resulting candidates are processed in ascending
key order for deterministic cleanup.

## Plan of Work

First add a test-only `debug_tracked_dir_count` accessor and two focused tests
in the existing `dir_prefetch_tests` module. The batching test will populate
more directories than the eventual cap while the temporary cap is large, then
lower the cap and invoke the private eviction method. The existing test hook
will count victim-selection callbacks; the current implementation will fail
because it invokes the hook once for each victim/full-map scan instead of once
for the batch. The test will also assert that only the newest directories
remain. The concurrent-capacity test will release several registration threads
from a barrier at once and assert that the tracker ends with exactly the
configured number of directory states.

Next add the eviction coordinator field and initialize it in
`new_with_capacity`. Replace the `min_by_key` loop with a loop that computes
the current excess, selects at most that many candidates using a bounded
`BinaryHeap`, and conditionally removes each directory with the observed
`last_touch`. Cleanup of a removed state will continue to call
`remove_child_mapping_if_same` with its observed `readdir_touch`. A failed
conditional removal will cause a fresh selection; no ordinary child-read path
will lock the coordinator.

Finally run the new tests first in debug mode, then the focused `readahead`
unit filter in debug and release mode. The release runs will include the
large oversubscription and concurrent-registration tests so the plan records
whether the algorithmic change is visible without relying on debug timings.
Run the targeted static checks required by the repository, but do not run the
full workspace suite.

The private eviction helper may be decomposed into a selector with the
