# SFS-932 generic/089 mount-table lock regression

This living plan follows `.agent/PLANS.md`.

## Purpose / Big Picture

xfstests generic/089 runs `src/t_mtab`, which imitates util-linux's old
`/etc/mtab` locking. Each process creates `t_mtab~<pid>`, hard-links it to
`t_mtab~`, unlinks the pid name, and treats a successful `link()` as owning the
lock (`EEXIST` means someone else holds it). The owner copies `t_mtab` to
`t_mtab.tmp`, renames it over `t_mtab`, and unlinks `t_mtab~`. On StudioFS the
lock name vanished while held, so owners hit `Cannot remove lock file: ENOENT`,
two processes owned the lock at once, and `rename(t_mtab.tmp, t_mtab)` failed
with `ENOENT`. After the change the same replay completes on a local Linux FUSE
mount.

## Surprises & Discoveries

- The failing build `c6435f07` predates the SFS-927 self-replay fixes, but the
  failure reproduces unchanged on `main` `e41e7088`.
- The single-process phase already failed: unlinking `t_mtab~<pid>` (an empty
  unpublished draft with `nlink` 2) emitted inode-removal events. Self replay's
  pending-suffix reducer turns `RemoveAttr` into removal of every alias, so the
  lock name disappeared later.
- Concurrency added three independent defects. The PG engine serializes local
  mutations under `pending_state`, so the redb `link_atomic` race does not
  reproduce through a PG mount, but it is real for the redb engine.
- The mount trace showed `heal_orphaned_dentry` deleting the live lock name.
  FUSE sends `RELEASE` asynchronously after `close()`, so the pid name is often
  unlinked while its create handle is still open. `unlink_with_open_handles`
  marked the inode orphan regardless of `nlink`, and the last close then ran
  deleted-inode cleanup (`remove_attr`) on an inode still reachable through
  `t_mtab~`. Outside xfstests this loses a hard-linked file's inode and data.
- Once two holders exist, each owner's `unlink("t_mtab~")` removes the other's
  lock, so violation counts are a chain reaction; only the first mismatch is
  diagnostic.

## Decision Log

- Decision: Guard the empty-draft unlink branch with `nlink == 0` instead of
  changing replay reduction.
  Rationale: `deleted_before_publish` already requires `nlink == 0`; the draft
  branch was the only inode-removal path without it.
  Date/Author: 2026-10-31 / Claude Opus 5.5.
- Decision: Keep the epoch-guarded dentry admission rather than dropping
  cache inserts after mutations.
  Rationale: Uncontended create/unlink keep their cache hits (WinFSP resolves
  paths per callback); a contended record falls back to a fresh redb lookup.
  Date/Author: 2026-10-31 / Claude Opus 5.5.
- Decision: Do not change the `LocalOnlyDeletion` pending hint.
  Rationale: Guarding it by `nlink` had no measurable effect on the mount and
  no red test; the trace pointed elsewhere.
  Date/Author: 2026-10-31 / Claude Opus 5.5.

## Context and Orientation

Unlink events are written in `crates/studiofs-meta/src/redb_engine/fs_ops.rs`
(`append_unlink_events`, `execute` for `NamespaceDeleteTxn`, `link_atomic`).
VFS namespace callbacks live in `crates/studiofs-vfs/src/vfs/namespace_ops.rs`;
the VFS dentry cache and `NamespaceMutationOps` live in
`crates/studiofs-vfs/src/vfs/namespace.rs`. Orphan cleanup on last close is
`cleanup_orphan_on_last_handle_close` in `crates/studiofs-vfs/src/vfs/sync_ops.rs`.
