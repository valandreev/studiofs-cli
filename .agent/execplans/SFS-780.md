# Reuse speculative VFS read-window storage

This ExecPlan follows `.agent/PLANS.md` and is maintained as work proceeds.

## Purpose / Big Picture

Sequential reads smaller than the 4 MiB VFS read window currently allocate and zero a new large buffer on each window miss. Reuse initialized storage without changing cached `Bytes` ownership, hole handling, EOF, or read-ahead owner switching.

## Surprises & Discoveries

The allocation is in `crates/studiofs-vfs/src/vfs/io_ops.rs`, not the `sync_ops.rs` wrapper named by the issue. Codebase Memory reported changed source metadata; current source was read directly. There was no running StudioFS process at discovery; the user authorized `mount test Z:`. Windows devbench reports throughput and RSS; global allocation counters are published every second in the host-local cache `write_path_observability.json`. Its per-phase allocator values are cumulative snapshots, not interval deltas. A separate read-only pass with timestamp-gated bracketing is needed. Memory bandwidth is not directly instrumented.

## Decision Log

Reuse the existing BufferPool with an initialized read lease whose owner is retained by `Bytes::from_owner`. Keep initialized buffer length when returning it; ordinary write acquisition still clears its logical length. A separate VFS read pool retains at most two buffers, each at most 4 MiB. Active windows remain bounded per handle as before. This avoids unsafe output APIs and preserves the old cache on read failure/cancellation. The executor overwrites each returned range, including explicit holes and short payload tails. Do not change window geometry or remove the cache.

## Validation and Acceptance

Tests must prove reuse preserves the allocation pointer and existing initialized contents, clones delay recycling, only the written prefix is exposed, Drop recycles cancelled/error leases, and retained buffers respect count/capacity limits. Real VFS reads must return dense bytes and zeros for holes despite stale pooled contents and leave caller tails untouched at EOF. Compare release pool benchmark against fresh zeroed 4 MiB Vec allocation; this is mechanism evidence only. A mounted benchmark additionally needs rebuilt before/after binaries, WinFSP mounts and identical data/cache/configuration. Its request size must be smaller than 4 MiB to exercise speculative windows. Preserve reports under `target/perf/` and record unavailable instrumentation honestly.
