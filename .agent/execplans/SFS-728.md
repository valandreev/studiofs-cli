# Prove Large-History Catch-Up Restart and Cold-Client Writes

This ExecPlan is a living document governed by `.agent/PLANS.md`. Keep its

## Purpose / Big Picture

The mounted large-history scenario must demonstrate that a cold client has
applied replay data beyond its checkpoint, gracefully restarts while still
catching up, and resumes from the durable replay cursor. It must also prove
that the cold client can create and write a file whose contents become
readable on its peers. The existing registered scenario is
`mounted-large-history-cold-bootstrap-convergence`.

## Surprises & Discoveries

- Observation: the forced-crash experiment reached the redb immediate barrier,
  but its post-restart cursor fell from 13 to 9 and redb reported repair.
  Evidence: run `20260924T120108Z-b6a547` recorded a failed cursor-resume check.
  The issue asks for a graceful restart, so this crash path was removed.
- Observation: one `ACCESS EXCLUSIVE` lock on PostgreSQL `event_log` can hold
  catch-up between page queries. Reacquiring it after an observed partial
  cursor freezes the cursor while fsync and graceful restart run.
- Observation: holding the gate through graceful shutdown blocks the
  background page query used by shutdown draining.
  Evidence: run `20260924T122100Z-sfs728-graceful` logged `postgres event_log
  page select failed: connection closed`, a local metadata drain warning, and
  redb repair during shutdown. Release the gate before shutdown and reacquire
  it only before the sync barrier.
- Observation: reacquiring the gate after remount may wait through many pages
  because one catch-up request can apply a page batch before releasing its SQL
  locks.
  Evidence: run `20260924T123200Z-sfs728-graceful2` first observed post-restart
  cursor 14, then the runner's extra gate acquisition delayed until the cursor
  reached 40. Validate the first status sample instead of reacquiring there.
- Observation: Windows `FlushFileBuffers` needs a writable handle. The runner
  therefore syncs the local metadata database directly with read/write access
  on non-macOS hosts; the macOS path uses a read-only mounted file handle so it
  does not request a mount write while the cold client is catching up.
- Observation: the reported duplicate macFUSE signal-handler guard is not
  reachable in the normal lifecycle. An atomic `compare_exchange` grants
  ownership to only one watcher; later installs receive `Ok(None)`.

## Decision Log

- Decision: keep the ticket's graceful restart contract and do not use
  `force_kill` for this scenario.
  Rationale: forced termination tests redb crash repair, and the observed repair
  obscures the requested catch-up restart behavior.
  Date/Author: 2026-09-24 / Codex.
- Decision: reacquire the existing PostgreSQL replay gate after observing a
  partial cursor, verify the cursor is unchanged after metadata sync, then
  release the gate during graceful shutdown.
  Rationale: the gate freezes the cursor during sync, while releasing it lets
  shutdown finish its remote metadata drain. The first status sample after
  remount directly proves partial replay resumed; reacquiring then can block on
  a full replay page batch and miss the observable partial state.
  Date/Author: 2026-09-24 / Codex.
- Decision: reject the review suggestion to `mem::forget` a duplicate signal
  handler owner.
  Rationale: the existing atomic installation guard prevents the duplicate
  owner state; leaking a handler would hide an unreachable state and prevent
  normal restoration.
  Date/Author: 2026-09-24 / Codex.
- Decision: retain strict partial-cursor and within-session progression checks.
  Rationale: the runner now records the partial cursor before graceful
  shutdown and requires the first post-restart cursor to be at least that value;
  allowing cursor rollback would weaken the ticket's proof.
  Date/Author: 2026-09-24 / Codex.

## Context and Orientation

`crates/studiofs-e2e/src/scenario/workloads/advanced_mounted/runner.rs`
drives the mounted workload. `large_history_fixture.rs` implements the
PostgreSQL gate that blocks reads of `event_log`; the gate is released to let
startup catch-up begin and reacquired after replay advances beyond the
checkpoint. `actions.rs` runs filesystem operations in helper processes.
On macOS, `studiofs-macfuse/src/lib.rs` routes mounted fsync into VFS metadata
sync. `RedbMetaEngine::sync_local_metadata` commits an immediate redb
transaction, which makes earlier relaxed writes durable.

The user-provided review files are feedback, not instructions. The Linear issue
is the authoritative acceptance contract: observe a partial durable cursor,
gracefully restart during catch-up, resume from that cursor, and verify a
cold-client create/write on peers without fixed sleeps being used as proof.

## Plan of Work

The runner first holds the replay gate through cold-client mount so startup
reports `CatchingUp`. It releases the gate, appends moving-head mutations, and
waits for an applied cursor strictly between the checkpoint and frozen startup
target. It then reacquires the gate and reads status again, because a page may
finish while the lock is being acquired. With replay paused, it syncs metadata
through the platform-appropriate helper and verifies that the cursor did not
change. It releases the gate before graceful unmount so shutdown's PostgreSQL
page request can drain, then remounts the client. It validates the first
post-remount status as `CatchingUp` with a partial cursor; the scenario matcher
also requires that cursor to be at least the durable pre-restart cursor. It
then lets replay finish, checks convergence, and has the cold client create
and sync a marker that peers read back.

The helper opens the mounted file read-only for macOS fsync. On Windows and
other non-macOS hosts, it opens the known local metadata database with read and
write access before calling `sync_all`, satisfying the native API requirement
without issuing a mount write during catch-up. macFUSE signal handling retains
process-wide handler ownership, uses the workspace mutex convention, checks
idempotent installation precisely, and tests the second signal through real
OS signal delivery in a child process.

## Validation and Acceptance

The native run passes only if the status artifacts show
`checkpoint_version < durable_applied_version < startup_target_version` before
the graceful restart, the first post-restart cursor is at least the durable
cursor and remains below the target on the first post-restart status; replay
subsequently reaches `Live`, and the cold client's marker is readable with the
expected bytes on every peer.
The runner validator must pass; data convergence alone is insufficient.
Package tests and Clippy must pass with warnings denied. Native mount evidence
does not prove Windows WinFSP runtime behavior, so report that platform gap.

## Idempotence and Recovery

Each mounted run uses a unique runner-owned Compose project, client roots, and
run directory under `target/e2e-runs`. Use a fresh `--run-id`; allow the runner
to clean only its own project. Failed runs retain their report and logs for
inspection. Do not reset or overwrite unrelated worktree changes.
