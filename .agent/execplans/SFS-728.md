## Surprises & Discoveries

- Observation: the forced-crash experiment reached the redb immediate barrier,
  but its post-restart cursor fell from 13 to 9 and redb reported repair.
  Evidence: run `20260924T120108Z-b6a547` recorded a failed cursor-resume check.
  The issue asks for a graceful restart, so this crash path was removed.
- Observation: one `ACCESS EXCLUSIVE` lock on PostgreSQL `event_log` can hold
  catch-up between page queries. Reacquiring it after an observed partial
  cursor freezes the cursor while fsync and graceful restart run.
- Observation: holding the gate through graceful shutdown blocks the
  background page query used by shutdown draining.
  Evidence: run `20260924T122100Z-sfs728-graceful` logged `postgres event_log
  page select failed: connection closed`, a local metadata drain warning, and
  redb repair during shutdown. Release the gate before shutdown and reacquire
  it only before the sync barrier.
- Observation: reacquiring the gate after remount may wait through many pages
  because one catch-up request can apply a page batch before releasing its SQL
  locks.
  Evidence: run `20260924T123200Z-sfs728-graceful2` first observed post-restart
  cursor 14, then the runner's extra gate acquisition delayed until the cursor
  reached 40. Validate the first status sample instead of reacquiring there.
- Observation (historical): Windows `FlushFileBuffers` needs a writable handle, which the
  catching-up mount cannot provide. Directly syncing `meta.redb` from the E2E
  helper bypassed the VFS immediate metadata barrier and was not a valid
  durability proof. The 2026-09-24 runner used mounted fsync on Unix and
  reported the scenario unsupported on Windows.
- Observation: under the stricter SFS-728 matcher, the Windows cursor was 11
  before restart and 9 afterward even when the old metadata-file sync helper
  returned successfully. Scenario 24 can replay those pages and still prove
  convergence; the durable partial-cursor assertion was an extra contract.
- Observation: the warm client used the product's 64-batch page default while
  the cold client used one batch. In run `20260925T133040Z-7233c2`, warm
  catch-up repeatedly exceeded its command deadline at applied 41/head 82 and
  the final mounted tree snapshot timed out. Giving both clients the existing
  one-batch setting passed run `20260925T133955Z-1a5e8b`.
- Observation: the reported duplicate macFUSE signal-handler guard is not
  reachable in the normal lifecycle. An atomic `compare_exchange` grants
  ownership to only one watcher; later installs receive `Ok(None)`.
- Observation: retaining the installed handler in a process-global mutex after
  the session ends does leak signal disposition into embedding hosts. CLI
  ownership now lasts through post-session cleanup and ends with the guard.

## Decision Log

- Decision: keep the ticket's graceful restart contract and do not use
  `force_kill` for this scenario.
  Rationale: forced termination tests redb crash repair, and the observed repair
  obscures the requested catch-up restart behavior.
  Date/Author: 2026-09-24 / Codex.
- Decision: reacquire the existing PostgreSQL replay gate after observing a
  partial cursor, verify the cursor is unchanged after metadata sync, then
  release the gate during graceful shutdown.
  Rationale: the gate freezes the cursor during sync, while releasing it lets
  shutdown finish its remote metadata drain. The first status sample after
  remount directly proves partial replay resumed; reacquiring then can block on
  a full replay page batch and miss the observable partial state.
  Date/Author: 2026-09-24 / Codex.
- Decision: reject the review suggestion to `mem::forget` a duplicate signal
  handler owner.
  Rationale: the existing atomic installation guard prevents the duplicate
  owner state; leaking a handler would hide an unreachable state and prevent
  normal restoration.
  Date/Author: 2026-09-24 / Codex.
- Decision: hold macOS CLI signal handlers in a launch-scope guard and let a
  library mount with `InstallForCli` own handlers only for its session.
  Rationale: both paths restore previous process handlers at a defined end of
  lifetime, while CLI cleanup remains protected after kernel detach.
  Date/Author: 2026-09-24 / Codex.
- Decision: retain strict partial-cursor and within-session progression checks.
  Rationale: the runner now records the partial cursor before graceful
  shutdown and requires the first post-restart cursor to be at least that value;
  the runner now checks that bound immediately rather than only at final match.
  Date/Author: 2026-09-24 / Codex.
- Decision: supersede the SFS-728 additions to scenario 24. Keep the cold
  bootstrap, restart, moving head, and final mounted tree comparison; permit
  replay to resume from an older cursor while requiring monotonic progress
  within each session. Remove the fsync and cold-client writer gates.
  Rationale: the user explicitly defined scenario 24 as a convergence check
  that must run without elevated rights on Windows, macOS, and Linux.
  Date/Author: 2026-09-25 / Codex.
- Decision: apply the existing one-batch catch-up override to both the warm
  and cold clients in this scenario.
  Rationale: the warm client's default page exceeded its command deadline;
  a fresh native A/B run confirmed the smaller page permits full convergence.
  Date/Author: 2026-09-25 / Codex.

## Context and Orientation

`crates/studiofs-e2e/src/scenario/workloads/advanced_mounted/runner.rs`
drives the mounted workload. `large_history_fixture.rs` implements the
PostgreSQL gate that blocks reads of `event_log`; the gate is released to let
startup catch-up begin. `actions.rs` runs filesystem operations in bounded
helper processes. Both mounted clients receive the scenario's one-batch page
setting. A final mounted marker and tree comparison prove convergence; the
scenario does not request a mounted fsync or direct database sync.

The user-provided 2026-09-25 scope correction is authoritative for scenario
24. The earlier SFS-728 issue and review files document a separate durability
proof that should not be folded into this convergence gate.

## Plan of Work

The runner prepares 90,000 initial mutations, mounts the warm client, then
holds the PostgreSQL replay gate while the cold client starts in
`CatchingUp`. At the first catching-up sample it records the session boundary,
releases the gate,
appends 10,000 moving-head mutations, and gracefully restarts the cold client.
Replay may repeat pages after restart; each session's applied versions must
remain monotonic. The cold client must reach `Live`, both mounts must read the
final marker, the remote head must stabilize, and the mounted tree validator
must find identical trees. Both clients use one batch per catch-up page so a
large response cannot consume the entire metadata command deadline in this
fixture.
