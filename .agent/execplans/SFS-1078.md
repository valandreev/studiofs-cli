# Promote a scratch entry on rename

This ExecPlan follows `.agent/PLANS.md`.

## Purpose / Big Picture

Applications can write to a local scratch name such as `shot.exr.tmp` and
rename it to the tracked name `shot.exr`. The original file handle keeps
working and StudioFS uploads the existing payload objects in the background.
Directories move with their contents in one metadata commit.

## Surprises & Discoveries

The cache describes scratch payloads as locally present with no upload
scheduled. When a crash leaves a tracked graph pointing at an object with
scratch origin, startup must enqueue that object rather than treat it as
already uploaded. The subprocess regression exits with code 42 at that
boundary and verifies that the next VFS instance queues the original object.

## Decision Log

The VFS holds the existing exclusive file-session permits in inode order
through the commit and upload handoff. This makes scratch writes and ordinary
tracked writes meet at the same per-inode boundary.

The metadata operation reuses tracked rename replacement and deletion
bookkeeping. It creates tracked inode and child rows and journals the tracked
root binding through the rename event. The source scratch binding cannot
displace a tracked source name.

## Context and Orientation

`crates/studiofs-vfs/src/vfs/namespace_ops.rs` classifies the target, waits for
deferred writer work, and applies the same local durability barrier as a
flush. A scratch entry exists only in the mounting client's local redb
database. Tracked entries use a replication event journal.

`crates/studiofs-meta/src/redb_engine/scratch.rs` moves the namespace, attributes,
symlinks, and slice metadata in the redb transaction. Slice metadata maps file
ranges to immutable payload files. The upload queue can use those files
through hardlinks after commit. `crates/studiofs-vfs/src/vfs/startup_replay.rs`
recreates that handoff after an interrupted rename.

## Plan of Work

Freeze writer buffers while holding each file's session permit. Revalidate
the source tree in the metadata write transaction so a new child cannot
enter the promotion without a permit. Convert the scratch rows to tracked
rows and commit the tracked rename. Submit only the object IDs present in
the committed graph. On startup, include scratch-origin objects referenced
by a pending tracked graph in ordinary upload replay.

## Validation and Acceptance

The writer test must pass through rename, then write and flush using the
original handle. Verify the subtree's inode numbers, payload object ID,
destination replacement, and over-limit `EXDEV`. The crash test must reopen
redb and restore an upload for the existing object after the subprocess exits
with no queued work.

## Idempotence and Recovery

A failed metadata transaction leaves all bindings and payload references in
scratch storage. A committed transaction becomes a tracked rename even if the
process exits before handing its payloads to the upload queue. Startup derives
the missing upload work from the committed metadata and local payload origin.
