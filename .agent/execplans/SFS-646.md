# Remove dead diagnostics, S3 janitor lease, and fake upload-journal flush

This ExecPlan is a living document. It follows `.agent/PLANS.md`; keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current while implementing SFS-646.

## Purpose / Big Picture

SFS-646 removes three surfaces that cannot provide production value: an environment-gated debug writer that writes to a developer-specific Windows path, an S3 janitor lease whose field is always `None`, and an upload-queue `flush_journal` method whose body does nothing. After the change, no host build contains the debug environment probe or hard-coded path, janitor coordination uses the live PostgreSQL global lock only, and shutdown logs describe the real local payload synchronization instead of claiming that an in-memory queue was journaled.

The behavior is visible through repository searches and focused compilation. The janitor still runs through `try_acquire_global_janitor_lock`; strict local cache persistence still calls `local_payload_backend.sync_data()`; upload recovery and queue state remain otherwise unchanged.

## Surprises & Discoveries

- Observation: The code graph found 11 direct callers of `StudioVfs::debug_write_probe` and one caller of `write_debug_enabled`; the calls span VFS, deletion cleanup, workers, sync operations, and upload lifecycle.
  Evidence: `trace_path` on `StudioVfs.debug_write_probe` returned 11 direct callers; `rg` found the corresponding call sites in `crates/studiofs-vfs/src`.
- Observation: `janitor_lease` is initialized as `None` in `crates/studiofs-vfs/src/vfs/bootstrap.rs`, while the janitor worker has a separate PostgreSQL global-lock path.
  Evidence: bootstrap constructs `janitor_lease: None`; `background_janitor` calls `try_acquire_global_janitor_lock()` after the dead optional branch.
- Observation: `CachedStore::shutdown` only requests `UploadQueue` shutdown and then awaits an empty compatibility method; the real local durability boundary is the following `local_payload_backend.sync_data()` call.
  Evidence: `UploadQueue::flush_journal` has an empty body, and `VfsUploadLifecycle::persist_cache_result` calls `sync_data()` immediately afterward.
- Observation: The word `journal` also describes real metadata/event and landing-journal concepts elsewhere, so broad deletion of every journal mention would be unsafe and out of scope.
  Evidence: `studiofs-meta` has local replication journals and VFS tests cover real landing-journal behavior.
- Observation: Test compilation exposed two test groups that referenced the deleted debug-only admission fields and reread-delay helpers even though library checks were clean.
  Evidence: the focused VFS test build reported stale `SustainedWriteAdmission::{duration_ms,delay_ms}` and `WriteAdmissionPressure::pending_upload_bytes` references; those tests were removed or narrowed to the live pre-drain/admission behavior.

## Context and Orientation

The workspace is a Rust 2024 project at `E:\dev\studiofs-cli`. `crates/studiofs-vfs` owns the platform-independent filesystem runtime and its background janitor. `crates/studiofs-cache` owns local payload caching and the in-memory upload queue. `crates/studiofs/src/cli/mount/session.rs` maps mount environment variables into `VfsConfigRaw`. `crates/studiofs-vfs/tests/vfs_test.rs` supplies test configuration and ignored S3-backed janitor tests. The macFUSE, Linux/FUSE, and WinFSP crates depend on the shared VFS APIs and therefore must compile after the deletions.

The debug probe is `StudioVfs::debug_write_probe` in `crates/studiofs-vfs/src/vfs.rs`. Its callers only build JSON for a hard-coded `STUDIOFS_WRITE_DEBUG` file and must lose those blocks without changing surrounding write, upload, deletion, or scheduling behavior.

The dead lease consists of `JanitorLease`, `janitor_lease`, `janitor_lease_ttl`, `acquire_janitor_lease`, lease record helpers, the TTL fields in `VfsConfig` and `VfsConfigRaw`, the mount/test environment mapping, and the optional branch in `background_janitor`. The janitor's call to `try_acquire_global_janitor_lock()` remains.

The upload queue is an in-memory pending-operation tracker. `UploadQueue::flush_journal` and `CachedStore::flush_upload_journal` do nothing. `CachedStore::shutdown` must continue requesting queue shutdown, while `VfsUploadLifecycle::persist_cache_result` must continue calling `local_payload_backend.sync_data()` and reporting that real local synchronization result.

## Plan of Work

First remove all `debug_write_probe` and `write_debug_enabled` blocks from their callers, then delete the helper and its debug-only imports. Keep calculations and metrics that still affect scheduling or observability; remove only values that existed solely inside the deleted JSON payloads.

Next remove the dead lease type, methods, fields, bootstrap-plan plumbing, config fields/defaults/normalization/round-trip mappings, mount environment variable mapping, test environment capture, and the obsolete test-only TTL assignment. Simplify the janitor worker so it proceeds directly to the PostgreSQL global lock check.

Finally remove both no-op journal methods. Keep `CachedStore::shutdown` as the real asynchronous queue-stop entry point, remove its no-op flush call, and replace current comments and tracing strings that claim an upload journal was persisted with wording about stopping the upload queue and synchronizing the local payload backend. Do not remove `sync_data`, upload-stage recovery, metadata journals, or landing-journal tests.
