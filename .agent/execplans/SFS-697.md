# SFS-697 Add Explicit PG Sync Lifecycle and Write-Authority States Implementation Plan

**Purpose / Big Picture**

Introduce one backend-facing PostgreSQL synchronization lifecycle contract that
distinguishes a usable local serving view, startup catch-up, target completion,
allocator readiness, degraded read-only operation, and fatal failure. Expose the
lifecycle together with the existing paired allocator authority through the
metadata replication interface, and make the VFS mutation gate consume both
dimensions. A discovered client will persist a small local pending marker so a
later normal mount cannot mistake an unfinished fresh bootstrap for an
established offline-capable client.

The implementation deliberately leaves the moving-head replay algorithm and
remote-work placement unchanged; bounded frozen-target replay belongs to
SFS-701 and removing replay from `PgMetaEngine::open` belongs to SFS-698.

**Context and Orientation**

The canonical contract is `docs/pg-sync-contract.md`. Foreground metadata is
served from local `redb`; PostgreSQL validates, bootstraps, and replicates
metadata. `MetadataAuthorityStatus` currently contains the trusted inode and
object allocator headroom pair, and `StudioVfs::enforce_metadata_mutation_authority`
is the existing central policy point. `discover` imports a serving checkpoint
and primes a PostgreSQL engine, while ordinary mount opens the same local DB
without a fresh-client argument.

**Surprises and Discoveries**

- `discover` calls `open_meta_engine_with_options` immediately after importing
  its checkpoint, but the subsequent normal mount call has no provenance flag.
- A local replay cursor of zero is not sufficient as a fresh-client predicate:
  an initialized/established client can also have no applied remote batch yet
  and may have trusted local allocator state.
- A normal remote checkpoint replacement clears most local PG counters by
  design, so the fresh-client marker needs a narrow preservation exception;
  preserving the marker does not preserve the client slot or allocator windows.
- The existing allocator flags are intentionally independent of remote
  connectivity. The new lifecycle must not turn a trusted established client
  read-only merely because PostgreSQL is unavailable.
- `CoherenceHealthState` in `studiofs-vfs` is a cache/coherence health tracker,
  not the PG startup/write-authority lifecycle and must remain separate.

**Decision Log**

1. Define `PgSyncLifecycle` and
   `PgSyncStatus` in `studiofs-meta::engine`, because the lifecycle is a shared
   metadata contract and the ports layer must not depend on the PG adapter.
2. Include `TargetReached` in addition to the issue's minimum state list. The
   canonical SFS-695 contract names target completion explicitly, and keeping it
   distinct from `AllocatorPending` makes the two gates observable.
3. `PgSyncLifecycle::allows_reads` is true for every usable state except
   `Fatal`; `PgSyncLifecycle::allows_new_mutations` is true only for `Live`.
   `PgSyncStatus::allows_new_mutations` additionally requires both allocator
   headroom flags. Thus local-ready/catching-up/target-reached are read-only,
   while established trusted offline operation remains `Live` with allocator
   authority even when the remote source is unavailable.
4. Persist `pgFreshClientPending` as a local-only redb counter. `discover` sets
   it through `MetaOpenOptions::fresh_client`; a successful startup catch-up
   clears it, and remote checkpoint import preserves this marker without
   preserving the writer slot or allocator windows.
   `init` and ordinary reopen keep the option false and therefore preserve the
   established-client offline contract.
5. Keep the lifecycle read-only gate in `StudioVfs` as one central decision
   combined with the existing `metadata_authority_status` override and deferred
   namespace safety checks. Do not add bridge-specific branches.
6. A failed fresh startup remains `Degraded` with the marker retained. Existing
   clients that fail remote synchronization remain governed by their trusted
   allocator status; remote outage alone is not converted into degraded
   read-only behavior.
7. Keep lifecycle validation as the `can_transition_to` predicate. The runtime
   only needs to log invalid pairs, so a public transition error/result wrapper
   is unnecessary.

**Validation and Acceptance**

The issue is accepted when:

1. One exported lifecycle/status contract contains the required states,
   explicit read/write permission helpers, deterministic transitions, and tests.
2. `PgSyncStatus` keeps lifecycle/convergence and allocator authority separate,
   while its mutation decision is the conjunction of both gates.
3. A fresh discovered client is marked and cannot become writable before
   startup catch-up reaches its current transitional target and allocator
   authority is ready; a failed fresh startup is recoverable read-only.
4. An established client with trusted paired allocator headroom remains
   writable during remote unavailability; allocator exhaustion or loss still
   blocks new mutations.
5. All runtime adapters expose the same status and the VFS has one central
   mutation admission decision. Focused tests execute at least one test each.

**Idempotence and Recovery**

Setting the fresh marker repeatedly is idempotent. Successful startup clears
only the marker and does not rewrite replay history. Snapshot import preserves
the marker as local state. If startup catch-up fails, the marker and local
serving DB remain available for a later retry/reopen; no destructive reset or
compatibility conversion is attempted.

**Outcomes and Retrospective**

The exported `PgSyncLifecycle`/`PgSyncStatus` contract now separates local
read readiness, startup catch-up, target completion, allocator readiness,
degraded recovery, and fatal state. `PgMetaEngine` reports that status through
`MetaReplication`, `RuntimeMetaHandle` forwards it, and the VFS mutation gate
requires both `Live` lifecycle and paired allocator headroom. `discover` marks
fresh bootstrap state, and remote checkpoint replacement preserves only that
marker until successful startup catch-up clears it. Established clients still
enter `Live` from trusted local allocator state when the remote source is
unavailable.

**Interfaces and Dependencies**

The change uses existing `redb`, `tokio`, and `serde` dependencies only. The
public interface is `studiofs_meta::engine::{PgSyncLifecycle, PgSyncStatus}`
plus `MetaReplication::pg_sync_status()` and
the `fresh_client` open option. No new external service, schema migration, or
remote API is introduced by SFS-697.
