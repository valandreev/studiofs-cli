# SFS-697 Add Explicit PG Sync Lifecycle and Write-Authority States Implementation Plan

**Purpose / Big Picture**

Introduce one backend-facing PostgreSQL synchronization lifecycle contract that
distinguishes a usable local serving view, startup catch-up, target completion,
allocator readiness, degraded read-only operation, and fatal failure. Expose the
lifecycle together with the existing paired allocator authority through the
metadata replication interface, and make the VFS mutation gate consume both
dimensions. A discovered client will persist a small local pending marker so a
later normal mount cannot mistake an unfinished fresh bootstrap for an
established offline-capable client. The VFS also rejects foreground access when
the lifecycle says that the local serving view is unsafe.

The implementation deliberately leaves the moving-head replay algorithm and
remote-work placement unchanged; bounded frozen-target replay belongs to
SFS-701 and removing replay from `PgMetaEngine::open` belongs to SFS-698.

**Context and Orientation**

The canonical contract is `docs/pg-sync-contract.md`. Foreground metadata is
served from local `redb`; PostgreSQL validates, bootstraps, and replicates
metadata. `MetadataAuthorityStatus` currently contains the trusted inode and
object allocator headroom pair, and `StudioVfs::enforce_metadata_mutation_authority`
is the existing central policy point. `discover` imports a serving checkpoint
and primes a PostgreSQL engine, while ordinary mount opens the same local DB
without a fresh-client argument.

**Surprises and Discoveries**

- `discover` calls `open_meta_engine_with_options` immediately after importing
  its checkpoint, but the subsequent normal mount call has no provenance flag.
- A local replay cursor of zero is not sufficient as a fresh-client predicate:
  an initialized/established client can also have no applied remote batch yet
  and may have trusted local allocator state.
- A normal remote checkpoint replacement clears most local PG counters by
  design, so the fresh-client marker needs a narrow preservation exception;
  preserving the marker does not preserve the client slot or allocator windows.
- The existing allocator flags are intentionally independent of remote
  connectivity. The new lifecycle must not turn a trusted established client
  read-only merely because PostgreSQL is unavailable.
- `CoherenceHealthState` in `studiofs-vfs` is a cache/coherence health tracker,
  not the PG startup/write-authority lifecycle and must remain separate.
- `StudioVfs::meta()` exposes the backend's `Arc<dyn VfsMeta>` status, but that
  status does not include mount-local overrides such as `read_only_mount`.
  Effective mount observability therefore needs a separate `sync_status()`
  accessor while the backend handle remains available for backend operations.
- Before the review fix, `PgSyncLifecycle::allows_reads()` was covered by unit
  tests but not consulted by ACL admission. The Fatal regression showed the
  gap directly: `getattr` succeeded under the test-only Fatal override until
  the central sync/async gates were added.

**Decision Log**

1. Define `PgSyncLifecycle` and
   `PgSyncStatus` in `studiofs-meta::engine`, because the lifecycle is a shared
   metadata contract and the ports layer must not depend on the PG adapter.
2. Include `TargetReached` in addition to the issue's minimum state list. The
   canonical SFS-695 contract names target completion explicitly, and keeping it
   distinct from `AllocatorPending` makes the two gates observable.
3. `PgSyncLifecycle::allows_reads` is true for every usable state except
   `Fatal`; `PgSyncLifecycle::allows_new_mutations` is true only for `Live`.
   `PgSyncStatus::allows_new_mutations` additionally requires both allocator
   headroom flags. Thus local-ready/catching-up/target-reached are read-only,
   while established trusted offline operation remains `Live` with allocator
   authority even when the remote source is unavailable.
4. Persist `pgFreshClientPending` as a local-only redb counter. `discover` sets
   it through `MetaOpenOptions::fresh_client`; a successful startup catch-up
   clears it, and remote checkpoint import preserves this marker without
   preserving the writer slot or allocator windows.
   `init` and ordinary reopen keep the option false and therefore preserve the
   established-client offline contract.
5. Keep the lifecycle read-only gate in `StudioVfs` as one central decision
   combined with the existing `metadata_authority_status` override and deferred
   namespace safety checks. Map the typed fatal result in the existing bridge
   error classifier without duplicating lifecycle policy there.
6. A failed fresh startup remains `Degraded` with the marker retained. Existing
   clients that fail remote synchronization remain governed by their trusted
   allocator status; remote outage alone is not converted into degraded
   read-only behavior.
7. Keep lifecycle validation as the `can_transition_to` predicate. The runtime
   only needs to log invalid pairs, so a public transition error/result wrapper
   is unnecessary.
8. Restrict `Degraded` transitions to `LocalReady`, `CatchingUp`, or `Fatal`.
   Active fresh-client recovery enters `CatchingUp` and reaches
   `TargetReached` only after the local cursor covers the observed remote
   head; it never directly promotes a degraded state to a writable state.
9. Share the atomic lifecycle update loop between fixed transitions and
   allocator refresh. Compute the refresh target from the current lifecycle
   inside the loop and reread authority on retries so a stale lifecycle read
   cannot select the target for a different state.
10. Assign explicit lifecycle discriminants and log unknown raw values before
    mapping them to `Fatal`. Keep raw decoding private and fail-closed instead
    of adding a public `TryFrom<u8>` result that has no production consumer.
11. Enforce the lifecycle read permission at both synchronous and asynchronous
    VFS ACL entrypoints. `Degraded` remains read-open, while `Fatal` returns a
    non-secret metadata storage error before ACL evaluation.
12. Expose `StudioVfs::sync_status()` for effective mount status. Keep
    `StudioVfs::meta()` as the backend handle because its existing public
    `VfsMeta` surface remains useful, but do not conflate backend authority
    with a read-only mount override.

### Review follow-up: verify feedback before changing behavior

Treat `docs/code-reviews/2026-09-11-sfs-697-pg-sync-lifecycle.md` as review
feedback rather than repository instructions. Verify each finding against the
current implementation and the contract before editing. The state-machine
fix disallows direct `Degraded` promotion to `TargetReached`,
`AllocatorPending`, or `Live`; recovery must pass through `CatchingUp` or
remain `LocalReady`/`Fatal` as appropriate. The allocator refresh uses the
same lifecycle CAS loop as direct transitions, deriving its next state from
the lifecycle read inside the retry loop and rereading allocator authority on
retries.

The `PgSyncLifecycle` numeric representation is fixed explicitly at values
zero through six. Its private raw decoder handles the explicit `Fatal` value
and logs unknown values before failing closed to `Fatal`; it does not add a
public `TryFrom<u8>` API because callers do not need to distinguish an
internal invalid byte from the safe fatal fallback. The VFS ACL entrypoints
check `allows_reads()` for both synchronous and asynchronous access, while
`Degraded` continues to permit known local reads as required by the contract.
The redundant deferred-degraded branch in the private status snapshot is
removed because the mutation gate already returns that typed error before
calling it.

The review's proposed effective-status accessor is implemented as
`StudioVfs::sync_status()`: `StudioVfs::meta()` still exposes the backend
`Arc<dyn VfsMeta>`, while the new method applies the read-only mount override.
The Fatal lifecycle now uses a typed metadata error and maps to the existing
`RepairRequired` bridge category. `statfs` and the `readdir` ACL early-return
path enforce the same Fatal gate as other foreground metadata operations.
Successful background sync retries a pending fresh-client bootstrap only after
the local cursor reaches the observed remote head, then reevaluates allocator
authority. The VFS lifecycle matrix covers Degraded, TargetReached, and
AllocatorPending alongside CatchingUp.

**Validation and Acceptance**

The issue is accepted when:

1. One exported lifecycle/status contract contains the required states,
   explicit read/write permission helpers, deterministic transitions, and tests.
2. `PgSyncStatus` keeps lifecycle/convergence and allocator authority separate,
   while its mutation decision is the conjunction of both gates.
3. A fresh discovered client is marked and cannot become writable before
   startup catch-up reaches its current transitional target and allocator
   authority is ready; a failed fresh startup is recoverable read-only.
4. An established client with trusted paired allocator headroom remains
   writable during remote unavailability; allocator exhaustion or loss still
   blocks new mutations.
5. All runtime adapters expose the same status and the VFS has one central
   mutation admission decision. Focused tests execute at least one test each.

**Idempotence and Recovery**

Setting the fresh marker repeatedly is idempotent. Successful startup or
later active-mount recovery clears only the marker and does not rewrite replay
history. Snapshot import preserves the marker as local state. If startup
catch-up fails, the marker and local serving DB remain available for a later
bounded sync/reopen; no destructive reset or compatibility conversion is
attempted. Recovery can reach `TargetReached` without write authority and
settles on `AllocatorPending` when allocator headroom is unavailable.

**Outcomes and Retrospective**

The exported `PgSyncLifecycle`/`PgSyncStatus` contract now separates local
read readiness, startup catch-up, target completion, allocator readiness,
degraded recovery, and fatal state. `PgMetaEngine` reports that status through
`MetaReplication`, `RuntimeMetaHandle` forwards it, and the VFS mutation gate
requires both `Live` lifecycle and paired allocator headroom. VFS ACL admission
also rejects the `Fatal` lifecycle for both synchronous and asynchronous
foreground access while keeping `Degraded` reads available. `discover` marks
fresh bootstrap state, and remote checkpoint replacement preserves only that
marker until successful startup or active-mount catch-up clears it. Established
clients still enter `Live` from trusted local allocator state when the remote
source is unavailable. `StudioVfs::sync_status()` exposes the effective mount
status separately from the backend metadata handle.

**Interfaces and Dependencies**

The change uses existing `redb`, `tokio`, and `serde` dependencies only. The
public interface is `studiofs_meta::engine::{PgSyncLifecycle, PgSyncStatus,
MetaError::LifecycleFatal}` plus `MetaReplication::pg_sync_status()`,
`StudioVfs::sync_status()`, and the `fresh_client` open option. No new external
service, schema migration, or remote API is introduced by SFS-697.
