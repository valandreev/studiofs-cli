# Полный аудит производительности чтения StudioFS

**Дата:** 2026-02-18

---

## Краткое резюме ✅
- Ключевая находка: в продакшне используется **VFS v1**, а не оптимизированный **VFS v2** — это основной источник read amplification и низкой скорости чтения из кэша.
- Цель: устранить read amplification и повысить чтение из кэша до целевых ~1.5 ГБ/с.

---

## Проблема 1 — Read amplification (симптомы)
- Наблюдаемая скорость чтения для конечного пользователя: ~30 МБ/с.
- Сетевой канал загружается полностью (~2.5 Гбит/с) — при этом клиент получает гораздо меньше данных.

### Причина (корневые):
1. **Повторная загрузка root-объекта на каждый read** (VFS v1 `read_from_storage()` читает/декомпрессирует/десериализует root для каждого обращения).
2. **Двойная сериализация/обёртка данных** (ObjectPayload + STFS object) — дополнительные alloc/copy и CPU.
3. **Prefetch запускает несколько параллельных задач, каждая пересчитывает root** — множит amplification.
4. **Root-объект растёт линейно с размером файла** — чтение большого файла требует парсинга большого списка ссылок.
5. **Отсутствие кэширования разобранных метаданных** — каждая операция повторяет парсинг.

---

## Проблема 2 — Низкая скорость чтения из кэша (150–300 МБ/с)
- Диск обеспечивает 3.5–4 ГБ/с, цель — 1.5 ГБ/с, фактическая скорость из кэша — 150–300 МБ/с.

### Причины (технические узкие места):
- LZ4 декомпрессия + postcard десериализация на каждом попадании в кэш (CPU + копирования).
- `fsync()` (`file.sync_all()`) при записи в диск-кэш — избыточная синхронизация тормозит загрузку кэша.
- `spawn_blocking` + `read_to_end` (без предаллокации) — syscall/thread overhead и лишние реаллокации.
- Множественные копирования буферов (read -> decompress -> deserialize -> assemble).
- Mutex contention в LRU/entries при высокопараллельном доступе.
- `block_on` в WinFSP callback — может сериализовать операции при ограниченном пуле.

---

## Подробные выводы (ключевые места в коде)
- `crates/studiofs-vfs/src/vfs.rs` — `read_from_storage()` и `commit_uploads()` — главный источник read amplification (root object + ObjectPayload).
- `crates/studiofs-cache/src/disk.rs` — `get_object()` использует `spawn_blocking` + `read_to_end` и вызывает `file.sync_all()` при записи.
- `crates/studiofs-cache/src/memory.rs` — единый Mutex + LruCache (точка contention при параллельных чтениях).
- `crates/studiofs-winfsp/src/context.rs` — `read()` использует `rt.block_on()` (WinFSP thread blocking).
- `crates/studiofs-vfs/src/vfs_v2.rs` — уже реализует архитектуру, лишённую многих проблем (рекомендуется перейти на неё).

---

## Рекомендации и приоритеты (конкретно и по порядку)
### Непосредственные быстрые изменения (быстрый выигрыш)
1. **Убрать `file.sync_all()` для DiskCache** (sync только для journal). — Тривиально, сильный эффект на throughput записи кэша.
2. **Предаллокация буферов при чтении (`with_capacity(metadata.len())`)** — уменьшает реаллокации.
3. **Хранить в DiskCache распакованные (decompressed) блоки** — устраняет декомпрессию при каждом попадании в кэш (трейдофф: место на диске).

### Сильные архитектурные улучшения (высокий эффект)
4. **Перейти на VFS v2** (используется `crates/studiofs-vfs/src/vfs_v2.rs`). — Устраняет read amplification и двойную сериализацию.
5. **Использовать mmap для чтения дискового кэша** (или zero-copy wrapper вокруг mmap). — Значительное снижение CPU/syscall overhead.
6. **Параллельное чтение блоков в VFS (batch/parallel fetch)** — повышает throughput для больших sequential reads.

### Стабильность и масштабируемость
7. **Шардирование кэшей** (MemoryCache/DiskCache) для снижения contention.
8. **Кэш атрибутов (InodeAttr) с коротким TTL** — уменьшит обращения в redb на высокочастотных паттернах.
9. **WinFSP tuning (increase worker threads / file info caching)** — снизит блокировки на уровне драйвера.

## Таблица сравнения — ожидаемый эффект

| Мера | Ожидаемый эффект на read throughput | Сложность реализации |
|---|---:|---:|
| Перейти на VFS v2 | Очень высокий (устранение read amplification) | Средняя—высокая |
| Хранить распакованные блоки в DiskCache | +2–3× | Низкая |
| mmap для DiskCache | +1.5–2× | Средняя |
| Убрать sync_all() | Немедленный выигрыш в записи кэша | Низкая |
| Параллельное чтение блоков | +2–4× для больших reads | Низкая |
| Шардирование кэша | +30–50% при параллелизме | Средняя |

## Рекомендуемый порядок внедрения
1. Убрать `sync_all()` в DiskCache (низкая сложность, быстрый выигрыш).
2. Предаллокация буферов и мелкие оптимизации чтения (низкая сложность).
3. Сохранение распакованных данных в DiskCache (низкая/средняя).
4. Внедрить mmap для DiskCache (средняя сложность).
5. Перевод продакшна на **VFS v2** (высокий эффект; требуется миграция/проверки).
6. Параллельное чтение блоков и шардирование кэшей.
7. WinFSP / runtime tuning и замеры.

---

## План валидации (бенчмарки)
- Нагрузочный тест: последовательное чтение больших файлов (1–10 GiB) — метрики: user throughput, client IOPS, network bandwidth, CPU.
- Тест cache-hit: заполнить DiskCache и измерить sustained throughput (цель 1.5 GB/s).
- A/B: текущая ветка vs. изменения P2–P4, затем P5.

---

## Заключение — кратко и по делу 💡
- Основная причина: продакшн использует **VFS v1**, который создаёт read amplification через root-object + двойную сериализацию. Это даёт огромный выигрышей, если перейти на **VFS v2**. 
- Быстрые улучшения (удаление fsync в кэше, хранение распакованных блоков, mmap) дадут заметный прирост немедленно.
