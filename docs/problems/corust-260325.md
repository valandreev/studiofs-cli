## Issue 1 — God-object `VfsState` (60+ fields)

**Severity:** High  
**File:** `crates/studiofs-vfs/src/vfs.rs`, `struct VfsState`

`VfsState` holds 60+ fields covering completely unrelated concerns: ingress WAL counters, cache coherence epochs, ACL state, upload cancellation tokens, foreground read speedometer shards, shutdown flags, background task handles, and more — all behind individual `Mutex` / `Atomic` wrappers with no grouping.

**Problems:**
- No way to reason about which locks protect which invariants.
- Subsystems that should be independently testable (e.g., ingress WAL, ACL cache, upload throttle) are structurally coupled through a single shared object.
- Any change to one concern requires reading the entire struct to understand side effects.

**Recommended fix:**  
Decompose into cohesive sub-structs, each lockable independently:
```rust
struct IngressState { /* WAL counters, segment id, spill index */ }
struct UploadState  { /* cancel tokens, sticky errors, requeue counters */ }
struct AclState     { /* acl_epoch, acl_namespace_epoch, effective_acl_cache */ }
struct CacheCoherenceState { /* dentry_cache, path_shortcut_cache, attr_read_cache, namespace_epoch */ }
struct ShutdownState { /* shutdown_requested, uploader_shutdown_token, background_tasks */ }
```

## Issue 2 — 300-line constructor that spawns background tasks

**Severity:** High  
**File:** `crates/studiofs-vfs/src/vfs.rs`, `StudioVfs::new()`

`StudioVfs::new()` is a single function that:
1. Validates and clamps all 80 config fields
2. Derives tuning parameters from config
3. Constructs all subsystems (fetch scheduler, upload scheduler, block cache, ingress recovery)
4. Builds the `Arc<Self>`
5. Immediately spawns 8+ background `tokio::spawn` tasks

The entire body is wrapped in an unnecessary nested `{ ... }` block. The function is ~300 lines and untestable as a unit.

**Problems:**
- Impossible to construct a `StudioVfs` in tests without spawning real background tasks.
- Config derivation logic (e.g., AIMD window calculations) is buried and cannot be tested independently.
- Any failure path inside the constructor leaves partially-spawned tasks with no cleanup.

**Recommended fix:**  
Separate construction from activation:
```rust
impl StudioVfs {
    pub fn new(meta, data_config, cache_dir, ...) -> VfsResult<Arc<Self>> { /* build only */ }
    pub fn start(self: &Arc<Self>) { /* spawn background tasks */ }
}
```
Extract subsystem builders into private helpers (`fn build_fetch_scheduler()`, `fn build_upload_scheduler()`, `fn recover_ingress()`, etc.).

## Issue 3 — Three copy-pasted two-tier LRU cache implementations

**Severity:** High  
**File:** `crates/studiofs-vfs/src/vfs.rs`

`DentryCache`, `PathShortcutCache`, and `AttrReadCache` are three independent structs that each implement the same two-tier (probationary / protected) CLOCK-like LRU with lazy-order compaction. The following logic is duplicated verbatim across all three:

- `next_stamp()` — monotonic stamp generation
- `enforce_limits()` / `enforce_protected_budget()` — eviction loops
- `maybe_compact_orders()` / `compact_order()` — lazy queue compaction
- `demote_one_protected()` / `evict_one_from()` — tier demotion/eviction
- `metrics()` — occupancy snapshot

This is approximately 600 lines of duplicated logic. The implementations have already diverged in minor ways (`AttrReadCache` has no `parent_index`; `PathShortcutCache` has a more complex charge estimation). Any bug fixed in one must be manually replicated to the other two.

**Recommended fix:**  
A single generic `TwoTierCache<K, V>` parameterised over key/value types, with a `CachePolicy` trait for charge estimation and staleness checks. The three current structs become thin wrappers or type aliases.

## Issue 4 — `MetaEngine` trait with 50+ methods and silent default no-ops

**Severity:** High  
**File:** `crates/studiofs-meta/src/engine.rs`

The `MetaEngine` trait has grown to 50+ methods. Many have default implementations that silently succeed as no-ops (`Ok(())`, `Ok(Vec::new())`), or return a runtime error:

```rust
fn get_referenced_object_ids(&self) -> MetaResult<HashSet<u64>> {
    Err(MetaError::Storage("get_referenced_object_ids not implemented".to_string()))
}
```

This means:
- A new backend implementation compiles without implementing critical GC functionality.
- The janitor silently skips GC when the default error is returned, with no compile-time signal.
- The trait is not a contract — it is a menu of optional capabilities.

**Recommended fix:**  
Split into focused sub-traits with minimal required methods:
```rust
pub trait MetaNamespace: Send + Sync { /* lookup, readdir, create, unlink, rename */ }
pub trait MetaBlocks:    Send + Sync { /* get/set/remove file blocks, flush batch */ }
pub trait MetaGc:        Send + Sync { /* pending deletions, referenced object ids */ }
pub trait MetaReplication: Send + Sync { /* flush, sync, version tokens, backlog */ }
pub trait MetaSnapshots: Send + Sync { /* create/list/get snapshots */ }
```
Backends opt into capabilities explicitly. The VFS requires `MetaNamespace + MetaBlocks + MetaGc` at minimum.

## Issue 5 — Synchronous `MetaEngine` wrapped in `spawn_blocking` at 50+ call sites

**Severity:** Medium  
**File:** `crates/studiofs-vfs/src/runtime.rs`, `run_meta()` + `vfs.rs`

The entire metadata layer is synchronous (`redb` is a sync embedded KV store). The VFS wraps every metadata call in `run_meta()` → `task::spawn_blocking`, allocating a new blocking task per operation:

```rust
pub async fn run_meta<T: Send + 'static>(
    engine: Arc<dyn MetaEngine>,
    operation: impl FnOnce(Arc<dyn MetaEngine>) -> MetaResult<T> + Send + 'static,
) -> VfsResult<T> {
    task::spawn_blocking(move || operation(engine).map_err(VfsError::Meta))
        .await
        .map_err(VfsError::Join)?
}
```

This pattern appears at 50+ call sites. Meanwhile, `PgMetaEngine` runs its own internal async Tokio runtime for Postgres access inside a sync wrapper, creating a nested-runtime situation that is fragile under `current_thread` runtimes (acknowledged in a comment in `StudioVfs::new()`).

**Problems:**
- Each metadata op pays a task-allocation and context-switch overhead.
- Batching metadata ops (e.g., reading multiple block refs in one transaction) is impossible at the call site.
- The nested runtime in `PgMetaEngine` is a latent deadlock risk.

**Recommended fix:**  
Define an `AsyncMetaEngine` trait with `async fn` methods (or use `async-trait`). Provide a `SyncMetaEngineAdapter` that wraps sync implementations. This makes the async/sync boundary explicit and eliminates the 50+ ad-hoc `spawn_blocking` sites.

## Issue 6 — 80-field `VfsConfig` with no validation and magic-number defaults

**Severity:** Medium  
**File:** `crates/studiofs-vfs/src/vfs.rs`, `struct VfsConfig`

`VfsConfig` has ~80 public fields, all `pub`, with `Default` providing magic numbers inline:

```rust
max_dirty_bytes: 12 * 1024 * 1024 * 1024,  // 12 GiB hardcoded in Default impl
max_spill_bytes: 64 * 1024 * 1024 * 1024usize,  // 64 GiB hardcoded
```

Invalid combinations are silently clamped in the constructor (e.g., `upload_min_window > upload_max_window` is corrected without warning). The struct is `#[serde(default)]` and deserialized directly from user config files, meaning any field rename is a silent breaking change.

**Problems:**
- Users cannot distinguish "I set this" from "the library defaulted this."
- No validation means misconfiguration is discovered at runtime, not at config parse time.
- The 80-field flat struct is overwhelming as a user-facing API surface.

**Recommended fix:**  
Separate `VfsConfigRaw` (the serde-deserialised user input with `Option<T>` fields) from `VfsConfigValidated` (the resolved runtime config). Validation and defaulting happen in `VfsConfigRaw::validate() -> Result<VfsConfigValidated>`, surfacing errors before any VFS is constructed.

## Issue 7 — Ingress WAL subsystem embedded inline in `vfs.rs`

**Severity:** Medium  
**File:** `crates/studiofs-vfs/src/vfs.rs`

The ingress segment WAL — a self-contained persistence subsystem responsible for append-only durability, segment rotation, checkpoint writing, and crash recovery — is implemented as ~500 lines of free functions and inline logic inside `vfs.rs`:

```
append_ingress_record()
recover_spill_dir()
write_ingress_checkpoint()
replay_ingress_segment_records()
load_latest_ingress_checkpoint()
list_ingress_segment_files()
reset_ingress_artifacts_for_fast_mode()
ingress_segment_path()
...
```

The codebase already uses `#[path = "commit.rs"]` and `#[path = "materialize.rs"]` to pull out submodules, but this larger subsystem was never extracted.

**Problems:**
- The WAL logic is untestable without constructing a full `StudioVfs`.
- `vfs.rs` is already enormous; the embedded WAL makes it harder to navigate.
- The WAL has its own on-disk format (`INGRESS_SEGMENT_MAGIC`, record layout) that deserves isolated ownership.

**Recommended fix:**  
Extract to `crates/studiofs-vfs/src/ingress_wal.rs` (or a sub-crate). The module owns its own types (`IngressSegment`, `IngressCheckpoint`, `IngressRecovery`) and exposes a clean API to `vfs.rs`. The existing tests for WAL recovery (`test_recover_spill_dir_*`) move with it and become unit tests of the module.

## Issue 8 — Probe-and-drop pattern to detect metadata backend type

**Severity:** Medium  
**File:** `crates/studiofs-meta/src/lib.rs`, `open_meta_engine_with_options()`

```rust
pub fn open_meta_engine_with_options(path, options) -> MetaResult<Arc<dyn MetaEngine>> {
    let redb = RedbMetaEngine::open(path)?;   // acquires exclusive lock
    match redb.get_format_info() {
        Ok(info) if info.metadata.backend == MetadataBackend::Postgres => {
            // Redb holds an exclusive process-local open lock. Release probe handle first.
            drop(redb);
            let pg = PgMetaEngine::open_with_options(path, ...)?;
            ...
        }
    }
}
```

The function opens `RedbMetaEngine` (acquiring an exclusive process lock) solely to read the `FormatInfo`, then drops it to release the lock before opening `PgMetaEngine`. 

**Problems:**
- TOCTOU window: the format info could theoretically change between the probe `drop(redb)` and the `PgMetaEngine::open_with_options()` call.
- The comment "Release probe handle first" signals this is a known workaround, not a design.
- Any future backend requiring a different probe mechanism requires modifying this function.

**Recommended fix:**  
Store the backend type in a small, non-exclusively-locked sidecar file (e.g., `meta.backend`) that can be read without opening the redb database. Alternatively, expose a `RedbMetaEngine::read_format_info_readonly(path)` that uses a read-only open, avoiding the exclusive lock entirely.

## Issue 9 — `parse_size_bytes` utility function living in `vfs.rs`

**Severity:** Low  
**File:** `crates/studiofs-vfs/src/vfs.rs`, `pub fn parse_size_bytes()`

`parse_size_bytes` is a pure string-parsing utility with zero dependency on VFS types. It is publicly exported from `studiofs_vfs` and re-exported from the lib root. Its presence inside `vfs.rs` — the largest and most complex file in the workspace — is a symptom of `vfs.rs` acting as a catch-all module.

**Recommended fix:**  
Move to a `utils.rs` module within `studiofs-vfs`, or into a shared workspace utility crate if other crates need it.

## Issue 10 — Duplicate `parse_size` implementation in CLI crate

**Severity:** Low  
**File:** `crates/studiofs/src/cli/mount.rs`, `fn parse_size()`

The CLI crate defines its own private `fn parse_size(s: &str) -> anyhow::Result<u64>` that parses TB/GB/MB/KB suffixes. `studiofs-vfs` already exports `parse_size_bytes` doing the same thing. The two implementations are not identical:

- `parse_size_bytes` supports fractional values (`1.5GB`) and returns `Option<usize>`
- `parse_size` in `mount.rs` does not support fractional values and returns `anyhow::Result<u64>`

These will silently diverge over time (e.g., `parse_size_bytes` gains a new suffix; `mount.rs` does not).

**Recommended fix:**  
Remove `mount.rs::parse_size` and use `parse_size_bytes` from `studiofs-vfs` directly, with a thin wrapper to convert `Option<usize>` to `anyhow::Result<u64>` at the call site.
