# StudioFS 0.2.3

This release adds four volume-management features: an opt-in recoverable
trash, S3 credential rotation without remounting, live upload and download
bandwidth limits, and a logical volume size limit. It also fixes two replay
consistency bugs and lets a client that crashed reopen offline from its own
local metadata.

**0.2.3 uses volume format 6.** Every computer must run `studiofs upgrade` on
its local cache before mounting with 0.2.3. See [Upgrade](#upgrade).

## Highlights

- Recoverable trash (opt-in): with `studiofs trash-days <name> 7`, items moved
  with the operating system's own Move to Trash are kept for 7 days and can be
  restored from the Windows Recycle Bin or Linux `gio`/`.Trash-<uid>` on any
  computer that uses the volume. `rm`, Shift+Delete and overwrites still delete
  permanently. The trash is off (0 days) by default.
- `studiofs umeta`: change the endpoint, bucket, region, access key, secret key
  or trash retention stored in PostgreSQL. Running 0.2.3 mounts switch to a new
  access/secret key pair after their next metadata poll, without remounting.
- Bandwidth limits: `--upload-limit <Mbps>` and `--download-limit <Mbps>` on
  `studiofs mount` and `studiofs settings`. `studiofs settings` applies new
  limits to running mounts without remounting. `studiofs status` shows the
  limits and the time spent waiting on them.
- Volume size limit: `studiofs quota <name> 500G` limits the logical size of
  all files. A write past the limit fails with "disk full", and `df`, Finder
  and Explorer show the limit and the free space.
- Crash recovery: a client that stopped uncleanly now reopens from its own
  local metadata and can keep writing while PostgreSQL is unreachable. It
  publishes the offline work when PostgreSQL returns.

## New and changed commands

| Command | What it does | Notes |
| --- | --- | --- |
| `studiofs upgrade <name>` | Upgrades a stopped format-5 cache to format 6 | **Required once per computer** |
| `studiofs trash-days <name> [<days>]` | Shows or sets shared trash retention | `0` (default) turns the trash off |
| `studiofs init … --trash-days <days>` | Creates a volume with the trash on | Optional |
| `studiofs umeta (--meta <dsn> <name> \| --disk <name>) …` | Updates shared S3 settings and trash retention | Upgrade every client first |
| `studiofs quota <name> [<limit>\|unlimited]` | Shows or sets the logical size limit | Binary units: `500G` = 500 GiB |
| `studiofs mount/settings --upload-limit/--download-limit <Mbps>` | Caps payload transfer per mount | `0` means unlimited (default) |

Reference: [configuration](https://github.com/valandreev/studiofs-cli/blob/main/docs/configuration.md);
guides: [trash](https://github.com/valandreev/studiofs-cli/blob/main/docs/user-guide/en/23-deleting-files-there-is-no-magic-trash-can.md)

## Fixes

- Overlapping writes that were still pending could be committed out of order,
  and the newer bytes could be lost. Commit order now follows write order.
- Replaying a rename after another client's unlink could bring back the
  deleted file without its content. The unlink now wins.
- A crashed client no longer needs a full rebuild from PostgreSQL when its
  local metadata is intact. The local journal is made durable before it is
  published, so the local copy is always safe to reopen.
- `quinn-udp` was updated to 0.5.16 for RUSTSEC-2026-0538.

## Download names

Archive names are shorter: `-msvc` and `-unknown-` are no longer part of them.
For example, `studiofs-0.2.3-x86_64-pc-windows.zip` and
`studiofs-0.2.3-x86_64-linux-gnu.tar.gz`. `BUILD-INFO.json` still records the
full Rust target triple. Update download scripts that build the old names.

## Upgrade

1. Install 0.2.3 on **every** computer that uses the volume. Older clients
   cannot publish into an upgraded volume, and an older mount can write stale S3
   settings back over `umeta` changes.
2. On each computer, unmount the volume and stop its janitors. Keep the local
   cache: it may hold unpublished changes.
3. On each computer, run `studiofs upgrade <name>`. It needs PostgreSQL and
   schema deployment privileges. After a timeout or error, run the same command
   again. Do not reinitialize the volume or clear the cache.
4. Mount as usual. Turn on the trash or a quota only when every computer is
   upgraded.

The upgrade does not turn on the trash, a quota or bandwidth limits. It sets
the database-wide janitor schema marker to 2. After that, 0.2.2 janitors stop
for every volume in that PostgreSQL database, including volumes still on
format 5. Use 0.2.3 janitors there.

Only volumes created with the 0.2.x PostgreSQL metadata layout are supported.
Older volumes are not converted.

## Rollback

There is no downgrade from format 6. A 0.2.2 binary refuses format-6 metadata
and cannot publish to or delete from the upgraded volume, so it cannot damage
trashed items. To stop using a feature, set `trash-days 0`, `quota unlimited`
or a bandwidth limit of `0`. Do not edit the format or schema version in
PostgreSQL by hand.

## Known limits

- Trash: `gio trash --empty` and "Empty Trash" empty every volume's trash on
  that computer. Trashed items use storage until they expire or are cleared,
  and S3 space is freed only by a later `studiofs janitor` run.
- `umeta`: access key and secret key change on live mounts. Endpoint, bucket
  and region apply after a remount. Keep the old key pair valid until every
  mount has completed a PostgreSQL poll.
- Bandwidth limits apply to mount traffic only. Snapshot workers and the
  janitor are not limited.
- Quota: each computer checks the limit against what it knows locally, so
  concurrent or offline writers can briefly go past it. Directories, symlinks
  and snapshot history do not count, so the quota does not predict the S3 bill.
- A computer that crashes while **both** PostgreSQL and S3 are unavailable does
  not mount again until PostgreSQL is reachable. Its local data is kept.
