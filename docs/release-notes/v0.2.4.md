# StudioFS 0.2.4

This release adds three storage features: a local-only scratch layer for
temporary files, adaptive zstd compression of remote payloads, and a background
check of the local cache that repairs damaged data. It keeps volume format 6,
so `studiofs upgrade` is not needed.

**Install 0.2.4 on every computer that uses a volume before you turn on
compression or create a new volume.** 0.2.3 clients cannot read compressed
objects. See [Upgrade](#upgrade).

## Highlights

- Scratch layer: files that match a `.studiofsignore` rule stay on the computer
  that created them. They are not uploaded to S3, not replicated through
  PostgreSQL, and not included in snapshots. Rules use `.gitignore` syntax and
  replicate like ordinary files. Renaming a scratch file to a tracked name, as
  in an atomic save of `shot.exr.tmp` to `shot.exr`, makes it tracked without
  copying its data. macOS `._*` sidecars are scratch by default.
- Compression: payload fragments are compressed with zstd before upload. A fast
  check stores data that does not compress, such as EXR or video, as it is. The
  local cache stays uncompressed, and the quota counts logical bytes. New
  volumes use `zstd:3`; existing volumes keep compression off until you turn
  it on.
- Cache scrub: a background worker checks the local cache against stored
  checksums, at most 20 MiB/s and only while the cache is otherwise idle. It
  downloads damaged objects again from S3. One pass runs every 7 days by
  default and resumes after a restart.

## New and changed commands

| Command | What it does | Notes |
| --- | --- | --- |
| `studiofs compression <name> [off\|zstd[:<level>]]` | Shows or sets the shared compression policy | Levels 1 to 19; `zstd` means `zstd:3` |
| `studiofs scratch list\|clean\|promote\|restore` | Lists, removes, promotes or restores scratch entries | Works mounted or offline with `--volume` |
| `studiofs status <name>` | New Scratch, Cache scrub and compression sections | Compression shows stored/logical ratio |
| `studiofs fsck <name> [--repair]` | Also checks the scratch tables | |
| `studiofs mount/settings --cache-scrub <bool>` | Turns the cache scrub on or off | On by default |
| `studiofs mount/settings --cache-scrub-interval-secs/-bytes-per-sec/-iops` | Tunes the scrub schedule and rate | Defaults: 7 days, 20 MiB/s, 200 IOPS |

Reference: [configuration](https://github.com/valandreev/studiofs-cli/blob/main/docs/configuration.md);
guide: [scratch layer and `.studiofsignore`](https://github.com/valandreev/studiofs-cli/blob/main/docs/user-guide/en/31-scratch-layer-and-studiofsignore.md),
with a sample `.studiofsignore` for Maya, Blender, Houdini, Nuke and Photoshop.

## Upgrade

1. Install 0.2.4 on **every** computer that uses the volume. 0.2.3 cannot read
   compressed objects or the format-4 metadata checkpoints that 0.2.4 serves.
2. Unmount and mount again. No `studiofs upgrade` step is needed, and the local
   cache is kept.
3. When every computer runs 0.2.4, turn on compression for an existing volume
   with `studiofs compression <name> zstd` if you want it. Only data uploaded
   afterwards is compressed; existing objects are not rewritten.

## Rollback

There is no downgrade to 0.2.3. 0.2.3 cannot read compressed objects or
format-4 checkpoints. `studiofs compression <name> off` stops compressing new
uploads but does not rewrite objects that are already compressed. To stop
using the scratch layer, remove the `.studiofsignore` rules; existing scratch
entries are then promoted automatically.

## Known limits

- Scratch files exist only on the computer that created them. If that disk is
  lost, they are lost. They are not in snapshots and are not backed up.
- Adding a rule does not move files that are already tracked; `studiofs status`
  lists them. Removing a rule promotes matching scratch entries automatically,
  up to 100,000 entries per directory; larger trees need
  `studiofs scratch promote`.
- If a peer creates a tracked file with the same name, the scratch entry is
  renamed to `<name>.scratch-conflict-<n>`.
- The cache scrub verifies only payloads that have a stored checksum. Payloads
  cached by 0.2.3 are checked after they are downloaded again.
- Compression applies to fragments prepared for upload after a policy change
  reaches the client.
