# StudioFS 0.2.5

StudioFS 0.2.5 establishes the first supported persisted-format baseline.
Volumes from 0.2.0–0.2.4 need an explicit upgrade. Pre-0.2.5 clients cannot
interoperate with an adopted volume.

## Compatibility baseline

- PostgreSQL schema components are `core` 1, `payload_gc` 2,
  `client_sessions` 1, `checkpoint_encodings` 1 and `event_publication_fence` 1.
- Shared metadata and `FormatInfo` use format 7. Local redb uses layout
  revision 6. New volume policies start at epoch 1 and write requirement 1.
- Events use `SFS-EVT` wire 1. Serving checkpoints are written in format 4
  with schema 1, and formats 1–4 remain readable.
- Read capabilities are `event.codec.v1`, `payload.stfs.v2`, `payload.stfs.v3`
  and `payload.sfec.v1`. The volume requires the same capabilities for writes
  except `payload.stfs.v2`. Maintenance requires `maintenance.payload_gc.v2`.

When a minor line changes schema or volume state, clients from the previous
minor line keep full read-write mount, read, write and delete access for the
entire new line. The window starts at 0.2.5 for the 0.2 line. Features that
would take away this access must wait until those clients are outside the
window. See the [full contract and supported-release matrix](../persisted-format-compatibility.md).

## Upgrade and rollback

`studiofs compatibility <volume>` reports what the current binary can do.
`studiofs upgrade <volume> --dry-run` previews pending migrations. Use the
[operator checklist](../user-guide/en/32-upgrades-and-version-compatibility.md#operator-checklist)
for backups, staged rollout and feature activation.

`studiofs upgrade <volume>` adopts shared format 5 or 6 into format 7. The
shared commit fences old publishers. Complete the upgrade on every stopped
cache before remounting. After an interruption, retry the same command with
the same cache and binary.

Additive feature preparation keeps the baseline serving format available.
After activation, use a documented `deactivate` path only while the volume's
persisted state remains compatible. Irreversible activation, committed local
revision cutover, Contract and format-7 adoption carry no downgrade guarantee.
See the [rollback limits](../persisted-format-compatibility.md#rollback-limits).

## Known limitations and release blockers

- macOS is the primary acceptance host for SFS-1020. Windows (SFS-1135)
  and Linux (SFS-1136) repeat the suite separately and both block release until
  they pass. The prior SFS-1019 WinFSP runs cover their tested binaries.
- Restore from a pre-cutover backup with its matching release only for
  disaster recovery. Changes made after the backup can be lost. `load` refuses
  version-4 dumps. If a v4 dump is your only copy, restore it with 0.2.4 and
  then adopt the restored volume using 0.2.5.
- The 0.3.0 upgrade source is 0.2.5 or later. SFS-982's older wording about
  mixed writers must be reconciled with the adjacent-minor read-write window.
  SFS-983 and SFS-984 should build on the current evaluator and explicit
  upgrade workflow. SFS-985 still needs sealed format-7 inputs and live
  cross-release evidence for PostgreSQL and the later Redis-compatible
  backend. Encrypted S3 objects from earlier releases remain in the readable
  data inventory. [SFS-982](https://linear.app/valandreev/issue/SFS-982),
  [SFS-983](https://linear.app/valandreev/issue/SFS-983),
  [SFS-984](https://linear.app/valandreev/issue/SFS-984),
  [SFS-985](https://linear.app/valandreev/issue/SFS-985).
- SFS-980's `payload_gc` 2 marker is monotonic and database-wide. Older
  Janitors must stay stopped. A dump does not include GC queue, sweep
  checkpoint or upload ledger state. Snapshot pins, upload fences and
  ambiguous objects must remain protected across upgrade and retry.
  [Janitor schema and recovery](../janitor-performance.md#schema-version-deployment-and-recovery-sfs-980).
- Publication still needs its local durability barrier, atomic PostgreSQL
  version advance and complete event batch. Replay must commit the complete
  batch and cursor together. The stamp query must be accounted for without
  weakening policy fencing, the durable journal or retry semantics.
  [PostgreSQL sync contract](../pg-sync-contract.md),
  [SFS-1014 publication fence](../../.agent/execplans/sfs-1014-event-publication.md).
