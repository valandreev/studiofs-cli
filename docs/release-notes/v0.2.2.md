# StudioFS 0.2.2

This release rewrites the standalone `studiofs janitor` command. It now cleans
large volumes in bounded, resumable steps. It checks every deletion against
PostgreSQL, reports progress while it runs, and returns exit codes that scripts
can act on. The background janitor inside mounted clients is unchanged.

## Highlights

- Known garbage first: each cycle drains a PostgreSQL queue of objects already
  known to be unused before it lists the bucket.
- Resumable orphan sweep: the S3 listing is streamed, and its position is saved
  in PostgreSQL per volume, so the next run continues where the last one stopped.
- Fenced deletion: each object is rechecked, claimed in PostgreSQL, deleted
  (all canonical keys, batched where the provider supports it) and confirmed.
  Snapshot-pinned, referenced and in-flight objects are kept.
- Bounded load: S3 requests are paced (default 4/s) and slow down by themselves
  on HTTP 429/503. PostgreSQL work is batched and sent one command at a time.
- Operations: progress every 5 seconds, `--output jsonl`, graceful Ctrl+C, and
  documented exit codes.

See [Maintenance and removing a volume](https://github.com/valandreev/studiofs-cli/blob/main/docs/user-guide/en/27-maintenance-and-removing-a-volume.md)
for the step-by-step guide and [configuration](https://github.com/valandreev/studiofs-cli/blob/main/docs/configuration.md#janitor) for
the reference.

## What changed in `studiofs janitor`

| Area | 0.2.1 | 0.2.2 | Action needed |
| --- | --- | --- | --- |
| Listing | Listed the whole bucket before any work | Streams the listing and resumes from a saved position | None |
| Coverage of one run | Whole bucket, however long it took | May be partial; the summary prints `scan coverage` | Repeat runs until `scan coverage: complete` |
| `--max-deletes` (default 500) | Listing continued after the cap | Counts confirmed deletions only and stops listing at the cap; 0 is rejected | Use `--dry-run` instead of `--max-deletes 0` |
| `--skip-newer-minutes` (default 15) | Grace period of 15 minutes | Same; unknown-age objects are also kept | None |
| New limits | — | `--max-scan-entries`, `--max-runtime-minutes`, `--s3-requests-per-second` (1–32, default 4) | Optional |
| New flags | — | `--full-scan` (restart the sweep), `--output text\|jsonl` | Optional |
| Deletion safety | One-pass check, fragment keys only | PostgreSQL recheck, per-object fenced claim, all canonical keys | None |
| Dry run | Reported candidates | Also writes nothing in PostgreSQL: no queue, checkpoint or fence changes | None |
| Exit codes | 0 or error | 0 complete, 2 partial, 3 lock busy, 4 unsafe, 5 failure (including any object that could not be checked or deleted), 130 second Ctrl+C | **Update scripts that treated any nonzero code as fatal** |
| Prerequisites | Volume set up on this computer and not mounted on it | Also requires PostgreSQL metadata and this computer's changes published; stops with exit code 4 otherwise | Let a mount finish syncing before unmounting |
| PostgreSQL schema | — | Versioned GC queue/checkpoint schema, checked before any work | **Apply it once with `studiofs init` (see below)** |
| Mounted background janitor | — | Unchanged | None |

Breaking changes for scripts: a run that stops at a limit now exits with 2
instead of 0, and `--max-deletes 0` is rejected.

## Upgrade

1. Install 0.2.2 on the computers that will run `studiofs janitor`.
2. Apply the schema once, from any of them, with the options used to create the
   volume: `studiofs init <name> --endpoint … --bucket … --access-key …
   --secret-key … --meta "<dsn>"`. Use exactly the same bucket: `init` creates
   a missing one. For an existing volume it applies the schema
   and then exits with `Volume '<name>' already exists`. **That is expected; do
   not run the `destroy` command it suggests.** Reapplying is safe.
3. Preview: `studiofs janitor <name> --dry-run --full-scan`.
4. Start small: `studiofs janitor <name> --max-deletes 100 --skip-newer-minutes 60`,
   then repeat or use `--loop`.

Only volumes created with the 0.2.x PostgreSQL metadata layout are supported;
older volumes are not converted.

## Rollback

There is no schema downgrade. To stop using the new command, stop running it:
the mounted clients do not depend on it. A binary built for an older schema
version refuses a newer schema with exit code 5 instead of using it. Do not
edit the schema version in PostgreSQL by hand. Interrupted runs need no
cleanup: confirmed work is kept, and unfinished claims expire after 60 seconds.

## Known limits

- A partial sweep is not a full cleanup. Only `scan coverage: complete` means
  the whole prefix was examined in that sweep.
- Behavior was tested against PostgreSQL 18 with RustFS, and with a Backblaze
  B2 adapter smoke test. Other S3 providers' consistency and multi-delete
  behavior is not guaranteed. On versioned buckets (B2 always versions), a
  deletion hides the object but does not remove older versions; use the
  provider's lifecycle rules for that.
- Throughput depends on network latency to PostgreSQL and on the S3 rate. In a
  test with 100 ms PostgreSQL latency, 500 orphans were deleted in 14 seconds
  ([release gate](https://github.com/valandreev/studiofs-cli/blob/main/docs/janitor-performance.md#release-gate-sfs-981);
  earlier measurements in [the benchmark](https://github.com/valandreev/studiofs-cli/blob/main/docs/perf/sfs-979-janitor-benchmark.md)).
