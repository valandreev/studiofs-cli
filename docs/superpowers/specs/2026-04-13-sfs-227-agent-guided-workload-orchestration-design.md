# SFS-227 Agent-Guided Workload Orchestration Design

## Goal

Add the first supported human-in-the-loop workload orchestration surface for
live investigation sessions so an attached agent can guide a real workload,
execute bounded automation where safe, pause for operator-driven steps where
required, and keep the investigation timeline aligned with what actually
happened.

The first built-in workflow target is an AJA-style hybrid scenario, but the
design must remain generic so later workloads can reuse the same format instead
of adding one-off orchestration code paths.

## Existing Base

- `crates/studiofs/src/diagnostics.rs` already provides attach discovery,
  controller lease enforcement, runtime snapshots, recent events, safe debug
  actions, profiling windows, evidence views, single-run reports, span
  comparisons, and hypothesis updates.
- `crates/studiofs/src/investigation.rs` already persists investigation cases,
  runs, marker-boundary snapshots, profiling windows, timeline entries, reports,
  comparisons, and hypotheses.
- `crates/studiofs/src/cli/internal.rs` already exposes hidden diagnostics
  helpers that mirror the live diagnostics protocol for development and tests.
- `docs/ideas/runtime-investigation-attach-prd.md` explicitly calls for an
  optional workload orchestration surface that mixes manual and automated steps.

## Chosen Approach

Introduce a generic hybrid workflow format with a controller-only orchestration
surface inside the existing diagnostics host.

The workflow engine does not expose arbitrary shell execution. Instead, it uses
an allowlisted tool catalog that can:

- call existing diagnostics operations
- invoke a limited set of StudioFS-owned internal CLI actions
- run explicitly registered workload scripts or wrappers
- read workflow-generated artifacts

Manual operator work remains first-class. The workflow can pause on a manual
step, require explicit acknowledgement, and record that acknowledgement in the
investigation timeline before later automated steps continue.

This keeps the first slice practical for partially scriptable workloads such as
AJA while protecting the repo and runtime from an unrestricted command surface.

## Workflow Model

Each workflow preset is a versioned declarative definition with:

- `workflow_id`
- `version`
- `title`
- `supported_workload`
- `description`
- ordered step list
- allowlisted tool references used by those steps
- recommended marker titles
- optional profiling hooks
- expected artifacts

The generic step kinds for the first slice are:

- `marker`
- `note`
- `profiling_window`
- `safe_action`
- `tool_step`
- `manual_step`
- `report_step`

Each step carries:

- `step_id`
- `title`
- `instructions`
- `kind`
- `requires_controller`
- `allowed_after`
- `expected_artifacts`
- `failure_policy`
- optional `on_enter_marker`
- optional `on_exit_marker`
- optional `operator_ack_text`

`tool_step` uses a catalog entry plus typed arguments. `manual_step` always
waits for explicit operator acknowledgement or skip. Acknowledgement becomes a
durable timeline event so the run can later be interpreted correctly.

## First Built-In Preset

The first preset should be `aja_hybrid_v1`.

It is still described using the generic format and acts as proof that the model
supports:

- automated preparation or wrapper-script launch
- explicit operator instructions for the AJA-controlled phase
- marker-aligned profiling windows around the interesting span
- post-run report generation and optional span comparison against a baseline run

The preset should document the intended operator flow clearly enough for repeat
use without re-inventing the steps each time.

## Tool Catalog

The workflow executor uses a stable registry-based tool catalog. The first slice
supports four tool families.

### Diagnostics Tools

These wrap existing live diagnostics capabilities:

- runtime snapshot
- recent events
- evidence view
- start/stop profiling window
- safe debug action invocation
- materialize report
- compare run span
- create or update hypothesis

### Internal CLI Tools

These wrap explicitly approved hidden internal CLI operations that already align
with the investigation model. The workflow engine does not expose the full
internal CLI surface automatically. Each command must be registered by a stable
`tool_id`.

### Script Hooks

These run explicitly registered StudioFS-owned scripts or wrappers for workload
setup and bounded automation. A script hook defines:

- executable
- fixed command template
- typed argument schema
- working-directory policy
- environment allowlist
- timeout
- artifact destinations

### Artifact Readers

These read structured artifacts generated by diagnostics or workflow execution,
such as profiling summaries, bundle files, workflow logs, and generated reports.

## Persistence Model

Add durable workflow state under the existing investigation store so workflow
progress survives reconnects and lease renewals.

Each workflow run belongs to a specific investigation run and stores:

- workflow preset identity and version
- current workflow status
- current step id
- per-step execution status
- operator acknowledgements
- tool-step invocation metadata
- artifact references
- failure summary when applicable

Per-step status should distinguish at least:

- `pending`
- `in_progress`
- `waiting_for_operator`
- `completed`
- `skipped`
- `failed`
- `aborted`

Workflow execution should append timeline entries for state transitions that are
important to later interpretation, especially:

- workflow started
- manual step acknowledged or skipped
- bounded tool step completed or failed
- workflow aborted or completed

The store should preserve enough detail for a later report to reconstruct which
parts of a run were agent-driven versus operator-driven.

## Diagnostics Surface

Extend the controller-only diagnostics protocol with workflow RPCs:

- `ListWorkflows`
- `StartWorkflow`
- `GetWorkflowRun`
- `AdvanceWorkflowStep`
- `AcknowledgeManualStep`
- `AbortWorkflow`
- `CompleteWorkflow`

The execution model is intentionally step-oriented. The client asks the host for
the current workflow state, then advances the next allowed step explicitly.
This keeps control flow observable and avoids hidden background automation.

For `tool_step`, the request references a registered `tool_id` plus typed
arguments. The host resolves that request against the catalog, enforces safety
rules, executes it, captures stdout/stderr metadata as artifacts, and returns a
structured outcome.

The hidden internal CLI should expose matching `diagnostics-workflow-*`
commands so the first workflow can be exercised locally in tests and by human
operators without an MCP adapter.

## Safety Boundaries

The workflow engine must not expose an arbitrary command runner.

Safety rules for the first slice:

- tools are selected by stable `tool_id`, not free-form shell text
- only catalog-registered commands may run
- each tool has an explicit argument schema
- each tool has a controlled working-directory policy
- each tool has an environment allowlist
- tool execution is cancellable and time-bounded
- workflow-managed writes are restricted to designated artifact/output
  directories
- destructive git and destructive filesystem operations are not allowed through
  the workflow executor
- manual operator steps cannot auto-complete without explicit acknowledgement

This protects the repo while still letting the attached agent do useful
orchestration work.

The user may still let the agent continue into full development follow-up after
the investigation reaches a supported hypothesis, but that follow-up happens
outside the workflow executor and uses the normal coding workflow rather than
the orchestration contract itself.

## Report And Comparison Integration

Workflow orchestration should reuse the existing investigation surfaces instead
of creating a parallel reporting system.

Specifically:

- marker steps should continue to capture boundary snapshots
- profiling steps should reuse the existing profiling coordinator
- report steps should call the existing single-run report materialization
- comparison steps should call the existing marker-span comparison flow
- hypothesis steps should reuse the existing hypothesis persistence and evidence
  linkage

This keeps workflow orchestration as a thin coordination layer over the
diagnostics and investigation model already shipped in `SFS-221`, `SFS-222`,
`SFS-223`, and `SFS-226`.

## Testing Strategy

Testing priority should focus on the scriptable and persistence-heavy parts of
the feature, while the manual path is validated through a documented human pass.

### `crates/studiofs/src/investigation.rs`

- workflow-run persistence
- step status transitions
- operator acknowledgement durability
- artifact reference persistence
- restart/reload behavior for in-progress workflow runs

### `crates/studiofs/src/diagnostics.rs`

- list/start/get/advance/ack/abort workflow RPCs
- controller enforcement for mutating workflow actions
- allowlisted tool resolution
- tool-step failure handling and fail-open behavior where applicable
- integration with marker snapshots, profiling windows, reports, and
  comparisons

### `crates/studiofs/src/cli/internal.rs`

- parsing for hidden `diagnostics-workflow-*` helper commands

### Human Validation

Document and perform one operator validation pass against the first AJA-style
workflow preset. That validation should confirm:

- the operator instructions are clear
- the manual pause/resume behavior is not fragile
- the timeline remains aligned with the real workload phases
- the generated artifacts are sufficient for a follow-up report/comparison

## Documentation Deliverables

This slice should ship with:

- the generic workflow format documented for maintainers
- the first built-in preset documented for operators
- a short repeatable operator playbook for the hybrid AJA-style path

The documentation should explain which steps are automated, which require human
action, and where resulting artifacts can be found.

## Non-Goals

- no arbitrary shell execution surface
- no unrestricted git or filesystem mutation through workflow tools
- no attempt to automate every GUI interaction in the first slice
- no generalized remote orchestration platform
- no replacement of the normal post-investigation coding workflow
