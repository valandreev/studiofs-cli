## Surprises & Discoveries

number. `crates/studiofs/build_support.rs` uses the manifest base and Git history;
an uncommitted new base may report dev.unknown. Only a clean exact vBASE tag
reports the plain version. `docs/development.md` documents this distinction.

Codebase Memory project E-dev-studiofs-cli resolves to this checkout. Coverage
checks on build_support.rs, schema.rs, store.rs, namespace_ops.rs, statfs.rs and
WinFSP context.rs reported metadata_match with no recorded gaps on 2026-11-12.
This is best-effort coverage, not exhaustive proof. Recheck on each feature branch.
The current trash helper explicitly logs destructive deletion; FormatInfo calls
itself immutable; statfs hardcodes 1024^5 bytes. These are starting points, not
proof that any proposed replacement is safe.

### Milestone 2: SFS-1054 recoverable native trash


Create a concrete feature ExecPlan after bounded discovery. Its FIRST engineering
milestone proves native Windows recycle feasibility: Explorer offers recycling
on the WinFSP disk volume, native software discovers/opens trash roots, per-SID
recycle behavior works with the actual security descriptors, and explicit trash
intent can be distinguished from ordinary unlink/replacement. Prove an enforced
persisted compatibility boundary: incompatible old binaries reject before
writing retained entries. An ignored capability flag or documentation is
insufficient. Record actual commands, old binary identities, mounted artifacts
and outcomes. If impossible, report concrete evidence to the parent/user;
never silently substitute CLI-only UX for native UI. Record Linux/macOS native
proof separately; Windows tests do not establish their support.

The implementation contract is self-contained here: trash is shared per volume,
filtered by current original-parent identity and access. Parent moves preserve
identity; missing parents, including parents themselves trashed, hide entries
until restored. Recreating the old path grants nothing. Read-only can list;
permanent purge/Clear requires current original-parent write access. Restore
requires both original-parent and destination write access, plus explicit
native collision choices; denial
or failure leaves data recoverable. There is no administrator bypass until a
future ACL redesign. The configured mount principal is not authenticated
per-request OS identity; do not invent a new isolation guarantee.

Only native OS Move to Trash retains data. rm, rm -rf, Shift+Delete, overwrite
and rename replacement bypass it. Files, directory trees, hard links and open
handles need defined native behavior. Whole-day TTL (time to retain an entry)
is global per volume. New volumes default to 0, disabling retention. An explicit
post-creation CLI command changes the same versioned shared setting and
replicates it. This needs a new mutable volume-setting path within the enforced
compatibility boundary, not machine-local settings or mutation of FormatInfo.
Positive periods apply to all entries from their initial deletion time; shortening
can make entries immediately eligible. Zero disables new retention without
immediately purging existing entries or suspending their expiry; retain the
last positive TTL for existing entries. Re-enabling applies the new period.

Offline unpublished data stays locally recoverable; peers see it after required
metadata replication and payload publication. Retained trash counts against
logical quota, including hidden entries; no early pressure purge is allowed.
Use existing GC/janitor protections for live links, handles, snapshots and local
unpublished payloads. Define/test atomic retryable transitions and authority
fencing for offline restore versus peer purge/expiry before enabling retention;
local purge alone never authorizes remote payload deletion. Do not promise a
single global winner while offline. Acceptance covers those conflicts, crash
recovery, permissions, controlled-clock expiry and configuration convergence,
with native restore/list/Clear evidence and English/Ukrainian guides.

### Milestone 3: SFS-1056 stopped-mount credential rotation


After bounded discovery, write its own concrete plan tracing format loading,
lifecycle locking, credential persistence and client construction. Add explicit
atomic same-storage credential replacement on an unmounted volume. Preserve
UUID, endpoint, bucket, prefix, region, encryption identity, metadata binding,
cache and pending writes. Hot reload is unnecessary. Define local versus shared
credential scope and protect against stale replicated FormatInfo restoring old
keys. Use protected secret input and bounded permission validation against the
same storage; any temporary validation object must be isolated and cleaned up.
Invalid input, timeout, interruption and failed commit leave the old complete
pair and pending data intact. Acceptance proves remount read/publication using
new credentials, mounted-volume rejection and synthetic-secret redaction across
output/errors/Debug. Record isolated service-backed and native remount proof
separately, and document peer behavior and provider revocation as separate work.

### Milestone 4: SFS-1057 aggregate upload limit


After tracing upload workers, encrypted transfer boundaries, retries, cancellation
and status, write its own plan. Implement one per-mount aggregate cap on actual
encrypted payload upload bytes across workers, with bounded burst allowance and
correct retry charging. Do not apply it to downloads, PostgreSQL/control traffic
or fleet-wide traffic. Include limits below one object size, unlimited mode,
invalid configuration and precedence. Owned cancellable waits must terminate
on shutdown. Keep foreground durability and existing cache-pressure admission
intact. Deterministic-clock tests prove aggregate rate and burst behavior;
focused runtime tests prove cancellation/retry accounting. Status distinguishes
intentional throttling/backlog from failure and full publication. Explain delayed
peer visibility and backlog pressure without depending on future dashboards.

### Milestone 5: SFS-1058 logical quota


After discovering write/truncate/append admission, writer authority, counters,
replay and statfs consumers, write its own plan. Logical quota limits logical
file bytes, not S3 bills. Define sparse files, hard links, deleted-open data,
trash and snapshots before changing accounting. USED_SPACE is currently based
on referenced payloads and must not be assumed to equal logical lengths.
Persist optional shared policy with authorization, propagation and compatibility.
Reserve local-authority growth including accepted uncommitted writes and
concurrent handles; statfs-only enforcement is insufficient. Release only the
failed operation's reservation, reconcile restart/replay, and avoid duplicate
hard-link accounting. Cover restore/replacement, shrink and deletion. At/above
a lowered quota, free space saturates at zero while reads, non-growing overwrite,
cleanup, flush/fsync and shutdown remain usable. Retained trash stays charged
until purge/expiry; snapshots can retain physical bytes independently.

Prove consistent quota/disk-full bridge errors and mounted capacity reports.
Two-client lag/offline tests demonstrate accepted soft cross-client overshoot;
there is no strict global cap and no foreground PostgreSQL/S3 admission wait.
