# 09. Перевіряємо інфраструктуру

> **Українська чернетка для редакторського погодження.** Текст ще не затверджено.

Bucket уже створено, PostgreSQL працює, VPN показує зелений індикатор. Можна встановлювати StudioFS? Майже. Зелений індикатор — приємний співрозмовник, але він не знає, чи правильний у нас пароль до бази.

Перед встановленням перевіримо весь шлях **із того робочого комп’ютера, на якому працюватимемо з файлами**. Успішне підключення із самого VPS не доводить, що монтажна станція бачить той самий сервер. Краще з’ясувати це зараз, ніж під час першого копіювання матеріалів зі знімання.

## Спочатку — адреси й маршрут

Зберіть параметри з трьох попередніх розділів. Для S3 потрібні endpoint, bucket, region і пара ключів; для PostgreSQL — адреса, порт, користувач, пароль і домовленість про TLS. Секрети тримайте в менеджері паролів. У звичайній нотатці достатньо записати, де їх знайти.

Переконайтеся, що VPN увімкнено й робочий комп’ютер має маршрут до бази. Для Tailscale повторіть:

```bash
tailscale status
tailscale ping 100.101.102.103
```

Тут і далі `100.101.102.103` — приклад із попереднього розділу: замініть його адресою свого сервера. Для NetBird перевірте стан підключення та доступ до потрібного вузла у своєму клієнті.

Якщо використовуєте ім’я сервера, перевіряйте з’єднання **саме за цим ім’ям**. Успіх за IP-адресою не підтверджує, що DNS на робочому комп’ютері налаштовано правильно. А для TLS ім’я ще й має відповідати сертифікату сервера.

Доступність TCP-порту можна перевірити в PowerShell:

```powershell
Test-NetConnection 100.101.102.103 -Port 5432
```

На macOS або Linux, якщо встановлено `nc`:

```bash
nc -vz 100.101.102.103 5432
```

Очікуємо `TcpTestSucceeded : True` або повідомлення про успішне TCP-з’єднання. Якщо цього немає, спочатку перевірте VPN, маршрут, firewall і публікацію порту PostgreSQL. Заміна пароля не відчинить закритий порт.

## PostgreSQL: не лише порт, а й справжній вхід

Для наступної перевірки потрібен **клієнт `psql` на робочому комп’ютері**. Він входить до клієнтських інструментів PostgreSQL; встановлювати локальний сервер бази не потрібно. Якщо `psql` не знайдено, встановіть клієнт або додайте його каталог до `PATH`.

Спершу визначте, як захищене підключення. Це важливо і для тесту, і для майбутнього параметра `--meta` у StudioFS.

Для сервера з налаштованим TLS використовуйте його справжнє DNS-ім’я та `sslmode=require`. StudioFS у цьому режимі вимагає TLS і перевіряє сертифікат сервера, зокрема відповідність імені. Поточний клієнт використовує вбудований набір довірених кореневих сертифікатів; самопідписаний сертифікат чи приватний центр сертифікації потребують окремої перевірки сумісності. Не припускайте, що додавання сертифіката в операційну систему автоматично налаштує StudioFS.

У простому Docker-прикладі з розділу 07 TLS для PostgreSQL окремо не налаштовано. Якщо весь шлях до бази проходить захищеною приватною мережею і ви свідомо покладаєтеся на VPN, можна явно вибрати `sslmode=disable`. Це вимикає **TLS PostgreSQL**, а не шифрування VPN. Не використовуйте таку схему для незахищеного підключення через інтернет; якщо база доступна через шлюз, врахуйте також ділянку від шлюзу до бази.

Якщо режим не вказано, поточний StudioFS віддає перевагу TLS, але може перейти на незашифрований транспорт, коли сервер TLS не підтримує. Тому відсутність помилки ще не означає, що підключення зашифроване.

Для перевірки нашого VPN-прикладу виконайте однією командою:

```bash
psql "host=100.101.102.103 port=5432 user=studiofs dbname=studiofs sslmode=disable connect_timeout=10" -W -c "SELECT current_database(), current_user;"
```

Пароль введіть у відповідь на запит: він не потрапить у текст команди. Очікуємо базу `studiofs` та ім’я вашого користувача. Якщо ви змінили користувача в попередніх прикладах, відповідь також буде іншою.

Для TLS-сервера замініть `host` на його DNS-ім’я, а `sslmode=disable` на `sslmode=require`. Врахуйте, що `psql` і StudioFS використовують різні TLS-клієнти: успіх цього тесту ще не підтверджує, що StudioFS довірятиме тому самому сертифікату.

Поточний `studiofs init` також підключається до службової бази `postgres`. Перевірте її з тими самими параметрами маршруту й захисту:

```bash
psql "host=100.101.102.103 port=5432 user=studiofs dbname=postgres sslmode=disable connect_timeout=10" -W -c "SELECT 1;"
```

Очікуємо `1`. Якщо `studiofs` ще не створено, перша команда повідомить про відсутню базу. Її може заздалегідь створити адміністратор; інакше користувачеві, від якого виконуватиметься `init`, потрібне право створення бази. У вже створеній `studiofs` потрібні права на створення службових об’єктів і подальшу роботу з ними. Самого дозволу на вхід недостатньо — узгодьте ці права з адміністратором, особливо для керованого PostgreSQL.

Не запускайте `studiofs init` просто як тест пароля. Ця команда створює стан нового тому, може створити базу та bucket. До неї перейдемо після встановлення програми.

## S3: перевіряємо маленьким файлом

Вхід у панель провайдера підтверджує доступ до панелі. Нам же потрібно, щоб **окремі ключі StudioFS** могли переглядати bucket, записувати, читати й видаляти об’єкти.

Це можна перевірити S3-клієнтом із підтримкою вашого endpoint. Нижче — варіант через **AWS CLI**, окрему програму, яка працює також із багатьма S3-сумісними сервісами. Якщо її ще немає, скористайтеся [інструкцією встановлення AWS CLI](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html). Це допоміжний інструмент для перевірки, а не залежність StudioFS.

Створіть окремий профіль:

```bash
aws configure --profile studiofs-preflight
```

На запити введіть Access Key ID, Secret Access Key і регіон із панелі провайдера. Формат виводу можна залишити типовим. **AWS CLI збереже ключі в локальних файлах конфігурації та облікових даних**: працюйте у своєму обліковому записі ОС і не додавайте ці файли до проєкту чи листування.

У прикладах нижче замініть endpoint, bucket і region своїми значеннями. Використовуйте саме S3 API endpoint, а не адресу вебпанелі. Для віддаленого сховища потрібен HTTPS.

```bash
aws --profile studiofs-preflight --endpoint-url https://s3.example.com --region us-east-1 s3api list-objects-v2 --bucket studiofs-projects-demo --max-keys 1
```

Успішна відповідь без помилки доступу — добрий початок; порожній bucket також нормальний. Але перегляд списку не перевіряє запис.

Створіть у поточному локальному каталозі невеликий текстовий файл `studiofs-connection-test.txt` із будь-якою впізнаваною фразою, без приватних даних. Для тестового об’єкта оберіть **новий, ще не зайнятий ключ поза каталогами томів**. Наприклад, замініть `UNIQUE-ID` у всіх наступних командах власним унікальним значенням. Запис за наявним ключем може замінити чужий об’єкт.

```bash
aws --profile studiofs-preflight --endpoint-url https://s3.example.com --region us-east-1 s3api put-object --bucket studiofs-projects-demo --key _preflight/UNIQUE-ID/connection.txt --body studiofs-connection-test.txt
```

Тепер завантажте його назад під іншою локальною назвою:

```bash
aws --profile studiofs-preflight --endpoint-url https://s3.example.com --region us-east-1 s3api get-object --bucket studiofs-projects-demo --key _preflight/UNIQUE-ID/connection.txt studiofs-connection-test-downloaded.txt
```

Відкрийте завантажений файл і перевірте фразу. Нарешті приберіть **лише створений вами тестовий об’єкт**:

```bash
aws --profile studiofs-preflight --endpoint-url https://s3.example.com --region us-east-1 s3api delete-object --bucket studiofs-projects-demo --key _preflight/UNIQUE-ID/connection.txt
```

За потреби повторіть перегляд списку з `--prefix _preflight/UNIQUE-ID/`, щоб перевірити результат. У bucket із версіонуванням видалення може залишати попередню версію: це поведінка сховища, а не помилка StudioFS.

Усі чотири операції мають пройти з тими самими ключами. Якщо політика доступу обмежує дозволені префікси, успіх у `_preflight/` не доводить доступ до майбутнього `<назва-тому>/objects/`. Узгодьте з адміністратором права саме на робочий префікс StudioFS; не виправляйте відмову, роблячи bucket публічним.

## Якщо перевірка зупинилася

Помилка розпізнавання імені зазвичай веде нас до DNS або неправильної адреси. Тайм-аут підключення — до маршруту, firewall чи недоступного сервісу. Відмова PostgreSQL в автентифікації — до користувача, пароля та правил доступу сервера; повідомлення про відсутню базу — до її створення.

Для S3 `AccessDenied` означає, що треба перевірити ключі й політику доступу. Помилки підпису запиту можуть вимагати перевірки регіону, endpoint, секретного ключа й системного часу. Помилка сертифіката потребує перевірки адреси та довіри до сертифіката, а не вимкнення захисту навмання.

Якщо звертаєтеся по допомогу, передавайте назву невдалої операції та очищений текст помилки. Не надсилайте секретний ключ, пароль або повний DSN із паролем.

## Що залишимо собі перед встановленням

Замість скриншотів із секретами збережіть коротку робочу нотатку:

| Що записати | Приклад або пояснення |
| --- | --- |
| S3 endpoint, bucket, region | Точні значення з панелі провайдера |
| Де лежать ключі | Назва запису в менеджері паролів |
| PostgreSQL host, port, user | Приватна адреса або DNS-ім’я та погоджений користувач |
| Бази | Доступ до `postgres`, стан підготовки `studiofs` |
| Захист підключення | TLS із `sslmode=require` або свідомо обраний VPN-сценарій |
| Результат перевірки | З якого комп’ютера й коли пройшли S3-операції та SQL-запити |

Публічний порт PostgreSQL має залишатися закритим згідно з налаштуваннями попереднього розділу. Для S3 перевірте, що bucket приватний, а правила автоматичного видалення не прибиратимуть об’єкти майбутнього тому.

Тепер ми знаємо, що робочий комп’ютер дістається обох сервісів і має потрібні облікові дані. Це ще не тест змонтованого диска: його проведемо після встановлення й створення тому, на невеликих файлах, перш ніж переносити справжній проєкт. Далі оберіть розділ для своєї системи: [Windows](10-install-studiofs-on-windows.md), [macOS](11-install-studiofs-on-macos.md) або [Linux](12-install-studiofs-on-linux.md).
