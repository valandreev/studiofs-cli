# 28. Усунення несправностей: коли кіт перестає муркотіти

Диск не підключається, колега не бачить учорашній рендер, а SSD раптом закінчився? Почнімо з того, що саме не працює. Перевстановити все завжди встигнемо. А от незавантажені зміни краще спершу зберегти.

## Спочатку — три короткі перевірки

У прикладах `myvolume` — назва вашого тому. Замініть її на свою.

```bash
studiofs --version
studiofs settings
studiofs status myvolume --verbose
```

Перша команда показує версію клієнта, друга — збережені налаштування майбутніх підключень, третя — стан тому та доступні діагностичні показники. `settings` без параметрів нічого не змінює. Налаштування не обов’язково збігаються з чинним підключенням: параметри могли перевизначити під час запуску.

Якщо підключали том з окремим каталогом кешу, вкажіть той самий **базовий каталог**, без додавання UUID:

```powershell
studiofs status myvolume --verbose --cache-dir D:\StudioFSCache
```

Не сприймайте порожню чергу чи відсутні показники як доказ завершеної синхронізації. Частина даних доступна лише від запущеного підключення; застарілий знімок не описує поточний стан.

**Поки причина невідома, не видаляйте кеш і локальну базу та не створюйте том заново.** Там можуть залишатися єдині копії змін, які ще не дійшли до сховища. `destroy`, ремонт метаданих і ручне прибирання службових каталогів — не перші кроки діагностики.

## Диск узагалі не підключається

Збережіть повний текст помилки. Різниця між «немає локального тому», «не завантажився драйвер» і «сервер недоступний» суттєвіша, ніж здається о третій ночі.

* **Невідома команда або параметр.** Перевірте `studiofs mount --help` саме у встановленій версії. Поточна команда не має параметра `--tray`: на Windows і macOS StudioFS автоматично пробує показати індикатор, якщо доступне графічне середовище. Невдалий запуск індикатора сам по собі не зупиняє підключення.
* **Том не знайдено.** Перевірте написання назви, обліковий запис ОС і `STUDIOFS_CLIENT_ROOT`. На іншому комп’ютері наявний спільний том підключають через `discover`, як у [главі 16](16-connect-a-second-computer-studiofs-discover.md). Повідомлення `status` може радити `init`, але воно не доводить, що потрібно створювати новий том.
* **Зайнята літера або точка підключення.** На Windows виберіть вільну літеру, наприклад `Z:`. На macOS і Linux перевірте каталог та права свого користувача. Якщо там уже працює StudioFS, спершу закрийте програми й виконайте звичайне відключення за [главою 17](17-unplug-safely-studiofs-umount.md). Не видаляйте lock-файли, щоб обійти активне підключення.
* **Термінал не повертає запрошення.** Це нормальна поведінка: звичайний `mount` працює в передньому плані. Не закривайте його як «завислий». Для фонового запуску є `--detach`.

Для повторного запуску з докладнішим журналом, **після звичайного відключення попереднього підключення**, можна використати:

```powershell
studiofs --log-level debug mount myvolume Z:
```

На macOS або Linux замість `Z:` вкажіть свій каталог. `--log-level` стоїть перед `mount`. Якщо ви використовували окремий кеш чи інші параметри, збережіть їх і в цій команді.

## Помилка WinFSP або FUSE

### Windows

Перевірте, чи встановлено **WinFSP**, а не лише сам StudioFS. Далі звіртеся з [інструкцією встановлення](10-install-studiofs-on-windows.md).

Під час першого підключення StudioFS може запросити UAC, щоб налаштувати інтеграцію WinFSP із менеджером підключень Windows. Якщо запит відхилили, початкове налаштування може не завершитися. У сеансі служби чи CI інтерактивний UAC недоступний — адміністратор має підготувати систему заздалегідь. Звичайні наступні підключення не потребують постійної роботи від адміністратора.

### macOS

Потрібен **macFUSE** і дозволи, яких вимагає його встановлення. Якщо система просить дозволити компонент або перезавантажитися, завершіть ці кроки за [главою 11](11-install-studiofs-on-macos.md).

### Linux

Поточний backend використовує **FUSE3**. Перевірте утиліту й пристрій ядра:

```bash
fusermount3 --version
ls -l /dev/fuse
```

Якщо бібліотека не знаходиться під час збирання, перевірте пакунки розробки FUSE3 за [главою 12](12-install-studiofs-on-linux.md). Якщо `/dev/fuse` відсутній або недоступний, потрібна перевірка модуля ядра й дозволів. У контейнері також потрібен дозволений доступ до FUSE на хості: встановлення пакунка всередині контейнера цього не гарантує. Не починайте з запуску всього від `root`.

## Помилка PostgreSQL або VPN

**Timeout**, **connection refused**, помилка DNS і **password authentication failed** означають різні речі.

1. Перевірте, чи підключено Tailscale або NetBird і чи сервер доступний у приватній мережі. Статус VPN «підключено» ще не гарантує дозвіл на PostgreSQL у правилах доступу.
2. Звірте адресу й порт із налаштуваннями сервера. Перевірте firewall, VPN ACL та стан самого PostgreSQL за [главами 7](07-postgresql-the-brain-behind-the-files.md) і [8](08-tailscale-netbird-a-private-path-to-postgresql.md).
3. Якщо мережа працює, перевірте користувача, пароль, назву бази й серверні правила автентифікації. Не відкривайте публічний порт PostgreSQL як спосіб «полагодити VPN».

За наявності клієнта `psql` можна перевірити справжнє підключення з робочого комп’ютера. Замініть адресу та користувача на свої; пароль введіть у запиті:

```bash
psql -h VPN_SERVER_ADDRESS -p 5432 -U studiofs -d studiofs -W -c "SELECT 1;"
```

Відповідь `1` підтверджує доступ цього користувача до цієї бази. Вона не перевіряє S3 і не гарантує всі потрібні права для ініціалізації тому.

Втрата PostgreSQL не обов’язково миттєво зупинить уже підключений диск: StudioFS працює з локальними метаданими. Але обмін змінами між клієнтами потребує відновленого зв’язку.

## Папки видно, але файл не відкривається

Якщо кешовані файли читаються, а новий великий файл — ні, перевірте доступ до **S3**. Видимість назви файлу ще не підтверджує доступність його вмісту.

Звірте endpoint, bucket, регіон і чинність ключів. У журналі шукайте помилки DNS, TLS, timeout або `AccessDenied`. Перевірте також стан сховища, квоту й проксі перед ним. Несправність S3 можлива навіть за справного VPN до PostgreSQL: це окремі маршрути доступу.

Не вимикайте перевірку сертифікатів і не перемикайте HTTPS на HTTP навмання. Якщо серверна адреса змінилася, погодьте нову адресу з адміністратором. Докладніше про налаштування — у [главі 6](06-s3-a-home-for-your-files.md).

Помилка `Permission denied` може також стосуватися прав на сам файл. Звірте користувача й параметр `--principal`, якщо команда використовує ACL. Наявність прав на bucket не скасовує прав усередині тому.

## Збереження завершилося, а колега бачить старий файл

У StudioFS збереження на одному комп’ютері та публікація для інших — різні етапи. Закриття файлу не є підтвердженням, що всі колеги вже отримали нову версію.

Спершу перевіряйте **комп’ютер автора змін**: чи він увімкнений, чи працює підключення, чи доступні S3 та PostgreSQL. Подивіться `status --verbose` і журнал на повторні спроби завантаження або публікації. Потім перевірте зв’язок на комп’ютері колеги.

Якщо доступний індикатор, червона пульсація означає, що локальним змінам ще потрібна синхронізація. Анімований синьо-жовтий прапор з’являється після підтвердження віддаленого завершення прийнятих цим підключенням даних і метаданих. Відсутній, застарілий чи невизначений стан нічого такого не підтверджує. Індикатор автора не засвідчує, що конкретна програма колеги вже перечитала файл.

Залиште комп’ютер автора працювати й відновіть зв’язок. Після підтвердженої синхронізації попросіть колегу оновити список файлів або заново відкрити файл у програмі. Перед цим збережіть її власні правки. Не переписуйте спільний файл старою локальною копією, щоб «проштовхнути оновлення».

Про затримки й спільну роботу докладніше — у [главах 19](19-sync-bad-wi-fi-and-other-surprises.md) та [21](21-two-people-one-file-collaboration-and-conflicts.md).

## Кеш заповнився або закінчилося місце на SSD

Перевірте дві речі: ліміт кешу StudioFS і вільне місце на **фізичному диску**, де він лежить. Збільшити ліміт на заповненому SSD — приблизно як написати «великий» на маленькій валізі.

За замовчуванням клієнтський корінь — `~/.studiofs` (на Windows — у домашньому каталозі користувача). Локальні метадані лежать у `meta/<назва>`, типовий базовий каталог кешу — `meta/<назва>/cache`, а всередині дані розділено за UUID тому. `STUDIOFS_CLIENT_ROOT` змінює клієнтський корінь; `--cache-dir` або збережене `cache_dir` можуть спрямувати кеш на інший диск.

StudioFS прибирає придатні до витіснення кешовані дані автоматично. Ще не синхронізовані зміни — інша справа: ручне видалення кешу може їх знищити. Припиніть нові великі записи, відновіть S3/мережу й звільніть місце за рахунок **інших, завідомо непотрібних файлів** на цьому диску.

Зміну ліміту або розташування кешу плануйте за [главою 20](20-cache-why-is-the-cloud-using-my-ssd.md). Нове значення `studiofs settings` не переносить поточний кеш і не змінює вже запущене підключення. Не спрямовуйте клієнт на порожній кеш, поки старий містить незавершені зміни.

## Файл зник або папка виявилася порожньою

Спершу переконайтеся, що дивитеся саме на підключений диск, правильний том і потрібну папку. Після відключення звичайний каталог точки підключення може виглядати порожнім — це ще не доказ видалення файлів.

Запитайте автора, де саме він зберіг файл і чи завершилася його синхронізація. Перевірте, чи файл не перейменували або не перемістили. Порівняйте версії клієнтів і уточніть у адміністратора ідентичність тому: однакова локальна назва на двох комп’ютерах сама по собі не доводить, що це один спільний диск.

Якщо є підозра на видалення або конфлікт, припиніть зміни в цій папці та збережіть доступні незалежні копії. Не запускайте повторний `init`, відновлення поверх чинного тому чи масове копіювання без розуміння причини. Перевірте резервні копії разом з адміністратором. StudioFS не має універсального кошика, який поверне все одним кліком.

## Коли потрібна допомога

Якщо причина не стала зрозумілою, підготуйте версію StudioFS, ОС, час події з часовим поясом, команду запуску без секретів, точну помилку й короткий опис: що очікували та що сталося. Додайте результат `status --verbose` і відповідний фрагмент журналу. Для фонового підключення журнали лежать у `<клієнтський корінь>/logs`; для звичайного запуску дивіться термінал.

Перед передаванням перевірте матеріали й приховайте паролі, ключі S3, токени та повні DSN із секретами. Не надсилайте весь `config.toml` або локальну базу без окремої потреби. У [наступній главі](29-logs-diagnostics-and-asking-for-help.md) розберемо, як зібрати корисний діагностичний звіт. Кіт може мовчати з багатьох причин; точний текст помилки звужує коло підозрюваних краще за перевстановлення.
