# 12. Встановлюємо StudioFS на Linux

На Linux StudioFS підключає сховище через **FUSE3**. Цей компонент дозволяє програмі показати файли із S3 як звичайну папку: монтажна програма бачить шлях до матеріалів, а StudioFS займається їхнім отриманням і збереженням.

У цій главі підготуємо систему, зберемо консольну програму й перевіримо, чи вона запускається. Створення тому та справжнє підключення сховища залишимо наступним главам. Папка для майбутнього диска поки що буде порожньою — це нормально, матеріали ще не приїхали.

## Який Linux підійде?

У репозиторії є перевірки для **Ubuntu 24.04** і **Rocky Linux 9**. Для перевірки справжнього підключення на Rocky документація вимагає **9.4 або новішу версію**. Це орієнтири для вибору робочої системи, а не обіцянка, що будь-який дистрибутив із подібною назвою вже перевірено.

Нижче наведені команди для цих двох систем. На Debian, Fedora, Arch та інших дистрибутивах набір і назви пакунків можуть відрізнятися; окремих перевірених інструкцій для них тут поки немає.

Для збирання потрібні Git, компілятор C/C++, інструменти збирання, `pkg-config` і **Rust 1.95 або новіший** із Cargo. Якщо Rust ще немає, встановіть його за [офіційною інструкцією Rust](https://www.rust-lang.org/tools/install), потім відкрийте новий термінал і перевірте:

```bash
rustc --version
cargo --version
```

Знадобляться також місце на локальному диску для вихідного коду й результатів збирання та доступ до інтернету для завантаження залежностей. Права адміністратора потрібні для системних пакунків; саму програму збиратимемо й запускатимемо від свого звичайного користувача.

## Встановлюємо системні залежності

### Ubuntu 24.04

Відкрийте термінал і виконайте:

```bash
sudo apt-get update
sudo apt-get install -y build-essential git ca-certificates curl pkg-config \
  fuse3 libfuse3-dev libgtk-3-dev libxdo-dev
sudo apt-get install -y libappindicator3-dev || \
  sudo apt-get install -y libayatana-appindicator3-dev
```

`fuse3` надає утиліти для підключення, зокрема `fusermount3`, а `libfuse3-dev` — файли, потрібні для збирання StudioFS. GTK та бібліотеки індикатора потрібні компонентам інтеграції з робочим столом, які входять до поточної програми. Навіть якщо ви плануєте працювати переважно в терміналі, ці залежності для збирання пропускати не варто.

Остання команда спершу пробує встановити один пакунок індикатора, а якщо він недоступний — альтернативний. Такий самий вибір використано в перевірках репозиторію.

### Rocky Linux 9.4 і новіший у гілці 9

Частина потрібних пакунків надходить із додаткових репозиторіїв. Команди нижче вмикають EPEL та CRB, тобто змінюють системні джерела пакунків. На робочій станції, яку адмініструє студія, узгодьте це із системним адміністратором.

```bash
sudo dnf install -y dnf-plugins-core epel-release
sudo dnf config-manager --set-enabled crb
sudo dnf install -y ca-certificates curl gcc gcc-c++ git make \
  gtk3-devel libappindicator-gtk3-devel fuse3 fuse3-devel \
  libxdo-devel openssl-devel pkgconf-pkg-config
```

Цей перелік відповідає залежностям у сценарії перевірок Rocky. Якщо пакунок не знаходиться, спочатку перевірте доступність репозиторіїв і версію системи. Не варто навмання замінювати FUSE3 на старий FUSE2: поточний Linux-компонент StudioFS використовує саме третю версію.

## Перевіряємо FUSE3

Для обох систем перевірка однакова:

```bash
pkg-config --modversion fuse3
fusermount3 --version
ls -l /dev/fuse
```

Перша команда має показати версію бібліотеки: для збирання потрібна **libfuse3 щонайменше 3.2**. Друга перевіряє, що утиліта `fusermount3` доступна. Третя показує пристрій ядра, через який відбувається підключення.

Якщо `/dev/fuse` відсутній на звичайній Linux-системі, адміністратор може спробувати завантажити модуль:

```bash
sudo modprobe fuse
```

Після цього повторіть перевірку пристрою. У контейнері або обмеженому середовищі одного встановлення пакунків недостатньо: хост має надати доступ до `/dev/fuse` і дозволити підключення FUSE. Якщо це керований сервер, таку зміну має зробити його адміністратор.

## Збираємо StudioFS

Для цього способу встановлення беремо вихідний код із репозиторію проєкту й збираємо програму на своєму комп’ютері.

Перейдіть у папку, де зберігаєте програми або вихідний код, і виконайте:

```bash
git clone https://github.com/valandreev/studiofs-cli.git
cd studiofs-cli
cargo build --release -p studiofs
```

Перше збирання може тривати довше: Cargo завантажує та компілює залежності. Після успіху консольна програма буде в `target/release/studiofs`. Перевірте її без встановлення:

```bash
./target/release/studiofs --version
./target/release/studiofs --help
```

Для однакової версії на кількох робочих місцях використовуйте узгоджений із командою стан репозиторію. Поточна гілка розробки змінюється, тому дві збірки, зроблені в різні дні, можуть відрізнятися. Перед оновленням важливих робочих станцій перевіряйте сумісність на тестовому томі.

## Робимо команду доступною в терміналі

Встановимо зібраний файл у власну папку користувача:

```bash
mkdir -p "$HOME/.local/bin"
install -m 755 target/release/studiofs "$HOME/.local/bin/studiofs"
export PATH="$HOME/.local/bin:$PATH"
studiofs --version
studiofs --help
```

Команда `export` діє в поточному терміналі. Щоб шлях зберігся після його закриття, додайте цей рядок до файлу налаштувань своєї оболонки, якщо такого запису там ще немає. Для Bash це зазвичай `~/.bashrc`. Потім відкрийте новий термінал і повторіть `studiofs --version`.

Якщо раніше вже встановлювали StudioFS, перевірте, який файл запускається:

```bash
command -v studiofs
```

У цьому прикладі очікуємо шлях до `studiofs` у вашій папці `.local/bin`. Інший шлях може означати, що термінал знаходить попередню копію раніше за нову.

## Готуємо папку для підключення

Виберіть порожню папку у своєму домашньому каталозі. Наприклад, для майбутнього тому `studio`:

```bash
mkdir -p "$HOME/StudioFS/studio"
ls -ld "$HOME/StudioFS/studio"
```

Створена папка має належати вашому користувачеві. Не складайте в неї матеріали до підключення: звичайні локальні файли не стануть файлами тому автоматично, а після підключення вміст папки буде приховано за змонтованою файловою системою.

Запускайте StudioFS від того самого користувача, який працюватиме з матеріалами. Не потрібно робити папку доступною всім через `chmod 777` або запускати програму через `sudo`, щоб обійти незрозумілу помилку доступу. Спочатку перевірте власника папки та доступ до `/dev/fuse`. Ці приклади готують підключення для вашого користувача; доступ інших облікових записів потребує окремої перевірки прав.

## Якщо щось не запускається

* **`pkg-config` не знаходить `fuse3`.** Перевірте, чи встановлено пакунок для розробки: `libfuse3-dev` на Ubuntu або `fuse3-devel` на Rocky. Однієї утиліти `fusermount3` для збирання недостатньо.
* **Збирання скаржиться на версію Rust.** Звірте `rustc --version` з вимогою 1.95 або новішої версії. Системний пакунок Rust може бути старішим.
* **`studiofs: command not found`.** Запустіть файл за повним шляхом `"$HOME/.local/bin/studiofs" --version` і перевірте налаштування `PATH`.
* **Помилка доступу до FUSE.** Перевірте наявність `/dev/fuse`, права на нього та обмеження середовища. У контейнері це часто питання налаштування хоста.

Успішні `--version` і `--help` означають, що консольна програма запускається. Вони ще не перевіряють підключення файлової системи, PostgreSQL чи S3. Ці перевірки зробимо під час створення та підключення першого тому.

## Що далі?

Тепер є програма, FUSE3 та місце для майбутнього диска. У наступній главі створимо перший том командою `studiofs init` і з’єднаємо підготовлені раніше PostgreSQL та S3 в одне робоче сховище.
