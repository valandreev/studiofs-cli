# 25. Перенесення метаданих StudioFS на новий сервер PostgreSQL
> **Сторінка в процесі доповнення**

У цій главі описано, як перенести метадані StudioFS на новий сервер PostgreSQL, залишивши наявне сховище S3. Клієнти тимчасово зупиняють роботу, їхній локальний стан видаляється, а після перенесення кожен клієнт заново під’єднується до тому командою `discover`.

Команди `dump` і `load` переносять лише частину метаданих StudioFS. Вони не копіюють файлів із S3 і не створюють повної резервної копії PostgreSQL. Якщо потрібна повна копія бази або в томі є дані, яких ці команди не переносять, скористайтеся штатними засобами міграції PostgreSQL.

## Перед початком

1. Узгодьте короткий період технічного обслуговування й попросіть усіх користувачів зберегти роботу та закрити програми, що використовують StudioFS.
2. Штатно відключіть том на кожному клієнті. Переконайтеся, що немає помилок і незавершених завантажень до S3: `dump` синхронізує метадані з PostgreSQL, але не завантажує вмісту файлів до S3.
3. Підготуйте новий сервер PostgreSQL і DSN із потрібними правами. Переконайтеся, що надалі конфігурація клієнтів вказуватиме саме на новий сервер.

## Перенесення

Виконуйте кроки послідовно. На комп’ютері, з якого запускаєте експорт, `dump` потрібно виконати **до** `destroy --local`, бо команді потрібна локальна база метаданих тому.

1. На одному з клієнтів, де є локальний стан тому, створіть дамп:

   ```bash
   studiofs dump projectfs --path-to-dump ./projectfs-metadata.json
   ```

   Замініть `projectfs` на назву свого тому. Збережіть JSON-файл у безпечному місці: він містить конфігурацію тому. Якщо хочете зберегти попередній файл, не запускайте повторний експорт у той самий шлях.

2. Після успішного експорту видаліть локальні метадані на **всіх** клієнтах, зокрема на тому, де виконували `dump`:

   ```bash
   studiofs destroy projectfs --local
   ```

   Ця команда видаляє локальні метадані й кеш цього клієнта, але не чіпає спільних метаданих у PostgreSQL і даних у S3. Не запускайте її, якщо на клієнті є ще не завантажені зміни.

3. Завантажте дамп у новий сервер PostgreSQL:

   ```bash
   studiofs load --path-to-dump ./projectfs-metadata.json --postgresql-address "<new-postgres-dsn>"
   ```

   Команда змінює дані в базі, указаній у DSN. Перед запуском перевірте адресу й не перемикайте клієнтів на новий сервер, доки завантаження не завершиться успішно.

4. На кожному клієнті заново створіть локальний стан, отримавши його з нового сервера:

   ```bash
   studiofs discover projectfs --meta "<new-postgres-dsn>"
   ```

5. Переконайтеся, що клієнти бачать потрібну структуру й можуть відкривати файли, і лише тоді відновіть звичайну роботу.

## Межі `dump` і `load`

`dump` синхронізує локальні метадані цього клієнта, а потім експортує з PostgreSQL записи `volumes`, `metadata_state`, `counters` і `event_log`. `load` застосовує ці дані до цільової бази й знаходить том за UUID. Вмісту файлів у S3 ці команди не переносять.

Крім того, дамп містить не всі таблиці StudioFS: зокрема, у ньому немає окремої таблиці `volume_crypto_keys`, повного стану Snapshot v2 та обліку об’єктів. Тому успішне виконання `load` саме по собі не доводить, що перенесено всі дані, потрібні конкретному тому. Якщо для тому потрібні ці записи або `load` не приймає цільову базу, не видаляйте й не змінюйте таблиць вручну: виконайте повну міграцію PostgreSQL зі збереженням усіх таблиць і перенесіть налаштування доступу до того самого сховища S3.

Зберігайте дамп і DSN як конфіденційні дані: обмежте доступ до JSON-файлу й не додавайте пароль із DSN до спільних журналів чи документації.
