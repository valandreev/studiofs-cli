# 21. Двоє людей, один файл: співпраця та конфлікти
> **Сторінка в процесі доповнення**

Спільний диск зручний тим, що монтажер, колорист і композер бачать ті самі матеріали. Але спільний доступ до файлу ще не означає спільного редагування його вмісту. Якщо двоє людей відкрили одну сцену, кожен застосунок працює з власною копією стану, а StudioFS не знає, який із двох варіантів режисер уже схвалив.

Ризики паралельного редагування властиві не лише StudioFS: вони є й в інших розподілених файлових системах. Спільний доступ сам по собі не об’єднує паралельних змін у файлі. Конкретна поведінка та доступні механізми блокування залежать від системи й від того, чи підтримує їх застосунок.

**Домовтеся, що в кожен момент робочий файл змінює лише одна людина.** Паралельно працюйте з різними сценами, кадрами чи окремими версіями. Це простіше, ніж після дедлайну з’ясовувати, чий дракон залишився без хвоста.

Чітко організований робочий процес допомагає уникнути зайвих конфліктів.

## Що буде, якщо працювати навипередки?

| Ситуація | У чому ризик | Як організувати роботу |
| -- | -- | -- |
| Двоє змінюють той самий файл | StudioFS не об’єднує правок в одну сцену; потрібний варіант може стати недоступним під спільною назвою | Домовитися, хто один редагує файл, або працювати в окремих файлах |
| Двоє створюють файл із тією самою назвою | Однакова назва не дасть зберегти два незалежні результати | Унікальні назви з номером версії та ім’ям автора |
| Один перейменовує файл, інший його редагує | Відкритий файл і його назва в папці — різні речі; старий шлях може вже не працювати | Перейменовувати лише після того, як усі закрили файл |
| Один видаляє файл, інший із ним працює | Відкрита сцена не гарантує, що файл і далі існує за цим шляхом | Видаляти лише після того, як усі учасники завершили роботу |
| Один переносить матеріали, інший відкриває проєкт | Посилання на текстури, кліпи чи кеші можуть вказувати на старі шляхи | Планувати перенесення окремо й перевіряти залежності |

Не покладайтеся на правило «перемагає той, хто останнім натиснув „Зберегти“». Порядок локальних збережень і порядок публікації змін — не одне й те саме. Не варто чекати й автоматичної «конфліктної копії»: вона не збереже обох результатів. Потрібні версії створюйте самостійно.

## А блокування файлів?

У StudioFS є механізм спільних блокувань через PostgreSQL. Якщо клієнт знає, що файл виключно заблокував хтось інший, він відхиляє нові конфліктні зміни — запис, перейменування чи видалення. Читати файл при цьому можна.

Проте це не універсальна заборона редагування для будь-якої програми. Чи використовуватимуться блокування, залежить від застосунку й того, як він працює з файловою системою на вашій платформі. Крім того, запис, який уже триває, може завершитися за правилами відкритого файлу. Те, що хтось відкрив сцену, ще не означає, що її заблоковано для всієї команди.

Якщо ваш робочий процес покладається на блокування, спершу перевірте його на двох комп’ютерах із конкретною програмою й тимчасовим тестовим файлом. Службові файли блокувань, які створює застосунок, теж варто перевірити окремо. І все одно домовляйтеся, хто й коли передає роботу.

## Якщо обидва вже зберегли свої правки

**Спершу припиніть запис у спільний файл.** Не влаштовуйте змагання повторних збережень: це лише ускладнить пошук потрібної версії.

Якщо в обох застосунках ще відкрито різні варіанти сцени, збережіть кожен через «Зберегти як» під унікальною назвою на звичайний локальний диск, поза томом StudioFS. Перевірте ці копії, перш ніж закривати застосунки. Для проєктів із зовнішніми залежностями збережіть також потрібні матеріали або скористайтеся функцією пакування проєкту в програмі.

Потім порівняйте варіанти в самому застосунку, виберіть основу й перенесіть потрібні правки вручну чи штатними засобами програми. Погоджений результат збережіть як нову версію й передайте колезі, як домовилися. Художнього зведення двох сцен StudioFS за вас не зробить.

Якщо файл перейменували чи видалили, поки ви працювали, не закривайте єдиний відкритий варіант, доки не збережете окрему копію. Стан, який видно в програмі, ще може знадобитися, навіть якщо початкової назви вже немає в папці. Якщо потрібного варіанта немає ні у відкритому застосунку, ні в окремій копії, перевірте автозбереження програми та незалежні резервні копії. Не розраховуйте на відновлення лише тому, що «файл був у хмарі».

## Якщо зміни не доходять

Перевірте з’єднання з PostgreSQL і S3 на обох комп’ютерах, а також стан StudioFS. Коли доступ відновиться, дочекайтеся завершення передавання й знову відкрийте погоджену версію на другому комп’ютері. Доти не передавайте права редагування й не перейменовуйте файл навздогін колезі.

Не видаляйте кешу, не створюйте тому заново й не запускайте очищення, щоб «підштовхнути» синхронізацію: локально можуть залишатися єдині копії ще неопублікованих змін. Спершу збережіть доступні результати окремо. Якщо проблема не зникає, запишіть назву файлу, послідовність дій і повідомлення про помилки для діагностики.

## Що далі?

Тепер у команди є просте правило: файл змінює одна людина, версії названо зрозуміло, а передавання перевіряють з іншого комп’ютера. У наступній главі розглянемо налаштування, стан і активність StudioFS, щоб ви могли зрозуміти, чи триває передавання даних і коли варто шукати причину затримки.
