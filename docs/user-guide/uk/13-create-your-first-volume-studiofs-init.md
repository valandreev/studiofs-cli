# 13. Створюємо перший том — studiofs init
> **Сторінка в процесі доповнення**

У S3 уже є місце для файлів, PostgreSQL готовий запам’ятовувати їхню структуру, Tailscale забезпечує зв’язок, а StudioFS встановлено. Тепер об’єднаймо ці складники в **том** — окремий диск StudioFS із власним ім’ям, налаштуваннями та ключем шифрування.

Для цього призначена команда `studiofs init`. Вона створює новий том, але ще не підключає його як диск у системі. Літера диска або каталог монтування з’являться на наступному кроці. Новосілля вже можна планувати, але меблі поки що не заносимо.

## Що має бути готове

Запускайте команду на тому комп’ютері, з якого почнете працювати з томом, під своїм звичайним обліковим записом. Локальні метадані створюються для цього користувача; якщо запустити команду через `sudo`, вони можуть опинитися в домашньому каталозі іншого користувача.

Вам знадобляться адреса S3 API, приватний bucket, регіон та окремі ключі доступу з [глави 06](06-s3-a-home-for-your-files.md), а також DSN PostgreSQL — рядок підключення з адресою, іменем користувача й паролем. Перевірки з [глави 09](09-check-your-infrastructure.md) мають успішно проходити саме з цього комп’ютера.

Віддалений PostgreSQL має бути доступний приватним шляхом, наприклад через Tailscale або NetBird. **Не відкривайте порт 5432 для всього інтернету.** Встановлення VPN саме по собі не закриває публічного порту: перевірте прив’язку порту та правила firewall на сервері.

Оберіть коротке зрозуміле ім’я, наприклад `studio-projects`. Це ім’я тому, а не bucket і не майбутня літера диска. Для початку зручно використовувати латинські літери, цифри й дефіси. Не вказуйте шлях: символи `/`, `\` і `:` у назві заборонені. StudioFS використовуватиме це ім’я також у префіксі об’єктів: `studio-projects/objects/`.

## Команда створення

Спершу можна перевірити, які параметри підтримує встановлена версія:

```text
studiofs init --help
```

Нижче наведено **шаблон**: усі значення, написані великими літерами, замініть своїми. Команду показано одним рядком, щоб її можна було використати в Bash, PowerShell чи іншій оболонці без різних символів перенесення рядка:

```text
studiofs init studio-projects --endpoint 'https://S3_API_HOST:PORT' --bucket 'YOUR_PRIVATE_BUCKET' --region 'YOUR_S3_REGION' --access-key 'YOUR_ACCESS_KEY_ID' --secret-key 'YOUR_SECRET_ACCESS_KEY' --meta 'postgresql://YOUR_PG_USER:YOUR_URL_ENCODED_PASSWORD@PRIVATE_PG_HOST:5432/studiofs?sslmode=require'
```

| Частина команди | Що вказати |
| -- | -- |
| `studio-projects` | Ім’я нового тому. Це позиційний аргумент, без окремого прапорця. |
| `--endpoint` | Адресу S3 API, а не панелі керування чи окремого об’єкта. Для віддаленого сховища — з `https://`. |
| `--bucket` | Точну назву bucket для вмісту файлів. |
| `--region` | Регіон із налаштувань провайдера. Якщо параметр пропустити, буде використано `us-east-1`; для хмари краще вказати регіон явно. |
| `--access-key` | Access Key ID окремого ключа StudioFS. |
| `--secret-key` | Secret Access Key цього ключа. |
| `--meta` | DSN сервера PostgreSQL. Обов’язковий параметр. |

У прикладі `PRIVATE_PG_HOST` означає приватне ім’я вашого сервера.

Якщо пароль містить символи на кшталт `@`,`:`, `/` або `#`, його потрібно закодувати за правилами URL. Лапки навколо DSN захищають рядок від оболонки, але не кодують його. Неправильно записаний пароль легко перетворюється на «дивну адресу сервера».

## Що відбудеться після запуску

Спершу StudioFS підключається до службової бази PostgreSQL **`postgres`** і перевіряє, чи існує база **`studiofs`**. Якщо її немає, StudioFS намагається її створити. Назва бази фіксована: якщо вказати в DSN іншу назву, окрема база для цього тому не з’явиться — StudioFS замінить назву на потрібну.

Далі команда перевіряє bucket у S3. Якщо перевірка не вдається, вона пробує створити bucket, для чого може знадобитися додаткове право `CreateBucket`. Повідомлення про спробу створення **не означає, що bucket не існує**: причиною невдалої перевірки можуть бути неправильні ключі, endpoint або права. Якщо створити доступний bucket заздалегідь, право на його створення не знадобиться.

Після перевірок StudioFS готує спільні метадані, перевіряє, чи немає тому з таким самим ім’ям, і створює локальну базу, кореневий каталог та ключ шифрування нового тому. Початковий стан публікується в PostgreSQL.

Типово локальна база зберігається в `~/.studiofs/meta/studio-projects/studio-projects.db`, де `~` — домашній каталог користувача. Якщо ви налаштували `STUDIOFS_CLIENT_ROOT`, коренем буде вказаний у ній каталог. Точний шлях команда покаже наприкінці.

Налаштування містять облікові дані, а PostgreSQL також зберігає ключі шифрування тому. Тож не вважайте локальну базу чи спільні метадані безпечними для публікації лише тому, що вміст файлів зашифровано.

## Як зрозуміти, що все вдалося

Дочекайтеся, доки команда завершиться без помилок. Наприкінці має з’явитися рядок:

```text
✓ Volume 'studio-projects' initialized
```

Поруч буде показано UUID тому, розмір блока, endpoint і bucket, позначку `Metadata backend: Postgres`, ідентифікатор тому та шлях до локальних метаданих. Перевірте, чи ім’я тому й bucket збігаються з тими, які ви планували. Самого повідомлення про успішне підключення до PostgreSQL ще недостатньо: після нього ініціалізація триває.

Додатково можна переглянути стан тому:

```text
studiofs status studio-projects
```

Команда має показати інформацію про ваш том, а не повідомлення `Volume ... not found`.

## Якщо потрібно спробувати ще раз

`init` створює новий том і **не призначена для безпечного «оновлення налаштувань»**. Якщо сталася помилка, спершу прочитайте повідомлення й з’ясуйте, на якому кроці зупинилася команда.

* **Помилка S3:** перевірте endpoint, регіон, ключі та доступ до наявного bucket. Не додавайте навмання адміністративних прав лише через повідомлення про спробу створити bucket.
* **Помилка PostgreSQL:** перевірте приватний маршрут, пароль, TLS і доступ до обох баз — `postgres` і `studiofs`. Помилка створення бази може означати, що її потрібно заздалегідь підготувати разом з адміністратором.
* **Том уже існує в PostgreSQL:** не запускайте `destroy`, навіть якщо текст помилки це пропонує. Це не звичайний крок для повторної спроби. Якщо том уже створено й потрібно підключити інший комп’ютер, скористайтеся командою `studiofs discover`, описаною в [главі 16](16-connect-a-second-computer-studiofs-discover.md).
* **Запит `Do you want to CLEAR it and start fresh? [y/N]:`:** StudioFS знайшов локальний каталог метаданих і пропонує його видалити. Якщо ви не впевнені, що там лише непотрібні залишки невдалого тесту, натисніть Enter або введіть `n`. Відповідь `y` видаляє каталог, а не просто повторює перевірку.

Не розраховуйте, що невдала ініціалізація автоматично скасує всі попередні дії. Можливо, уже встигли з’явитися база, bucket, локальні файли чи запис про том. Якщо фінального повідомлення немає, але ім’я вже зайняте або з’явився запит на очищення, збережіть текст помилки (без секретних даних) і розберіться зі станом системи, перш ніж продовжувати. Видаляти метадані вручну чи створювати інший том поверх того самого префікса — погана заміна діагностиці.

Якщо команда успішно завершилася, повторювати `init` не потрібно. Том створено, і в наступній главі ми підключимо його до файлової системи комп’ютера.
