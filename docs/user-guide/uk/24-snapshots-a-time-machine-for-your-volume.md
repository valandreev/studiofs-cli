# 24. Знімки: машина часу для вашого тому

Учора монтаж відкривався, а сьогодні хтось перезаписав потрібний файл. Хотілося б повернутися на крок назад і забрати стару версію. Для цього StudioFS має **знімки**: зафіксовані стани всього тому, які можна відкрити окремо й переглянути без права запису.

Машина часу тут має цілком практичне призначення: знайти потрібний файл і скопіювати його назад. Але квиток у минуле треба придбати заздалегідь — знімок, створений після помилки, не покаже стан до неї.

## Що саме потрапляє у знімок?

Snapshot v2 фіксує стан тому за спільними метаданими PostgreSQL. Це знімок **усього тому**, а не вибраної папки. Його вміст пов’язаний із даними в об’єктному сховищі.

Тут важлива вже знайома різниця: локально збережені зміни можуть ще не бути опубліковані для інших клієнтів. Знімок не підбирає автоматично все, що лежить у локальному кеші вашого комп’ютера. Перед важливою контрольною точкою збережіть роботу в програмі, дочекайтеся завантаження даних і синхронізації метаданих. Якщо проєкт складається з кількох взаємопов’язаних файлів, дайте програмі завершити їх запис; за потреби закрийте проєкт і узгодьте паузу з колегами.

**Знімок не перетворює збереження багатофайлового проєкту на одну неподільну операцію.** Якщо програма саме переписує його частини, зафіксований стан може не бути придатним для відкриття в ній.

Для наведених команд потрібні налаштований том із PostgreSQL, доступ до цієї бази та, для створення й читання знімка, до об’єктного сховища.

## Створюємо контрольну точку

Перед великим прибиранням або змінами у проєкті виконайте:

```bash
studiofs snapshot create --ttl 7d
```

Команда зареєструє знімок і чекатиме, доки він стане **`Ready`** — готовим до використання. Збережіть ідентифікатор із відповіді. Його призначає StudioFS; власну назву в цю команду передавати не потрібно.

`--ttl 7d` означає сім діб зберігання **від моменту готовності**, а не від початку створення. Дозволені додатні цілі числа із суфіксами `s` (секунди), `m` (хвилини), `h` (години), `d` (доби) та `w` (тижні): наприклад, `12h`, `7d`, `2w`.

Можна створити знімок без автоматичного строку закінчення:

```bash
studiofs snapshot create
```

Такий ручний знімок зберігається до явного видалення. «Без строку» не означає «безкоштовно»: історичні дані також займають місце у сховищі.

Зверніть увагу на синтаксис: команди `studiofs snapshot` **не приймають назву тому**. Вони знаходять поточний том за локальними службовими даними клієнта й перевіряють його в PostgreSQL. Потрібен один однозначно визначений том із PostgreSQL у корені даних клієнта. Якщо команда повідомляє про кілька томів або недоступний контекст, додавання назви наприкінці не допоможе: спочатку потрібно впорядкувати конфігурацію клієнта. Не видаляйте службові бази навмання.

## Дивимося, що вже є

```bash
studiofs snapshot list
```

Для докладнішої перевірки скопіюйте ідентифікатор зі списку:

```bash
studiofs snapshot inspect projectfs.2026-08-12T14-07-09.482Z
```

Тут і далі `projectfs` та наведений ідентифікатор — приклади. Замініть їх своїми значеннями.

У відповіді корисно розрізняти такі поля:

| Поле | Що воно пояснює |
| --- | --- |
| `origin` | Знімок створено вручну (`manual`) чи за розкладом (`automatic`). |
| `captured_at`, `cut_version` | Час фіксації та версія спільних метаданих, яку зафіксовано. |
| `state` | Загальний стан знімка. Для монтування потрібен `Ready`. |
| `creation` | Окремий службовий стан роботи зі створення знімка. |
| `ready_at`, `expires_at` | Коли знімок став готовим і коли спливає його строк. |
| `checksum` | Контрольна сума підготовленого знімка. |
| `last_error` | Остання зафіксована помилка, якщо вона є. |

Значення `-` означає, що відповідного значення немає. Наприклад, ручний знімок без TTL не має `expires_at`.

`Creating` ще не означає готовності; `Failed` вказує на невдале створення, а `Deleting` та `Deleted` — на видалення. Не намагайтеся монтувати знімок лише тому, що його ідентифікатор уже з’явився у списку.

Якщо перервати `create` через Ctrl+C, реєстрація у PostgreSQL залишається. Перевірте цей ідентифікатор через `inspect`, перш ніж створювати ще один знімок. Перерваний термінал і скасоване завдання — різні речі.

## Відкриваємо минуле окремим диском

Для готового знімка є команда `smount`. Ось тут назва тому **потрібна**: після неї йдуть ідентифікатор знімка та окрема точка монтування.

У Windows, якщо літера `Z:` вільна:

```powershell
studiofs smount projectfs projectfs.2026-08-12T14-07-09.482Z Z:
```

У Linux або macOS використайте підготовлений окремий каталог, наприклад:

```bash
studiofs smount projectfs projectfs.2026-08-12T14-07-09.482Z /mnt/snapshot
```

Оберіть шлях, доступний вашому користувачеві; не монтуйте знімок поверх робочого тому. За потреби можна задати окремий кеш через `--cache-dir <шлях>`.

`smount` завжди відкриває знімок **лише для читання**. Прапорець `--read-only` не потрібен і не підтримується. У цьому диску можна переглядати файли й копіювати їх назовні, але не можна змінювати, перейменовувати чи видаляти їх.

Щоб повернути файл, скопіюйте його зі знімка в окрему папку на звичайному диску або в робочому томі. Перевірте, що це потрібна версія, і лише потім замініть нею поточний файл. Для проєкту з кількох файлів копіюйте потрібний комплект разом і перевіряйте його у відповідній програмі. Окремої команди відкату всього тому тут немає.

Після роботи відмонтуйте знімок звичайною командою StudioFS:

```powershell
studiofs umount Z:
```

Або для шляху з прикладу Unix:

```bash
studiofs umount /mnt/snapshot
```

## Щоденні знімки без нагадувань у календарі

Для тому можна встановити одну щоденну політику. Наприклад, щодня о 02:30 за київським часом із зберіганням готових знімків протягом двох тижнів:

```bash
studiofs snapshot policy set --daily-at 02:30 --timezone Europe/Kyiv --retention 14d
studiofs snapshot policy show
```

Час задається у форматі `HH:MM`, часовий пояс — назвою IANA. Якщо пропустити `--timezone`, буде використано **UTC**, навіть якщо ваш комп’ютер живе за київським часом. `--retention` обов’язковий; для автоматичних знімків потрібен скінченний додатний строк. Він також відраховується від `Ready`.

Повторний `policy set` замінює поточну політику. Щоб вимкнути майбутні автоматичні створення:

```bash
studiofs snapshot policy cancel
```

Це не видаляє вже створені знімки.

Розклад виконує фоновий механізм запущеного монтування робочого тому. Сам запис політики не запускає окремий цілодобовий сервер: якщо всі клієнти вимкнені, знімок рівно о 02:30 не з’явиться. Після простою механізм може опрацювати останній належний запуск, але не створює окремий знімок за кожен пропущений день і не відновлює минулі стани заднім числом.

Є й нюанс переведення годинника: якщо в обраному поясі заданий місцевий час цього дня не існує, цей запуск пропускається; якщо час повторюється двічі, використовується перший момент. Для передбачуваного розкладу перевірте пояс через `policy show`.

## Видаляємо непотрібне

Коли знімок більше не потрібен, спочатку завершіть роботу з його змонтованою копією, а тоді виконайте:

```bash
studiofs snapshot delete projectfs.2026-08-12T14-07-09.482Z
```

Це запит на видалення, який можна повторити. Він не означає, що всі пов’язані об’єкти миттєво зникнуть зі сховища. Уже відкриті монтування можуть певний час продовжувати роботу: вони утримують поновлювані дозволи на використання знімка — leases. Очищення має дочекатися їх завершення. Спливання TTL також не слід сприймати як обіцянку звільнити місце рівно в ту саму секунду.

Перед видаленням звірте ідентифікатор. Копія потрібного файлу, яку ви ще не встигли забрати зі знімка, після його видалення може стати недоступною.

## Чому це ще не резервна копія?

Знімок допомагає повернути стару версію, поки доступні потрібні метадані, об’єкти та ключовий матеріал тому. Він залежить від тієї самої інфраструктури й не створює незалежну копію всіх даних в іншому місці.

Втрата PostgreSQL, потрібних об’єктів S3 або ключового матеріалу може позбавити вас і робочих файлів, і можливості скористатися знімками. Для таких випадків потрібні резервні копії та перевірений спосіб відновлення. Саме їм присвячено наступну главу.
