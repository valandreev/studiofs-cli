# 24. Знімки: машина часу для вашого тому
> **Сторінка в процесі доповнення**

Учора монтаж відкривався, а сьогодні хтось перезаписав потрібний файл. Хотілося б повернутися на крок назад і забрати стару версію. Для цього в StudioFS є **знімки** — зафіксовані стани всього тому, які можна відкрити окремо й переглядати в режимі лише для читання.

Ця машина часу має цілком практичне призначення: знайти потрібний файл і скопіювати його назад. Але квиток у минуле треба придбати заздалегідь — знімок, створений після помилки, не покаже стану до неї.

## Що саме потрапляє у знімок?

Знімок фіксує стан тому на основі спільних метаданих у PostgreSQL. Це знімок **усього тому**, а не окремої папки. Його вміст пов’язаний із даними в об’єктному сховищі.

Тут важлива вже знайома відмінність: зміни, збережені локально, можуть бути ще не опубліковані для інших клієнтів. Знімок не захоплює автоматично все, що лежить у локальному кеші вашого комп’ютера. Перед важливою контрольною точкою збережіть роботу в програмі й дочекайтеся завантаження даних і синхронізації метаданих. Якщо проєкт складається з кількох пов’язаних файлів, дайте програмі завершити їх запис; за потреби закрийте проєкт і домовтеся з колегами про паузу.

**Знімок не робить збереження багатофайлового проєкту однією неподільною операцією.** Якщо програма саме перезаписує його частини, зафіксований стан може виявитися непридатним для відкриття в ній.

Для тому має бути налаштовано доступ до PostgreSQL. Для створення й читання знімків також потрібен доступ до об’єктного сховища.

## Створюємо контрольну точку

Перед великим прибиранням або змінами у проєкті виконайте:

```bash
studiofs snapshot projectfs create --ttl 7d
```

Команда зареєструє знімок і чекатиме, доки він перейде в стан **`Ready`** (готовий до використання). Збережіть ідентифікатор із відповіді: його призначає StudioFS, власну назву знімкові задати не можна.

`--ttl 7d` означає, що знімок зберігатиметься сім діб **від моменту готовності**, а не від початку створення. Можна вказувати додатні цілі числа із суфіксами `s` (секунди), `m` (хвилини), `h` (години), `d` (доби) та `w` (тижні), наприклад `12h`, `7d`, `2w`.

Можна створити знімок без автоматичного строку закінчення:

```bash
studiofs snapshot projectfs create
```

Такий знімок зберігається, доки ви його явно не видалите. «Безстроковий» не означає «безкоштовний»: історичні дані теж займають місце у сховищі.

У кожній команді для роботи зі знімками потрібно явно вказувати том. Наприклад, `studiofs snapshot projectfs create` працює лише з томом `projectfs`; команда ніколи не визначає поточний том автоматично за локальними даними клієнта. Такий самий формат використовують `list`, `inspect`, `delete` і `policy`:

```text
studiofs snapshot <назва-тому> create [--ttl <тривалість>]
studiofs snapshot <назва-тому> list
studiofs snapshot <назва-тому> inspect <ідентифікатор-знімка>
studiofs snapshot <назва-тому> delete <ідентифікатор-знімка>
studiofs snapshot <назва-тому> policy set --daily-at <HH:MM> [--timezone <назва IANA>] --retention <тривалість>
studiofs snapshot <назва-тому> policy show
studiofs snapshot <назва-тому> policy cancel
```

У прикладах нижче замініть `projectfs` на точну назву свого тому. Якщо назва невідома чи некоректна, команда пояснить проблему й підкаже, що виправити; інший том замість указаного вона не підставить.

## Дивимося, що вже є

```bash
studiofs snapshot projectfs list
```

Для докладнішої перевірки скопіюйте ідентифікатор зі списку:

```bash
studiofs snapshot projectfs inspect projectfs.2026-08-12T14-07-09.482Z
```

Тут і далі `projectfs` і наведений ідентифікатор — лише приклади. Замініть їх своїми значеннями.

У відповіді варто звернути увагу на такі поля:

| Поле | Що воно пояснює |
| --- | --- |
| `origin` | Знімок створено вручну (`manual`) чи за розкладом (`automatic`). |
| `captured_at`, `cut_version` | Час фіксації та версія спільних метаданих, яку зафіксовано. |
| `state` | Загальний стан знімка. Для монтування потрібен `Ready`. |
| `creation` | Службовий стан процесу створення знімка. |
| `ready_at`, `expires_at` | Коли знімок став готовим і коли спливає його строк. |
| `checksum` | Контрольна сума підготовленого знімка. |
| `last_error` | Остання зафіксована помилка, якщо вона є. |

Прочерк `-` означає, що значення немає. Наприклад, ручний знімок без TTL не має `expires_at`.

Стан `Creating` означає, що знімок ще не готовий; `Failed` — що створення не вдалося, а `Deleting` і `Deleted` — що знімок видаляється або вже видалений. Не намагайтеся монтувати знімок лише тому, що його ідентифікатор уже з’явився в списку.

Якщо перервати `create` комбінацією Ctrl+C, запис про знімок у PostgreSQL залишиться. Перш ніж створювати ще один знімок, перевірте цей ідентифікатор командою `inspect`. Перервана команда в терміналі й скасоване завдання — різні речі.

## Відкриваємо минуле окремим диском

Готовий знімок відкривають командою `smount`. Тут **обов’язково потрібна назва тому**, а після неї — ідентифікатор знімка й окрема точка монтування.

У Windows, якщо літера `Z:` вільна:

```powershell
studiofs smount projectfs projectfs.2026-08-12T14-07-09.482Z Z:
```

У Linux або macOS використайте підготовлений окремий каталог, наприклад:

```bash
studiofs smount projectfs projectfs.2026-08-12T14-07-09.482Z /mnt/snapshot
```

Виберіть шлях, до якого має доступ ваш обліковий запис, і не монтуйте знімок поверх робочого тому. За потреби вкажіть окремий кеш параметром `--cache-dir <шлях>`.

`smount` завжди відкриває знімок **лише для читання**. На цьому диску можна переглядати файли й копіювати їх в інше місце, але змінювати, перейменовувати чи видаляти їх не можна.

Щоб повернути файл, скопіюйте його зі знімка в окрему папку на звичайному диску або на робочий том. Переконайтеся, що це потрібна версія, і лише потім замініть нею поточний файл. Якщо проєкт складається з кількох файлів, скопіюйте весь потрібний комплект і перевірте його у відповідній програмі. Окремої команди для відкату всього тому немає.

## Щоденні знімки без нагадувань у календарі

Для тому можна налаштувати один щоденний розклад (політику). Наприклад, створювати знімки щодня о 02:30 за київським часом і зберігати готові знімки два тижні:

```bash
studiofs snapshot projectfs policy set --daily-at 02:30 --timezone Europe/Kyiv --retention 14d
studiofs snapshot projectfs policy show
```

Час задається у форматі `HH:MM`, часовий пояс — назвою з бази IANA. Якщо не вказати `--timezone`, буде використано **UTC**, навіть якщо ваш комп’ютер живе за київським часом. Параметр `--retention` обов’язковий: строк зберігання автоматичних знімків має бути скінченним і додатним. Його також відраховують від моменту переходу в стан `Ready`.

Повторна команда `policy set` замінює поточну політику. Щоб вимкнути автоматичне створення знімків надалі, виконайте:

```bash
studiofs snapshot projectfs policy cancel
```

Це не видаляє вже створені знімки.

Розклад виконується у фоновому режимі, доки робочий том підключено хоча б на одному комп’ютері. Сама політика не запускає окремого цілодобового сервера: якщо всі клієнти вимкнені, знімок о 02:30 не з’явиться. Після простою StudioFS може виконати останній запланований запуск, але не створює окремого знімка за кожен пропущений день і не відтворює минулих станів заднім числом.

Є ще нюанс із переходом на літній чи зимовий час: якщо в обраному часовому поясі цього дня заданого місцевого часу не існує, запуск пропускається; якщо ж цей час повторюється двічі, використовується перший із двох моментів. Щоб розклад був передбачуваним, перевірте часовий пояс командою `policy show`.

## Видаляємо непотрібне

Коли знімок більше не потрібен, спершу завершіть роботу з його підключеною копією, а потім виконайте:

```bash
studiofs snapshot projectfs delete projectfs.2026-08-12T14-07-09.482Z
```

Запит на видалення можна безпечно повторити. Проте це не означає, що всі пов’язані об’єкти миттєво зникнуть зі сховища. Уже відкриті монтування можуть ще якийсь час працювати, бо утримують поновлювані дозволи на використання знімка (leases). Очищення почнеться після завершення цих дозволів. Так само завершення TTL не означає, що місце звільниться тієї ж миті.

Перед видаленням звірте ідентифікатор. Файл, який ви ще не встигли скопіювати зі знімка, після його видалення може стати недоступним.

## Чому це ще не резервна копія?

Знімок допомагає повернути стару версію, доки доступні потрібні метадані, об’єкти та ключі шифрування тому. Він залежить від тієї самої інфраструктури й не є незалежною копією всіх даних в іншому місці.

Утрата PostgreSQL, потрібних об’єктів у S3 чи ключів шифрування може позбавити вас і робочих файлів, і можливості скористатися знімками. Для таких випадків потрібні резервні копії та перевірений спосіб відновлення. Докладніше про перенесення метаданих — у наступній главі.
