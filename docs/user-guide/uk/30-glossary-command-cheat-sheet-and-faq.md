# 30. Глосарій, шпаргалка команд і поширені запитання
> **Work in progress**

Ця глава — щоб швидко згадати слово, знайти команду й повернутися до роботи. Якщо налаштовуєте StudioFS уперше, почніть із [вибору схеми](05-choose-your-setup.md), а не з копіювання всіх команд поспіль.

## Короткий словник

| Термін | Що це означає на практиці |
| --- | --- |
| **Том (volume)** | Спільний файловий простір StudioFS зі своєю структурою папок і налаштуваннями. У прикладах його назва — `projectfs`. |
| **Монтування (mount)** | Підключення тому як диска або каталогу, з яким працюють звичайні програми. |
| **Точка монтування** | Місце, де видно файли: наприклад, `Z:` у Windows або каталог у macOS. Це не адреса S3. |
| **Клієнт** | Комп’ютер і запущений на ньому StudioFS, який працює з томом. |
| **S3-сумісне сховище** | Сервіс, де StudioFS зберігає вміст файлів у власному форматі. Це може бути хмарний сервіс або ваше сховище. |
| **Бакет (bucket)** | Контейнер об’єктів у S3. Його вміст не слід редагувати як звичайну папку проєкту. |
| **Endpoint** | Адреса сервісу S3, через яку клієнт звертається до сховища. |
| **Метадані** | Відомості про назви, папки, розміри й версії файлів. Саме відео чи вміст сцени — це дані, а не метадані. |
| **PostgreSQL** | База спільних метаданих, через яку клієнти отримують інформацію про опубліковані зміни. |
| **Локальна база метаданих** | Робоча копія метаданих на комп’ютері. Монтування використовує її, щоб не звертатися до PostgreSQL для кожної файлової операції. |
| **Кеш** | Локальні дані на SSD: уже завантажені частини файлів і нові зміни, які ще можуть чекати передавання. Це не просто папка з тимчасовим сміттям. |
| **Синхронізація** | Фонове передавання даних і поширення метаданих між клієнтами. Збереження у програмі й поява результату в колеги відбуваються не одночасно. |
| **Знімок (snapshot)** | Зафіксований стан усього тому, який можна відкрити лише для читання й скопіювати звідти потрібні файли. |
| **TTL / retention** | Строк зберігання знімка. У командах Snapshot v2 він відраховується від готовності `Ready`. |
| **Резервна копія** | Незалежна копія потрібних даних, метаданих і ключів із перевіреним способом відновлення. Самого знімка для цього недостатньо. |

Докладніше про зв’язок цих частин — у главі [«Як це все працює?»](02-how-does-this-thing-work.md).

## Шпаргалка команд

У прикладах `projectfs` — назва вашого тому, `Z:` — вільна літера диска Windows. У macOS замість неї використайте підготовлений каталог. Стан підтримки платформ перевірте в [главі про вимоги](03-capabilities-limits-and-requirements.md) та [інструкції для Linux](12-install-studiofs-on-linux.md).

| Що потрібно | Команда | Де прочитати подробиці |
| --- | --- | --- |
| Подивитися версію | `studiofs --version` | [Встановлення у Windows](10-install-studiofs-on-windows.md) |
| Знайти довідку | `studiofs --help` або `studiofs mount --help` | Довідка саме вашої встановленої версії |
| Підключити том | `studiofs mount projectfs Z:` | [Монтування](14-mount-your-volume-studiofs-mount.md) |
| Задати ліміт кешу для монтування | `studiofs mount projectfs Z: --cache-size 500GB` | [Кеш](20-cache-why-is-the-cloud-using-my-ssd.md) |
| Переглянути стан | `studiofs status projectfs` | [Налаштування, стан і активність](22-settings-status-and-activity.md) |
| Отримати докладніший стан | `studiofs status projectfs --verbose` | Та сама глава |
| Переглянути збережені налаштування | `studiofs settings` | Та сама глава |
| Зберегти типовий ліміт кешу | `studiofs settings --cache-size 500GB` | Та сама глава |
| Подивитися активність монтування | `studiofs perf Z: --count 5` | Та сама глава |
| Відключити диск | `studiofs umount Z:` | [Безпечне відключення](17-unplug-safely-studiofs-umount.md) |
| Створити знімок на сім діб | `studiofs snapshot create --ttl 7d` | [Знімки](24-snapshots-a-time-machine-for-your-volume.md) |
| Переглянути знімки | `studiofs snapshot list` | Та сама глава |
| Перевірити розклад знімків | `studiofs snapshot policy show` | Та сама глава |
| Попередньо оцінити прибирання | `studiofs janitor projectfs --dry-run` | [Обслуговування](27-maintenance-and-removing-a-volume.md) |

Для знімка скопіюйте справжній ідентифікатор зі списку. Наприклад, якщо він `projectfs.2026-08-12T14-07-09.482Z`:

```powershell
studiofs snapshot inspect projectfs.2026-08-12T14-07-09.482Z
studiofs smount projectfs projectfs.2026-08-12T14-07-09.482Z Y:
```

`Y:` має бути вільною окремою літерою. `smount` відкриває знімок лише для читання; після роботи використайте `studiofs umount Y:`. Команди `snapshot` не приймають назву тому: їм потрібен однозначно визначений локальний контекст тому з PostgreSQL. У `smount` назва тому, навпаки, потрібна.

### Команди, перед якими варто відкрити відповідну главу

`studiofs init` створює новий том і потребує параметрів сховища та PostgreSQL. Готовий приклад із поясненням параметрів є в [главі про перший том](13-create-your-first-volume-studiofs-init.md). Для наявного тому на іншому комп’ютері потрібен `studiofs discover`, а не повторний `init`: дивіться [підключення другого комп’ютера](16-connect-a-second-computer-studiofs-discover.md).

`studiofs fsck projectfs` перевіряє метадані й **може запропонувати виправлення**. Це не гарантовано пасивний звіт. Прапорець `--repair` дозволяє виправляти знайдене без інтерактивного підтвердження. Підготовку й обмеження описано в [главі про обслуговування](27-maintenance-and-removing-a-volume.md).

`studiofs destroy projectfs` — **руйнівне видалення тому**, а не відмонтування. Варіант `--local` залишає віддалені дані, але видаляє локальний стан і може знищити ще не передані зміни. Не використовуйте його як спосіб «освіжити кеш».

`studiofs dump projectfs --path-to-dump ./projectfs-metadata.json` експортує частину метаданих PostgreSQL. Цей JSON не містить самих файлів і не є повною резервною копією бази чи тому. `load` змінює цільову базу; порядок застосування й межі обох команд наведено в [главі про перенесення метаданих](25-migrating-studiofs-metadata-to-new-postgresql-server.md).

## Поширені запитання

### Чи потрібен постійний інтернет?

Для отримання відсутніх даних потрібен доступ до S3, для поширення спільного стану — до PostgreSQL. Уже закешовані дані за певних умов можна читати під час розриву зв’язку, а локальні зміни можуть чекати відновлення мережі. Це не гарантія повноцінної автономної роботи. Деталі — у [главі про поганий Wi-Fi](19-sync-bad-wi-fi-and-other-surprises.md).

### Де кнопка «Синхронізувати зараз»?

Передавання відбувається у фоні; окремої публічної команди `studiofs sync` немає. Перевірте `status`, активність і помилки. На Windows і macOS `mount` автоматично намагається показати індикатор у треї або рядку меню, якщо графічне середовище доступне; окремого `--tray` не потрібно. Якщо індикатор не запустився, монтування продовжує працювати через CLI.

### Файл збережено. Можна вимикати комп’ютер?

Спочатку збережіть роботу, дайте програмі завершити запис і дочекайтеся передавання змін. Червона пульсація індикатора означає активну синхронізацію — у цей момент краще зачекати. Один спокійний значок не доводить, що всі колеги вже отримали потрібну версію. Закрийте програми, що використовують том, і виконайте `umount`; якщо команда завершилася з помилкою, з’ясуйте причину перед вимкненням. Дивіться [безпечне відключення](17-unplug-safely-studiofs-umount.md).

### Чому файли у хмарі, а SSD зайнятий?

StudioFS тримає потрібні дані близько до програм і накопичує нові зміни перед передаванням. Не видаляйте кеш вручну: там можуть бути єдині локальні копії ще не опублікованих даних. Як оцінити використання місця — у [главі про кеш](20-cache-why-is-the-cloud-using-my-ssd.md).

### Змінив `settings`, а поведінка та сама. Чому?

`settings` зберігає типові параметри наступних монтувань, а не переналаштовує вже запущений процес. Явні параметри `mount` мають пріоритет. У CLI ця команда називається `settings`; команди `studiofs prefs` немає. Дивіться [главу 22](22-settings-status-and-activity.md).

### Знімок замінює резервну копію?

Ні. Знімок залежить від доступності потрібних метаданих, об’єктів і ключів того самого тому. Він також не підхоплює автоматично все, що ще лежить неопублікованим у локальному кеші. Для аварій потрібні незалежні резервні копії з перевіреною процедурою відновлення.

### Після розриву зв’язку треба знову виконати `init` чи `discover`?

Звичайне відновлення мережі не потребує нового тому. Перевірте VPN, доступність S3 і PostgreSQL, стан клієнта та вільне місце. Якщо монтування зупинилося, з’ясуйте причину й підключіть наявний том через `mount`. `discover` призначений для підготовки клієнта до наявного тому; повторний `init` не є ремонтом синхронізації. Якщо проблема лишилася, перейдіть до [діагностики](29-logs-diagnostics-and-asking-for-help.md).
