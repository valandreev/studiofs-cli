# 06. S3 — дім для ваших файлів
> **Сторінка в процесі доповнення**

У попередній главі ми визначилися, де житимуть ваші дані: на власному сервері чи в хмарі провайдера. Тепер час підготувати для них місце.

Припустімо, у вас є 8 ТБ вихідних матеріалів, рендерів і проєктів. Зазвичай ми уявляємо сховище як великий диск із папками. S3 працює інакше: воно зберігає **об’єкти**, а не звичну файлову систему. І саме це потрібно StudioFS.

## Що ми насправді кладемо в S3?

Amazon S3 — це сервіс об’єктного зберігання даних, а S3 API — інтерфейс для роботи з таким сховищем. Цей API підтримують й інші сервіси, тому «S3-сумісне сховище» не обов’язково означає Amazon.

У S3 є **bucket** — умовний контейнер для об’єктів. У нашому випадку це місце, куди StudioFS завантажуватиме вміст файлів. Назвами файлів, структурою папок та інформацією про зміни керуватиме PostgreSQL, який ми підготуємо в наступній главі.

Не дивуйтеся, якщо після копіювання відео в StudioFS ви не знайдете в bucket об’єкта з назвою `interview.mov`. StudioFS зберігає дані частинами під власними технічними іменами та шифрує їх перед завантаженням. **Bucket — це не резервна копія звичайної структури папок і не місце для ручного редагування файлів.**

Це також означає, що без відповідних метаданих у PostgreSQL набір об’єктів у S3 не вдасться перетворити назад на ваш диск. Щоб зберегти проєкти, вам знадобляться резервні копії **обох** компонентів.

## Створюємо bucket

Назви кнопок у кожного провайдера свої, але послідовність дій майже однакова.

1. Відкрийте панель керування вашим S3-сервісом і знайдіть пункт для створення bucket.
2. Задайте назву, наприклад `studiofs-projects-demo`. Використовуйте малі латинські літери, цифри та дефіси. Назва має відповідати правилам вашого провайдера, зокрема вимогам щодо унікальності.
3. Оберіть регіон, якщо сервіс це дозволяє. Бажано, щоб він був географічно близько до основних робочих місць; також ураховуйте розташування команди й вартість передавання даних.
4. Залиште bucket **приватним**. Для роботи StudioFS публічний доступ до об’єктів не потрібен.
5. Створіть bucket і запишіть його назву та S3 endpoint. У Backblaze адресу зазвичай показують у параметрах bucket, а в AWS вона залежить від регіону.

Поки що не вмикайте правила автоматичного видалення об’єктів (lifecycle expiration), якщо не впевнені в їхніх наслідках. StudioFS сам визначає, які об’єкти належать файловій системі. Якщо провайдер видалить потрібний об’єкт за власним розкладом, PostgreSQL не зможе чарівним чином повернути його вміст.

**Чи обов’язково створювати bucket вручну?** Ні. Якщо bucket недоступний, `studiofs init` може спробувати створити його автоматично — за умови, що має відповідні права. Але краще створити bucket заздалегідь: так ви контролюєте його налаштування й не мусите надавати StudioFS зайвих дозволів.

## Створюємо окремі ключі

Сховище створено. Залишилося визначити, хто має право з ним працювати.

Для підключення StudioFS до S3 потрібна пара ключів:

* **Access Key ID** — ідентифікатор доступу.
* **Secret Access Key** — секретний ключ, яким підписуються запити.

Створіть **окремий ключ для StudioFS замість того**, щоб використовувати головні ключі адміністратора всього сховища.

Для звичайної роботи потрібні права на перегляд переліку об’єктів у bucket, а також на читання, завантаження й видалення об’єктів. У термінах AWS це, зокрема, `s3:ListBucket` для самого bucket і `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` для його об’єктів.

Не надавайте ключеві доступу до всіх bucket у своєму обліковому записі без потреби. І збережіть Secret Access Key у захищеному місці відразу після створення: деякі сервіси показують його лише один раз.

**Важливо:** не вставляйте секретні ключі в листування, знімки екрана чи публічні звіти про помилки. Під час створення тому StudioFS зберігає параметри доступу в конфігурації тому, тому не вважайте локальну конфігурацію чи PostgreSQL захищеним сховищем секретів. Якщо згодом ви відкличете ключ у провайдера, наявні клієнти втратять доступ до S3, доки їхні параметри доступу не буде правильно оновлено.

## П’ять значень, які знадобляться StudioFS

Коли bucket і ключі готові, зберіть такі п’ять параметрів:

* **Endpoint** — адреса S3 API. Для віддаленого сервісу використовуйте `https://`. Це не адреса сторінки керування й не посилання на окремий файл.
* **Bucket** — точна назва створеного контейнера, наприклад `studiofs-projects-demo`.
* **Region** — регіон, який провайдер використовує для S3-запитів та їхнього підписування.
* **Access Key ID** — ідентифікатор створеного ключа.
* **Secret Access Key** — секретна частина цього ключа.

Приклади адрес і регіонів:

| Сервіс | Endpoint (приклад) | Region (приклад) |
| -- | -- | -- |
| Amazon S3 | `https://s3.eu-central-1.amazonaws.com` | `eu-central-1` |
| Backblaze B2 | `https://s3.us-west-004.backblazeb2.com` | `us-west-004` |
| Локальний RustFS | `http://127.0.0.1:9000` | `us-east-1` |

У поточній версії StudioFS ці значення передаються команді `studiofs init` через параметри `--endpoint`, `--bucket`, `--region`, `--access-key` і `--secret-key`. Якщо не вказати `--region`, StudioFS типово використовуватиме `us-east-1`. Для хмарного сховища обов’язково вкажіть регіон, який надав ваш провайдер.

## Кілька правил, які збережуть вам нерви

**Не робіть bucket публічним.** Клієнти StudioFS отримують доступ за ключами, а не за анонімними посиланнями. Для віддаленого S3 обирайте HTTPS; звичайний HTTP доречний лише там, де ви свідомо організували безпечне тестове або приватне підключення.

**Не змінюйте об’єкти StudioFS вручну.** Їхні технічні назви й вміст не призначені для ручного керування. Видаливши «незрозуміле сміття» з bucket, ви можете видалити частину потрібного медіафайлу.

**Не плутайте шифрування зі збереженням.** StudioFS автоматично шифрує дані перед надсиланням у S3, але це не захищає від випадкового видалення bucket, утрати метаданих чи неправильної політики зберігання. Шифрування каналу через HTTPS теж має інше призначення.

**Пам’ятайте про географію.** Якщо користувачі в Європі, а сховище — на іншому континенті, затримка запитів може бути відчутно більшою. Локальний кеш допомагає, але не скасовує фізики мережі.

Отже, ми підготували місце для даних: приватний bucket, окремі ключі, endpoint і регіон. Наступний крок — **PostgreSQL**, який відповідатиме за спільну структуру файлів і передавання змін між комп’ютерами. Далі залишиться встановити StudioFS, об’єднати S3 і PostgreSQL в один том — і ваш хмарний диск буде готовий до роботи.
