# 22. Налаштування, стан і активність

StudioFS зазвичай працює десь поруч із монтажною програмою: ви відкриваєте файли, а він читає дані, тримає кеш і передає зміни у фоні. Але інколи хочеться зрозуміти: що зараз відбувається, чи вистачає місця і чому вчора той самий кліп відкривався швидше?

Для цього є три команди: `settings` показує збережені налаштування, `status` — стан конкретного тому, а `perf` — активність підключеного диска в часі. Значок у системному треї або рядку меню допомагає стежити за синхронізацією без відкритого термінала. Розберімося, яке запитання ставити кожному з них.

## Налаштування: що збережено для наступного підключення

Почніть із команди:

```bash
studiofs settings
```

Вона показує стандартну точку підключення, каталог і розмір кешу, а також параметри читання. Позначка `<unset>` означає, що відповідне значення не збережене. Без окремого налаштування бюджет дискового кешу становить `100GB`; політику роботи з цим бюджетом StudioFS обирає автоматично.

`settings` показує **збережені значення для наступних запусків `mount`**, а не повну конфігурацію вже підключеного диска. Наприклад, під час підключення ви могли явно вказати інший розмір кешу.

Припустімо, ви вирішили відвести під кеш 200 ГБ на локальному SSD. У Windows це може виглядати так:

```powershell
studiofs settings --cache-dir "D:\StudioFS-cache" --cache-size 200GB
```

На macOS або Linux виберіть свій локальний каталог, наприклад:

```bash
studiofs settings --cache-dir "$HOME/StudioFS-cache" --cache-size 200GB
```

Команда зберігає налаштування у `config.toml` і друкує шлях до нього. Зазвичай це:

| Система | Файл налаштувань |
|---|---|
| Windows | `%APPDATA%\studiofs\config.toml` |
| macOS | `~/Library/Application Support/studiofs/config.toml` |
| Linux | `~/.config/studiofs/config.toml` |

Зміна значень не переналаштовує чинне підключення й не переносить старий кеш у новий каталог. Щоб застосувати їх, завершіть роботу з файлами, нормально відключіть том і підключіть його знову. Старий кеш не видаляйте навмання: у ньому можуть залишатися ще не передані зміни.

Для каталогу й розміру кешу явні параметри `mount` мають пріоритет над збереженими значеннями, а ті — над стандартними. Якщо каталог не задано, StudioFS використовує `<meta-dir>/cache`, зазвичай у `~/.studiofs/meta/<назва-тому>/cache`. Усередині базового каталогу кеш кожного тому розміщується окремо за UUID.

На macOS і Linux можна також зберегти стандартну точку підключення:

```bash
studiofs settings --mount-point /mnt/studio
```

Це приклад для Linux; на macOS виберіть доступний вам каталог. Правила додавання назви тому до шляху розглянуто у [главі про підключення](14-mount-your-volume-studiofs-mount.md). У Windows під час `mount` явно вказуйте літеру диска, наприклад `Z:`.

## Дисковий кеш і пам’ять — різні ресурси

Більший кеш допомагає повторно відкривати вже прочитані матеріали без повторного завантаження з S3. Він також бере участь у локальній роботі із записаними даними. Проте `--cache-size` не збільшує місткість самого тому і не резервує весь зазначений обсяг на диску наперед. Залишайте вільне місце для операційної системи, програм і їхніх тимчасових файлів. SSD, забитий під зав’язку, рідко стає швидшим від нашого оптимізму.

Для читання доступні ще три публічні параметри:

| Параметр | Що задає |
|---|---|
| `--read-buffer SIZE` | Бюджет буфера читання в оперативній пам’яті; розмір округлюється вгору до МіБ. |
| `--readahead BLOCKS` | Ширину випереджального послідовного читання у блоках. |
| `--prefetch COUNT` | Бюджет паралельного попереднього завантаження. |

Наприклад, така команда зберігає бюджет буфера та параметри випереджального читання:

```bash
studiofs settings --read-buffer 4GB --readahead 256 --prefetch 192
```

Це приклад синтаксису, а не універсальний рецепт для монтажної станції. На комп’ютері з невеликим обсягом RAM буфер змагатиметься за пам’ять із редактором, а зайве попереднє завантаження може читати матеріал, який ви навіть не відкриєте. Починайте зі стандартних значень, змінюйте один параметр і порівнюйте ту саму робочу дію. Розмір буфера має бути більшим за нуль; `readahead` і `prefetch` — цілими числами від `1`.

Ці параметри можна передавати й безпосередньо в `mount` для окремого підключення. Для них пріоритет такий: явний параметр команди, відповідна змінна середовища `STUDIOFS_*`, збережене значення, вбудоване стандартне значення. Якщо результат відрізняється від очікуваного, перевірте також середовище, з якого запускається StudioFS. Внутрішні пороги та службові перемикачі для щоденної роботи налаштовувати не потрібно.

## Стан тому: знімок, який треба читати разом із попередженнями

У прикладах `projectfs` — назва вашого тому:

```bash
studiofs status projectfs
studiofs status projectfs --verbose
```

Залежно від доступності локальної бази та діагностики підключеного процесу команда показує відомості про том, метадані, кеш і синхронізацію. `--verbose` додає докладні показники шляху запису, якщо вони доступні. Підключений процес може тримати локальну базу відкритою; у такому разі команда може показати попередження про блокування й доступну діагностику цього процесу замість повного звіту. Саме таке попередження ще не доводить пошкодження бази.

Якщо ви використовуєте власний каталог кешу, передайте **той самий базовий каталог**, що й під час підключення:

```powershell
studiofs status projectfs --cache-dir "D:\StudioFS-cache" --verbose
```

Поточна команда `status` без `--cache-dir` шукає кеш у `<meta-dir>/cache`, навіть якщо в `settings` збережено інший шлях. Не дописуйте UUID до параметра: команда сама знаходить каталог тому.

У розділі `Local Cache` корисно розрізняти такі поля:

* `Usage bytes` — врахований обсяг локальних даних кешу.
* `Dirty bytes` — обсяг даних, які ще мають статус незавершених локальних змін.
* `Evictable bytes` — обсяг даних, які кеш може витісняти.
* `Pending uploads` — кількість локальних об’єктів, що очікують передавання, а не кількість файлів вашого проєкту.

`Runtime readiness: ready` у цьому розділі стосується локальної структури кешу. Це **не підтвердження**, що всі зміни вже передані в S3, що інший комп’ютер їх отримав або що можна вимикати живлення. Так само `Reconcile needed: no` не є загальним сертифікатом синхронізації.

Читайте попередження разом із числами. Якщо індекс кешу недоступний або заблокований, підрахунок може не вдатися; зокрема, після попередження про неможливість обчислити чергу команда може надрукувати `Pending uploads: 0`. Це не доказ порожньої черги. `unknown`, `unavailable` і застарілий знімок означають нестачу достовірних даних.

Коли доступний розділ `PostgreSQL Sync`, він допомагає побачити перебіг застосування метаданих, давність успішної синхронізації та помилки. Завершення одного етапу наздоганяння метаданих саме по собі не підтверджує передавання всього вмісту файлів.

## Активність: що змінюється просто зараз

`perf` працює з **точкою підключення**, а не з назвою тому. Для Windows:

```powershell
studiofs perf Z: --interval 1000 --count 10
```

Для macOS або Linux передайте фактичний шлях підключеного тому:

```bash
studiofs perf /mnt/studio/projectfs --interval 1000 --count 10
```

Інтервал задається в мілісекундах; тут буде десять інтервальних вимірювань із кроком близько секунди. Без `--count` перегляд триває до переривання через `Ctrl+C`; це зупиняє спостереження, а не відключає диск.

У таблиці є показники використання ресурсів, файлових операцій, метаданих, кешу й об’єктного сховища. Поспостерігайте спочатку під час простою, потім відкрийте великий кліп і повторіть відкриття. Перше читання може звертатися до S3, повторне — використовувати вже отримані дані. Операційний кеш теж впливає на результат, тож одна швидка спроба ще не доводить, що ви знайшли ідеальні налаштування.

Для докладнішого спостереження є `--verbosity verbose`; зверніть увагу, що тут це не прапорець `--verbose`, як у `status`. Щоб записати короткий звіт для розбору проблеми:

```powershell
studiofs perf Z: --interval 1000 --count 10 --json-lines > studiofs-perf.jsonl
```

`--json-lines` записує окремий JSON-рядок для кожного вимірювання. Варіант `--json` формує один масив і потребує `--count`. Якщо статистика недоступна, перевірте, що вказано саме підключений диск StudioFS; повідомлення про недоступні показники не означає нульове навантаження.

## Значок синхронізації: зручно, але читайте підказку

StudioFS автоматично намагається показати індикатор у треї Windows або Linux чи в рядку меню macOS. Його видимість залежить від графічного середовища; окремого параметра для ввімкнення не потрібно. Якщо індикатора немає, користуйтеся доступними показниками командного рядка.

Червона пульсація означає, що прийняті цим підключенням зміни ще потребують синхронізації. Причиною можуть бути дані запису, підготовлені або повторні завантаження, публікація версії файлу чи підтвердження метаданих. Завершене передавання одного об’єкта ще не завершує всю цю роботу.

Анімований синьо-жовтий прапор з’являється, коли свіжа перевірка підтвердила віддалене завершення прийнятих цим підключенням даних і метаданих. Звичайне читання та попереднє завантаження самі по собі не означають наявності ваших вихідних змін. Під час запуску, втрати діагностики або застарівання її даних індикатор не може підтвердити завершення; наведіть курсор і прочитайте підказку.

Навіть повідомлення `safe to shut down` описує момент перевірки. Відкрита програма може одразу записати ще щось. Перед вимкненням закрийте програми, що працюють із томом, і виконайте звичайне [відключення](17-unplug-safely-studiofs-umount.md). Прапор не замінює цю процедуру й не доводить, що інший комп’ютер уже застосував зміни у своєму локальному стані.

## Коли варто втрутитися

Під час копіювання великого матеріалу зростання черги й червона пульсація очікувані. Після завершення запису та за доступної мережі робота має поступово просуватися. Оцінюйте кілька спостережень: одна цифра не показує напрямку руху.

Якщо після припинення запису черга довго не зменшується, повторюються помилки або бракує місця, перевірте вільний простір на диску кешу, доступ до мережі й VPN, а також доступність S3 та PostgreSQL. Запишіть час проблеми, дію, яка її спричинила, і збережіть доступний звіт `status --verbose` або короткий запис `perf`. Перед передаванням звітів іншим перевірте, чи немає там приватних адрес і шляхів.

Не лікуйте незрозумілий стан видаленням кешу або повторним створенням тому. Спочатку з’ясуйте, що саме зупинилося: читання, передавання даних чи синхронізація метаданих. Це значно корисніше, ніж одразу збільшити всі числа в налаштуваннях.
